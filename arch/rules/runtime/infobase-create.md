# Создание базы подтверждается повторным опросом раннера

Адаптер раннера создаёт отсутствующую базу, а существующую файловую
пересоздаёт только по выбору человека. Что в ней окажется, решает
раннер по виду цели, и ответ называет это, а не умалчивает. Закреплённый раннер
собирает файловую базу сразу с основной конфигурацией проекта — набором
`CONFIGURATION` — и записывает память об этом наборе: ответ сообщает
`initializesSources: true` и имя набора в `sourceSet`. Базу в кластере, как и
файловую без набора конфигурации, раннер создаёт пустой: `initializesSources:
false`. Вид цели адаптер читает из секции `origin` обоих слоёв так же, как
раннер. Защита поколения — свойство `push`
([план импорта исходников](source-import-plan.md)), поэтому план создания
поля `generationProtection` не содержит.

Первый `push` после создания файловой базы набор основной конфигурации
не грузит, если исходники не менялись, а остальные объявленные наборы грузит
целиком; после пустого создания он грузит целиком все наборы. Ни один из них
не отказывает `untracked_base`. Записи поколения после создания ещё нет, и первая
загрузка поколение базы не сверяет: её `generationProtection: true` называет
режим, а не состоявшуюся сверку.

`infobase.create` берёт соединение из конфигурации проекта с локальным
дополнением и не принимает
аргументов соединения. Используется
[режим previewApply](../mcp/run-operation-names.md).
Preview допускает только запланированное создание (`planned`), без запуска
платформы; отсутствие базы раннер проверяет только у файловой цели. Существующая файловая база получает отказ
`invalid_state`: раннер отвергает её отказом проверки ещё до запуска
платформы. При исполнении отказ несёт
[вопрос человеку](../mcp/human-choice.md) `infobase.exists`. Вариант
«Пересоздать базу» повторяет тот же вызов с отметкой согласия, и адаптер
передаёт раннеру `infobase create --recreate`. Раннер удаляет файлы базы и
создаёт её заново, а при ошибке или отмене возвращает прежнюю. Превью не
спрашивает. Клиент без вопросов получает прежний отказ с указанием на
`infobase.restore`. Базу в кластере раннер до создания не видит, поэтому
вопроса о ней нет. Занятую базу раннер не пересоздаёт: отказ о сеансах
получает [вопрос о занятой базе](infobase-sessions.md), и завершить их
отсюда нельзя. Запланированное EDT-пространство также отклоняется.

Исполнение использует текущую конфигурацию проекта.
Проектный файл и его локальное дополнение сверяются до и после внутреннего
preview раннера в текущем вызове. Их изменение даёт `concurrent_change`
до создания базы.

Если при применении раннер сообщает, что база уже появилась, ответ —
`concurrent_change`. Успех файловой базы требует повторного preview, который
подтверждает, что база есть: отказ раннера на существующей базе.
Пересозданная база подтверждается тем же повторным preview, а ответ
называет пересоздание: `kind: "recreated"`. Базу в
кластере раннер до создания не видит и планирует всегда, поэтому её создание
засвидетельствовано только шагом провайдера, и ответ говорит это в `receipt`.
Превью и ответ для кластера предупреждают `cluster_database_unverified`:
раннер создаёт базу с `CrSQLDB=Y`, и база данных СУБД с тем же именем
берётся молча.
Результат явно называет провайдера источником сведений о состоянии базы;
пути базы и установки платформы наружу не передаются.

Проверки используют управляемые ответы раннера и подтверждают их
интерпретацию адаптером; состояние настоящей информационной базы
они не проверяют.
