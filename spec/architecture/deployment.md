# Развёртывание

Развёртывание Unica проходит четыре контура: рабочее дерево разработчика,
релиз исходного репозитория, публичный маркетплейс и машина потребителя. Ниже
описан каждый контур и то, что его удерживает.

## Исходный чекаут

Каталог плагина под контролем версий — это дерево разработки. Его `.mcp.json`
запускает Rust-workspace через Cargo, а собранные бинарники в репозиторий не
попадают (INV-PKG-UNTRACKED-BUILD-OUTPUT). Локальная отладочная упаковка собирает одну целевую
платформу и переписывает `.mcp.json` так, чтобы запускать бинарник `unica`
этой платформы напрямую, без bootstrap-нагрузки, которую несёт опубликованный
пакет; поэтому установка для разработки никогда не идёт опубликованным путём
запуска (INV-PKG-DEV-ONLY-PACKAGE). Имя каталога разводит эти два случая только на Codex, где
сгенерированный каталог переименовывается (по умолчанию в `unica-dev`);
каталог для Claude Code выводится из упакованного манифеста и сохраняет
опубликованное имя `unica`.

## Релиз из исходников

`IngvarConsulting/unica` публикует детерминированные архивы полного runtime и
метаданные в JSON для `darwin-arm64`, `linux-x64` и `win-x64`. В одном архиве
ровно одна целевая платформа. Публикация архивов происходит только по тегу
(INV-CI-TAG-ONLY-PUBLISH).

Порядок шагов важен и часто читается неверно. Ассеты релиза выкладываются
первыми; смоук тонкого плагина и повторная загрузка опубликованных байтов идут
после и проверяют уже выложенное (INV-CI-SELF-VERIFIED-ARCHIVE). То есть гарантия
ADR-0008 не в том, что наружу не попадут непроверенные байты, — а в том, что на
них не укажет каталог: перевод каталога маркетплейса выполняется отдельным
изменением после того, как проверки прошли. До этого момента потребитель не
получает их через стабильный каталог, хотя сами GitHub Release assets уже
публичны.

## Публичный маркетплейс

`IngvarConsulting/unica-marketplace` хранит тонкий плагин в `plugins/unica`:
пакет несёт нативные bootstrap-бинарники и метаданные плагина, но не полный
runtime (INV-PKG-THIN-PACKAGE). Один и тот же пакет описывают два каталога, по одному на
хост, и оба разрешают его через `git-subdir` по неизменяемому тегу
маркетплейса:

| Хост | Каталог | Каталог манифеста |
| --- | --- | --- |
| Codex | `.agents/plugins/marketplace.json` | `.codex-plugin/plugin.json` |
| Claude Code | `.claude-plugin/marketplace.json` | `.claude-plugin/plugin.json` |

Оба манифеста несут одну версию (INV-PKG-VERSION-LOCKSTEP) и не выходят за набор
ключей, который принимает самый старый поддерживаемый клиент
(INV-PKG-OLDEST-CLIENT-KEYS); для Claude Code эта нижняя граница — 2.1.69.
Публикация идёт в две фазы: staging-PR меняет только файлы плагина, а
promotion-PR — только записи каталогов. Неизменяемый подписанный тег указывает
на коммит слияния staging. При ручном выпуске тег создают до promotion-PR;
Release Warden открывает promotion-PR сразу после слияния staging, но до
появления тега потребительские проверки остаются красными и PR нельзя слить.
В обоих путях стабильный каталог переводится только после тега и зелёных
проверок; точный порядок операций задаёт
[release runbook](../../docs/release-runbook.md).

## Хост потребителя

Оба хоста хранят тонкий плагин в собственном управляемом кеше плагинов и
запускают его одинаково: `.mcp.json` вызывает стандартный Git с алиасом,
областью которого является одна команда, и этот алиас стартует переносимый
селектор bootstrap. Поэтому одна и та же команда работает и с POSIX-Git, и с
Git for Windows. Выбранный нативный bootstrap скачивает runtime для текущей
целевой платформы, сверяет его с записанной контрольной суммой, устанавливает
атомарно и только после этого запускает единственный публичный MCP-процесс
(INV-PKG-VERIFIED-ATOMIC-INSTALL, INV-MCP-NO-ENGINE-SERVERS).

Предварительные требования — Git и один из хостов: Codex CLI либо Claude Code
2.1.69 и новее. Node.js, Python, HTTP-клиенты, инструменты для JSON и архивные
утилиты в поставку потребителю не входят.

Корень кеша runtime разрешается детерминированно, побеждает первое совпадение
(INV-CACHE-RUNTIME-ROOT-ORDER):

1. `UNICA_RUNTIME_CACHE_DIR` как есть — эту переменную пакет выставляет для
   хостов, у которых есть собственный каталог данных на плагин; значение, в
   котором осталась неразвёрнутая подстрока `${`, отбрасывается, потому что
   хост её не подставил;
2. `<CLAUDE_PLUGIN_DATA>/runtimes`;
3. `<CODEX_HOME>/unica/runtimes`; без `CODEX_HOME` за дело берётся домашний
   каталог с сегментом `.codex`, то есть путь становится
   `<HOME или USERPROFILE>/.codex/unica/runtimes`.

Когда не задана ни одна из этих переменных, bootstrap завершается
типизированной ошибкой вместо того, чтобы угадывать место.

Шаг 1 host-нейтрален: `UNICA_RUNTIME_CACHE_DIR` выставляет пакет, а не хост.
Шаги 2 и 3 приходят из дескрипторов host-фасада
`crates/unica-bootstrap/src/host/`, единственного места, которое знает
переменные окружения хостов, — поэтому новый хост добавляет в эту цепочку
дескриптор, а не ветвление (INV-HOST-KNOWLEDGE-BEHIND-FACADE, INV-HOST-UNIFORM-CALL-SITES).

Внутри этого корня состояние runtime разложено по версии и целевой платформе
(`<корень кеша>/<версия плагина>/<платформа>`) и защищено маркером готовности
`.ready.json`. Загрузка и распаковка идут в отдельный каталог транзакции, и
только полностью проверенный результат переезжает на своё место, — поэтому
недокачанный runtime хосту не достаётся никогда.

## Состояние и откат

Состояние рабочего пространства живёт под `.build/unica` внутри корня рабочего
пространства или под корнем, названным в `UNICA_CACHE_DIR` (INV-CACHE-WORKSPACE-ROOT). Оно
изменчиво: его удаление стоит пересборки, но не корректности. Состояние runtime
разложено по версиям и платформам, поэтому установка новой версии не изменяет
предыдущую, а откат сводится к выбору более ранней версии.

Действующие пакеты не несут движка миграции с прежних контрактов: установки
старше контракта тонкого runtime переходят вперёд через неизменяемый
переходный релиз `v0.7.8`, а не через путь миграции внутри пакета (ADR-0008).
