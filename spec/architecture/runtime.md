# Поведение во времени выполнения

Документ описывает наблюдаемое поведение процессов во время работы. Строительные
блоки, которые здесь упоминаются, разобраны в
[строительных блоках](building-blocks.md); нормативные правила принадлежат
[реестру инвариантов](invariants.md) и цитируются по ID.

## Инициализация

1. В исходном чекауте `.mcp.json` запускает
   `cargo run --quiet --manifest-path ../../Cargo.toml --bin unica`. Путь к
   манифесту Cargo записан относительно каталога плагина.
2. В пакете `.mcp.json` вызывает Git-алиас, объявленный на время одной команды.
   Переносимый селектор запускает один нативный `unica-bootstrap` для текущего
   хоста.
3. Bootstrap проверяет манифест закреплённого релиза, получает или переиспользует
   атомарно опубликованный кеш runtime, затем замещает собой `unica` или
   надзирает за ним, сохраняя stdio.
4. Резолвер runtime на Rust запускает внутренние поставляемые инструменты прямо
   из кешированного `bin/<target>/<tool>` после сверки SHA-256.
5. Транспорт MCP — официальный Rust SDK (`rmcp`, ADR-0013). Он соблюдает
   рукопожатие спецификации: первым запросом обязан быть корректный
   `initialize` (перед ним допускается `ping`), а `protocolVersion`
   согласовывается с клиентом.
6. MCP-вызов `initialize` возвращает `serverInfo.name = "unica"`.

У `unica` нет подкоманд: по умолчанию процесс становится stdio MCP-сервером.
Аргумент `--help` или `-h` печатает версию и список поддерживаемых MCP-методов;
`--workspace-service` и `--runtime-job-worker` включают скрытые внутренние
режимы, описанные ниже.

## Перечисление инструментов

1. MCP-вызов `tools/list` обращается к реестру инструментов приложения.
2. В ответе присутствуют только инструменты `unica.*`.
3. Внутренние адаптеры не перечисляются.

## Параллельная диспетчеризация и отмена

1. SDK запускает каждый запрос отдельной задачей, поэтому `initialize`,
   `tools/list` и `ping` никогда не ждут активного `tools/call`. Исполнение
   инструмента идёт в блокирующем рабочем потоке; одновременно допускается не
   более 32 вызовов инструментов, а при насыщении возвращается `-32603` с
   сообщением про перегрузку, пока `ping` и отмена остаются рабочими.
2. SDK ведёт для каждого идентификатора запроса собственный токен отмены.
   Уведомление `notifications/cancelled` с `params.requestId` отменяет этот
   токен; интерфейс MCP пробрасывает отмену в доменный токен, который расходится
   через порты приложения, команды CLI и индекса и коннектор сервиса рабочего
   пространства.
3. Запрос, отменённый через `notifications/cancelled`, ответа не получает, как и
   предписывает спецификация MCP; опоздавший результат обработчика SDK
   отбрасывает.
4. По EOF SDK доводит до конца начатые вызовы (не дольше 5 секунд), после чего
   процесс отменяет все ещё выполняющиеся доменные операции и ждёт их не дольше
   2 секунд, прежде чем завершиться и закрыть stdout, — так реализации
   инструментов успевают снять свои деревья дочерних процессов. Длину входной
   строки на публичном транспорте контролирует SDK; у внутреннего протокола
   сервиса рабочего пространства собственная граница в 8 МиБ.

## Предпросмотр мутации

1. Вызывающая сторона обращается к мутирующему инструменту, не передав
   `dryRun: false`.
2. Приложение разрешает `dryRun` в `true`.
3. Адаптер возвращает запланированную команду или содержательный предпросмотр,
   не изменяя файлов.
4. Приложение формирует соответствующее доменное событие для расчёта влияния.
5. Отчёт о кеше возвращает `mode = "dry-run"` и имена затронутых кешей.

## Применённая мутация

1. Вызывающая сторона явно передаёт `dryRun: false`.
2. Нативный обработчик MCP выполняет операцию.
3. Успешная мутация порождает доменные события.
4. `WorkspaceStateRepository` помечает затронутые кеши устаревшими и записывает
   упреждающие обновления.
5. Результат возвращается конвертом
   `{ ok, summary, changes, warnings, errors, artifacts, cache }`.

## Runtime build и временная полная повторная попытка

1. `unica.runtime.execute` и `unica.runtime.job.start` для операции `build`
   используют одну нормализацию и одну политику повтора. Состояние поддержки не
   читается и не выбирает режим. Вызов без явного `fullRebuild: true` остаётся
   обычным `v8-runner build`, получает глобальный `--json-message` и
   предупреждение о возможной одной полной попытке; предпросмотр показывает
   именно эту первую команду. Явный `fullRebuild: true` сразу выбирает полный
   путь и повторной попытки не имеет (INV-APP-PARTIAL-FALLBACK, ADR-0061).
2. Эффективный `config` разрешается только внутри того же рабочего пространства
   в абсолютный нормализованный путь, а `sourceSet` обрезается по краям так же,
   как в `v8-runner`. Авторизация
   обычного режима связывает точные байты `config`, а также присутствие и точные
   байты соседнего `v8project.local.yaml` по SHA-256 с идентичностью корня и
   эпохой рабочего пространства. Основной файл обязан оставаться ограниченно
   читаемым обычным файлом; соседний локальный файл может доказанно
   отсутствовать либо обязан удовлетворять тем же требованиям. Синхронный путь
   повторяет проверку
   непосредственно перед первым и вторым процессами; фоновый обработчик — при
   захвате запуска и перед заменой процесса. Изменение пути или байтов `config`,
   появление, удаление или изменение локального файла конфигурации, корня либо
   эпохи завершает операцию без полной попытки. Явно переданный файл
   не подменяется `V8TR_CONFIG` или изменением относительного рабочего каталога.
3. Полный повтор разрешает только целая необрезанная JSON-квитанция закрытой
   схемы закреплённого `v8-runner` после обычного завершения первого процесса с
   внешним кодом `4`. Она должна взаимно согласованно доказать общий
   `platform_failure` вида `platform` и ровно один завершившийся ошибкой шаг
   Designer в режиме `partial` с положительными числом файлов и внутренним кодом
   платформы. Запрошенный `sourceSet`, сообщение шага и общий отказ должны
   относиться к одному набору и одной ошибке. Сырая квитанция ограниченно
   удерживается только в памяти задания, которому разрешён fallback; в журналы
   записывается вычищенная копия.
4. После такого доказательства оба публичных пути один раз запускают ту же
   команду с единственным добавленным `--full-rebuild`; результат второго
   процесса окончателен. Успех первой команды, ошибка шага `edt_export`, явный
   полный режим, отмена или превышение срока, отмеченные внешним процессом Unica,
   обрезанный или повреждённый JSON, неизвестная форма квитанции и несвязанный
   отказ сохраняют обычный итог первой команды без повтора. Закреплённая
   квитанция не несёт признак отложенного внутреннего тайм-аута критического
   шага: его последующий точный отказ частичной загрузки остаётся допустимым для
   временного повтора до v14. Эвристика по неструктурированному тексту `stdout`
   или `stderr` вне полей закрытой квитанции не применяется.
5. Отмена проверяется до запуска синхронного процесса, до постановки задания в
   очередь и перед полной попыткой. Опубликованный маркер отмены выигрывает у
   ещё не начатого повтора; если защищённый запуск второго критического процесса
   выиграл блокировку жизненного цикла раньше, следующая отмена становится
   отложенной по общему правилу критических операций.
6. Предпроверка и классификатор не читают файлы хешей, список изменений или
   прочее частное состояние `v8-runner` (INV-CACHE-ORCHESTRATOR-OWNED). Два
   процесса остаются временным слоем Unica до переработки `v8-runner` поколения
   `v14`: между ними нет непрерывного владения внутренней блокировкой runner-а,
   а его срок исполнения начинается заново для полной команды. Долговременный
   путь удерживает собственный `active.lock`, но синхронные и прямые запуски
   этим ограничением не связаны.
7. Унаследованный `unica.build.load`, идущий через отдельный `CliAdapter`,
   находится вне этой политики (ADR-0061).

## Операция чтения

Инструменты чтения не порождают событий мутации. Предметные кеши только
наблюдаются: устаревший кеш сообщается как устаревший, а не пересобирается на
чтении. Отдельное исключение — закрытый индекс поставщика RLM: один
`unica.code.search` может дождаться его фонового build/update в пределах своего
бюджета и сообщает этот ход через progress (INV-CACHE-RLM-REVISION,
INV-MCP-CODE-SEARCH-ROLES).

## Снимок операционной конфигурации

1. После обнаружения рабочего пространства приложение определяет, относится ли
   вызов к `unica.code.search`, `unica.code.definition`,
   `unica.code.outline` или `unica.code.diagnostics` в режиме `analyze`. Только
   эти вызовы обращаются к операционной конфигурации
   (INV-APP-CONFIG-SNAPSHOT).
2. Инфраструктурный порт независимо читает присутствующие
   `<workspaceRoot>/unica.toml` и `<workspaceRoot>/unica.local.toml` как
   самостоятельные слои единой неверсионируемой закрытой схемы с полями
   `operational`, `network`, `providers`. `version` считается неизвестным на
   корне и отклоняется как любое другое неизвестное поле. Ошибка синтаксиса
   или корневой структуры останавливает всех потребителей контейнера, а
   операционный потребитель затем проверяет только `[operational]`: ошибки
   `network` и `providers` его не останавливают.
3. Проверенные слои сливаются по полям поверх скомпилированных значений.
   Локальный слой перекрывает общий, а явный
   `unica.code.diagnostics.timeoutSeconds` перекрывает оба файла. После слияния
   проверяются отношения итоговых сроков. Файловые значения — целые секунды не
   меньше 1 без верхнего ограничения операционной политики; скомпилированные
   300, 300, 2, 45 и 120 служат умолчаниями, а не потолками. Итоговые сроки
   `RLM` и `git-grep` не
   превышают общий срок поиска. Явный `timeoutSeconds` сохраняет отдельный
   публичный диапазон `30..=3600`.
4. Полученный `OperationalConfig` неизменяем и принадлежит одному вызову. Все
   его фазы используют значения этого снимка без повторного чтения файлов;
   следующий вызов разрешает конфигурацию заново, поэтому замечает изменение
   файла и не переиспользует снимок другого рабочего пространства.
5. Многофазные исполнители поиска и чтения хранят один момент начала и одну
   длительность бюджета, а остаток получают как бюджет минус прошедшее время,
   не складывая потенциально большую длительность с `Instant`. Readiness,
   подключение и работа поставщика получают только остаток; переход к следующей
   фазе срок не продлевает, а отмена имеет приоритет и над одновременно
   полученной ошибкой загрузки конфигурации. Однофазный процесс диагностики
   получает эффективную длительность снимка. Внутренние умолчания обычных и
   управляющих путей скрытого сервиса сохраняются, но рабочие пути анализатора
   и RLM с бюджетом вызывающей стороны получают полный остаток вызова и не
   обрезают его до 120 секунд.
6. `initialize`, `tools/list`, другие инструменты и остальные режимы
   `unica.code.diagnostics` не разрешают `OperationalConfig` и не читают
   `[operational]`. Потребители сетевой политики документации и стандартов
   независимо читают `network` и `providers` по
   `INV-APP-DOCUMENTATION-NETWORK-POLICY`. Поэтому перечисление инструментов
   остаётся статическим и не зависит от рабочего пространства.

## Снимок ресурсов и полная замена BSL

1. `unica.source.resolve` и `unica.source.children` разрешают именованный набор
   исходников и возвращают канонические цели либо наблюдаемые неадресуемые узлы
   без закрытого состояния поставщика (INV-SOURCE-LOGICAL-IDENTITY).
2. `unica.source.resources` открывает в текущем экземпляре приложения
   неизменяемый снимок на пять минут либо продолжает его страницу.
   `unica.source.read` проверяет пару снимка и ресурса и возвращает точный
   ограниченный диапазон байтов как UTF-8 либо base64
   (INV-SOURCE-SNAPSHOT-BINDING, REQ-PERF-SOURCE-BOUNDS).

## Явная проверка готовности проекта

`unica.project.status` по одному читающему вызову собирает ограниченный снимок
workspace, объявленных source sets, Git index и применимых правил ресурсов и
передаёт его доменному вычислению готовности. Наличие проблем проекта остаётся
успешным результатом с типизированными диагностиками; отмена или внутренний
отказ без достоверного снимка остаются ошибкой вызова
(INV-MCP-PROJECT-READINESS). Корень source set проверяется отдельно от
репозиторной политики (INV-SOURCE-ROOT-SEPARATION,
INV-SOURCE-PORTABLE-GIT). Вызов ничего не пишет и не запускает скрытый сервис.

## Скрытый сервис поставщиков рабочего пространства

Здесь и далее RLM — внутренний индекс и движок чтения BSL. Unica строит индекс
поставляемым инструментом `rlm-bsl-index`, а читает его через MCP-процесс
`rlm-bsl-mcp`. Оба исполняемых файла принадлежат апстриму и группе релиза
`rlm-tools-bsl` (`Dach-Coin/rlm-tools-bsl`, MIT) и закреплены на `v1.33.0`,
коммит `3e6920cd015a61af4ba7aa1a5f1fedd8bc935549`, в
`plugins/unica/third-party/tools.lock.json`. Аббревиатура пришла из
апстрим-проекта и в репозитории не расшифровывается. Индекс построителя 15 —
файл SQLite в каталоге `rlm-bsl/index-v15` под постоянным корнем состояния
поставщика. Этот корень всегда выводится из нормализованной пары
`workspaceRoot + sourceRoot`.
Если корень кеша рабочего пространства лежит вне выбранного корня исходников,
парный корень помещается под `<cacheRoot>/provider-state`; иначе он помещается
под внешний `UNICA_PROVIDER_STATE_DIR`. Каталог, маркер состояния и маркер
блокировки построителя 14 не переносятся, не открываются и не удаляются;
построитель 15 начинает холодное поколение. Его `bsl_index_status.json` и
`bsl_index.lock` координируют только ту же нормализованную пару и поколение и
находятся соответственно под
`caches/rlm-bsl/index-v15` и `locks/rlm-bsl/index-v15` её постоянного корня.
Состояния `building` и `incomplete` запрещают чтение с опорой на `RLM`
(INV-CACHE-PROVIDER-STATE-OUTSIDE-SOURCE,
INV-CACHE-GENERATION-CUTOVER). Публичных инструментов
`unica.rlm.*` не существует: индекс скрыт за `unica.code.*`, а связанные секции
метаданных доступны только как обогащение `unica.meta.info`
(INV-PRODUCT-NO-ENGINE-ROUTING, INV-MCP-META-SURFACE); его частную SQLite-схему Unica не читает
(INV-CACHE-ORCHESTRATOR-OWNED). См. также [глоссарий](glossary.md).

В пакетном запуске точный внешний корень разрешает host-фасад bootstrap и
передаёт дочернему runtime только нейтральной переменной
`UNICA_PROVIDER_STATE_DIR`; процесс `unica` не знает переменных и каталогов
конкретного хоста (INV-HOST-NEUTRAL-ORCHESTRATOR). Прямой запуск из исходного
дерева без bootstrap использует `HOME` или `USERPROFILE` с суффиксом
`.unica/provider-state`.

1. `unica.code.search` канонически разрешает один обязательный `sourceSet` и
   необязательный `metadataPath`; переходный `sourceDir` принимается только
   вместо логического селектора. Остальные path-based операции кода сохраняют
   выбор явного `sourceDir`, затем `main`, затем единственного
   `CONFIGURATION`. Любой вариант разрешает рабочее пространство и ровно один
   эффективный корень исходников; ошибка не расширяет область до рабочего
   пространства (INV-SOURCE-SINGLE-RESOLVED-ROOT,
   INV-MCP-CODE-SEARCH-ROLES).
2. Поиск передаёт один `CodeIntelligenceContext` ролям `semantic`, `symbol` и
   `lexical`, которые сейчас реализуют `rlm`, `bsl-analyzer` и `git-grep`;
   операции навигации выбирают исполнимую возможность RLM
   (INV-APP-CODE-PROVIDER-BOUNDARY). Поставщик, которому нужно
   тёплое состояние, просит у внутреннего менеджера сервис по ключу из
   нормализованных `workspaceRoot` и `sourceRoot`. Разрешённый источник обязан
   остаться внутри рабочего пространства; его выбор согласован с картой
   `project.map`, а `project.status` независимо проверяет все объявленные
   наборы исходников.
   Исполнители поиска наблюдают отмену MCP-запроса и собственный срок, а на
   каждого поставщика одновременно удерживается не более 32 исполнителей.
   Завершившийся по сроку некооперативный исполнитель сохраняет место до
   фактического завершения; его handle остаётся в реестре жизненного цикла и
   делит с активными вызовами один общий двухсекундный срок остановки
   (INV-MCP-BOUNDED-ADMISSION).
   Оркестратор ждёт терминального состояния всех ролей либо их срока; при
   progress token публикует старт, смену фаз, двухсекундный heartbeat и
   терминальный снимок, не создавая отдельной polling-поверхности
   (INV-MCP-CODE-SEARCH-ROLES).
3. Если подходящий живой сервис есть, `unica` отправляет внутренний запрос JSONL
   на localhost с токеном из `service.json`.
4. Если сервис отсутствует, устарел, недостижим или собран другой версией,
   `unica` запускает скрытый режим `unica --workspace-service ...`.
5. Сервис держит независимые постоянные дочерние процессы `bsl-analyzer` и RLM
   в режиме MCP на рабочее пространство. Транспорт анализатора перезапускается
   при смене поколения исходников или явной инвалидации. При каждом запуске
   workspace-профиля сервис передаёт `bsl-analyzer` ровно один внешний
   `--cache-dir`. Сам частный кеш обычно располагается под
   `<cacheRoot>/providers/bsl-analyzer/source-<identity-digest>`. Если этот путь
   оказался бы внутри выбранного корня исходников, например при
   `sourceDir="."` и стандартном `<workspaceRoot>/.build/unica`, тот же частный
   ключ размещается под коротким runtime-корнем вне дерева. Digest выводится из
   нормализованной пары `workspaceRoot + sourceRoot`, поэтому кеш переживает
   пересоздание сервиса, но не разделяется между наборами исходников и
   связанными рабочими деревьями; ни основной, ни резервный путь не принадлежит
   каталогу процесса-сервиса (INV-CACHE-ORCHESTRATOR-OWNED,
   INV-CACHE-WORKTREE-ISOLATION, ADR-0018).
6. Готовностью, сборкой и обновлением индекса RLM управляет тот же сервис, но
   сам индекс остаётся постоянным файловым индексом вне выбранного корня
   исходников. Индексатор и читающий процесс получают один и тот же каталог,
   разрешённый по INV-CACHE-PROVIDER-STATE-OUTSIDE-SOURCE. Готовность
   классифицируется как готов, отсутствует, устарел, строится, отказал или
   недоступен. Внутренний `RlmReady` получает полный
   остаток срока вызывающей операции через `timeout_seconds` и `timeout_nanos`;
   выполняемый внутри него отдельный процесс `info` ограничен 30 секундами и
   тем же токеном отмены. Background build/update ограничен сутками и токеном
   отмены обслуживания индекса.
   Блокировка индекса обновляется каждые 5 секунд и считается
   протухшей через 10 минут. Чтения переиспользуют одну логическую сессию
   `rlm_start` до инвалидации индекса или домена, истечения сессии, остановки
   сервиса либо смены корня исходников и закрывают её через `rlm_end`
   (INV-APP-LAZY-HIDDEN-SERVICES).
   `SourceRevisionService` хранит доверенное поколение и SHA-256 корпуса;
   готовность содержит полную ревизию. На локальном APFS FSEvents-fence делает
   тёплую проверку без полного обхода; точные file-events обновляют manifest
   чтением только изменённых файлов. Холодный старт, событие каталога и разрыв
   наблюдателя требуют полного согласования. Неподдерживаемый fence оставляет
   ревизию недоверенной и RLM недоступным: повторный обход дерева не считается
   барьером. Build/update сверяет ревизию перед публикацией `ready`, RLM-вызов —
   до и после исполнения (INV-CACHE-RLM-REVISION).
7. Каждый рабочий запрос к анализатору или к RLM, включая `RlmReady`, несёт
   `operation_id` в виде
   UUID. Общий рантайм регистрирует по одному токену отмены на операцию и
   отклоняет повторяющиеся идентификаторы, а также новую работу после начала
   остановки. Бюджеты рабочих запросов анализатора и RLM передаются внутренним
   протоколом с `schema_version = 4` без потерь как `timeout_seconds` и
   `timeout_nanos`; граница отклоняет длительности вне положительного диапазона
   `i64` секунд, а запись сервиса с прежним `schema_version = 3` не
   переиспользуется.
8. Принятые соединения обслуживаются независимо. `ping`, `cancel` и `shutdown`
   никогда не занимают полосу поставщика и остаются отзывчивыми, пока идёт
   работа. Задания индекса RLM выполняются вне этих полос; тёплые MCP-транспорты
   анализатора и RLM имеют отдельные сериализованные полосы.
   Рантайм ограничивает число общих обработчиков 64, а рабочих исполнителей — 8.
   Насыщение общей ёмкости переводит соединение в ограниченный классификатор
   управляющих запросов на 64 сокета с совокупным бюджетом 500 мс и префиксом
   классификации 64 КиБ, а также до 8 зарезервированных управляющих
   обработчиков. Классифицированную работу он отклоняет стабильной ошибкой
   перегрузки общих обработчиков, а неклассифицированный избыток закрывает;
   неограниченной очереди потоков или соединений не создаётся.
9. Отмена на уровне MCP заставляет коннектор отправить `cancel { operation_id }`
   отдельным соединением. Разрыв рабочего сокета тоже отменяет свою операцию.
   Страж операции снимает идентификатор на любом пути завершения, поэтому
   следующий вызов не требует перезапуска сервиса.
10. Обычные точки входа рабочих запросов и `Ping`, `Invalidate`, `Shutdown`
    используют умолчание 120 секунд, отсчёт начинается до подключения. Операция
    с кодом и бюджетом вызывающей стороны вместо этого передаёт полный остаток
    своего elapsed-budget, даже когда он больше 120 секунд; умолчание не
    является потолком. Для управляющих запросов
    действует потолок подключения 500 мс; подключение, запись, сброс буфера и
    чтение расходуют остаток общего бюджета. Чтение опрашивается каждые 100 мс,
    чтобы отмена наблюдалась вовремя; отмена имеет приоритет над таймаутом, EOF,
    ошибкой протокола и гонкой с успешным завершением процесса. Иначе устроен
    `Cancel` без гарантии доставки: у него собственный совокупный бюджет 500 мс
    на подключение, запись и сброс буфера, а ответа он не читает. Строки
    внутреннего запроса и ответа ограничены 8 МиБ. У разбора заголовка запроса
    один совокупный срок 5 секунд от момента приёма соединения, опрос идёт
    кусками не длиннее 100 мс, и приход очередного байта срок не продлевает.
11. Остановка помечает рантайм недоступным, отменяет все активные операции,
    отклоняет новую работу, удаляет принадлежащую ей запись о сервисе и
    доводит обработчики до конца в пределах настроенной отсрочки.
12. Постоянные дочерние процессы анализатора и RLM работают через
    `ManagedChild`. В Windows процесс запускается приостановленным, приписывается
    к Job Object с уничтожением по закрытию и только затем возобновляется; в Unix
    создаётся отдельная группа процессов. Отмена, таймаут и разрушение объекта
    снимают всё дерево с ограниченным ожиданием. На платформах, отличных от
    Windows и Unix, доступно только завершение непосредственного потомка.

`initialize`, `tools/list`, `unica.project.status`, `unica.project.map` и
предпросмотр скрытых сервисов не запускают. Настоящий
`unica.code.search` может запустить сервис для ролей `semantic` и `symbol`;
текущая реализация роли `lexical` выполняется без сервиса
(INV-APP-LAZY-HIDDEN-SERVICES).

Сервис, индекс и логическая сессия изолированы парой
`workspaceRoot + sourceRoot`: связанное рабочее дерево получает отдельное
состояние. Постоянный индекс при этом не входит в индексируемое им дерево.
Общего индекса основной ветки и дельты рабочего дерева нет
(INV-CACHE-WORKTREE-ISOLATION,
INV-CACHE-PROVIDER-STATE-OUTSIDE-SOURCE, ADR-0018).

Версии и состав поставляемых исполняемых файлов выбираются из
`plugins/unica/third-party/tools.lock.json`. CI проверяет CLI- и MCP-поверхность
артефакта, выбранного этим файлом, а не хранит вторую константу с версией
анализатора.

## Долгоживущие задания runtime

Долгие операции runtime 1С не держат MCP-вызов открытым: они вынесены в
отдельный процесс с состоянием на диске. Публичная поверхность —
`unica.runtime.job.start`, `.status`, `.wait`, `.logs`, `.cancel`, `.list`;
набор инструментов и схема аргументов синхронного `unica.runtime.execute`
остаются прежними. Операция `build` обоих входов проходит описанную выше
независимую от состояния поддержки политику одной полной повторной попытки.

1. `unica.runtime.job.start` разрешает корень плагина, разрешает поставляемый
   `v8-runner` и отклоняет аргументы ограниченного по времени запуска внешней
   обработки — `waitForExit`, `waitTimeoutMs` и `stderrOutput`, — которые
   принадлежат `unica.runtime.execute`. Без `dryRun: false` инструмент
   возвращает запланированную команду и ничего не запускает.
2. Применённый запуск принимает одну из меток операции: `make`, `syntax`,
   `test`, `tools-download`, `config-init`, `init`, `build`, `dump`, `convert`,
   `load`, `launch`, `extensions`, — ставит задание в очередь и порождает
   отсоединённый рабочий процесс.
3. Рабочий процесс — тот же исполняемый файл, вызванный повторно как
   `unica --runtime-job-worker`. Через stdin ему передаются два JSON-документа:
   сначала запрос с нормализованными исполняемыми аргументами `v8-runner`, а для
   обычного `build` также с типизированной авторизацией `buildPreflight` и
   единственной полной командой повтора; затем подтверждение запуска с решением
   об отмене на границе передачи. Полная команда отличается от первой только
   `--full-rebuild`, не записывается дословно в `record.json` и после передачи
   может быть потреблена только один раз. Родитель удерживает блокировку
   жизненного цикла при записи обоих документов и повторно наблюдает отмену
   после записи подтверждения; отмена во время этой записи переводит задание в
   `cancelled` до допуска рабочего процесса к активации. До второго документа
   рабочий процесс не активирует задание. Если первый документ уже декодирован
   и запись всё ещё имеет фазу `queued`, ошибка чтения второго переводит её в
   `failed` и освобождает принадлежащую ей блокировку. EOF или ошибка до
   декодирования первого документа не позволяют рабочему процессу определить
   `cacheRoot` и `jobId`; если родительский процесс также не выполнил очистку,
   немедленные завершение записи и освобождение `active.lock` на этом пути не
   происходят. Документы не передаются через argv скрытого рабочего процесса;
   его единственный собственный аргумент — флаг режима.
4. Состояние заданий лежит под `<cacheRoot>/jobs/`. Каждому заданию принадлежат
   `<jobId>/record.json`, `stdout.log`, `stderr.log` и, после запроса отмены,
   `cancel.json`. Сырые аргументы никогда не сохраняются дословно, а
   захваченный вывод вычищается от секретов до записи.
5. `jobs/active.lock` допускает одно активное задание на корень кеша рабочего
   пространства. Создание и проверяемое по владельцу удаление этого пути
   сериализованы постоянным файлом `jobs/active.lifecycle.lock` и его
   межпроцессной блокировкой с повторной проверкой владельца перед удалением.
   Та же блокировка линеаризует подтверждение передачи задания, публикацию
   отмены для `queued`, восстановление протухшей записи и захват worker-ом
   перехода `queued` → `running`, опрос процесса, решение о полной попытке,
   смену PID и терминализацию. Входы, обслуживающие вызов пользователя —
   постановка задания и запрос отмены, — ждут эту блокировку ограниченное время
   и по его истечении возвращают явную ошибку занятости вместо неограниченного
   ожидания. Worker перечитывает запись и повторяет предпроверку под этой
   блокировкой перед первым запуском. Перед полной попыткой он ещё раз проверяет
   идентичность build, заменяет в той же записи PID завершившегося процесса и
   сохраняет прежние `jobId`, `createdAt`, `startedAt` и `active.lock`;
   промежуточная терминальная фаза и окно для другого задания не публикуются.
   Уже записанное терминальное состояние не перезаписывается активацией или
   устаревшим опросом. `status` и `list` пробуют lifecycle-блокировку без
   ожидания и при занятости пропускают восстановление текущего чтения.
   Блокировка, владелец которой перестал слать сердцебиение,
   восстанавливается под отдельной блокировкой восстановления через пять минут:
   брошенное задание завершается фазой `lost`, а блокировка освобождается, если
   запись доказывает, что дочернего процесса не существует. Доказательством
   служит признак попытки порождения: рабочий процесс записывает его до
   обращения к раннеру, поэтому запись не может утверждать отсутствие потомка,
   когда тот уже создан. Доказательством считается только явное отрицательное
   значение. Отсутствие признака — а так выглядят записи сборок, которые его не
   писали, — читается как неизвестность и блокировку сохраняет: прежний рабочий
   процесс мог погибнуть после порождения и до записи PID, оставив живого
   потомка за записью, в которой его следа нет. Задание, дошедшее до порождения,
   сохраняет блокировку и после `lost` — осиротевшее дерево процессов способно
   продолжать менять рабочее пространство. Блокировка, взятая раньше своей записи, когда родитель
   погиб между захватом и созданием `record.json`, освобождается по истечении
   того же окна; часами для неё служит возраст самого файла блокировки.
   Освобождение всегда ограничено идентификатором, записанным в блокировке:
   восстановление не снимает блокировку, которую уже занял другой владелец.
   Чтение хвоста вывода завершившегося процесса ограничено по времени: если
   унаследованный потомок удерживает канал открытым, читатель бросается,
   квитанция считается неполной, и полная повторная попытка запрещена.
6. Фазы: `queued`, `running`, `cancelRequested`, `succeeded`, `failed`,
   `cancelled`, `timedOut`, `lost`. Нетерминальны только первые три, и каждый
   переход сверяется со списком разрешённых преемников.
7. Рабочий процесс опрашивает своё задание каждые 25 мс до терминальной фазы,
   записывая на каждом опросе сердцебиение и ограниченные 16 КиБ хвосты вывода.
   Если первая команда доказанно завершила частичный шаг ошибкой, её вычищенные
   хвосты сохраняются в памяти worker-а и объединяются с хвостами полной команды
   под явными разделителями. Оба потока продолжают публиковаться в прежних
   `stdout.log` и `stderr.log`; общий предел применяется после объединения.
8. `unica.runtime.job.cancel` пишет маркер отмены, а не убивает процесс
   напрямую. Операция, признанная безопасной для прерывания — `make`, `syntax`,
   `test`, `tools-download`, — отменяется через фасад платформы, снимающий дерево
   процессов, с ограниченной пятисекундной уборкой и завершается фазой
   `cancelled`. Любая другая операция способна оставить рабочее пространство в
   несогласованном состоянии, поэтому задание сообщает `cancelRequested` с
   признаком `cancelDeferred` и небезопасной фазой и всё равно доводится до
   конца. Маркер, опубликованный до защищённого решения о полной попытке
   `build`, запрещает её; маркер после смены PID относится к уже запущенной
   критической полной команде и сохраняет отложенную семантику.
9. `unica.runtime.job.status` и `.list` читают снимки состояния и никогда не
   блокируются. `.wait` опрашивает состояние каждые 25 мс в пределах заданного
   вызывающей стороной `timeoutSeconds` (по умолчанию 30, допустимо от 1 до 60)
   и по истечении возвращает текущий снимок с признаком `waitTimedOut`, а не
   ошибку. `.logs` возвращает вычищенные от секретов хвосты stdout и stderr и
   пути к ним; размер хвоста задаётся `tailChars` со значением по умолчанию
   4096 символов.
10. На успешной терминальной фазе рабочий процесс заново обнаруживает рабочее
    пространство от записанного рабочего каталога, порождает доменное событие
    своей операции, сообщает влияние на кеш через `WorkspaceStateRepository` и
    после фиксации состояния пытается без гарантии доставки уведомить живые
    сервисы рабочего пространства об инвалидации
    (INV-CACHE-PERSISTED-STALENESS). Неудача при применении этих эффектов
    записывается как предупреждение задания, а не как потерянная мутация. Для
    `build` эти эффекты выполняются один раз после окончательного успеха, но не
    между частичной и полной попытками.
11. Две попытки остаются двумя процессами `v8-runner`. `active.lock` непрерывно
    защищает долговременное задание Unica, но между процессами заканчивается
    владение внутренней блокировкой runner-а, поэтому прямой или синхронный
    запуск ею не исключён. Срок исполнения поставщика также начинается заново
    для полной команды; срок ожидания вызывающей стороны продолжает относиться к
    одному заданию и не превращается в общий бюджет двух процессов. Этот разрыв
    принят временно до переноса политики в `v8-runner` поколения `v14`
    (ADR-0061).

## Публикация кеша bootstrap

1. Манифест обязан однозначно называть исходный коммит, тег
   `v<plugin-version>`, утверждённый источник релиза на GitHub и все три
   поддерживаемые цели сборки.
2. Корень кеша runtime разрешается нейтрально к хосту, в фиксированном порядке:
   `UNICA_RUNTIME_CACHE_DIR` — значение отбрасывается, если в нём остался
   неподставленный токен `${`, который хост не раскрыл, — затем
   `CLAUDE_PLUGIN_DATA` с суффиксом `runtimes`, затем `CODEX_HOME`, затем `HOME`
   или `USERPROFILE` с суффиксом `.codex`; двум последним дополнительно
   дописывается `unica/runtimes`. Если не задана ни одна переменная, bootstrap
   завершается ошибкой, а не догадкой (INV-CACHE-RUNTIME-ROOT-ORDER, ADR-0012).
3. Блокировка на пару «версия и цель» сериализует наполнение
   `<cacheRoot>/<pluginVersion>/<target>`.
4. Скачивание и распаковка идут в транзакционном каталоге с именем UUID на той
   же файловой системе, что и итоговый кеш.
5. Состав архива и отпечатки SHA-256 обязаны в точности совпасть с манифестом.
6. `.ready.json` пишется только после проверки, а транзакция переименовывается
   атомарно. Некорректное предыдущее состояние помещается в карантин и
   удаляется владеющей транзакцией.
7. `verify` выполняет MCP-вызовы `initialize` и `tools/list` и требует наличия
   стабильных инструментов `unica.project.status`, `unica.standards.search` и
   `unica.standards.explain`, прежде чем сообщить об успехе.
