# `unica.code.patch` v1: границы и контракт

- Status: `accepted`
- Date: `2026-07-21`
- Scope: контракт одного поставляемого публичного инструмента
- Связанная задача: #73

Это контракт реализованного инструмента, а не проект. `unica.code.patch`
объявлен в реестре инструментов (`crates/unica-coder/src/application/mod.rs`),
реализован в
`crates/unica-coder/src/infrastructure/native_operations/code.rs` и закреплён
тестами, перечисленными ниже. Документ описывает границы, которые нельзя
расширять без нового решения.

Отдельная запись в `spec/decisions/` для этого контракта не создавалась:
решение узкое, касается одного инструмента и не меняет ни один
общеархитектурный контракт. Владельцем нормы остаётся этот файл, а
общеприменимые следствия вынесены в реестр инвариантов
(`INV-MCP-04`, `INV-SOURCE-04`, `INV-CACHE-04`). Расширение инструмента за
границы v1 — `replace`, `delete`, пакетная правка, EDT или расширения
конфигурации — меняет публичный контракт и требует записи решения
(`INV-MCP-08`).

## Цель

Добавить одну безопасную точечную мутацию BSL-модуля через публичный MCP
`unica.code.patch`. Инструмент не является редактором произвольного текста и не
заменяет общий контракт записи из #74.

## Границы v1

- Только набор исходников платформенного XML вида `CONFIGURATION`, выбранный
  обычной политикой выбора набора исходников Unica.
- Только один существующий обычный файл `*Module.bsl` в поддерживаемой
  канонической раскладке платформенного XML внутри автоматически выбранного
  набора исходников; объект-владелец метаданных и обязательные сопутствующие
  описатели должны существовать.
- Только одна операция за вызов; пакетная правка, несколько файлов и каскадные
  изменения запрещены.
- Только операция `insert` с одним из селекторов — `method` или `anchor`.
- `ExternalDataProcessor`, `ExternalReport`, EDT, расширение конфигурации,
  создание модуля, `delete`, переименование и `allowMissing` в v1 не входят.
- `dryRun` остаётся значением по умолчанию. Применяющий вызов требует
  `dryRun: false` и проходит обычную политику путей рабочего пространства и
  стража поддержки.

Такие границы покрывают исходный сценарий: добавить фрагмент BSL в известный
существующий модуль без широкого переписывания источника.

## Публичный MCP-контракт

Имя: `unica.code.patch`.

Общие поля остаются едиными для публичных инструментов: `cwd`, `sourceDir` и
`dryRun`. `sourceDir` выбирает один настроенный набор исходников
`Configuration` и обязателен, когда выбор неоднозначен.

| Поле | Тип | Правило v1 |
| --- | --- | --- |
| `path` | string | Обязательный путь к существующему `*Module.bsl` относительно рабочего пространства. |
| `operation` | string | Обязательное значение `insert`. |
| `selector` | object | Ровно один селектор — `method` или `anchor`. |
| `content` | string | Непустой фрагмент BSL для вставки. |
| `position` | string | `before` или `after`; вставка всегда происходит по границе строки метода или якоря. |
| `sourceDir` | string | Необязательный путь к настроенному набору исходников; разрешает неоднозначность. |

`selector.method` — точное имя процедуры или функции из AST. Индекс и валидация
используют `parser` и `syntax` из того же исходного коммита `bsl-analyzer`,
который закреплён в `third-party/tools.lock.json`; контрактный тест не даёт этим
версиям разойтись. Диапазон метода включает связанные аннотации, а слова в
свойствах, строках и комментариях методов не образуют.

`selector.anchor` — точный многострочный текст. Он должен дать ровно одно
совпадение в допустимой области внутри метода. Неоднозначный или отсутствующий
селектор — ошибка, а не пустая операция. Переводы строк в полезной нагрузке
приводятся к канону, поэтому якорь с LF сопоставляется с источником на LF, CRLF
и смешанным, но найденные диапазоны остаются настоящими байтовыми диапазонами
исходника. Пересекающиеся совпадения считаются по отдельности.

Для `before` выбирается начало строки объявления или якоря. Для `after` — байт
сразу после конца его строки. Если у последней строки нет перевода строки,
писатель сначала добавляет перевод строки непосредственного контекста, поэтому
закрывающая лексема и новый текст не склеиваются.

## Результат и идемпотентность

`OperationResult.data` обязан включать:

- канонический `path`, выбранный `sourceSet` и `affectedTarget` с ролью модуля;
- `preHash` и `postHash` — SHA-256 по исходным байтам;
- `changedRanges` в байтовых координатах и в координатах строка/колонка по
  образу после записи;
- унифицированный diff, построенный из того же образа после записи, что и
  `postHash`;
- нормализованную затронутую цель: набор исходников, владельца, роль модуля и
  хеш сырых байтов образа после записи;
- завершающую `validation`: `kind=bsl-analyzer-parser`,
  `status=passed|failed`, `validatedPostHash` и структурированные диагностики с
  байтовыми и строчно-колоночными диапазонами.

Это именно JSON-объект в `OperationResult.data`; `stdout` не используется как
внутренний контейнер для сериализованного JSON.

Повторный идентичный вызов распознаётся до записи как семантически пустой:
`preHash` равен `postHash`, diff пуст, диапазоны пусты, ни кеш, ни событие не
публикуются. Первый вызов отклоняется без записи, если его образ после записи не
позволяет доказать такую пустоту при следующем идентичном вызове — например,
если вставка создаёт второй подходящий метод или якорь.

## Требования к побайтовой записи

- Неизменённые байты сохраняются, включая BOM, окружающую XML-структуру файла,
  завершающий перевод строки и локальный стиль перевода строки.
- Преамбулой считается только первый ведущий UTF-8 BOM; последующие U+FEFF
  остаются обычным содержимым и сохраняются побайтно.
- Вставленный фрагмент получает перевод строки своего непосредственного
  контекста; смешанные переводы строк не нормализуются целиком по файлу.
- Если исходный модуль не содержит ни одного перевода строки, `code.patch`
  использует LF для разделителя и вставленного фрагмента, сохраняя
  совместимость v1.
- Исходный модуль с любым одиночным CR отклоняется до мутации: v1 умеет
  сохранять только LF, CRLF и их смешение без одиночных CR.
- Унифицированный diff, диапазоны и `postHash` вычисляются из одного и того же
  побайтно точного образа после записи; перед возвратом diff заново разбирается
  и применяется в памяти, и результат обязан побайтно совпасть с этим образом.
- Точный образ после записи валидируется до подготовки и публикации; применяющая
  запись затем выполняется через промежуточный файл и атомарную замену. Ошибка
  валидации оригинал не меняет.

## Связь с синхронизацией источников

v1 возвращает `affectedTarget`, но не утверждает, что обычная сборка runtime
загрузила модуль в информационную базу. До появления контракта доставки из #76
результат является доказательством мутации источника, а не распиской о
round-trip между runtime и выгрузкой. Связывание события мутации с устойчивым
состоянием «источник грязный» выполняется отдельным изменением после принятия
контракта #76.

## Что удерживает контракт

Перечисленные ниже свойства не являются пожеланиями: каждое закреплено тестом.
Изменение поведения без изменения этого списка — регрессия.

1. BOM и CRLF: предпросмотр показывает только вставку, хвост файла не
   превращается в ложную замену, применённый результат побайтно идентичен вне
   вставки.
2. Смешанные переводы строк: метод и многострочный якорь используют локальный
   перевод строки; повторное применение — пустая операция без записи.
3. Свойства, комментарии и строки, содержащие `Обработчик.Процедура` или
   `Обработчик.КонецПроцедуры`, границы метода не меняют.
4. Отсутствующий, двусмысленный или пересекающий закрывающую лексему селектор
   отклоняется до записи.
5. `path` вне рабочего пространства, выход через символическую ссылку, файл не
   `*Module.bsl`, неизвестный набор исходников, внешняя цель, EDT или расширение,
   а также `operation != insert` отклоняются.
6. `dryRun` возвращает те же хеши до и после, тот же diff и те же диапазоны, но
   не меняет ни файл, ни состояние; успешное применение публикует ровно одну
   затронутую цель.
7. Ошибка валидации образа после записи до подготовки файла и занятый путь
   промежуточного файла сохраняют исходные байты.

Проверки:

- `crates/unica-coder/src/infrastructure/native_operations/code.rs` — поведение
  селекторов, границы методов, переводы строк и BOM, идемпотентность, а также
  отказ `resolve_target` для набора исходников, не являющегося платформенным XML
  вида `CONFIGURATION`.
- `crates/unica-coder/src/infrastructure/native_operations/text_snapshot.rs` —
  байтовая стабильность писателя и политика переводов строк.
- `crates/unica-coder/src/application/mod.rs` — предпросмотр по умолчанию и
  форма результата на уровне вызова инструмента.
- `crates/unica-coder/src/infrastructure/native_operations/tests.rs` —
  типизированный путь диспетчеризации: `code-patch` не проходит через общий
  путь, теряющий `data`.
- `crates/unica-coder/src/infrastructure/format_guard.rs` — сверка формата
  выгрузки с активным профилем: вызов внутри набора исходников более старого
  формата блокируется.

## Границы расширения

- `replace`, `delete`, документирование методов и атомарная пакетная правка — за
  пределами v1; каждое требует собственного контрактного решения, а не
  расширения этого документа.
- Общие гарантии записи для XML и остальных изменяющих инструментов
  развиваются отдельно (#74) и не должны раздувать v1 `code.patch`.
