# ADR-0059: Терминальный результат runtime возвращается в том же вызове

- Статус: `accepted`
- Дата: `2026-08-14`
- Задача: [#406](https://github.com/IngvarConsulting/unica/issues/406)

## Контекст

Длительный `unica.runtime.execute` может пережить срок, который хост MCP отвёл
одному `tools/call`. Процесс `v8-runner` тогда способен завершить работу уже
после того, как вызывающая сторона прекратила ждать, и терминальный результат
теряется. Автоматический повтор через долговременное задание не исправляет
исходный вызов: он повторяет дорогую операцию и создаёт второй жизненный цикл.

Уведомления `notifications/progress` сами по себе не продлевают крайний срок
хоста и не являются терминальным результатом. Новые версии одного из
поддерживаемых хостов, кроме того, могут автоматически перевести долгий вызов в
фоновое задание и вернуть иной идентификатор. Настройка дочернего MCP-сервера не
доказывает, что родительский хост сохранил исходный вызов.

Закреплённый `v8-runner` владеет собственным `execution_timeout` до 86 400
секунд. Его непрерываемые критические фазы намеренно откладывают отмену, чтобы
не оставить информационную базу в повреждённом состоянии. Операции публикации
также не везде имеют доказанный ограниченный путь восстановления. Даже
оставшиеся проверки синтаксиса и запуск с ожиданием могут породить отдельную
группу процесса 1С: закреплённая версия не подтверждает готовность обработчика
сигнала до начала исполнения и очистку такой группы на каждом ошибочном пути.

Связанные изменения предметной поверхности отслеживает
[#465](https://github.com/IngvarConsulting/unica/issues/465), а стандартную
асинхронную границу MCP Tasks после снятия внешнего ограничения —
[#497](https://github.com/IngvarConsulting/unica/issues/497). Эта запись
закрывает дефект v0.12 для существующего `unica.runtime.execute`, не реализуя
ни будущие предметные инструменты, ни Tasks.

## Решение

1. Один применённый `unica.runtime.execute` принадлежит ровно одному
   `tools/call`. `unica.runtime.job.*` не используется как продолжение, повтор
   или запасной путь этого вызова.
2. До обнаружения рабочего пространства и запуска процесса приложение
   классифицирует выбранную операцию по возможности безопасного завершения.
   Любая неизвестная будущая ветвь по умолчанию получает отказ, пока отдельное
   решение не докажет обратное.
3. Все текущие применённые операции возвращают стабильный
   `runtime_operation_unbounded` в терминальном `OperationResult` исходного
   вызова. Предпросмотр остаётся доступным.
4. `init`, `build`, `load`, `test` и `extensions` отказывают из-за
   непрерываемых критических фаз. `config-init`, `dump`, `convert`, `make` и
   `tools-download` отказывают из-за записи или публикации без ограниченного
   восстановления. Запуск без ожидания отказывает из-за отсоединённого
   жизненного цикла. Все режимы `syntax` и запуск с `waitForExit=true`
   отказывают из-за недоказанного владения отдельно сгруппированным процессом
   1С; эта причина не называется непрерываемой критической фазой.
5. Общая `.mcp.json` не увеличивает крайний срок всех инструментов и не
   передаёт серверу неподтверждённую метку бюджета. При отсутствии допущенной
   применённой ветви такой предел не приносит пользы и ослабил бы защиту от
   зависания остальных `unica.*`.
6. Будущий допуск оформляется отдельным решением и требует одновременно
   доказать: сохранение хостом исходного `tools/call` без автоматического
   фонового перевода; достаточный крайний срок с резервом ответа; владение всем
   деревом процессов на путях успеха, ошибки, отмены и аварийного завершения;
   ограниченное завершение либо безопасное восстановление записи; работу
   наблюдаемости и отмены на минимальных поддерживаемых версиях обоих хостов.
7. Долговременные `unica.runtime.job.*` остаются отдельной явно вызываемой
   поверхностью для совместимости. Их запись, журналы и опрос не считаются
   результатом `unica.runtime.execute`.
8. Унаследованные `unica.build.*` не предлагаются как запасной путь вокруг
   отказа `unica.runtime.execute`. Они остаются отдельной существующей
   поверхностью, а решение об их миграции принадлежит #465.

## Неграницы

1. Решение не снимает и не переименовывает публичные инструменты runtime;
   окончательным разбиением владеют #465 и #497.
2. Существующие `unica.build.*` предшествуют этому изменению и остаются
   отдельной поверхностью до миграции по #465. Эта запись не подтверждает их
   безопасность и не изменяет их исполнение.
3. Решение не меняет транспорт MCP, платформенный фасад процессов,
   `execution_timeout` движка и исключение runtime из ADR-0023.
4. Решение не обещает прогресс для текущего применённого вызова: работа не
   начинается, поэтому изображать её ход нельзя.
5. Решение не объявляет предпросмотр свидетельством успешного исполнения в 1С.

## Последствия

1. Все текущие применённые режимы `unica.runtime.execute` возвращают
   терминальный отказ до обнаружения рабочего пространства и запуска процесса;
   потерянного результата и оставленного процесса нет, потому что работа не
   начинается.
2. Все текущие режимы `unica.runtime.execute` временно полезны только для
   предпросмотра. Это осознанная публичная деградация v0.12: прежнее исполнение
   сохраняло недоказанный жизненный цикл.
3. Скиллы не выдают предпросмотр за проверку runtime и не обходят отказ прямым
   запуском движка либо долговременным заданием.
4. Новая операция или режим должны получить явную классификацию; неизвестная
   ветвь остаётся закрытой по умолчанию.

## Верификация

- `cargo test -p unica-coder runtime_admission` проверяет полную карту текущих
  операций и режимов синтаксиса, точные причины и закрытие неизвестной ветви.
- `cargo test -p unica-coder applied_runtime_fails_closed` проверяет отказ до
  обнаружения рабочего пространства и форму терминального результата.
- `tests/ci/test_unica_skills.py` проверяет только предпросмотр во всех
  поставляемых инструкциях и запрет обходных путей.
- `tests/ci/test_package_unica_plugin.py` проверяет, что общий сервер не получает
  расширенный крайний срок и неподтверждённую метку бюджета.
