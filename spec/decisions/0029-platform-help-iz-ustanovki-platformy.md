# ADR-0029: Справка платформы читается из установки, а поиск по документации нейтрален к поставщику

- Статус: `proposed`
- Дата: `2026-08-08`
- Задача: https://github.com/IngvarConsulting/unica/issues/242

## Контекст

Публичными источниками справки были только `unica.standards.search` и
`unica.standards.explain`. Они проксируют v8std, то есть стандарты разработки и
диагностики, и не являются доказательством поведения платформы. Использование их
как справки по API смешивает разные классы доказательств и уже привело к
неверной маршрутизации.

После PR #232 подмена прекращена, но штатным ответом скилла `platform-help` стал
отказ: источника справки платформы на публичной поверхности нет. Пользователи
предъявили цену этого отказа дважды.

Все ранее рассмотренные источники отвергнуты: зеркало документации внутри
рабочего дерева создаёт состояние на каждое дерево и отдельный жизненный цикл
обновления; корпус внутри пакета противоречит тонкой поставке и лицензии; поиск
средствами хоста не является маршрутом MCP и не даёт версионной точности;
адаптер к ITS требует аутентификации и политики приватности.

Рассмотренные варианты, замеры стоимости чтения, проверка на вопросах задачи
#296 и отношение к внешнему проекту `1c-syntax/bsl-context` записаны в
[проектной записке](../../docs/design/2026-08-08-platform-help-documentation-provider-design.md).

## Решение

1. Источником справки платформы служат контейнеры справки той установки
   1С:Предприятия, которую Unica уже разрешает для рабочего пространства:
   Синтакс-помощник, встроенный язык и руководства платформы. Материалы вендора
   не копируются в репозиторий, не попадают в пакет и не кэшируются на диск.
2. Слой application работает через типизированный `DocumentationProvider`,
   нейтральный к источнику. Поставщик объявляет устойчивый идентификатор, свои
   корпуса и исполнимые возможности и возвращает собственную секцию поиска.
   Реестр собирается в корне композиции и допускает внедрение подмен для тестов;
   порядок реестра задаёт порядок секций публичного результата.
3. Контракт документации отделён от `CodeIntelligenceProvider` из ADR-0017.
   Данные, версии, доверие, лицензии и границы приватности у них различны, общий
   доменный контракт не вводится.
4. Поставщик и смысл источника — разные понятия. Поставщик описывает способ
   доступа, смысл источника описывает класс доказательства. Публичный запрос при
   необходимости ограничивает смысл источника, а не идентификатор поставщика.
5. Публичный поиск по документации — `unica.documentation.search`. Он возвращает
   типизированные данные секциями; каждое попадание несёт происхождение,
   авторитетность, применимую версию и устойчивый локатор. Ранги и оценки
   остаются локальными для секции: Unica не объединяет, не пересортировывает и
   не удаляет совпадения между секциями.
6. Отказ поставщика остаётся в его секции. Поиск успешен, если хотя бы один
   применимый поставщик вернул `ok` или `empty`; отмена имеет приоритет и
   никогда не выдаёт частичный результат за успешный.
7. Разбор корпуса не создаёт состояния на диске. Карта имён строится лениво,
   один раз на процесс на версию платформы, и живёт в скрытом сервисе.
8. Отсутствие источника, версии или страницы сообщается диагностичным статусом
   секции. Ответ по памяти вместо отказа не допускается, а вывод
   `unica.standards.*` не выдаётся за доказательство поведения платформы.
9. Публичная граница остаётся одним MCP-сервером `unica`. Выбор поставщика не
   становится аргументом инструмента.

## Неграницы

1. Решение не вводит `unica.documentation.get` и не переносит
   `unica.standards.*` за общий контракт: эти шаги остаются за задачей #242.
2. Решение не строит типизированную модель членов платформы. Ответ несёт
   сигнатуру и фрагмент страницы.
3. Решение не вводит удалённых и требующих аутентификации поставщиков, корпуса
   БСП и документации конфигурации.
4. Решение не вводит поиск средствами хоста как маршрут скилла.
5. Решение не публикует и не упаковывает материалы вендора.
6. Решение не вводит динамическую загрузку сторонних поставщиков и публичный
   ABI поставщика.

## Последствия

1. Скилл `platform-help` перестаёт отвечать отказом на обычный вопрос об API.
   Отказ сохраняется для двух проверяемых случаев: установка не разрешена и
   страницы в корпусе нет.
2. Ответ о поведении платформы становится точным по версии: он приходит из той
   установки, которой собирается конфигурация.
3. Загрузчик документации и корпус внутри рабочего дерева становятся не нужны и
   удаляются вместе с закрепляющими их проверками.
4. Новый источник документации проверяется подменным поставщиком без установки
   платформы.
5. Пакетные проверки обязаны удерживать отсутствие материалов вендора и
   загрузчика в архиве, а ведомость публичной поверхности — новый инструмент.

## Верификация

- `cargo test -p unica-coder documentation` — реестр и возможности поставщиков,
  внедрение подмен, порядок секций, частичный отказ, отмена, обязательность
  происхождения и применимой версии.
- `cargo test -p unica-coder --test platform_syntax_help` — разбор контейнера и
  ZIP на синтетической фикстуре, извлечение сигнатуры из `.st` в обеих локалях,
  сохранение обоих попаданий при коллизии имени, отсутствие записи на диск.
  Проверка против реальной установки включается переменной окружения.
- `python3.12 -m unittest tests.ci.test_unica_skills` — маршрутизация
  `platform-help` мимо `unica.standards.*`.
- `python3.12 -m unittest tests.ci.test_product_contracts` — отсутствие
  загрузчика и материалов вендора в отслеживаемом дереве и в архиве пакета.
- `python3 scripts/ci/generate-tool-surface.py --check` — синхронность ведомости
  публичной поверхности.
