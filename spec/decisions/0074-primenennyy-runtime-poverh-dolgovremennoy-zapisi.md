# ADR-0074: Применённый runtime исполняется в исходном вызове поверх долговременной записи

- Статус: `accepted`
- Дата: `2026-08-18`
- Задача: [#554](https://github.com/IngvarConsulting/unica/issues/554)

## Контекст

ADR-0066 закрыл применённый `unica.runtime.execute` целиком: любой режим с
`dryRun: false` возвращает `runtime_operation_unbounded` до обнаружения рабочего
пространства и запуска процесса. Причина была не в одной силе, а в четырёх:
непрерываемые критические фазы раннера, запись и публикация без ограниченного
восстановления, недоказанное владение отдельно сгруппированным процессом
платформы и отсоединённый жизненный цикл `launch`.

С тех пор наблюдаемая картина изменилась.

Долговременное задание уже исполняет применённые операции: гейт допуска
срабатывает только на `ToolHandler::RuntimeAdapter`, проверка аргументов
`unica.runtime.job.start` применённый режим не запрещает, а рабочий процесс
задания порождает раннера по-настоящему. То есть применённый runtime доступен из
текущей поставки — но только через поверхность, о которой поставляемые
инструкции говорят «не используй как обход отказа». Пользователи из этого
заключают, что применённых операций в продукте нет вовсе (#554).

Запись задания несёт фазу, отметку `heartbeat_at_ms` и признак небезопасной фазы. Это
наблюдаемое свидетельство того, что раннер вошёл в участок, который нельзя
рвать; раньше непрерываемость только предполагалась по имени операции.

Работу задания ведёт отсоединённый рабочий процесс, поэтому она переживает и
обрыв вызова, и остановку сервера. Раннер стартует своей группой процессов, а
отмена убивает группу целиком; на Windows дерево завершается `taskkill /T /F`,
что не достаёт отдельно сгруппированный процесс платформы.

Транспорт уже умеет наблюдаемость: MCP-слой достаёт `progressToken` из `_meta` и
публикует `notifications/progress`, а `notifications/cancelled` доведён до
доменного токена отмены. Спецификация MCP разрешает клиенту сбрасывать таймаут
при получении прогресса, но это `SHOULD`, поэтому поведение конкретного хоста
остаётся наблюдаемым фактом, а не гарантией.

## Решение

1. Применённый `unica.runtime.execute` не отказывает. Вызов заводит
   долговременную запись задания, ждёт её терминального состояния и возвращает
   результат операции в исходном `tools/call`.
2. Работу исполняет отсоединённый рабочий процесс задания; вызов только
   наблюдает запись. Терминальный результат принадлежит записи, а не живому
   вызову.
3. Пока вызов ждёт, сервер публикует `notifications/progress` по смене фазы и
   отметке `heartbeat_at_ms` записи. Прогресс не является результатом и не изображает
   процент выполнения.
4. `notifications/cancelled` вне небезопасной фазы отменяет задание вместе со
   всей группой процессов. Внутри небезопасной фазы вызов прекращает ожидание,
   задание доводится до конца, а ответ несёт `jobId` и названную причину, по
   которой прерывание не выполнено.
5. Обрыв вызова хостом не отменяет задание. Терминальный результат забирается по
   `jobId` через `unica.runtime.job.*`.
6. Классификация завершаемости из ADR-0066 сохраняется как классификация риска:
   названная причина едет в предупреждение перед стартом и в квитанцию, а не в
   отказ. Неизвестная операция остаётся неклассифицированной и отказывает.
7. `dryRun: true` остаётся синхронным предпросмотром без побочных эффектов и
   свидетельством runtime-исполнения не является.
8. `unica.runtime.job.*` остаётся отдельной явно вызываемой поверхностью для
   запуска без ожидания. Она не считается продолжением `unica.runtime.execute`,
   но запрет предлагать её как обход отказа снимается вместе с самим отказом.
9. Общая `.mcp.json` по-прежнему не увеличивает крайний срок всех инструментов и
   не передаёт серверу неподтверждённую метку бюджета: ожидание вызова опирается
   на прогресс и на долговременную запись, а не на расширенный срок.
10. Унаследованные `unica.build.*` остаются отдельной поверхностью и запасным
    путём вокруг применённого вызова не предлагаются; решение об их миграции
    принадлежит #465.

Запись заменяет ADR-0066.

## Неграницы

1. Решение не обещает целостность информационной базы после принудительного
   завершения раннера. Оно обещает не завершать его в небезопасной фазе и
   называть эту фазу вызывающей стороне.
2. Решение не меняет `execution_timeout` закреплённого раннера и не вводит
   ограниченное восстановление записи внутри него; такой контракт принадлежит
   апстриму RLM.
3. Решение не усиливает владение процессами на Windows. `taskkill /T /F` по
   дереву остаётся текущей границей, и отдельно сгруппированный процесс
   платформы ею не покрыт.
4. Решение не вводит асинхронную границу MCP Tasks; она принадлежит #497.
5. Решение не разбивает runtime на предметные инструменты; это #465.

## Последствия

1. Применённые операции снова доступны через `unica.runtime.execute`, включая
   обе формы `launch`. Для `launch` это осознанно принятый риск: отсоединённый
   клиент платформы не становится подконтрольным оттого, что его запустило
   задание.
2. Публичная деградация v0.12, названная в ADR-0066, снимается: предпросмотр
   больше не единственный доступный режим.
3. Поставляемые инструкции переписываются: маршрут «предпросмотр, затем
   применение» становится одним вызовом, а долговременное задание остаётся
   выбором для запуска без ожидания.
4. Хост, не сбрасывающий таймаут по прогрессу, всё равно обрубит долгий вызов.
   Это перестаёт быть потерей результата, но остаётся наблюдаемой разницей между
   хостами.
5. Отмена получает смысл, которого у неё не было: до этого решения отменять
   было нечего, потому что работа не начиналась.

## Верификация

- `cargo test -p unica-coder runtime_admission` — классификация риска больше не
  возвращает отказ для известных операций и по-прежнему отказывает
  неклассифицированной.
- `cargo test -p unica-coder applied_runtime_execute` — применённый вызов заводит
  запись задания, публикует прогресс по смене фазы и возвращает терминальный
  результат записи.
- `cargo test -p unica-coder applied_runtime_cancellation` — отмена вне
  небезопасной фазы убивает группу процессов, а внутри неё возвращает квитанцию
  с `jobId` и не убивает.
- `tests/ci/test_unica_skills.py` — поставляемые инструкции описывают применённый
  вызов и не выдают предпросмотр за исполнение.
- `manual` — ревьюер перечитывает поведение обоих хостов на минимальных
  поддерживаемых версиях: сбрасывается ли таймаут по прогрессу и доходит ли
  `notifications/cancelled` до сервера.
