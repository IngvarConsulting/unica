# ADR-0043: Читатели не принимают режим предпросмотра

- Статус: `accepted`
- Дата: `2026-08-10`
- Задача: [#297](https://github.com/IngvarConsulting/unica/issues/297)

## Контекст

Общий список аргументов MCP добавляет `dryRun` читающим и изменяющим
инструментам. Application вычисляет один boolean до проверки аргументов и
передаёт его всем обработчикам. Native typed readers, code intelligence и
documentation используют `true` как указание не читать и возвращают успешный
placeholder. Для типизированного reader такой ответ не содержит предметного
`OperationResult.data`, хотя утверждает `ok: true`.

`INV-SKILL-EXECUTABLE-EXAMPLES` закрепляет связанное допущение: тестовый стенд
насильно добавляет `dryRun: true` каждому примеру `tools/call`. У reader режим
предпросмотра не имеет отдельного предметного смысла. Он одновременно скрывает
зависимости примера и не доказывает исполнимость настоящего чтения.

Происхождение выбора и рассмотренные варианты записаны в
[проектной записке](../../docs/design/2026-08-10-reader-invocation-mode-design.md).

## Решение

1. `ToolSpec` называет категорию исполнения `Read` или `Mutation` вместо
   независимого поля `mutating: bool`. `dryRun` публикуется и принимается только
   категорией `Mutation`; категория `Read` отклоняет поле с любым значением как
   неизвестный аргумент до определения рабочего пространства, выбора
   поставщика и вызова внутреннего обработчика.
2. Прикладной слой владеет режимом вызова `Read`, `Preview` или `Apply`. `Read`
   выводится только из одноимённой категории, `Preview` — из мутации с
   отсутствующим `dryRun` или значением `true`, `Apply` — из мутации с
   `dryRun: false`. Неизвестное поле проверяется раньше, чем может повлиять на
   режим.
3. Общий `dry_run: bool` не пересекает границу чтения. Смешанные порты
   прикладного слоя принимают предметный режим, порты только для чтения не
   принимают его, а логическое значение для существующего адаптера
   предпросмотра выводится только внутри доказанной ветки мутации.
4. Читатель всегда выполняет предметное чтение. Нативные типизированные
   читатели, анализ кода, навигация и ресурсы исходников, стандарты,
   документация, инструменты проекта и читающие операции среды выполнения не
   имеют ответа-заглушки.
5. `ToolSpec` называет контракт результата `Typed` или `ExternalStream`, а CI
   сверяет его с `tool-surface-review.json`. Успешный вызов `Read + Typed`
   содержит `OperationResult.data`; отсутствие данных завершает вызов
   жёсткой ошибкой `typed_result_missing`. Предметный отказ с `ok: false` может
   не содержать данных.
6. Отчёт о кеше режима `Read` остаётся чтением, не создаёт доменных событий и
   не инвалидирует состояние. Контракт `Preview` и `Apply` для мутаций, включая
   предпросмотр по умолчанию, этой записью не меняется.
7. Пример скилла исполняется согласно категории инструмента: пример мутации —
   через предпросмотр MCP, пример чтения — обычным вызовом MCP над
   детерминированной фикстурой или локальным подставным поставщиком. Проверка
   одной схемы не заменяет исполнение предметного чтения.
8. При реализации вводится новая запись реестра о границе предпросмотра,
   расширяется `INV-MCP-TYPED-RESULT` и уточняется
   `INV-SKILL-EXECUTABLE-EXAMPLES`. ADR-0043 переводится в `accepted` только
   одним набором изменений с кодом, проверками, выведенными правилами и
   сгенерированной ведомостью поверхности.

## Неграницы

1. Решение не меняет `confirm`, `cwd` и предметные аргументы инструментов.
2. Решение не стабилизирует preview мутаторов и не закрывает #290.
3. Решение не меняет предметную структуру успешного reader, кроме требования
   присутствия `data`.
4. Решение не вводит alias `dryRun` для readers и не подменяет чтение
   синтетическим пустым результатом.
5. Решение не добавляет `outputSchema` всем инструментам и не меняет
   существующую транспортную форму ошибки выполнения.
6. Решение не разрешает parity-тесту обращаться к живой сети, пользовательской
   установке платформы или общему provider state.

## Последствия

- Схемы readers становятся уже, а ручной `dryRun` перестаёт скрывать
  предметные ошибки цели и поставщика.
- Внутренняя диспетчеризация становится исчерпывающей: reader нельзя случайно
  перевести в preview значением общего boolean.
- Каждый новый инструмент обязан явно назвать категорию исполнения и контракт
  результата; механическое добавление записи реестра становится заметнее.
- Skill parity потребует точных reader-фикстур и локальных stand-ins. Это
  увеличивает цену стенда, но он начнёт доказывать исполнение показанного
  чтения, а не только достижимость placeholder.
- Прямой MCP-клиент, который передавал `dryRun` reader-инструменту, должен
  удалить поле. Изменение закрывает unreleased regression версии 0.12.0 и не
  сохраняет неоднозначный alias.
- Решение принимается только вместе с реализацией, проверками, выведенными
  правилами и сгенерированной ведомостью поверхности; один документ без них не
  позволяет считать #297 исправленной.

## Верификация

- `manual` — архитектурное ревью проверяет разделение `Read`, `Preview` и
  `Apply`, отсутствие preview у readers, fail-closed постусловие typed success,
  детерминированность skill parity и границу implementation PR.
- `python3.12 -m unittest tests.ci.test_design_documents` — проверяет связь
  утверждённой проектной записки с ADR-0043 и обязательную шапку документа.
- `python3.12 -m unittest tests.ci.test_architecture_registry` — проверяет
  номер, принятый статус, индекс, ссылки и выведенные правила решения.
- `python3.12 -m unittest tests.ci.test_unica_mcp_script_parity` — исполняет
  примеры мутаций в preview, а readers — как настоящее локальное чтение.
- `cargo test -p unica-coder -- --test-threads=1` — проверяет вывод режима,
  отсутствие reader-placeholder и fail-closed постусловие typed reader.
