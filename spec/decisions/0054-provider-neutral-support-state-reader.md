# ADR-0054: Состояние поддержки читается по логической цели через порт

- Статус: `proposed`
- Дата: `2026-08-12`
- Задача: [#289](https://github.com/IngvarConsulting/unica/issues/289)

## Контекст

Семь предметных читателей получают состояние поддержки из функций
инфраструктуры, которые принимают файловый путь и сами предполагают раскладку
Platform XML. Для источника EDT отсутствие
`Ext/ParentConfigurations.bin` выглядит как законное `notSupported`, хотя
поставщик не прочитал состояние вообще. Эта подмена влияет на решение изменять
объект напрямую или через расширение.

`ResolvedTarget` уже отделяет логическую идентичность от файловой раскладки, но
типы ответа поддержки и способ чтения принадлежат
`native_operations/common.rs`. `unica.cf.info` читает состояние всей
конфигурации, а остальные шесть потребителей — состояние отдельного объекта;
один нетипизированный метод не выражает обе операции.

Происхождение выбора и рассмотренные альтернативы записаны в
[проектной записке](../../docs/design/2026-08-12-provider-neutral-support-state-reader-design.md).

## Решение

1. Домен определяет малый порт `SupportStateReader` с раздельными операциями
   `configuration_support` и `object_support`. Обе принимают
   `ResolvedTarget` и возвращают доменные типизированные данные либо
   `SupportReadError`; файловый путь частью порта не является.
2. Реализация reader-а связана со снимком рабочего пространства. Она разрешает
   `sourceSet`, выбирает поставщика по `SourceFormat` и хранит физическую ручку,
   идентификатор объекта и файл состояния поддержки внутри инфраструктуры.
3. Первый срез реализует чтение только для платформенного XML. Другой формат,
   неизвестный формат и недопустимый набор возвращают явную ошибку
   `provider_unavailable`, а не состояние `notSupported`.
4. У доказанного набора платформенного XML отсутствие
   `Ext/ParentConfigurations.bin` означает `notSupported`. Существующий, но
   нечитаемый, нерегулярный или повреждённый файл состояния завершает чтение ошибкой и
   не разрешает принимать решение о безопасности прямой правки.
5. Предметный читатель разрешает и логический, и временно сохранённый файловый
   селектор в пару из `ResolvedTarget` и закрытого пути ресурса. Предметный XML
   читается по закрытому пути, а состояние поддержки — только через порт по
   логической цели. Неоднозначный или недоказанный файловый путь не порождает
   эвристический адрес.
6. `unica.cf.info` вызывает конфигурационную операцию порта; `unica.meta.info`,
   `unica.form.info`, `unica.role.info`, `unica.mxl.info`,
   `unica.subsystem.info` и `unica.dcs.info` вызывают объектную. Успешные
   типизированные ответы на публичной границе сохраняют действующие поля и значения.
7. `unica.dcs.info` сохраняет существующее поле `data.support`. Отдельное
   текстовое представление состояния удаляется, чтобы один факт не имел второй
   грамматики рядом с типизированным результатом.

## Неграницы

1. Решение не реализует чтение состояния поддержки для EDT.
2. Решение не снимает файловые селекторы предметных читателей; их переходом
   продолжает владеть ADR-0049.
3. Решение не меняет правила мутирующего стража поддержки и инструмент
   `unica.support.edit`; их перевод на тот же порт требует отдельного
   доказательства атомарности и привязки pre-image.
4. Решение не добавляет и не меняет публичный инструмент, аргумент или поле
   успешного ответа.

## Последствия

1. `notSupported` снова означает прочитанное состояние, а не отсутствие
   реализации поставщика.
2. Подключение EDT-reader-а не потребует менять семь предметных обработчиков.
3. Путевой мост ADR-0049 получает обязанность доказать логическую цель до чтения
   поддержки; произвольный файл вне зарегистрированного набора больше не может
   дать правдоподобный ответ о поддержке.
4. Нечитаемый marker переводит читатель в отказ. Это строже прежнего поведения,
   но предотвращает небезопасное решение на основании выдуманного состояния.

## Верификация

- `cargo test -p unica-coder support_state -- --test-threads=1` — проверяет
  доменный порт, выбор поставщика и различение отсутствующего, нечитаемого и
  повреждённого marker-а.
- `cargo test -p unica-coder answers_identically -- --test-threads=1` —
  проверяет одинаковое состояние поддержки для логического и временного
  файлового селектора одной цели.
- `cargo test -p unica-coder role_info_reads_the_support_state_from_the_configuration_root -- --test-threads=1`
  — проверяет привязку `Rights.xml` к логической цели роли и корню конфигурации.
- `cargo test -p unica-coder infrastructure::application_ports::tests -- --test-threads=1`
  — проверяет внедрение порта и отсутствие прямого обхода семью читателями.
- `tests/ci/test_architecture_registry.py` — проверяет выведенное правило,
  решение-владелец и исполняемые цели проверки.
