# Разделение PR #601 по областям отказа

## Проблема

PR #601 смешал три независимо проверяемых изменения:

1. поставку малого ядра и загрузку движков по требованию;
2. замену нормативного слоя `spec/` на реестр `arch/`;
3. измерение и сокращение публичной MCP-поверхности.

Их нельзя откатить, проверить или принять одной границей. Поставка меняет
runtime, кеш и release pipeline; архитектурный reset меняет управление
решениями; поверхность меняет публичные схемы и стоимость каталога.

## Решение

Работа идёт последовательно двумя pull request, оба с базой `main`:

1. **Core-first delivery.** Из актуального `main` переносится только поставка
   ядра, артефактный кеш, доставка движков, `prefetch` и release-проверки.
   Действующие архитектурные обязательства оформляются в текущем `spec/`.
2. **Architecture v2 reset.** После слияния delivery PR новая ветка создаётся
   из обновлённого `main`; она меняет только нормативную документацию и её
   стражи, включая перенос уже принятого delivery-контракта.

Изменения MCP-поверхности, token-cost harness и решения будущих входов в эти
два PR не входят. Они остаются достижимыми через исходную ветку PR #601 и
получат отдельную границу после завершения reset.

## Почему delivery идёт первым

- #585 и #549 описывают пользовательский отказ и не должны ждать смены
  документационного слоя.
- Delivery можно проверить на трёх ОС и на опубликованных байтах независимо от
  формата архитектурного реестра.
- Architecture reset после слияния переносит фактически принятое решение, а не
  предполагаемую будущую реализацию.
- PR не образуют стек: второй открывается только после попадания первого в
  `main`.

## Граница delivery PR

Входит:

- `crates/unica-bootstrap`: раздельные артефакты, resumable download,
  артефактный lock, ready marker, очистка кеша и `prefetch`;
- `crates/unica-coder`: разрешение движка из артефактного кеша и серверная
  доставка с типизированным состоянием долгой работы;
- package/release scripts, runtime manifest, probes и published smoke;
- delivery-specific ADR, инварианты, runbook и пользовательская документация;
- regression tests для immutable identity, stale transaction и admission.

Не входит:

- `arch/`, перенос `spec/`, новый формат записей и новый `AGENTS.md`;
- изменение схем существующих MCP-инструментов, не требуемое доставкой;
- token-cost и будущая поверхность;
- отключение `tests/parity` или `tests/harness`.

## Граница architecture PR

Входит только новый реестр, его генератор и тесты, замороженный архив v1,
точка входа агента и полная таблица переноса. Runtime и публичные схемы должны
совпадать с `main` побайтово.

`active` означает действующее обязательство. Принятое, но ещё не реализованное
направление получает отличный статус и не выдаётся за текущее поведение.
Порядок источников истины сохраняется: код и тесты, контрактные метаданные,
спецификации форматов, нормативная архитектура, проза.

## Merge gate delivery PR

- cache identity включает immutable asset tag или digest;
- другая сборка той же upstream-версии не переиспользует старую установку;
- прерванные staging-транзакции очищаются под артефактным lock;
- ожидающие загрузку вызовы не исчерпывают общий MCP admission;
- Ubuntu, Windows и macOS Rust jobs зелёные;
- package, bootstrap probe, published smoke и повторная проверка байтов
  действительно выполнены;
- parity и harness не выключены.

## Merge gate architecture PR

- каждая запись v1 имеет явную судьбу;
- полнота переноса проверяется автоматически;
- правило утверждает не больше, чем проверяет названный check;
- `AGENTS.md` сохраняет порядок источников истины и release gate;
- diff вне документации и архитектурных стражей пуст;
- все ранее обязательные тестовые контуры остаются обязательными.
