# Ядро первым, движки по требованию

## Проблема

Полный runtime повторно публиковал 439 МБ движков из `unica-toolchain` и делал
их загрузку условием старта MCP. При этом один вызов использует один движок, а
кеш по одной семантической версии не различает пересобранные байты.

## Рассмотренные варианты

1. Оставить полный runtime и увеличить startup timeout. Это не убирает
   дублирование, не сокращает холодный путь и не исправляет идентичность кеша.
2. Раздать движки отдельными публичными MCP-серверами. Это ломает единый
   оркестратор и переносит согласование состояния на модель.
3. Запустить малое ядро, а закреплённые движки доставлять внутренне по
   требованию. Этот вариант сохраняет одну публичную границу и переносит
   стоимость сети на первый действительно нуждающийся вызов.

Выбран третий вариант. Байтовая идентичность включает SHA-256 asset, поставка
остаётся проверяемой и атомарной, одинаковые параллельные запросы делят одну
серверную доставку, а `prefetch` закрывает сборку офлайн-образов.

## Границы решения

Решение меняет контракт упаковки, кеша, релизного CI и общий результат вызова,
поэтому его владелец — ADR-0076. Набор `unica.*`, единственный сервер `unica`,
форматы 1С, состояние рабочего пространства и architecture v2 не меняются.

## Проверяемая приёмка

- пересборка той же версии с другим SHA-256 получает другой корень кеша;
- stale transaction удаляется только под точной блокировкой поставки;
- followers общей загрузки немедленно освобождают admission slot;
- опубликованный выпуск содержит только три пары core-ассетов;
- движки достижимы по манифесту и полный `prefetch` проходит до продвижения;
- core smoke и BSP assessment явно называют дополнительный engine input.
