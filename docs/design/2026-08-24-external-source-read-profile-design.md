# Read-only профиль внешних source-set

## Проблема

Designer source-set типов `EXTERNAL_DATA_PROCESSORS` и `EXTERNAL_REPORTS` уже
обнаруживаются проектом и навигируются на корневом уровне, но общий логический
resolver допускает только Configuration и Extension. Поэтому предметные
читатели расходятся с validate/outline на одном и том же корректном дампе.

## Выбор

Resolver получает отдельный read-only профиль для EPF/ERF. Он доказывает
владельца по корневому `<Имя>.xml`, дочерние Form/Template — по регистрации в
`ChildObjects` и отдельному дескриптору, а ObjectModule/FormModule — по той же
цепочке владельцев. Физический selector восстанавливает этот же логический
адрес. Профиль записи остаётся прежним и не принимает внешние source-set.

`meta.info` использует процессорную или отчётную внутреннюю проекцию свойств,
но сохраняет публичный discriminator `ExternalDataProcessor` либо
`ExternalReport`. Полная конфигурационная validation неприменима к внешнему
артефакту без `Configuration.xml`; внешний read gate использует уже доказанную
идентичность дескриптора и сохраняет ошибки дочерних ресурсов в результате.

## Проверка

Сквозной тест создаёт EPF 8.3.27 с формой, макетом и модулями, затем вызывает
публичные `source.children`, `meta.info`, `form.info`, `mxl.info`; диагностическая
проверка отдельно разрешает тот же логический `ObjectModule` до запуска
поставщика. Ещё одна проверка сохраняет отказ writer-профиля и доказывает, что
повреждённый дочерний XML не становится успешным чтением.
