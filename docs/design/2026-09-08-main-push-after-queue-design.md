# Push в `main` после очереди: тестов нет, отчёт с очереди, страница «Конвейер» снята

## Задача

Очередь слияния включена 05.09.2026 и проверяет ровно то дерево, которое ляжет
в `main`, полным набором small и medium на ubuntu и macOS. Push в `main`
после вливания остался от прежних ворот и гонял тот же набор второй раз.
Вопрос владельца 08.09.2026: зачем тратить раннеры на `main`, если очередь
уже всё проверила, а тяжёлый ярус идёт ночью.

Замысел площадки — [2026-09-04-test-pipeline-platform-design.md](2026-09-04-test-pipeline-platform-design.md),
план правок под параллельные сессии —
[2026-09-07-pipeline-parallel-sessions-plan-design.md](2026-09-07-pipeline-parallel-sessions-plan-design.md).

## Что показали прогоны

Три последних push-прогона `main` 07.09.2026 (34169905503, 34168876311,
34166064306), все зелёные, все на деревьях, уже проверенных очередью:

| Джоба | Минут |
| --- | --- |
| Rust tests (macos-14) | 9–11 |
| Rust tests (ubuntu-latest) | 7 |
| Python tests (ci-medium) | 5 |
| Python small, arch, dev, guards | 3 |
| Итого на вливание | около 25 |

Профили `queue` и `main` в `run-tests.py` и `.config/nextest.toml`
тождественны: размеры, матрица раннеров, фильтры. Дубль полный.

Кэш зависимостей push-прогон при этом не писал: в логе обоих Rust-раннеров
«Cache hit for: v0-rust-test-rust-platforms-…» на входе и «Cache up-to-date»
на выходе. Ключ кэша считается от `Cargo.lock` и toolchain, при точном
попадании действие не сохраняет. За 30 дней до 08.09.2026 в `main` 974
коммита, из них `Cargo.lock` или toolchain меняли 18. На остальных
push-прогон не давал ничего.

Репозиторий публичный, минуты бесплатны; цена — пять слотов macOS на
организацию: push в `main` держал один десять минут, пока его ждали PR и
очередь.

Сайт: шаг «Пересобрать страницы с итоговым статусом» шёл 109 с из 150 с
сборки. Всё это — критерии страницы «Конвейер»: список прогонов за 14 дней
и `gh run view --json jobs` на каждый из 60 последних. Ни ночь, ни релиз на
эти данные не опираются; контрибьютеру нужен статус PR.

## Решение

Каждая проверка идёт один раз на том дереве, где её результат что-то решает.
PR решает готовность автора, очередь — вход в `main`, ночь — тяжёлый ярус,
тег — выпуск. Push в `main` ничего не решает и не проверяет.

1. **Push в `main`** — контур `cache` в `evaluate-ci-gate.py`. Наборы Python
   не идут. Rust-джоба идёт только когда в диапазоне push (`github.event.before`
   → `GITHUB_SHA`) есть `toolchain_changed` или `ci_changed`: тогда ключ
   кэша зависимостей новый, и запись с ветки по умолчанию — единственная,
   которую читают pull request. Классификация диапазона — `classify-changes`
   тем же скриптом, что у pull request; без прежней вершины (первый или
   принудительный push) — полный контур. Ожидаемо остаются classify, guards
   и сводная «Unica CI», около минуты.
2. **Релизные линии `release-v*`** остаются на полном профиле `main`:
   очереди на них нет (ruleset не принимает шаблоны веток).
3. **Отчёт `main` на сайт** собирается из прогона очереди. `resolve-line.py`
   относит `gh-readonly-queue/<база>/pr-N-<sha>` к линии базы, и подпись
   результатов несёт `main`. `unica-pages.yml` принимает источник
   `merge_group` и push с `head_branch` не `main`; фильтр веток получает
   `gh-readonly-queue/main/*`. Очередь бывает только у своего репозитория,
   так что опора на доверие та же, что у push.
4. **Гонка деплоев Pages.** Очередь даёт по прогону на каждый pull request
   партии, и деплои идут друг за другом. Неудачный `deploy-pages`
   повторяется один раз после паузы 90 с; второй отказ — поломка, не гонка.
5. **Страница «Конвейер» снята**: `docs/pages/pipeline.html`,
   `scripts/ci/pipeline_metrics.py`, флаг `--metrics` в `site-status.py`,
   тест. Отчёты Allure, память `large.json` для ночи, история трендов и
   счётчики на главной не тронуты. Пороги плана от 07.09.2026 остаются
   целями; замер по требованию — те же запросы `gh run list` и
   `gh run view --json jobs`.

## Что проверяется где

- **Коммит в PR** (`pull_request`, профиль `pr`): guards, Python small, Rust
  small на одном ubuntu. Быстрый сигнал автору.
- **Вливание** (`merge_group`, профиль `queue`): guards, Python small и
  medium, Rust small и medium на ubuntu и macOS. Единственные ворота `main`;
  результаты едут на сайт в линию `main`.
- **`main` после вливания** (`push`, контур `cache`): classify, guards,
  сводная; Rust только при смене ключа кэша или конвейера.
- **Ночь** (`unica-nightly.yml` → `workflow_dispatch` с `profile: large`):
  ярус `large` на ubuntu, macOS и Windows, полный контур сборки, память
  проверенной вершины на сайт. Без изменений.
- **Тег `v*`** (профиль `release`): все размеры, упаковка, публикация, дым.
  Без изменений.

## Что потеряно и чем заменено

- История длительности и повторов по прогонам на сайте. Сырые данные
  остаются в junit каждого прогона семь дней; при следующем решении о числе
  повторов их собирает скрипт по `gh run download`.
- Прогон push в `main` как «второе мнение» о том же дереве. Второго мнения
  не было: те же профили на том же коммите.

## Проверка после вливания

1. Первый прогон очереди после вливания должен породить прогон
   `unica-pages` с событием-источником `merge_group`, и отчёт `main` на
   сайте получить его `sha`.
2. Push-прогон `main` без смены toolchain должен пройти за минуту с контуром
   `cache` в сводке «Unica CI» и без джоб тестов.
3. Ночь и тег не трогались; их проверяет следующий запуск как обычно.
