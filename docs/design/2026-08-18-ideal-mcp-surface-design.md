# Синтетическая модель идеальной поверхности MCP

## Зачем

Сравнение с EDT-MCP (18.08.2026) и инвентаризация дерева метаданных показали
три факта о текущей поверхности:

1. **Каталог дорог.** `tools/list` стоит ~67 000 токенов o200k_base на 71
   инструмент (~945 на инструмент против ~270 у EDT-MCP). Половину несёт союз
   `NATIVE_XML_DSL_ARGS` (28 инструментов публикуют по 130+ аргументов),
   ещё ~16 000 — две схемы `operations` у `meta.add`/`meta.edit`.
2. **Одно дерево обслуживают три несовместимые модели обращения:**
   типизированные операции (`sourceSet` + `metadataPath` + `operations`),
   путевые DSL-инструменты (`FormPath`/`RightsPath`/`TemplatePath`/`CIPath` +
   союз аргументов в PascalCase) и читатели снимка (`resourceId` +
   `snapshotId`). Вопрос «какую тулзу взять» неразрешим не из-за числа тулз,
   а из-за того, что три модели отвечают на пересекающиеся вопросы разными
   словами.
3. **Дерево покрыто неравномерно.** Из 43 видов объектов `meta.add` создаёт
   23; 33 ветки создаются без флагов («доделайте в Конфигураторе», реестр
   `spec/architecture/meta-capability-parity.json`); запись останавливается на
   глубине два, притом что чтение (`meta.info`) достаёт глубже; 56 веток живут
   в отдельных доменных семействах со своей адресацией.

Владелец поставил задачу: спроектировать модель «как если бы сервер писался с
нуля», оптимизируя три величины — лёгкость выбора инструмента моделью,
лёгкость формирования аргументов, лёгкость чтения результата, — и лишь затем
думать о пути приведения. Эта записка фиксирует выбранную модель. Путь
приведения — вне её объёма.

Рассмотрены три кандидата: (A) навигатор с операциями по предъявлению,
(B) специализированные тулзы по веткам с подсказками в результатах просмотра
(исходная гипотеза владельца), (C) фиксированная глагольная сетка
`домен × глагол`. Выбрана A; B отклонена из-за цены каталога (десятки тулз со
схемами в каждой сессии оплачивают различимость, которую подсказки уже дают
бесплатно) и неустойчивой границы «по веткам»; C — из-за разреженной матрицы
и сохранения выбора-припоминанием.

## Принципы

- **Узнавание вместо припоминания.** Выбор из восьми входов надёжнее выбора из
  семидесяти; выбор операции из списка, напечатанного в результате, надёжнее
  припоминания имени тулзы из каталога.
- **Словарь оплачивается по мере пользы.** Всё, что можно не класть в
  `tools/list`, переезжает в данные: доступные операции — в результат
  просмотра, скелеты аргументов — туда же, словарь действий платформы — в
  ответ пустого вызова.
- **Адрес переиспользуется вместо новых ручек.** Глубина просмотра, область
  поиска, цель проверки — всюду один и тот же адрес, а не отдельные параметры
  `depth`/`sections`/`scope` со своей грамматикой.
- **Ошибка — это дешёвый просмотр.** Промах возвращает материал для
  следующего вызова (словарь, допустимые значения, ближайшие адреса), а не
  отказ.
- **Пустое не сериализуется.** Ни обязательного конверта, ни пустых массивов,
  ни pretty-print. Замер 18.08: квитанция «наборов не найдено» стоит 209
  токенов, из них 148 — конверт.

## Адрес

Полное имя 1С, достроенное до листьев. Синтаксис платформы (`ПолноеИмя()`,
RLS, состав планов обмена) — модель знает его из обучения, новая грамматика
не вводится.

**Одно правило: чередование `Вид.Имя`.** Нечётный сегмент — вид узла, чётный
— имя. Адрес любой глубины выводится по индукции.

| Адрес | Узел |
| --- | --- |
| *(пусто)* | корень конфигурации |
| `Catalog` | ветка всех справочников |
| `Catalog.Валюты` | объект |
| `Catalog.Валюты.Attribute` | ветка реквизитов |
| `Catalog.Валюты.Attribute.Код` | реквизит |
| `Catalog.Валюты.TabularSection.Курсы.Attribute.Курс` | реквизит табличной части |
| `Catalog.Валюты.Form.ФормаСписка.Item.Курс` | элемент формы |
| `Catalog.Валюты.Template.Печать.Area.Шапка` | область макета |
| `Catalog.Валюты.Module.Manager` | модуль менеджера |
| `HTTPService.API.URLTemplate.orders.Method.get` | метод HTTP-сервиса |
| `Role.Продавец` | роль |

Следствия:

- **Ветка адресуема.** `Catalog` и `Catalog.Валюты.Form` — узлы, а не
  «unaddressable collection». Сценарии «перечисли справочники» и «покажи
  формы объекта» (сегодня оба — тупики, см. #548) закрываются самим адресом.
- **Глубина не ограничена.** Сегодняшний потолок «глубина два» — свойство
  формы операций, а не адреса; правило чередования его не содержит.
- **Граница адреса и данных.** Адрес достаёт до именуемых узлов дерева.
  Сквозные множества пар — права роли, состав подсистемы и плана обмена,
  движения документа, владельцы — не адресуются, а передаются данными внутри
  операции. Признак напечатан в результате: у строки-узла есть `at`, у
  строки-данных его нет.
- **Набор исходников необязателен.** При единственном наборе подставляется
  автоматически; при нескольких адрес может нести префикс `main:Catalog.…`;
  результат всегда возвращает разрешённый набор явно.
- **Язык.** Вид принимается на двух языках (`Справочник.Валюты` =
  `Catalog.Валюты`), имя — только программное (не синоним). Канонический
  ответ — с английским видом (совпадает с раскладкой XML и не зависит от
  варианта встроенного языка). Открытая деталь: если для потребителя важнее
  совпадение с русским кодом конфигурации, канон меняется на русский без
  изменения механики.

## `view` — один читатель на всё дерево

```
view(at, filter?, limit?, cursor?)
```

Глубину задаёт адрес, не параметр: `view(Catalog.Валюты)` — объект со сводкой
веток, `view(Catalog.Валюты.Attribute)` — список реквизитов. Параметров
`depth`/`sections`/`delivery`/`page` нет.

**Семь слотов, одинаковых для всех узлов:**

```jsonc
{
  "at":       "Catalog.Валюты",          // канонический адрес, готов к копированию
  "kind":     "Catalog",
  "title":    "Валюты — Валюты",
  "props":    { "hierarchical": false, "codeLength": 3 },   // только заданное
  "branches": [                          // навигация вниз: адреса, не имена
    { "at": "Catalog.Валюты.Attribute", "count": 12 },
    { "at": "Catalog.Валюты.Form",      "count": 4 }
  ],
  "can": [                               // операции этого узла со скелетами
    { "op": "attribute.add",
      "args": { "name": "…", "type": "СправочникСсылка.Страны",
                "indexing": "Index|DontIndex" } },
    { "op": "props.set", "args": { "hierarchical": true } },
    { "op": "delete",    "args": {} }
  ],
  "limits": [ "Реквизит: флаг nonneg не поддержан" ],
  "set":    "main"
}
```

- `branches[].at` — спуск копированием строки; `count` позволяет решить, надо
  ли спускаться, до вызова.
- `props` — только отличия от умолчаний платформы.
- `can` — скелет с плейсхолдерами (`"…"`) и закрытыми выборами
  (`"A|B|C"`), не JSON Schema. Список отфильтрован узлом: на объекте 5–8
  записей, на реквизите 3. Осознанный размен: ~250 токенов в `view` за
  попадание `apply` с первой попытки; подлежит замеру (см. «Риски»).
- `limits` — известные ограничения записи, названные до, а не после попытки.
- На ветке те же слоты плюс `items[]` и `cursor`. У элементов `items`,
  являющихся узлами, есть `at`; у строк-данных (права, состав) — нет.

Полиморфизм по виду узла: форма отдаёт элементы и команды, роль — счётчик
прав и ветку `Right`, макет — области и параметры, сервис — шаблоны и методы.
Слоты не меняются.

## `apply` — один писатель на всё дерево

```
apply(at, op, args, dryRun?, ifRev?)
```

- **`op` — строка из `can`.** Словарь операций не существует в `tools/list`;
  он напечатан в дереве на тех узлах, где применим.
- **Одна операция за вызов.** Пустой объект 1С валиден, поэтому «создать
  документ с пятью реквизитами» — `create` плюс пять `apply` с локальными
  ошибками. Где домен множественный по природе, `args` принимает массив
  (`attribute.add` — один или много): множественность данных, не операций.
- **Именование `существительное.глагол`,** глаголы: `add`, `set`, `remove`,
  `rename`, `create`. Алгебра сегодняшних `operations` сохраняется, меняется
  упаковка.
- **`dryRun`** — тот же вызов без публикации, та же валидация и квитанция.
  Отдельного двухфазного `confirm`-протокола нет. Опасные операции защищаются
  фактами: `delete` при живых ссылках возвращает отказ со списком ссылающихся
  и требует `args.force` (паттерн сегодняшнего `meta.remove`).
- **`ifRev`** — необязательная защита от потерянного обновления: `view`
  возвращает `rev` узла, `apply` с `ifRev` отклоняется при расхождении.
  Обобщение `contentHash`/`expectedHash` EDT-MCP с модуля на любой узел.

**Квитанция** в той же дисциплине слотов; пустое не сериализуется:

```jsonc
{
  "ok": true,
  "at": "Catalog.Валюты.Attribute.Страна",   // для create — новый адрес
  "did": "реквизит добавлен: СправочникСсылка.Страны, Index",
  "changed": ["Catalogs/Валюты.xml"],
  "next": [ { "op": "form.add", "at": "Catalog.Валюты",
              "why": "реквизит не размещён ни на одной форме" } ]
}
```

**Ошибка — дешёвый `view`.** `view` перед `apply` не обязателен: знающий
агент бьёт сразу, промах возвращает недостающее. Три формы покрывают три
способа промахнуться:

```jsonc
{ "ok": false,
  "error": { "code": "unknown_op",
             "message": "у узла Catalog.Валюты нет операции attribute.set" },
  "can": [ { "op": "attribute.add", "args": { "name": "…" } } ] }
```

```jsonc
{ "ok": false,
  "error": { "code": "bad_value", "at": "args.indexing",
             "message": "«Индекс» не значение" },
  "expected": "Index | DontIndex | IndexWithAdditionalOrder" }
```

```jsonc
{ "ok": false,
  "error": { "code": "not_found", "at": "Catalog.Валюта" },
  "nearest": ["Catalog.Валюты", "Catalog.ВалютыКурсы"] }
```

Максимум два вызова в любом из трёх путей: знающий — `apply`; незнающий —
`view` → `apply`; ошибшийся — `apply` → исправленный `apply`.

## Форма результата: JSON со слотовой дисциплиной

Результаты всех входов — компактный JSON, не проза. Критерий — тот же, что в
измеренной политике EDT-MCP (Markdown по умолчанию, JSON для round-trip
идентификаторов), применённый к нашей поверхности честно: в целевой модели
почти каждый результат несёт round-trip материал (`at` — в следующий вызов,
`op` — из `can` в `apply`, `rev` — в `ifRev`), поэтому дефолт
переворачивается. Из JSON-строки модель копирует адрес, из прозы —
пересказывает; с двуязычными адресами пересказ означает перевод и склонение,
и один промах `not_found` съедает всю markdown-экономию.

Замер 18.08 (o200k, всё компактно): квитанция `apply` в JSON — 47 токенов
против 41 у эквивалентной прозы (+15 %, а не «в разы»; в разы стоили конверт
и pretty-print — 209). В списке из 50 строк драйвер цены — не синтаксис, а
повторение префикса адреса: JSON-объекты с полным `at` — 25/строку, markdown
с полным `at` — 22, колоночный JSON — 19, markdown без префикса — 12.

Правила, возвращающие JSON почти всю экономию прозы:

- компактная печать, пустое не сериализуется (уже в «Принципах»);
- **относительные имена в больших листингах**: результат ветки несёт свой
  `at` один раз, строки `items[]` — короткое имя; полный адрес собирается
  конкатенацией по правилу. В `branches` объекта (5–7 строк) полный `at`
  остаётся — копируемость там дороже дюжины токенов;
- **колоночная форма** `{"columns": […], "rows": [[…]]}` для однородных
  списков длиннее ~20 строк — ключи один раз;
- проза живёт внутри значений (`did`, `why`, `title`, тексты диагностик);
- чистый markdown — только где ничего не round-trip'ится: статьи `docs`,
  логи `run`, объяснения `check`.

Ожидаемые стоимости после правил: строка листинга 112 → 10–19 токенов,
квитанция 209 → 47. Остаточная премия JSON над идеальной прозой — 15–20 % на
мелких ответах; она покупает точность копирования и проверяемость слотов.
Выбор подлежит замеру в гейте фазы 2 плана миграции: A/B «JSON-слоты против
markdown-сводки», решающая метрика — точность follow-up вызова (скопирован ли
`at` без искажений), а не только токены.

## Тяжёлые домены: где дерево, где данные

Формы, СКД, макеты и роли несут собственные внутренние структуры. Граница из
раздела «Адрес» применяется к ним буквально: **пока у сущности есть уникальное
имя — это узел с `at`; кончились имена — начались данные**, и они передаются
payload'ом операции. Признак напечатан в каждом результате (`at` есть / нет).

| Домен | Узлы (есть `at`) | Данные (payload операции) |
| --- | --- | --- |
| Форма | `Item.Имя`, `Command.Имя`, `Attribute.Имя`, `Module` | условное оформление (позиционный список) |
| СКД | `DataSet.Имя`, `DataSet.Имя.Field.Имя`, `Parameter.Имя`, `Variant.Имя` | структура варианта, отбор, сортировка, условное оформление |
| Макет MXL | `Area.Имя`, `Parameter.Имя` | ячейки, объединения, ширины (координатная сетка) |
| Роль | `RestrictionTemplate.Имя` | права — пары «объект × право» (`rights.set` массивом) |

Уточнения по доменам:

- **Форма.** Имя элемента управляемой формы уникально на всю форму, поэтому
  адрес плоский — `Form.Имя.Item.Курс` без пути через группы. Позиция в
  дереве компоновки — не адрес, а свойство: операция `move` с
  `parent`/`before`. Взрыв свойств (~50 у поля) гасится действующими
  правилами: `props` — только заданное, полный словарь вида элемента
  приходит в `expected` при промахе `props.set`, а не грузится заранее.
- **СКД.** Именованное ядро (наборы, поля, параметры, варианты) — узлы.
  Содержимое варианта — группировки, отбор, оформление — позиционно и
  безымянно; делать его узлами значит выдумывать имена, которых нет в
  платформе. Оно передаётся **типизированным массивом элементов** внутри
  операции (`op="structure.set"` на узле варианта), а не документом на
  внешнем языке (#377).
- **MXL.** Координата ячейки именем не является; правило чередования честно
  останавливается на областях и параметрах. Сетка передаётся типизированной
  операцией (`op="cells.set"` на узле области) — алгебру этих операций
  проектирует #378, и она же снимает `compile`/`decompile` (#381).
- **Роль.** Права — данные (решено выше); шаблоны ограничений RLS именованы
  и являются узлами со своими `view`/`apply`.

### Файловый DSL не переживает переход

Первая редакция этой записки предполагала, что `form.compile`/`dcs.compile`/
`mxl.compile` становятся `apply(op="create")` с целым DSL-документом в `args`.
**Это неверно и противоречит принятому решению.** ADR-0025 §10 объявил файловый
`Meta JSON DSL` неподдерживаемым публичным контрактом, а веха v0.13 (#283, #371,
#377, #378, #379, #380, #381) распространяет то же на остальные домены.

Три довода, и первый весомее остальных:

1. **Целостность байтов.** Схема «декомпиляция → правка файла → компиляция»
   пересобирает артефакт целиком и теряет то, что форматный контракт обязан
   сохранять: порядок узлов, уже присутствующие объявления префиксов
   пространств имён, BOM, наблюдённый стиль перевода строки (#283). Валидатор
   после такой пересборки лишь подтверждает, что результат разбирается, —
   потерю он не восстанавливает.
2. **Схема MCP не проверяет DSL до вызова.** Внешний язык модель обязана
   помнить, и ошибка в нём обнаруживается после записи, а не при валидации
   аргументов (#378).
3. **Адаптер DSL остаётся частью публичного продукта** — его спецификации,
   примеры и разборщик приходится поставлять и поддерживать.

Отсюда точная граница:

- **умирает** DSL как *документ*, читаемый из файла: аргументы `JsonPath` и
  `DefinitionFile` исчезают вместе с парами `compile`/`decompile`;
- **остаётся** массовое изменение одной операцией с типизированным массивом
  элементов в аргументах — ровно как `operations` у сегодняшнего `meta.edit`.
  Создание формы с двадцатью элементами — это одна операция с массивом, а не
  двадцать вызовов и не документ на внешнем языке.

Спецификации `references/specs/*-dsl-spec.md` после этого описывают не язык
вызывающего, а внутренний эмиттер — тот самый перенос уникальных фактов о
Platform XML, который предписывает ADR-0025 §10.

## Остальные входы

- **`find(query, kind?, limit?)`** — от чего угодно к адресу: голое русское
  имя, синоним, английский вид, путь файла выгрузки. Возвращает кандидатов с
  `at`; модули не подмешивает. Вид — фильтр, а не пропуск (сегодняшний
  `resolve` требует знать вид заранее). Граница: `find` — «где живёт X»,
  `view` — «что есть внутри Y».
- **`search(query, scope?, regex?, limit?)`** — по содержимому (код, тексты
  запросов, имена в формах). `scope` — адрес: поиск в поддереве. Режимы
  `definition`/`references` — виды поиска по символу. Outline модуля не
  нужен: это `view` узла модуля.
- **`check(at?, filter?)`** — без адреса — здоровье рабочего пространства,
  с адресом — валидация узла или поддерева. Диагностики возвращаются с `at`,
  пригодным для `view`/`apply`.
- **`run(op?, args?)`** — платформа: dump, load, make, update, тесты,
  выполнение кода. Тот же приём узнавания, что в дереве: `run()` без аргументов
  возвращает словарь действий со скелетами — то же самоописание. **Долгая работа
  идёт одним вызовом**: результат терминален, ход сообщается уведомлениями о
  прогрессе, отмена — уведомлением об отмене. Реестра заданий нет: ни `jobId`,
  ни опроса, ни отдельного ожидания. Когда хосты поддержат расширение задач
  протокола, долгая работа станет задачей протокола, а не нашей сущностью.
- **`docs(query, source?)`** — справка платформы и стандарты разработки.

Инициализации (`cf.init`, `cfe.init`, `epf.init`, `erf.init`) — `apply` с
`op="create"` на корне или пустом месте; заимствование в расширение —
`op="borrow"` на узле расширения; `project.map` растворяется в `view("")`.

## Итоговая поверхность

Восемь входов. Из текущей 71 поглощается 65, а шесть инструментов `runtime.job.*` снимаются без замены (DEC.2026-08-18.NO-JOB-REGISTRY). `diff` поглощает один инструмент и открывает недостающее сравнение конфигураций:

| Вход | Параметров | Поглощает | Сколько |
| --- | --- | --- | --- |
| `view` | 4 | все 8 `*.info`, `source.children`/`read`/`resources`, `mxl.decompile`, `cfe.diff`, `code.outline`, `project.map` | 15 |
| `apply` | 5 | `meta.add`/`edit`/`remove`, `form.add`/`compile`/`edit`/`remove`, `dcs.compile`/`edit`, `mxl.compile`, `role.compile`/`edit`, `subsystem.compile`/`edit`, `interface.edit`, `cf.edit`/`init`, `cfe.init`/`borrow`/`patch_method`, `epf.init`, `erf.init`, `support.edit`, `xdto.edit`, `code.patch` | 25 |

| `run` | 2 | `build.*` (5), `runtime.execute` | 6 |
| `docs` | 2 | `documentation.*` (2), `standards.*` (2) | 4 |

Каталог: восемь определений с однострочными описаниями и 2–5 параметрами —
порядка 2–3 тысяч токенов против сегодняшних ~67 тысяч. Словарь не исчез: он
переехал в `can`, `run()` и ошибки, где платится по мере пользы и
отфильтрован контекстом.

Поимённая разметка сверена с живым `tools/list`: 71 инструмент, каждый отнесён
ровно к одному входу, пересечений и пропусков нет. Читаемая карта с формой
вызова для каждого — артефакт «Семьдесят один в семь»
(`https://claude.ai/code/artifact/4510d630-508b-4708-9f7a-be2f812b0260`).

**Три перехода не сводятся к переименованию** и уходят в проработку фазы 2
отдельными вопросами, а не деталями реализации:

- `source.read` отдавал сырые байты по паре `(resourceId, snapshotId)`, где
  идентификаторы одноразовы и умирают вместе с процессом; в модели это
  постраничное чтение узла, и вопрос в том, что заменяет снимок как гарантию
  согласованности — `rev` узла или ничего;
- `mxl.decompile` отдавал редактируемый DSL-документ, а `view` отдаёт слоты.
  Либо выгрузка DSL остаётся режимом `view`, либо становится парной операцией
  к `template.create`; выбор влияет на то, где вообще живут DSL-документы;
- `cfe.diff` сравнивает расширение с базовой конфигурацией — это не чтение
  узла и, возможно, вообще режим `check`, а не `view`.

Модель отвечает на три исходные цели так: выбор — восемь входов с
непересекающимися вопросами (найти, посмотреть, изменить, поискать,
проверить, сравнить, запустить, справка); формирование — скелет приходит из `view` или
из ошибки, а не из чтения схемы; чтение — семь слотов, одинаковых всюду, и
квитанция без конверта.

## Чтение содержимого: что решено отдельными записями

Разбор чтения модулей и непонятого содержимого вынесен в реестр решений
(`arch/decisions/`), потому что каждый пункт заменяем по отдельности:

- **`DEC.2026-08-18.FILE-NODE-CONTENT`** — у узлов три природы, и файловый несёт
  слот `content`; постраничность режет по строкам, не по байтам.
- **`DEC.2026-08-18.MODULE-PROJECTIONS`** — модуль читается проекцией
  `depth` × (`region`, `method`), каждый фильтр принимает список; бюджет
  проверяется у каждой проекции и поднимается вызывающим.
- **`DEC.2026-08-18.OPAQUE-IS-VISIBLE`** — непонятое содержимое присутствует с
  видом `opaque`, обязательным `why` и путём `where`; отсутствие снова значит
  «нет такого».
- **`DEC.2026-08-18.RESOURCE-FOR-DEFERRED-BYTES`** — объёмное и бинарное
  предлагается ссылкой на ресурс, а не едет байтами.
- **`DEC.2026-08-18.CURSOR-CARRIES-REVISION`** — продолжение чтения несёт
  ревизию и отказывает при расхождении; она же служит условием записи.
- **`DEC.2026-08-18.FAILURE-NAMES-THE-FILE`** — отказ по цели, квитанция записи
  и перевод адреса в путь дают выход к файлам, когда Unica не справилась или
  справилась неверно.

Открытых вопросов по чтению после этого не остаётся: `source.read` уходит как
инструмент, а его способность живёт в `view`.

## Нерешённый конфликт с ADR-0025 §4

Модель кладёт словарь `op` в `can` результата, а не в схему `apply`. ADR-0025 §4
требует обратного и называет причину: закрытое размеченное объединение операций
живёт «непосредственно в `properties.operations.items`», не прячется за
`allOf`/`if`/`then` или `$ref`, потому что **хост, показывающий модели только
`properties`, обязан увидеть предметный тип операции** — иначе типизированный
контракт теряется по дороге к вызывающему.

Оба основания измеримы и оба настоящие: объединение `meta.edit` стоит 4 715
токенов только на ветвях (замер 18.08), а хост, отдающий модели одни лишь
`properties`, при переносе словаря в `can` не покажет ничего.

Три выхода, и выбор между ними — решение владельца, а не деталь реализации:

1. **Схема остаётся источником словаря**, `can` работает фильтром «что применимо
   на этом узле». Цена — union возвращается в каталог; выигрыш модели падает.
2. **Словарь переезжает в `can`**, ADR-0025 §4 в этой части заменяется новой
   записью, которая обязана ответить на его довод про хосты.
3. **Гибрид**: в схеме остаются имена операций закрытым перечнем без их
   аргументов, полный скелет приходит из `can`. Хост видит предметный тип,
   каталог не несёт ветвей.

Вариант 3 выглядит примиряющим, но он не проверен: сохраняет ли имя операции без
аргументов ту гарантию, ради которой писался §4. Это первый вопрос фазы 3.

## Риски и обязательные замеры

1. **Перенос `op` строкой.** Вся модель держится на допущении, что агент
   надёжно копирует `op` из `can` в `apply`. Проверяется каркасом метрики
   «токены на решение» (#479, `2026-08-17-token-cost-task-catalog.md`) без
   переделки: те же фикстурные задачи, поверхность A против текущей.
2. **Цена `can`.** ~250 токенов на объектный `view` окупаются, только если
   заметно поднимают first-call success `apply`. Мерить на тех же задачах;
   запасной вариант — `can` без скелетов (только имена `op`) плюс скелет в
   ошибке.
3. **Полиморфный `view` слабее проверяется машиной,** чем восемь узких схем.
   Компенсация — дисциплина слотов и закрытые перечни `kind`; это размен,
   а не бесплатность.
4. **Правило чередования не бесплатно на краях.** Стандартные реквизиты,
   предопределённые элементы, графы журналов с `References` — надо проверить,
   что для каждого узла карты (43 вида, 184 ветки) адрес выводится без
   исключений; карта — чек-лист этой проверки.

## Не-цели

- Записка не проектирует проводной протокол (кодировка результатов,
  `structuredContent`, пагинация) — это слой ADR-0069/0070 и не меняется
  моделью.
- Не задаёт путь миграции текущей поверхности и совместимость имён; это
  предмет отдельного плана после принятия модели.
- Не отменяет форматный слой (`references/specs/*`): форматные спецификации
  остаются, но как описание внутреннего эмиттера, а не языка вызывающего —
  см. «Файловый DSL не переживает переход».
