# Режим вызова читателей и обязательные типизированные данные

## Результат проектирования

`dryRun` принадлежит мутации, а не общему конверту вызова. Реестр инструментов
различает чтение и мутацию предметным типом, application выводит из него один
из режимов `Read`, `Preview` и `Apply`, а reader не публикует и не принимает
`dryRun`. Успешный типизированный reader обязан вернуть `OperationResult.data`;
пустой успех является нарушением контракта и отклоняется fail-closed.

Проект меняет аргументы существующих публичных инструментов `unica.*`, общую
границу диспетчеризации и правило исполнения примеров скиллов. Архитектурным
выбором владеет предложенная запись ADR-0042; эта записка фиксирует путь к нему
и нормативной не является. Proposal PR служит отдельной площадкой ревью и не
сливается: после утверждения его закрывают без merge, а независимый
implementation PR от `main` переносит утверждённые записку и ADR-0042 вместе с
кодом, выведенными записями реестра и статусом `accepted`. Иначе `proposed`
ADR-0042 сначала попала бы в `main`, стала неизменяемой историей, а последующий
перевод статуса нарушил бы `INV-DOC-SUPERSEDE-NOT-EDIT`.

## Исходное состояние

На baseline `b0205624` общий список в
`crates/unica-coder/src/application/tool_contracts.rs` добавляет `cwd`,
`dryRun` и `confirm` почти каждому `ToolSpec`, не учитывая
`ToolSpec.mutating`. Поэтому `tools/list` публикует `dryRun` у read-only
инструментов, а validator считает его допустимым.

`call_tool` читает `dryRun` до проверки аргументов и передаёт один `bool` через
application ports всем обработчикам. Несколько reader-маршрутов при `true`
отвечают предпросмотром вместо чтения:

- native typed readers пропускают предметный обработчик в
  `native_operations/typed_result.rs`;
- `unica.code.search` и остальные code-intelligence readers не вызывают
  поставщиков;
- `unica.documentation.search` и `unica.documentation.get` не опрашивают
  реестр документации;
- подготовка `unica.subsystem.info` возвращает placeholder до чтения цели.

Наблюдаемый результат для `unica.subsystem.info` с `dryRun: true` —
`ok: true`, summary с текстом `dry run` и отсутствующий `data`. Тем самым
публичный вызов одновременно утверждает успех и не несёт результата, ради
которого reader существует. Это нарушает смысл `INV-MCP-TYPED-RESULT`.

Историческая причина шире формулировки задачи #297. Общий `COMMON_ARGS`
включает `dryRun` с мая 2026 года; PR #285 не создал общий аргумент, а добавил
typed readers, для которых прежняя preview-ветка стала пустым типизированным
успехом. Исправление только семи native handlers устранило бы видимое
последствие, но оставило бы ту же неверную модель у code intelligence и
documentation.

## Противоречие со стендом скиллов

`INV-SKILL-EXECUTABLE-EXAMPLES` сейчас требует, чтобы каждый пример
`tools/call` успешно исполнялся как сухой прогон MCP. Функция
`dry_run_message_for_example` в
`tests/ci/test_unica_mcp_script_parity.py` реализует это требование буквально:
она принудительно добавляет `dryRun: true` каждому примеру, кроме
`unica.meta.info`.

Удалить аргумент у readers и оставить этот стенд без изменения невозможно:
исправленный validator обязан отклонить те сообщения, которые тест сам
конструирует. Кроме того, нынешний тест доказывает для reader-примера только
разбор аргументов и достижимость preview-placeholder, а не исполнимость
предметного чтения. Новая граница сохраняет сильное требование к примерам, но
разделяет способы его доказательства: мутация исполняется в preview, чтение —
как настоящее чтение над детерминированной фикстурой или локальным stand-in
поставщика.

## Цели

1. Удалить `dryRun` из схемы и validator-а каждого read-only инструмента.
2. Сделать preview состоянием только мутации и не передавать его reader-ветке.
3. Запретить `ok: true` без `data` у типизированного reader.
4. Сохранить без изменений preview/apply контракт мутаторов из задачи #290.
5. Сохранить реальное исполнение примеров скиллов без зависимости от сети,
   локальной установки платформы и пользовательского индекса.
6. Сделать нарушение новой границы видимым при регистрации следующего
   инструмента, а не после появления отдельного placeholder-теста.

## Неграницы

- Проект не меняет `confirm`, `cwd` и предметные аргументы инструментов.
- Проект не стабилизирует preview мутаторов и не закрывает #290.
- Проект не меняет полезную нагрузку успешного предметного reader, кроме
  требования, что она присутствует.
- Проект не добавляет `outputSchema` всем инструментам и не меняет форму
  транспортной ошибки MCP.
- Проект не делает сетевой или машинно-зависимый ресурс частью CI: ему нужен
  локальный stand-in либо подготовленная фикстура.
- Проект не сохраняет alias `dryRun` у readers. Дефект находится в ещё не
  выпущенной версии 0.12.0, а alias восстановил бы двусмысленный контракт.

## Рассмотренные варианты

### 1. Предметный режим `Read | Preview | Apply`

Реестр различает чтение и мутацию, validator сначала проверяет форму вызова,
затем application выводит допустимый режим. Reader-маршрут не получает
preview-флаг. Это выбранный вариант: он устраняет источник расхождения схемы,
validator-а и dispatch, а не только текущие ветки native readers.

### 2. Условно удалить `dryRun` из `allowed_args`

Этот вариант меньше по diff, но общий `dry_run: bool` продолжает пересекать
reader ports, code intelligence и documentation сохраняют preview-ветки, а
новый внутренний вызов может снова активировать их в обход публичной схемы.
Вариант отклонён как исправление симптома.

### 3. Разделить реестры на `ReaderToolSpec` и `MutationToolSpec`

Отдельные типы дали бы максимальную статическую гарантию, но потребовали бы
переписать регистрацию всей поверхности и связанные интерфейсы ради одного
unreleased regression. Предметная категория внутри общего `ToolSpec` даёт ту
же необходимую исчерпывающую проверку без несвязанной миграции реестра.

## Архитектура

### Категория инструмента

Поле `ToolSpec.mutating: bool` заменяется `ToolExecution` с вариантами `Read` и
`Mutation`. Проверки, которым нужен прежний признак, используют исчерпывающий
метод `is_mutating()`, а не сравнение независимых флагов.

`ToolSpec` также называет `ResultContract`: `Typed` или `ExternalStream`.
Значение является runtime-предикатом для постусловия результата. Тест сверяет
его с `scope` и `result.contract` в
`spec/architecture/tool-surface-review.json`, чтобы Rust и ведомость не стали
двумя расходящимися источниками.

### Допустимые режимы

Application владеет типом `InvocationMode`:

- `Read` выводится только из `ToolExecution::Read`;
- `Preview` выводится для `Mutation`, когда `dryRun` отсутствует или равен
  `true`;
- `Apply` выводится для `Mutation` только при `dryRun: false`.

`dryRun` добавляется в `allowed_args` и `inputSchema.properties` только для
`Mutation`. Специальные metadata schemas продолжают строиться своим текущим
путём, но проверяются той же таблицей соответствия категории и аргумента.
Описание `dryRun` перестаёт утверждать, что переключатель присутствует на
каждом инструменте.

### Двухфазная проверка вызова

Первая стадия проверяет закрытый набор имён и типы значений. Поэтому `dryRun`,
вручную переданный reader с любым значением, отклоняется как неизвестный
аргумент до workspace discovery, provider resolution и backend execution.

После успешной проверки формы application выводит `InvocationMode` и передаёт
его семантическим проверкам. Проверки обязательных payload и условий preview
остаются только у мутаций. Такой порядок не позволяет неизвестному полю
повлиять на режим до собственного отказа.

### Граница портов и адаптеров

Общий `dry_run: bool` заменяется `InvocationMode` в application orchestration и
смешанных портах. Reader-specific функции не принимают режим вообще. В
инфраструктуре `InvocationMode` преобразуется в boolean только после
исчерпывающего сопоставления с мутирующим adapter branch.

Native typed readers, code intelligence, source navigation, source resources,
standards, documentation, project readers и читающие runtime controls всегда
исполняют предметное чтение. `Preview` и `Apply` не являются допустимыми
вариантами их ветвей.

### Постусловие типизированного чтения

После возврата handler-а и до построения публичного `OperationResult`
application проверяет сочетание `Read + Typed`:

- при `ok: true` поле `data` обязательно;
- при `ok: false` отсутствие `data` допустимо;
- нарушение первого правила завершает вызов существующей транспортной формой
  ошибки с устойчивым префиксом `typed_result_missing`.

Пустой объект, `null` или синтетический placeholder не подставляются:
application не может угадать предметную структуру потерянного результата.
Mutations и `ExternalStream` этой проверкой не меняются.

## Поток вызова

1. `tools/list` строит закрытую схему из `ToolSpec`; reader не получает
   `dryRun`.
2. `tools/call` нормализует только разрешённые aliases и проверяет имена и
   типы.
3. Reader с ручным `dryRun` получает существующий отказ
   `does not accept argument` до любого порта.
4. Для допустимого вызова application выводит `InvocationMode`.
5. `Read` доходит до предметного handler-а без preview-ответвления.
6. Application применяет постусловие `Read + Typed`.
7. Cache report читателя получает режим `read`, не создаёт событий и не
   инвалидирует состояние.

## Исполнимые примеры скиллов

Стенд делит сообщения по `ToolExecution` из того же реестра, а не по списку
имён внутри теста:

- mutation-пример получает `dryRun: true` и исполняется в preview;
- reader-пример не получает `dryRun` и исполняется обычным вызовом;
- для файлового чтения стенд материализует минимальный точный источник;
- v8std обслуживает локальный HTTP JSON-RPC stand-in через
  `UNICA_STANDARDS_MCP_URL`;
- platform help получает синтетические `.hbk` из локальной фиктивной установки,
  закреплённой штатным `tools.platform.path`; `UNICA_PLATFORM_HELP_DIR` здесь
  неприменим, потому что он скомпилирован только для внутрикрейтовых
  `#[cfg(test)]`-проверок, тогда как parity запускает обычный бинарь;
- code intelligence получает подготовленный BSL source и изолированные
  provider state/cache;
- отсутствие детерминированной фикстуры считается дефектом примера, а не
  основанием заменить исполнение проверкой одной схемы.

Тест сохраняет byte snapshot рабочего пространства до и после всей пачки:
реальные readers не пишут, preview mutations не применяют изменения.

## Ошибки

- `dryRun` у reader — ошибка публичных аргументов с перечнем допустимых полей;
- предметный отказ reader сохраняет общий `OperationResult` с `ok: false` и
  может не иметь `data`;
- пустой typed success — внутренняя ошибка контракта
  `typed_result_missing`, а не предметный отказ и не успех;
- сбой локального stand-in в parity-тесте является отказом тестовой среды и не
  превращается в допустимый пустой результат;
- поведение отмены, сроков, format/support guards и cache-report сохраняется,
  но `Read` не преобразуется ими в preview.

## Стратегия реализации и проверки

Исправление следует TDD-правилу репозитория. Каждый дефект сначала закрепляется
тестом, который падает на текущем `main` по наблюдаемой причине.

1. Табличный unit-test проходит по всем `ToolSpec` и требует отсутствия
   `dryRun` у `Read` при сохранении аргумента у `Mutation`.
2. Dispatch-tests передают `dryRun: true` и `dryRun: false` representative
   native, code/RLM, source navigation, source resources, standards,
   documentation, project и read-only runtime routes. Каждый вызов обязан быть
   отклонён до обращения к порту или поставщику.
3. Regression-test воспроизводит нынешний native `ok: true` без `data`.
4. Postcondition-test принимает `ok: false` без данных и отклоняет только
   `Read + Typed + ok` без `data`.
5. MCP smoke вызывает representative readers обычным путём и проверяет
   `ok: true`, наличие `data` и отсутствие placeholder-summary.
6. Skill parity исполняет reader-примеры над фикстурами и mutation-примеры в
   preview, сохраняя рабочее пространство байт-в-байт.
7. Генератор ведомости обновляет `spec/architecture/tool-surface.md`; тест
   сверяет `ResultContract` с `tool-surface-review.json`.
8. Реализационный PR переводит ADR-0042 в `accepted`, добавляет новую запись
   реестра о границе предпросмотра, расширяет `INV-MCP-TYPED-RESULT` и уточняет
   `INV-SKILL-EXECUTABLE-EXAMPLES` вместе с названными проверками.

## Критерии приёмки

- Ни одна схема `ToolExecution::Read` не содержит `dryRun`.
- Reader с ручным `dryRun` не достигает workspace/provider/backend.
- Reader нельзя диспетчеризовать в `Preview` или `Apply` даже внутренним
  вызовом application.
- Каждый успешный `Read + Typed` содержит предметный `data`.
- Все текущие mutation schemas и их default preview сохраняются.
- Каждый MCP-пример скилла остаётся исполнимым в детерминированном CI.
- Сгенерированная ведомость, ADR, реестр инвариантов, Rust contracts и
  упакованный plugin описывают одну границу.

## Граница proposal PR

Этот pull request содержит только утверждённую проектную записку и
предложенную ADR-0042. Он не меняет runtime, опубликованные схемы, действующие
инварианты или статус задачи #297. Такое разделение сохраняет честное состояние
репозитория: proposed-решение можно ревьюить отдельно, затем proposal PR
закрывается без merge, а issue закрывает только независимый реализационный PR
от `main`, куда записка и ADR-0042 входят уже вместе с красно-зелёными тестами
и синхронной архитектурной документацией.
