# Дисциплина отказов канонической поверхности v0.13

## Откуда выросло

Аудит поверхности 8/11 от 01.09.2026 (методика tool-design из
Agent-Skills-for-Context-Engineering, живые замеры собранного бинаря) показал,
что коды отказов расходятся по трём каналам и двум степеням честности:

1. предметные инструменты отвечают `diagnostics[].code`, а compatibility
   task-инструменты кладут код в `data.code` без диагностик;
2. конфликт `ifRev` уходит кодом `provider_unavailable`, хотя его стратегия
   восстановления противоположна недоступному провайдеру: перечитать `rev` и
   повторить, а не ждать или сдаваться;
3. literal-поиск по валидному scope без исходного поддерева
   (`Catalogs/<Имя>/` не существует) роняет голый errno
   `No such file or directory (os error 2)`;
4. отказ «нет обязательного `mode`» не перечисляет режимы, хотя отказ
   «неверный `mode`» перечисляет — первая попытка агента гарантированно
   вторая.

Правило tool-design, под которым сделан выбор: стратегию восстановления агент
выбирает по коду; каждый отказ обязан говорить, что изменить перед повтором.

## Что сделано

- `task_tool_error_result` и терминальные failed/cancelled проекции Task
  отвечают `diagnostics[{code, message}]`; `data` остаётся чистым снимком.
- `WorkspaceActor::admit_apply` возвращает типизированную
  `ApplyAdmissionError { StaleRevision, Other }`; сервис отображает
  `StaleRevision` в код `stale_revision`, остальное — по-прежнему в
  `provider_unavailable`. `From<String>` в обе стороны сохраняет строковые
  внутренности допуска без переписывания их слоёв.
- Обход literal-поиска различает «исчезло» и «сломалось»: `NotFound` на
  спуске в scope — пустой результат, `NotFound` на элементе обхода — пропуск
  элемента (TOCTOU), остальные ошибки ввода-вывода оборачиваются фазой
  («could not open the scope subtree», «could not read a source file», …).
- Отказ по отсутствующему `mode` перечисляет допустимые режимы тем же
  списком, что и отказ по неверному значению.

## Чем проверено

`canonical_refusals_answer_one_diagnostics_channel_from_the_closed_code_set`
(daemon/server.rs) гоняет живой daemon-конвейер: единый канал и закрытое
множество кодов, `stale_revision` с обеими ревизиями, домен значений в отказе
без `mode`, пустой результат на scope без поддерева. Канал task-инструментов
закреплён юнит-тестами task_tools и обновлённым
`v13_compatibility_task_tools_are_profile_gated_durable_and_replay_free`.

## Границы

Наполнение секции `can` и код `unsupported_section` для незаполненных секций
view — отдельная работа за развилкой #572 (где живёт словарь операций); это
решение канал отказов не расширяет, а только упорядочивает существующие.
