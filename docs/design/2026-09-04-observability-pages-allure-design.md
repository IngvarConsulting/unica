# Опубликованная страница и отчёт прогона

## Что строится

Три вещи на одном адресе `https://ingvarconsulting.github.io/unica/`:

1. **Страница продукта** — что такое Unica, ссылки на продукт и Telegram,
   текущая публичная версия, путь установки, состояние сборки `main`.
2. **Отчёт Allure** последнего прогона `main`, со всеми тестами — включая те,
   которые в этом прогоне не исполнялись.
3. **История прогонов** рядом с отчётом, чтобы её скачивал следующий прогон и
   локальный запуск.

Страница статическая: значения подставляются на сборке, браузер не выполняет ни
строки скрипта. Рядом с ней лежит `status.json` с теми же значениями — машинный
ответ и человеческая страница порождаются из одного документа и разойтись не
могут.

## Что вскрылось при разборе

**На `main` сборок нет вообще.** `Build Unica Codex Plugin` запускается по
`pull_request`, по тегу `v*` и вручную; событий `push` в `main` у него нет. За
всю историю push-прогоны только на тегах. Значит, сегодня «статус сборки на
main» брать неоткуда, и отчёту на `main` тоже не из чего собираться. Первый шаг
работы — не Allure, а main-прогон.

**Pages уже включены и настроены на workflow.** `build_type: workflow`,
источник — `main`, `status: null`: ни одной сборки ещё не было. Ветка
`gh-pages` не нужна и не появится; деплой уходит артефактом через
`actions/deploy-pages`. Следствие: каждый деплой заменяет сайт целиком, поэтому
историю прошлого прогона нужно **скачать с живого сайта** и положить в новый
артефакт. Это ровно тот способ хранения, который был заказан.

**Версия уже разошлась в трёх местах.** Страница продукта на `ingvar.pro`
показывает `0.11.0`, `plugins/unica/.codex-plugin/plugin.json` — `0.12.0`,
последний релиз — `v0.12.3`. Поэтому версию на странице считает конвейер из
релиза, а не человек из памяти.

## Раскладка сайта

```
/                     страницы и status.json
/assets/              знак из visual-kit
/allure/<линия>/      отчёт линии
/allure/<линия>/history/   history.json, history-trend.json, duration-trend.json,
                      retry-trend.json, categories-trend.json
/data/<линия>/results.tar.gz  сырые результаты последнего прогона линии
/data/<линия>/summary.json    счётчики этого отчёта
```

**Сайт хранит свои входы.** Артефакты прогона живут девяносто дней, и это
максимум, разрешённый в репозитории. Поэтому рядом с отчётом публикуются сырые
результаты: линия, которая сегодня не собиралась, пересобирается из того, что
лежит на сайте, и не исчезает с него. Срок жизни артефактов перестаёт быть
частью замысла.

**Собранный отчёт в гит не кладётся.** Он производный: пересобирается из
результатов и истории. При этом он состоит из тысяч файлов и меняется целиком
на каждом прогоне, а гит хранит каждую версию — репозиторий рос бы вечно, и
платили бы этим все, кто его клонирует. Сырые результаты по той же причине
живут на сайте, а не в дереве.

## Конвейер

Отчёт не гоняет тесты второй раз и не читает артефакты чужих прогонов. Забрать
артефакт прогона-источника в `workflow_run` — известный способ протащить чужое
содержимое в публикацию: содержимое артефакта выбирает тот, чей прогон его
оставил. Поэтому свежие результаты появятся в конвейере вместе со своей
эмиссией, и канал для них будет выбран тогда же; сегодня публикатор собирает
каждую линию из того, что сайт хранит сам.

1. Джобы с тестами кладут `allure-results` артефактом — это часть работы по
   ярусам, её здесь ещё нет.
2. Workflow `unica-pages.yml` просыпается по `workflow_run: completed` для
   `Build Unica Codex Plugin` — тем же способом, каким уже устроен
   `publish-unica-marketplace.yml`. Он берётся из версии файла на `main`, а не из
   ветки прогона: это свойство события, и на него нельзя опираться иначе.

   Фильтра `branches` для доверия мало: он смотрит на имя ветки прогона, а его
   выбирает автор pull request. Форк с веткой `main` прошёл бы фильтр, и его
   артефакты уехали бы на наш сайт. Поэтому источник обязан быть успешным
   push-прогоном этого же репозитория; всё остальное отсекается условием джобы.
3. Скачивает `history/` с живого сайта в `allure-results/history/`.
4. Кладёт рядом `executor.json` (имя, номер и ссылка на прогон) и
   `categories.json` — категории отчёта, где дедлайн по настенным часам
   отделён от настоящего падения.
5. `allure generate --clean`, версия CLI закреплена: контракт истории у
   Allure 2 и Allure 3 разный.
6. Рендерит страницу `scripts/ci/render-pages.py` и деплоит каталог целиком.

**Одна и та же ОС — не ретрай.** Один тест приходит из трёх матричных джоб.
Если у результатов совпадёт `historyId`, Allure сочтёт их повторами одного
теста. Поэтому ОС кладётся параметром результата и входит в `historyId`: в
отчёте три строки, у каждой своя история.

## Честные скипы

Каждый прогон публикует результат **каждого известного теста**, а не только
исполненного. Тест, который ярус не пустил в этот прогон, приходит со статусом
`skipped` и причиной из манифеста — «ярус `release`: поднимает демона».

Перечисление без исполнения обе экосистемы дают штатно:

- Python — `unittest.defaultTestLoader.discover` отдаёт идентификаторы тестов,
  ничего не запуская;
- Rust — `cargo nextest list --message-format json` отдаёт состав целей без
  прогона.

`historyId` считается от полного имени теста и не зависит от машины, поэтому
переход теста из `passed` в `skipped` виден в истории одной строкой. Это не
украшение отчёта: молча вынести тест из гейта после этого нельзя — попытка
оставляет след на опубликованной странице.

## Локальный прогон

`scripts/dev/allure-local.py --tier change`:

1. скачивает `/allure/main/history/` с опубликованного сайта;
2. гоняет выбранный ярус через `run-cadence.py`;
3. помечает остальное `skipped` с причиной;
4. генерирует отчёт и открывает его.

История общая с `main`, поэтому локальный отчёт отвечает не «зелено ли», а «что
изменилось по сравнению с опубликованным прогоном».

## Что приходится принести

- **JVM.** Allure CLI — Java-приложение. В CI это шаг установки, локально
  `brew install allure`. Сегодня JVM в дереве нет.
- **Публичность отчёта.** Репозиторий публичный, имена тестов и так видны.
  Вывод упавшего теста содержит пути и окружение раннера, и он остаётся в
  отчёте: раннеры публичные, секретов в проекте нет, а этот вывод — самое
  полезное, что есть в отчёте.
- **Первый деплой.** Pages ещё ни разу не собирались; первый прогон конвейера и
  будет первой сборкой сайта.

## Порядок работ

1. `push: branches: [main]` для сборки — без него нет ни статуса, ни отчёта.
2. Страница и рендер: `docs/pages/index.html`, `scripts/ci/render-pages.py`,
   деплой на Pages. Уже можно смотреть — данные подставляются из `status.json`.
3. `cargo nextest` вместо `cargo test`: JUnit из коробки и процесс на тест.
4. Эмиссия `allure-results` из обеих экосистем плюс скипы по манифесту.
5. История, `executor.json`, категории, локальный прогон.

Шаги 1 и 2 не зависят от ярусов. Шаг 4 зависит: без `tests/cadence.json` нечем
объяснить, почему тест пропущен.
