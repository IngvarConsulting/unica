# Свойство обычного приложения клиентского модуля

## Проблема

Закрытая алгебра `unica.meta.add` и `unica.meta.edit` умеет менять флаги общего
модуля, но не принимает платформенное свойство
`ClientOrdinaryApplication`. Пользователь вынужден редактировать XML вручную,
а ошибка для неизвестного имени не сообщает, какие свойства этого вида объекта
вообще поддержаны.

## Решение

Добавить `ClientOrdinaryApplication` как boolean-свойство только для
`CommonModule` в существующий реестр writer, публичную inline-схему обеих
мутаций и XML round-trip. Не связывать его чтение с writer allowlist:
`meta.info` уже наблюдает платформенное поле через независимый профиль по
ADR-0042.

Диагностика неизвестного свойства строит точный список альтернатив из того же
реестра, отфильтрованного по виду владельца. Поэтому подсказка совпадает с
фактической доменной проверкой и включает новое свойство автоматически.

## Проверка

- preview и apply создания и изменения общего модуля сохраняют `true` и
  `false` в Platform XML;
- повторное чтение возвращает записанное значение;
- неизвестное имя отклоняется с точным полем и полным списком поддержанных
  свойств `CommonModule`;
- схема `meta.add` и `meta.edit` публикует boolean-поле.
