# Декомпозиция исследования внешних AI-проектов для 1С

- Date: `2026-08-03`
- Status: `approved`
- Decision: `none` — no architectural contract changed

## Результат проектирования

Issue #186 выполняется серией независимо проверяемых изменений. Первый срез —
единый source-backed screening всех перечисленных источников. Углублённое
исследование выполняется только после screening и группируется по сопоставимым
механизмам, а не по одному репозиторию за раз.

Такой порядок сначала создаёт общий реестр доказательств и shortlist, а затем
позволяет сравнивать прошедших кандидатов одинаковыми методами. Полный разбор
одного случайно выбранного источника до screening отклонён: он не показывает
относительную ценность механизма и создаёт риск вложиться в слабого или
дублирующего кандидата.

Исследование не меняет публичные инструменты `unica.*`, package contracts,
владение состоянием, границы слоёв или правила реестра архитектуры. Поэтому
новая ADR не требуется. Любое последующее решение о внедрении проходит
отдельный цикл проектирования и при необходимости получает собственную ADR.

## Цели

1. Проверить каждый источник issue #186 по одному воспроизводимому шаблону.
2. Отделить доказанные механизмы от заявлений README и внешних пересказов.
3. Зафиксировать точный срез источника, лицензию и происхождение каждой идеи.
4. Сопоставить находки с живым кодом, тестами и контрактами Unica.
5. Отсеять дубли и слабые кандидаты до дорогих экспериментов.
6. Сформировать входы для тематических глубоких исследований.

## Неграницы

- Внешний код, текст правил, skills и другие материалы не переносятся в Unica.
- Screening не доказывает производительность или полноту code-intelligence
  движка без общего эксперимента.
- Screening не создаёт follow-up issues на каждую интересную идею.
- Исследование не добавляет второй публичный MCP-сервер и не меняет границу
  `unica.*`.
- Telegram-публикации используются только как указатели на первичные источники.
- Отсутствие или противоречие лицензии не запрещает наблюдение поведения, но
  блокирует перенос материалов до юридического прояснения.

## Рассмотренные варианты

### Полный screening всех источников

Выбранный вариант создаёт горизонтально сопоставимый реестр: repository,
default branch, commit SHA или версия, дата среза, лицензия, доказанный механизм,
аналог или пробел в Unica и решение о глубоком исследовании. Его результат
самостоятельно полезен, даже если дальнейшая работа будет приостановлена.

### Полный разбор одного источника

Вариант быстро даёт подробный отчёт, но выбор первого проекта не опирается на
общую картину. Результат нельзя честно сравнить с остальными, а уникальная для
проекта методика затруднит последующее сведение. Вариант отклонён как основная
единица декомпозиции.

### Пилот одного источника перед screening

Пилот допустим только как внутренняя калибровка шаблона в первом срезе. Он не
становится самостоятельным итогом и не получает более сильного статуса, чем
остальные источники. Если первые карточки выявят неоднозначность полей,
шаблон исправляется до заполнения всего реестра.

## Первый срез: screening всех источников

### Артефакт

Первый PR добавляет один сравнительный документ в
`docs/provenance/reviews/`. Документ содержит:

- методику и дату исследования;
- реестр screening по всем источникам issue #186;
- ссылки на конкретные implementation, test, config и package/release файлы;
- лицензионные свидетельства и противоречия;
- первичное сопоставление с конкретными путями Unica;
- решение `deep-dive`, `defer` или `reject` с краткой причиной;
- тематический shortlist для следующих срезов.

Черновые клоны, логи проб и временные таблицы не включаются в пакет Unica и не
становятся нормативной архитектурной документацией.

### Карточка источника

Каждый источник получает одинаковый минимальный набор полей:

| Поле | Содержание |
| --- | --- |
| Source | Канонический repository URL и прежнее имя, если оно важно |
| Snapshot | Default branch, commit SHA или release version, дата среза |
| Evidence | Ключевые implementation, tests, configs и package metadata |
| License | LICENSE/NOTICE/COPYRIGHT, GitHub metadata и противоречия |
| Mechanism | Проверяемая полезная семантика, а не название инструмента |
| Unica mapping | Живой аналог, пробел или конфликт с контрактом Unica |
| Limits | Неполнота, недоказанные заявления и стоимость проверки |
| Decision | `deep-dive`, `defer` или `reject` с причиной |

README может объяснить заявленное назначение, но не является единственным
доказательством механизма. Для решения `deep-dive` требуется хотя бы одно
свидетельство из кода, тестов, package metadata или воспроизводимой пробы.

### Порядок исследования

1. Разрешить канонический URL, default branch и неизменяемый commit SHA.
2. Зафиксировать дерево и определить ключевые implementation/test/config файлы.
3. Проверить LICENSE, NOTICE, COPYRIGHT и metadata хостинга.
4. Сформулировать один или несколько механизмов, подтверждённых источниками.
5. Найти аналог или пробел в коде, тестах, package contracts и `spec/` Unica.
6. Записать ограничения и решение о глубоком исследовании.
7. После заполнения всех карточек нормализовать решения относительно друг друга.

Если репозиторий недоступен, переписан или не содержит заявленного механизма,
карточка остаётся в реестре с точным наблюдением и ограничением; источник не
исчезает из выборки молча.

## Последующие срезы

Каждый глубокий срез зависит только от принятого screening и может выполняться
независимо от остальных.

### Workflow, skills и управление контекстом

Сравниваются только прошедшие screening проекты. Общая матрица покрывает
discovery, исследование кода, планирование, TDD/SDD, review, verification,
память между фазами, синхронизацию инструкций и безопасную работу с 1С.

### Code intelligence

`code-index-mcp`, `bsl-atlas` и текущий provider Unica запускаются на общем
bounded harness и одинаковых fixtures. Измеряются полнота, truncation,
ambiguity, incremental update, invalidation, latency, ресурсы, cancellation и
поведение при неполном или повреждённом индексе.

### Живые среды, данные и безопасность

Проекты доступа к базе и EDT сравниваются по read/write границам, RLS,
маскированию, approval UX, cancellation, progressive disclosure и возможности
оставить механизм внутренним provider-ом за `unica.*`.

### Артефакты и документация

Формы, MXL, HBK/help и BSL tooling сравниваются по roundtrip, fail-closed
validation, dry-run, atomicity, platform-backed verification и переносимости.

### Benchmark и evaluation

Benchmark-источники проверяются на leakage, воспроизводимость, исполняемые
oracle и покрытие целых XML/форм/MXL/DCS/роль/интеграционных артефактов, а не
только текстовой генерации BSL.

### Итоговый синтез

Последний срез объединяет доказательства в матрицу
«идея → источник → аналог → пробел → рекомендация», выбирает 3–5 минимальных
измеримых экспериментов и создаёт follow-up issues только для одобренных
направлений. Этот срез закрывает issue #186.

## Проверка первого среза

Screening считается завершённым, когда:

- каждый источник из issue #186 присутствует ровно один раз;
- у каждой карточки есть неизменяемый SHA или явно объяснено, почему его нельзя
  получить;
- проверены фактическое дерево, ключевые файлы и лицензионные свидетельства;
- каждая рекомендация ссылается на первичный источник и живой путь Unica;
- `bsl-analyzer`, `rlm-tools-bsl` и `cc-1c-skills` не представлены как новые
  открытия;
- ни один внешний материал не скопирован в поставляемое дерево;
- итоговый shortlist выводится из карточек, а не добавлен отдельным мнением.

Для проектной записки выполняются проверки
`tests/ci/test_design_documents.py`. Для сравнительного документа отдельный
автоматический тест нужен только если в ходе реализации появится стабильный
машиночитаемый формат; заранее вводить новый формат и страж не требуется.

## Риски и меры

- **Дрейф источника.** Все утверждения привязываются к commit SHA и дате.
- **Пересказ маркетинга.** Решение о deep dive требует evidence вне README.
- **Несопоставимые карточки.** Используется единая схема и финальная взаимная
  нормализация решений.
- **Лицензионная неоднозначность.** Противоречия сохраняются явно и блокируют
  перенос, но не наблюдение поведения.
- **Разрастание scope.** Screening не запускает дорогие benchmark и не создаёт
  реализацию идей.
- **Предвзятость первого пилота.** Пилот калибрует только шаблон и не получает
  автоматического приоритета.
