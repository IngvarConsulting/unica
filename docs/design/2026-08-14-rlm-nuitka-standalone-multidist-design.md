# Поставка RLM через Nuitka standalone multidist

## Контекст

Unica закрепляет `rlm-bsl-index` и `rlm-bsl-mcp` `v1.33.0` как два прямых
исполняемых asset релиза `rlm-tools-bsl-v1.33.0-build.3` в
`plugins/unica/third-party/tools.lock.json`. Репозиторий
`IngvarConsulting/unica-toolchain` собирает каждый asset через PyInstaller
`--onefile`, а `scripts/ci/build-unica-tools.py` скачивает, проверяет и копирует
его как один файл в `bin/<target>`.

Замер из [#505](https://github.com/IngvarConsulting/unica/issues/505) показал
причину накладных расходов: PyInstaller распаковывает встроенный Python при
каждом запуске. Предварительный Nuitka standalone-вариант запускается заметно
быстрее и не создаёт временную распаковку на каждый вызов. Абсолютные числа
этого прогона не являются приёмочным доказательством: физически свободное место
до и после прогона было ниже установленного порога `20 GiB`. Они достаточны для
выбора следующего проверяемого кандидата, но после публикации нужен повторный
валидный замер.

Настоящий Nuitka standalone не является одним исполняемым файлом. Проверка
фактического артефакта показала, что вынесенный из `.dist` файл
`rlm-bsl-index` завершается с кодом `134`, потому что не находит соседний
`libpython3.12.dylib`. Следовательно, сохранить текущую стратегию
`direct-release-asset` и одновременно назвать результат standalone нельзя.

Nuitka `4.1.3` поддерживает multidist: несколько `--main` входят в один
скомпилированный runtime, а выбранная программа определяется именем запуска.
Это позволяет собрать обе команды в одном каталоге зависимостей. Для прямого
запуска на всех трёх платформах один и тот же multidist-бинарник копируется под
именами `rlm-bsl-index[.exe]` и `rlm-bsl-mcp[.exe]`; символические и жёсткие
ссылки не используются.

Конечный runtime Unica уже является многофайловым архивом. `unica-bootstrap`
сверяет SHA-256 архива и каждого объявленного файла, запрещает небезопасные
пути и атомарно публикует извлечённое дерево. Поэтому менять публичный
bootstrap-протокол не требуется. Изменить нужно границу получения стороннего
asset и упаковщик, который сейчас переносит только объявленные бинарники и
теряет соседние библиотеки standalone.

## Цели

1. Собирать `rlm-bsl-index` и `rlm-bsl-mcp` одной Nuitka standalone multidist
   компиляцией на `darwin-arm64`, `linux-x64` и `win-x64`.
2. Публиковать один неизменяемый архив `rlm-tools-bsl-<target>.tar.gz` на
   платформу с полным проверяемым payload и двумя текущими именами команд.
3. На стороне Unica скачивать общий архив один раз, безопасно проверять его
   содержимое и переносить полную замкнутую полезную нагрузку в
   `unica-runtime-<target>.tar.gz`.
4. Сохранить пути запуска `bin/<target>/rlm-bsl-index[.exe]` и
   `bin/<target>/rlm-bsl-mcp[.exe]`, один публичный MCP `unica` и текущие
   контракты внутренних процессов RLM.
5. Доказать работоспособность именно опубликованных многофайловых байтов на
   каждой поддерживаемой платформе до переключения потребительского lock.

## Неграницы

1. Версия upstream `rlm-tools-bsl` и его исходный commit не меняются.
2. Публичные инструменты `unica.*`, их аргументы и формы результата не
   меняются.
3. `RLM_INDEX_DIR`, поколение `index-v15`, маркеры состояния и блокировки не
   меняются.
4. Nuitka onefile и постоянный кеш распаковки не входят в реализацию.
5. `unica-bootstrap` не получает новый формат runtime manifest, новый сетевой
   маршрут или знание о Nuitka: он продолжает извлекать один конечный архив и
   проверять перечисленные файлы.
6. Символические ссылки, жёсткие ссылки и платформенные launcher-обёртки не
   используются для сокращения размера.
7. Предварительный прогон из #505 не становится финальным performance gate.

## Рассмотренные варианты

### 1. Nuitka onefile с постоянным кешем

Вариант сохраняет шесть одиночных assets и не требует изменения
`build-unica-tools.py`. Первый запуск, однако, распаковывает примерно полный
payload каждого executable в пользовательский кеш, две команды не делят
runtime, а старые immutable release identities накапливают отдельные копии.
Это устраняет повторную распаковку, но оставляет установку и уборку скрытого
кеша вне владельца runtime Unica.

### 2. Два независимых standalone-архива

Каждая команда получает собственный `.dist`. Реализация проста, но Python и
общие расширения дублируются в двух release assets и затем в конечном runtime.
Этот вариант не использует общий upstream source и общий жизненный цикл двух
команд.

### 3. Один standalone multidist-архив на платформу — выбран

Одна компиляция включает оба entrypoint и один набор зависимостей. Одинаковый
multidist executable материализуется под двумя именами, поэтому текущие пути
запуска и семантика `argv[0]` сохраняются на macOS, Linux и Windows без ссылок
или дополнительного launcher.

Внешний архив меняет только границу между toolchain и сборкой Unica. После
перепаковки конечный runtime остаётся обычным проверяемым архивом ADR-0008 и
ADR-0055.

## Контракт архива toolchain

Для каждой цели release содержит:

```text
rlm-tools-bsl-<target>.tar.gz
  manifest.json
  payload/
    rlm-bsl-index[.exe]
    rlm-bsl-mcp[.exe]
    <библиотеки и data-файлы Nuitka standalone>
```

`manifest.json` содержит:

- версию схемы, release tag, source commit и target;
- точное отображение entrypoint-имён на пути под `payload/`;
- отсортированный полный список обычных файлов payload;
- SHA-256, размер и признак исполнимости каждого файла;
- SHA-256 двух materialized executable, которые обязаны быть побайтово
  одинаковыми;
- закреплённые Python, uv и Nuitka и фактически использованный компилятор.

Архив детерминирован: пути отсортированы, uid/gid и имена владельцев пусты,
mtime равен нулю, режим каждого участника нормализован. В архиве нет каталогов
вне заявленного корня, абсолютных путей, `..`, обратных косых черт,
символических ссылок, жёстких ссылок, устройств или повторяющихся записей.

Target provenance и checksum-файл закрепляют внешний архив. GitHub attestation
подписывает архив как release subject; внутренний manifest связывает subject с
каждым исполняемым и вспомогательным файлом.

## Контракт сборки Unica

Обе записи RLM в `tools.lock.json` переходят на стратегию
`archive-release-asset`, указывают один release tag, один target archive и один
внешний SHA-256, но разные `archiveBinary`. Сборщик группирует совпадающие
asset identity, поэтому скачивает и извлекает общий архив ровно один раз.

До публикации файлов сборщик:

1. сверяет SHA-256 скачанного архива с lock;
2. извлекает его только в новый изолированный staging-каталог;
3. проверяет безопасный тип и путь каждой записи до записи на диск;
4. требует один `manifest.json`, точные release/source/target identities и
   полный набор entrypoints;
5. требует равенство фактического набора payload manifest, SHA-256, размеров и
   режимов;
6. отвергает коллизии с файлами других инструментов;
7. атомарно материализует payload под `bin/<target>`.

`tools.json` продолжает описывать две инструментальные идентичности и их
`binaryPath`, а отдельное поле `runtimeFiles` перечисляет полную замкнутую
полезную нагрузку с SHA-256 и режимом. `package-unica-runtime.py` включает
объединение `runtimeFiles` и проверяет, что каждый `binaryPath` входит в него.
Ни один необъявленный файл build-каталога в runtime не попадает.

Сгенерированные metadata конечного runtime уже перечисляют каждый файл.
Существующий `unica-bootstrap` поэтому проверяет и публикует расширенный набор
без изменения своей схемы или алгоритма.

## Последовательность поставки

### `unica-toolchain`

1. Добавить manifest-контракт и падающие тесты нового builder kind,
   детерминированного архива, multidist entrypoints и provenance.
2. Реализовать Nuitka builder с точными версиями Python `3.12.10`, uv
   `0.11.29` и Nuitka `4.1.3`.
3. Перевести только `manifests/rlm-tools-bsl.json`, увеличить
   `buildRevision`, сохранить source `v1.33.0`/commit и пустой список patches.
4. В PR собрать и извлечь архивы на всех трёх платформенных раннерах, выполнить
   root help обеих команд, полный help lifecycle index и реальный MCP contract.
5. После merge вручную выпустить новый immutable release и повторно скачать
   все target archives, checksum, provenance и attestation.

### Unica

1. До публикации нового toolchain release потребительский lock не менять.
2. Сначала падающими тестами закрепить новую archive strategy, безопасное
   извлечение, единственное скачивание общего asset, полный `runtimeFiles` и
   отказ при потере одной зависимости.
3. После публикации закрепить точный новый tag, размеры и SHA-256 трёх архивов.
4. На каждом runner собрать конечный runtime, проверить его metadata, извлечь
   в чистый каталог и выполнить текущий packaged MCP smoke.
5. Повторно скачать опубликованные runtime assets Unica и пройти действующий
   release gate ADR-0055.
6. После валидного прогона с физически свободными не менее `20 GiB` обновить
   #505 окончательными замерами опубликованного standalone runtime.

## Обработка ошибок и откат

- Неполный toolchain release, несовпавший архив, внутренний manifest, file set,
  SHA-256, режим или smoke блокирует публикацию и не меняет Unica.
- До переключения lock текущий `build.2` остаётся рабочим входом. Новый release
  не перезаписывает его.
- После переключения нет скрытого runtime fallback на PyInstaller: ошибка
  standalone payload делает сборку или runtime release красным.
- Если одна платформа несовместима с Nuitka multidist, новый release не
  публикуется частично. Отдельный builder по платформам требует нового
  согласованного решения.
- Если downstream-пакет потерял хотя бы одну библиотеку, проверка точного file
  set и packaged smoke падают до merge.
- Если изменение уже достигло публичного релиза Unica, применяется обычный
  release runbook: неизменяемые tag/assets не заменяются, исправление получает
  новую версию.

## Размер и производительность

Измеренный single-entrypoint Darwin standalone занимал `126.5 MiB`, из которых
около `102.1 MiB` приходилось на executable и `24.4 MiB` — на соседний payload.
Две обычные копии multidist executable и один общий payload дают верхнюю
предварительную оценку около `228.5 MiB` установленного RLM runtime против
примерно `42.7 MiB` пары текущих Darwin PyInstaller assets. Точный размер
multidist и сжатых архивов неизвестен до сборки на трёх release runners и
является обязательной частью отчёта PR.

Этот рост принимается ради отсутствия распаковки при каждом вызове index CLI.
Он не считается безусловно допустимым: PR фиксирует размеры target archive,
извлечённого payload и конечного runtime; если размер или время скачивания
нарушают release budgets, реализация возвращается на design review, а не
маскирует рост компрессией или исключением файлов Nuitka.

## Архитектурная оценка

Изменение меняет контракт получения и упаковки стороннего runtime, поэтому
`Decision: none` было бы неверно. ADR-0061 владеет выбором архивной замкнутой
полезной нагрузки, а `INV-PKG-TOOL-CLOSURE` — проверяемым обязательством не
терять файлы между toolchain release и конечным runtime.

ADR-0008 и ADR-0055 не заменяются: публичный marketplace остаётся тонким,
bootstrap продолжает проверять и атомарно публиковать один target runtime, а
smoke по-прежнему запускает извлечённые публикуемые байты. Новое решение
определяет более раннюю границу стороннего toolchain asset внутри этого потока.
