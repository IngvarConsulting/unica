# Провайдер-нейтральное чтение состояния поддержки

## Контекст

Issue [#289](https://github.com/IngvarConsulting/unica/issues/289) выявляет не
ошибку одного читателя, а обход уже принятой модели источников. Функции
`object_support_state`, `support_state_data` и `support_status_for_path` живут в
`native_operations/common.rs`, принимают файловый путь и сами ищут вверх
`Configuration.xml` и `Ext/ParentConfigurations.bin`. Эту раскладку имеет
Platform XML, но не EDT. Поэтому отсутствие Platform XML-файла у другого
поставщика ошибочно выглядит как законное состояние `notSupported`.

На текущем `main` часть исходного описания задачи уже устарела:
`unica.dcs.info` несёт типизированное поле `support` и покрыт тестом. Добавлять
поле повторно не нужно. Остаются прямой вызов path-функции и отдельная строка
`Поддержка: ...` в старом текстовом построителе DCS.

Вторая неоднозначность находится в предложенной сигнатуре задачи. Один метод
`object_support` не покрывает `unica.cf.info`: тот читает состояние всей
конфигурации, включая общую возможность изменения и счётчики правил объектов.
Остальные шесть читателей получают состояние одного объекта. Эти ответы имеют
разный смысл и не должны различаться условным вариантом одного неточного типа.

Третья неоднозначность следует из модели адреса. `ResolvedTarget` намеренно
содержит только логическую идентичность и не сериализует физическую ручку.
Следовательно, реализация порта не может найти provider-specific данные только
по значению аргумента: сам объект reader должен быть связан со снимком рабочего
пространства, в котором имя `sourceSet` разрешается однозначно.

## Цель

Сделать состояние поддержки результатом провайдер-нейтрального чтения по
`ResolvedTarget`, сохранить текущие типизированные wire-ответы Platform XML и
явно отказывать, когда поставщик или его свидетельство не позволяют прочитать
состояние.

## Выбранный подход

### Доменный порт и типы

Новый модуль `domain/support_state.rs` владеет типами данных, ошибкой и портом:

```rust
pub trait SupportStateReader: Send + Sync {
    fn configuration_support(
        &self,
        target: &ResolvedTarget,
    ) -> Result<ConfigurationSupportData, SupportReadError>;

    fn object_support(
        &self,
        target: &ResolvedTarget,
    ) -> Result<ObjectSupportData, SupportReadError>;
}
```

`ConfigurationSupportData`, `SupportCounts` и `ObjectSupportData` переезжают
из `native_operations/common.rs` в домен. Их сериализация сохраняет текущие
имена полей и значений, поэтому успешные ответы публичных инструментов не
меняют схему. Состояния выражаются закрытыми enum, а не свободными строками;
wire-значения остаются прежними.

`SupportReadError` различает как минимум:

- `provider_unavailable` — выбранный формат не имеет reader-а поддержки;
- `target_unsupported` — метод вызван для неподходящего `TargetKind`;
- `evidence_unavailable` — дескриптор или UUID цели нельзя доказать;
- `state_unreadable` — marker существует, но его нельзя прочитать;
- `state_invalid` — прочитанные данные не имеют известного формата.

Отсутствующий `ParentConfigurations.bin` у доказанного Platform XML-набора
остаётся состоянием `notSupported`. Нечитаемый, нерегулярный или повреждённый
marker больше не превращается в это состояние.

### Привязка к рабочему пространству и выбор поставщика

`InfrastructureApplicationPorts` создаёт на каждый вызов workspace-bound
реализацию `SupportStateReader`. Она удерживает только ссылку на текущий
`WorkspaceContext` и закрытый реестр реализаций, поэтому публичный метод порта
принимает только `ResolvedTarget`.

Reader разрешает `target.source_set` через действующую карту проекта и выбирает
реализацию по `SourceFormat`. В первом срезе зарегистрирован только адаптер
Platform XML. `Edt`, `Unknown` и `Invalid` возвращают
`provider_unavailable`; реализация чтения поддержки EDT в задачу не входит.

Platform XML-адаптер заново разрешает логическую цель под тем же
`WorkspaceContext`. Для конфигурационного метода допустим только
`TargetKind::SourceRoot`, для объектного — `TargetKind::MetadataObject`.
Физическая ручка, корень набора, descriptor UUID и
`Ext/ParentConfigurations.bin` остаются внутри инфраструктуры.

### Единая цель предметного чтения

Общий шов `native_operations/logical_selector.rs` начинает возвращать
`ResolvedReadTarget`:

```rust
pub struct ResolvedReadTarget {
    pub target: ResolvedTarget,
    pub resource_path: PathBuf,
}
```

Логический селектор уже получает обе части из `resolve_platform_xml_target`.
Для временно сохранённого файлового селектора шов находит содержащий
зарегистрированный набор исходников и использует существующую обратную
локализацию Platform XML. `Configuration.xml` связывается с
`SourceRoot`; прикреплённые `Rights.xml`, `Form.xml` и `Template.xml` — с
адресом владельца; descriptor объекта — с собственным адресом. Неоднозначный,
незарегистрированный или недоказанный путь отказывает и не порождает
эвристический адрес.

Так мост ADR-0049 сохраняет совместимость путевого селектора, но состояние
поддержки больше не читается по пути. Предметный XML по-прежнему открывается по
закрытому `resource_path`; в порт уходит только `target`.

`meta.info` уже разрешает логическую цель. Его `ResolvedMetadataObject`
сохраняет полученный `ResolvedTarget`, чтобы не реконструировать адрес из
descriptor path.

### Внедрение в обработчики

`NativeOperationAdapter::invoke_with_data` получает
`&dyn SupportStateReader` от композиционного корня и передаёт его только
типизированным читателям. Семь потребителей меняются так:

| Потребитель | Метод порта | Цель |
| --- | --- | --- |
| `cf.info` | `configuration_support` | корень выбранного `sourceSet` |
| `meta.info` | `object_support` | разрешённый объект метаданных |
| `form.info` | `object_support` | владелец `Form.xml` |
| `role.info` | `object_support` | владелец `Rights.xml` |
| `mxl.info` | `object_support` | владелец `Template.xml` |
| `subsystem.info` | `object_support` | descriptor подсистемы |
| `dcs.info` | `object_support` | владелец `Template.xml` |

Существующее поле `DcsInfoData.support` сохраняется. Функция
`support_status_for_path` удаляется, а старый DCS text builder перестаёт
добавлять отдельную строку поддержки. Типизированный `data.support` остаётся
единственным представлением этого факта согласно ADR-0023.

### Ошибки

Ошибка порта делает соответствующий читатель неуспешным и не публикует
частичные типизированные данные. Для нативных читателей стабильный код ошибки
попадает в `errors`; `meta.info` отображает его на типизированную диагностику
`ProviderUnavailable` с логическим `metadataPath`. Ни один отказ не раскрывает
физический путь поставщика наружу.

Отсутствие marker-а и ошибка чтения различаются до проекции результата.
Отсутствие означает доказанное `notSupported`; ошибка означает, что решение о
безопасности прямого редактирования принять нельзя.

## Рассмотренные альтернативы

### Один метод с enum-запросом и enum-ответом

Отклонён. Он позволил бы `cf.info` случайно принять объектный ответ, а
предметному читателю — конфигурационный. Два метода выражают разные операции в
типах и сохраняют узкий интерфейс.

### Методы непосредственно в `ApplicationPorts`

Отклонены. Это быстро устраняет прямые вызовы, но делает доменную способность
частью крупного application-фасада и затрудняет независимую реализацию другого
поставщика. `ApplicationPorts` остаётся композиционным владельцем внедрения, а
малый `SupportStateReader` — портом предметной способности.

### Обёртка над path-функциями

Отклонена. Передача `ResolvedTarget`, превращённого обратно в путь перед вызовом
старой функции, меняет только форму API. Поиск вверх и неразличимость
отсутствующего, нечитаемого и provider-unsupported состояния сохранили бы
исходный дефект.

### Добавить только проверку формата EDT

Отклонено как исправление симптома. Следующий источник без
`ParentConfigurations.bin` повторил бы дефект, а семь обработчиков продолжили
бы владеть знанием раскладки Platform XML.

## Проверка

Работа выполняется test-first следующими доказательствами:

1. Доменный fake-reader без способности чтения возвращает
   `provider_unavailable`, а не `ObjectSupportData::not_supported()`.
2. Platform XML-адаптер различает отсутствующий marker, ошибку чтения и
   повреждённый формат.
3. `role.info` на `Roles/<name>/Ext/Rights.xml` связывает путь с
   `ResolvedTarget` роли и читает правило UUID от корня конфигурации.
4. Логический и файловый селекторы одной фикстуры возвращают одинаковый
   `support` для каждого предметного читателя.
5. `dcs.info` сохраняет `data.support`, а текстовый построитель не создаёт
   второго представления.
6. Тест в `infrastructure/application_ports.rs` внедряет recording reader и
   доказывает, что семь маршрутов передают логическую цель; отдельный guard
   запрещает прямые упоминания удалённых path-функций в обработчиках.
7. Фильтры `cargo test -p unica-coder support_state`,
   `cargo test -p unica-coder answers_identically`, полный
   `cargo test -p unica-coder -- --test-threads=1`, архитектурные CI-тесты и
   `git diff --check` проходят.

## Архитектурное влияние

Работа меняет общий контракт нескольких потребителей: состояние поддержки
читается только через провайдер-нейтральный порт по логической цели, а
неспособность поставщика становится ошибкой. Выбор принадлежит ADR-0054; его
проверяемое следствие добавляется в реестр как `INV-APP-SUPPORT-STATE`.
