# Ограниченный низкоуровневый доступ к ресурсам исходников

- Date: `2026-07-30`
- Status: `draft`
- Decision: `ADR-0021`

## Результат проектирования

Unica сохраняет три публичных инструмента низкоуровневого доступа:

- `unica.source.resources` перечисляет ресурсы логической цели и открывает
  неизменяемый снимок;
- `unica.source.read` читает один ресурс снимка ограниченными фрагментами;
- `unica.source.apply` строит и применяет безопасную полную замену разрешённого
  существующего ресурса.

Это не файловый API и не сокращённый путь вокруг предметных writer-ов. Клиент
не получает физический путь и не выбирает произвольный файл. Доступ связан с
`SourceTarget` из ADR-0020, снимком поставщика, типизированной ролью ресурса,
его точным preimage и capability, доказанной поставщиком.

Первый пишущий срез намеренно узок: один существующий BSL-модуль в Platform XML.
XML-дескрипторы, регистрации, формы, DCS, MXL, права, двоичные макеты и
неизвестные роли остаются read-only независимо от media type.

## Зачем нужен отдельный контракт

Предметный инструмент остаётся основным способом изменения:

- `unica.code.patch` знает семантику вставки BSL;
- `unica.form.edit` знает структуру формы;
- `unica.dcs.edit`, `unica.mxl.compile`, `unica.role.compile` и другие
  операции владеют своими format/support/validation правилами.

Но высокоуровневая поверхность не может заранее охватить каждый ресурс
конфигурации. Без ограниченного fallback MCP-first workflow имеет два плохих
исхода: останавливается на отсутствующем writer-е либо выталкивает агента к
ручному редактированию файла вне Unica. `resources/read/apply` закрывает этот
разрыв, оставаясь внутри проверяемой границы.

Ресурсный API отделён от адресного ADR по двум причинам:

1. идентичность объекта и модуля нужна всем поставщикам независимо от наличия
   низкоуровневой записи;
2. расширение или последующее замещение аварийного writer-а не должно менять
   адреса и правила навигации.

Отделение не делает API необязательным. ADR-0021 создаёт самостоятельный
публичный контракт с собственной миграцией при будущем удалении.

## Рассмотренные варианты

### Удалить resource API

Вариант уменьшает публичную поверхность, но не обеспечивает заявленный
MCP-first fallback. Он снова делает физический файл единственным выходом для
ресурса без предметного writer-а. Отклонён по прямому продуктовому требованию.

### Включить resource API в ADR адресации

Один большой ADR проще прочитать как единый проект, но связывает постоянную
идентичность с более рискованным writer-контрактом. Любое сужение `apply`
потребовало бы замещать весь адресный выбор. Отклонён.

### Отдельный снимочный API с allowlist ролей

Выбранный вариант сохраняет все три операции, но не публикует файловую
систему. Чтение и запись получают разные capability; запись разрешается по
роли, состоянию снимка и доказанным гарантиям поставщика.

## Модель угроз

Контракт обязан закрывать следующие классы ошибок.

### Подмена цели

Клиент может повторно использовать `resourceId` с другим `snapshotId`,
подставить идентификатор другого source set или попытаться передать внутренний
handle. Поэтому оба идентификатора непрозрачны, связаны на стороне поставщика и
проверяются вместе с логическим владельцем.

### Устаревший снимок

Между перечислением, чтением, preview и apply файл может измениться. Поэтому
снимок несёт ревизию, ресурс — криптографический hash, а запись требует
`expectedHash`. Несовпадение не разрешается повторным чтением «на лету» внутри
того же apply: клиент получает стабильный отказ и открывает новый снимок.

### Выход за workspace

Даже корректно созданная ручка может устареть после замены каталога или
символической ссылки. Поэтому containment доказывается не только при создании
снимка, но и перед preview/apply по заново разрешённому фактическому пути.

### Неполный или ложный манифест

Отсутствие ресурса в выдаче нельзя трактовать как доказательство его
отсутствия. Каждая область сообщает `complete|partial|unavailable`; обрезанная
страница остаётся частью того же снимка и использует cursor. Запись из
неполного снимка запрещена.

### Повреждение структуры 1С

Текстовость или расширение файла не доказывают безопасность полной замены.
`Configuration.xml`, descriptor XML, регистрации и сериализованные формы могут
быть обычным текстом, но их изменение требует предметного writer-а. Разрешение
записи выдаётся по закрытому allowlist роли и provider-specific evidence.

### Расхождение preview и apply

Если diff строится отдельно от плана записи, показанный результат может не
совпасть с опубликованными байтами. Preview и apply поэтому используют один
`MutationPlan`, связанный с exact preimage, нормализацией EOL/BOM и
post-image.

### Частичная запись и устаревший кеш

Последовательная публикация нескольких ресурсов оставляет повреждённый агрегат
при втором отказе. Первый срез пишет только один ресурс. Многофайловая запись
появляется лишь после доказанной атомарности всего набора. Событие и
инвалидация кеша происходят только после подтверждённого успеха.

### Утечка внутреннего устройства

Ошибки, результаты и диагностические сообщения не раскрывают абсолютный путь,
строку соединения, содержимое закрытой ручки или соседние ресурсы вне
запрошенной области.

## Снимок и ресурс

`snapshotId` связан на стороне поставщика со следующими данными:

```text
ResourceSnapshot {
  providerId,
  sourceSet,
  sourceTarget,
  providerRevision,
  scope,
  completeness,
  createdAt,
  expiresAt
}
```

`providerRevision` не объявляется версией платформы и не обязан быть
долговечным номером. Это provider-specific доказательство, что состав и
preimages снимка не изменились. Публично возвращается только непрозрачный
`snapshotId` и данные, нужные для проверки свежести.

`resourceId` разрешается только внутри одного снимка:

```text
SnapshotResource {
  resourceId,
  owner,
  role,
  mediaType,
  size,
  hash,
  textProfile?,
  access,
  limits
}
```

`owner` — логический адресуемый владелец из ADR-0020. Для неадресуемого
служебного ресурса возвращается типизированное местоположение с ближайшим
владельцем, но не вымышленный `metadataPath`.

`role` является закрытым перечислением контракта, а не копией имени файла.
Начальный профиль как минимум различает:

- `bslModule`;
- `configurationDescriptor`;
- `metadataDescriptor`;
- `registration`;
- `form`;
- `dcs`;
- `mxl`;
- `rights`;
- `binaryTemplate`;
- `unknown`.

Поставщик может сообщить неизвестную роль для чтения, но не может выдать ей
`replace`.

## `unica.source.resources`

Вход первого контракта:

```json
{
  "sourceSet": "main",
  "metadataPath": "CommonModule.General.Module",
  "scope": "self",
  "limit": 100
}
```

Допустимые области:

- `self` — ресурсы самой точной цели;
- `aggregate` — ресурсы агрегата, которым владеет цель;
- `registrations` — необходимые регистрации выбранного агрегата.

Область не означает транзитивный обход ссылок и зависимостей. Поставщик
перечисляет только ресурсы, чью принадлежность способен доказать.

Ответ:

```json
{
  "snapshotId": "opaque",
  "sourceSet": "main",
  "target": {
    "metadataPath": "CommonModule.General.Module",
    "targetKind": "module"
  },
  "scope": "self",
  "completeness": "complete",
  "resources": [
    {
      "resourceId": "opaque",
      "role": "bslModule",
      "mediaType": "text/x-bsl",
      "size": 4312,
      "hash": "sha256:...",
      "textProfile": {
        "encoding": "utf-8",
        "bom": false,
        "eol": "crlf"
      },
      "access": ["read", "replace"]
    }
  ],
  "nextCursor": null
}
```

На первой странице `snapshotId` и `cursor` отсутствуют. Продолжение передаёт
оба значения из ответа; cursor действует только внутри указанного снимка.
Изменение `sourceSet`, target или scope при продолжении отвергается.
`partial`/`unavailable` никогда не повышается до `complete` по отсутствию
следующей страницы.

```json
{
  "snapshotId": "opaque",
  "cursor": "opaque",
  "limit": 100
}
```

## `unica.source.read`

Вход:

```json
{
  "snapshotId": "opaque",
  "resourceId": "opaque",
  "offset": 0,
  "limit": 65536
}
```

Смещение и размер определяются в байтах исходного снимка. Для текста ответ
дополнительно сообщает границы декодирования, кодировку, BOM и EOL. Поставщик
не разрывает многобайтовую последовательность: фактический диапазон может быть
уже запрошенного.

Ответ содержит:

- фактические `offset` и `length`;
- общий `size`;
- `hash` полного ресурса снимка;
- `content`;
- кодирование содержимого;
- `eof`;
- применённый предел.

Для двоичного ресурса допускается ограниченное base64-чтение, если provider
может сделать это без раскрытия закрытой ручки. Возможность чтения не создаёт
возможность записи.

## `unica.source.apply`

Первый контракт принимает:

```json
{
  "snapshotId": "opaque",
  "resourceId": "opaque",
  "expectedHash": "sha256:...",
  "content": "...",
  "contentEncoding": "utf-8",
  "dryRun": true
}
```

Правила:

1. `dryRun` по умолчанию равен `true`.
2. Первый срез принимает ровно один `resourceId`.
3. Ресурс уже существует и имеет роль `bslModule`.
4. Capability `replace` была выдана тем же provider-ом внутри полного снимка.
5. `expectedHash` совпадает с манифестом и текущим preimage.
6. `content` проходит ограничения размера и BSL-парсер.
7. Наблюдённые EOL/BOM сохраняются, если отдельное нормализующее поведение не
   стало явной частью более нового контракта.
8. XML, регистрации, формы, DCS, MXL, права, двоичные и неизвестные роли
   получают `resource_not_replaceable` до построения write plan.

Полная замена BSL-модуля не подменяет семантику `unica.code.patch`.
Высокоуровневая вставка выбирается всегда, когда задача выражается её
контрактом; `source.apply` нужен для изменения, которому ещё нет предметной
операции.

## Единый план preview/apply

Application layer строит типизированный `MutationPlan`:

```text
MutationPlan {
  sourceTarget,
  providerId,
  closedHandle,
  resourceRole,
  preimageHash,
  postimageHash,
  observedTextProfile,
  postimageBytes,
  diff,
  changedRanges,
  validationEvidence
}
```

План не сериализует `closedHandle`. Preview возвращает diff, диапазоны,
post-hash и доказательства, но ничего не пишет и не публикует событие.

Apply не принимает от клиента ранее показанный diff как источник истины. Он
повторно:

1. валидирует snapshot/resource binding;
2. разрешает закрытую ручку;
3. проверяет containment;
4. сравнивает provider revision и preimage hash;
5. проверяет формат и поддержку;
6. строит тот же план из тех же canonical inputs;
7. проверяет BSL;
8. атомарно публикует post-image;
9. подтверждает post-hash;
10. публикует доменное событие.

Если любой precondition изменился, новый план молча не принимается:
возвращается typed stale/hash error, и клиент снова вызывает preview.

## Containment и support

Удаление публичного path-аргумента не отменяет
`INV-SOURCE-WRITE-CONTAINMENT`. Инфраструктурный provider перед каждой
пишущей фазой получает фактический path из закрытой ручки и пропускает его
через `WorkspacePathPolicy::resolve_write`.

Одновременно проверяются:

- принадлежность handle выбранному workspace/source set/target;
- отсутствие выхода через `..` или символическую ссылку;
- Platform XML owner;
- writable format profile;
- поддержка объекта;
- exact preimage;
- atomic replace capability.

Ручка, созданная правильным resolver-ом, является входом этих доказательств, а
не доказательством сама по себе.

## Событие и кеш

После подтверждённого успеха публикуется одно типизированное событие:

```text
SourceResourcesReplaced {
  sourceSet,
  owner,
  roles,
  preimageHashes,
  postimageHashes,
  affectedTargets
}
```

Orchestrator инвалидирует workspace cache и provider-specific производные по
этому событию. Preview, validation failure, stale snapshot, containment denial
и cancellation не публикуют событие.

Если публикация байтов завершилась, но событие не может быть зафиксировано,
операция не сообщает обычный успех. Реализация обязана либо откатить атомарную
замену, либо вернуть типизированную integrity error с восстановительным
свидетельством. «Байты изменены, кеш когда-нибудь обновится» не является
допустимым состоянием.

## Ошибки

Минимальные стабильные коды:

- `snapshot_not_found`;
- `snapshot_expired`;
- `snapshot_incomplete`;
- `snapshot_scope_mismatch`;
- `resource_not_found`;
- `resource_not_readable`;
- `resource_not_replaceable`;
- `stale_revision`;
- `hash_mismatch`;
- `content_too_large`;
- `containment_denied`;
- `support_denied`;
- `format_denied`;
- `validation_failed`;
- `atomicity_unproven`;
- `cancelled`;
- `integrity_failed`.

Человекочитаемая диагностика не включает закрытый путь или handle. Повторяемый
отказ сообщает, нужно ли открыть новый снимок, выбрать предметный writer или
исправить содержимое.

## Пределы и отмена

Каждый инструмент имеет явные:

- максимальное число ресурсов на страницу;
- максимальный суммарный размер манифеста;
- максимальный размер read chunk;
- максимальный размер replacement;
- deadline;
- cancellation checkpoints.

Конкретные бюджеты задаются выведенным требованием качества при реализации.
До появления измерений проект не фиксирует случайные численные значения в ADR.

Отмена проверяется до чтения, между chunk-операциями, до построения плана и
перед атомарной публикацией. После начала неделимой публикации провайдер
завершает её согласно своей транзакционной гарантии и возвращает один из трёх
исходов: success, proven rollback или `integrity_failed`.

## Маршрутизация скиллов

Скилл выбирает операции в таком порядке:

1. существующий предметный read/write инструмент;
2. `unica.source.resources` + `unica.source.read` для исследования;
3. `unica.source.apply` только когда предметного writer-а нет и роль явно
   разрешена.

`source.apply` не описывается как общий редактор XML или замена
`unica.code.patch`. Перед применением скилл обязан показать preview и назвать,
почему предметная операция не выражает изменение.

## Этапы реализации

### Срез 1: снимок и read-only Platform XML

- доменные типы снимка, ресурса, роли, completeness и limits;
- `resources` и `read`;
- закрытые handles без физических путей в wire;
- `self/aggregate/registrations`;
- pagination и chunking;
- fixture с полным и неполным агрегатом;
- без `replace` capability.

### Срез 2: один BSL resource

- роль `bslModule`;
- один existing resource;
- `dryRun=true` по умолчанию;
- expected hash/provider revision;
- общий mutation plan;
- containment по closed handle;
- format/support/EOL/BOM/parser;
- atomic replace;
- доменное событие и cache invalidation.

### Срез 3 и далее

Новая роль записи или второй пишущий provider не подключаются по аналогии.
Каждый требует:

- provider evidence;
- fixture;
- threat-model delta;
- доказанную atomicity;
- acceptance tests;
- изменение ADR либо явно указанное совместимое расширение, разрешённое
  принятым решением.

EDT, CF/CFE, FileDB и автономный сервер могут сначала реализовать read-only.
Source readability не доказывает writer safety.

## Проверки проекта

До принятия ADR:

- схема трёх инструментов сверяется с `INV-MCP-NAMESPACE`,
  `INV-MCP-SURFACE-SYNC` и `INV-PRODUCT-DEVELOPER-OPERATIONS`;
- угрозы сопоставляются с действующими SOURCE-инвариантами;
- первый allowlist содержит только `bslModule`;
- design и ADR одинаково запрещают XML/registrations/binary write;
- lifetime снимка и связь resourceId проверяются на подмену;
- preview/apply используют один план;
- событие описывает все invalidation keys.

При реализации:

- forged snapshot/resource pair получает typed отказ;
- expired revision и hash mismatch ничего не пишут;
- symlink escape и смена owner отказывают;
- partial/unavailable snapshot не выдаёт `replace`;
- descriptor XML с media type `text/xml` остаётся read-only;
- preview не меняет bytes/cache и не публикует event;
- apply публикует ровно previewed bytes или требует новый preview;
- parser/support/format failure оставляет preimage;
- первый срез отклоняет второй resource;
- success публикует одно событие с pre/post hashes;
- cancellation доказывает success или rollback, а не partial state.

## Риски и цена решения

- Три новых инструмента увеличивают поверхность MCP. Это оправдано только как
  разработческий fallback, поэтому маршрутизация и allowlist входят в
  нормативный контракт.
- Полная замена BSL шире семантической вставки. Exact preimage, preview,
  parser, limits и предметный приоритет уменьшают риск, но не делают обе
  операции эквивалентными.
- Снимки требуют ограниченного provider state и очистки по TTL. Состояние
  остаётся worktree-scoped согласно ADR-0018.
- Read-only манифест для сложного агрегата может быть `partial`. Честная
  неполнота предпочтительнее ложной write capability.
- Будущее удаление `source.apply` является ломающей миграцией: потребуется
  замещающий ADR, таблица перехода и release notes. Адреса ADR-0020 при этом не
  меняются.
