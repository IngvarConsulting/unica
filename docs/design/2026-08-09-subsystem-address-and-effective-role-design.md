# Адрес подсистемы и эффективная роль в зарегистрированной топологии

## Контекст

PR #386 добавил проверку того, что регистр со стандартными командами достигает
хотя бы одного раздела командного интерфейса. Первый вариант вывел вложенность
подсистем в общий `MetadataAddress` как `Subsystem.Parent.Child` и собирал
доказательства обходом всех XML-файлов под `Subsystems/`.

Эти два упрощения меняют смысл уже существующих контрактов. Нечётное число
сегментов `MetadataAddress` означает терминал модуля, а физическое наличие XML не
означает регистрацию объекта в конфигурации. Кроме того, отдельные сканеры
публичного чтения и валидации по-разному трактовали отсутствующего предка,
повреждённый дескриптор и неканонический boolean.

Старший репозиторный контракт формата
`plugins/unica/references/specs/1c-subsystem-spec.md` требует явный
`IncludeInCommandInterface`. Попытка построить локальный официальный корпус 1Ci
не дала complete manifest: загрузчик получил 549 страниц без ожидаемого
`#xwikicontent`. Поэтому официальной фикстуры, которая могла бы опровергнуть
контракт формата, нет; неизвестное значение нельзя превращать в `true`.

## Требуемый результат

`unica.subsystem.info` отвечает только за структуру. Для каталога `Subsystems/`
он возвращает зарегистрированную иерархию `tree`. При чтении конкретной
зарегистрированной подсистемы её подробное описание содержит сфокусированное
`tree`: предки образуют единственную цепочку от корня до выбранного узла, а
выбранный узел раскрывается со всем деревом потомков. Соседние ветки предков в
сфокусированное дерево не входят. Анализ отдельного незарегистрированного XML
остаётся совместимым с прежним поведением, но не публикует недоказанное дерево.

`unica.meta.info` возвращает рядом с данными анализируемого объекта две плоские
коллекции членств, а не список всех подсистем конфигурации:

```json
{
  "functionalSubsystems": ["Служебные.ФоновыеЗадания"],
  "interfaceSubsystems": ["Продажи.ОптовыеПродажи"]
}
```

Адрес в обоих списках использует диалект БСП: это последовательность
программных имён от корня без `Subsystem.` и без повторения вида между уровнями.
Платформенное написание `Subsystem.A.Subsystem.B` остаётся форматом конкретного
XML-поля и преобразуется его reader-ом на границе.

## Доказанная топология

Единственный построитель начинает с `Configuration/ChildObjects`, затем читает
`ChildObjects` каждого зарегистрированного дескриптора. Файловая раскладка
подтверждает зарегистрированный узел, но не создаёт его. Незарегистрированный
файл, включая повреждённый, не влияет на результат.

Для зарегистрированного узла обязательны и согласованы:

- дескриптор по ожидаемому логическому пути без раскрытия symlink;
- единственный объект `Subsystem` и его `Properties`;
- `Name`, совпадающий с регистрацией и листом пути;
- канонический `IncludeInCommandInterface` со значением `true` или `false`;
- `Content` и `ChildObjects`, включая пустые элементы.

Каждый `Content/xr:Item` разбирается в закрытую сумму
`MetadataAddress | UUID`. Произвольная непустая строка не становится
третьим видом ссылки, а делает доказательство недоступным. Для
анализируемого descriptor `meta.info` получает его доказанные
`MetadataAddress` и UUID и сопоставляет оба варианта типизированной ссылки.

Все чтения доказательства идут через один удерживаемый корень, открытый
без раскрытия символических ссылок. Построитель не сканирует `Subsystems/` и не
переоткрывает корень для каждого descriptor. Он сначала запрашивает
`Configuration.xml`, затем транзитивно открывает только descriptor-файлы, названные в
регистрациях, и повторно подтверждает их идентичность перед terminal
`Complete`. Только эти файлы расходуют byte/file/entry budgets и образуют
точный набор format dependencies. Незарегистрированные файлы, каталоги и ссылки не
влияют ни на бюджеты, ни на вердикт.

Отсутствующий зарегистрированный файл, несовпадение имени, повторная
регистрация, обрыв цепочки, повреждённый XML, превышение бюджета, отмена или
deadline делают топологию недоступной. Пустые списки допустимы только тогда,
когда регистрация полностью прочитана и действительно не содержит подсистем.

Порядок дерева и членств — pre-order зарегистрированного дерева: порядок корней
задаёт `Configuration/ChildObjects`, порядок детей — `ChildObjects` родителя.
Сортировка имён файлов не подменяет значимый порядок регистрации.

## Эффективная роль

Узел относится к интерфейсным, только если его собственный флаг и флаги всех
зарегистрированных предков равны `true`. Во всех остальных доказанных случаях
узел функциональный. Поэтому `true` под `false` остаётся функциональным. Для
одного объекта две коллекции членств взаимно исключаются, но не обязаны покрывать
всё дерево: в них входят только узлы, чей `Content` содержит этот объект.

Совпадение функциональной и интерфейсной структуры в прикладном замысле не
образует третьего вида: при эффективном `true` узел интерфейсный.

## Потребители

`unica.subsystem.info` строит из доказанного графа полное дерево каталога или
сфокусированное дерево выбранной подсистемы. Для конкретного XML адрес выводится
из его физического пути относительно доказанного source root, а не из XML-`Name`.
Отдельный незарегистрированный XML сохраняет локальное описание без `tree`, но ошибка
доказательства в зарегистрированной области не подавляется. Инструмент не публикует ролевые
списки.
`unica.meta.info` из того же графа получает адреса всех подсистем, чей `Content`
содержит адрес или UUID текущего descriptor, и разделяет их на `functionalSubsystems` и
`interfaceSubsystems`. Валидатор принимает то же типизированное доказательство
и не обходит файловую систему повторно.

Публичный native path передаёт построителю cancellation и bounded deadline,
включая terminal checkpoint. Format guard получает от построителя точный набор
`Configuration.xml` и прочитанных зарегистрированных descriptors; его работа не зависит от
снятого публичного аргумента `Mode`.

Отсутствие доказательства у `meta.add` и `meta.edit` означает «не проверяли», а
не доказанное отсутствие подсистемы. Неполное доказательство у complete-read
публикуется как `provider_unavailable`; оно не превращается в семантическое
предупреждение «раздела нет».

Каталог `Subsystems` внутри зарегистрированной подсистемы сохраняет прежний
сценарий поддерева. При чтении XML вложенной подсистемы адрес выбранного узла
выводится из её зарегистрированной цепочки, а не из одного имени файла.

## Отвергнутые варианты

### Расширить `MetadataAddress`

Отвергнуто: это потребовало бы определить новый `TargetKind`, разрешение цели,
навигацию и ресурсный доступ. Для чтения топологии такая поверхность не нужна.

### Сканировать все XML и восстанавливать родителей из пути

Отвергнуто: незарегистрированный файл начинает влиять на семантический вердикт,
а отсутствующий родитель ошибочно выглядит как функциональный.

### Оставить два сканера

Отвергнуто: одинаковое дерево уже получало разные verdict при malformed XML и
ошибках чтения. Политика принадлежит одному построителю, а не потребителям.

## Проверка

- доменные тесты `SubsystemAddress` и неизменившейся общей грамматики
  `MetadataAddress`;
- матрица зарегистрированной топологии, identity, boolean, budget, symlink и
  terminal checkpoint;
- точная JSON-сериализация полного и сфокусированного `tree` в
  `subsystem.info` без ролевых списков;
- surface-тесты двух коллекций членств текущего объекта в `meta.info`;
- contract-тест, связывающий реализацию, ведомость инструмента и skill.
