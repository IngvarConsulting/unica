# Поколения исходников и свежесть RLM

## Контекст

Исправление #286 связало готовый RLM-индекс с `source_generation`, чтобы ответ
`rlm-bsl-index info = fresh` не узаконивал старый снимок SQLite после изменения
исходников. Поколение сейчас заново вычисляется по именам, размерам и `mtime`
всех релевантных файлов. Один RLM-backed вызов делает три обхода: проверку
готовности и проверки до и после execute.

Размен принимался при измерении около 440 мс на обход и 1,3 с на вызов для
43 299 файлов. На рабочем Sendbox прямой RLM-запрос занимает около 0,18 с, а тот
же путь через Unica — около 17 с. Следовательно, задержкой владеет доказательство
свежести, а не поиск RLM. Ограничение глубины, выборка файлов или TTL удешевили
бы симптом ценой возврата устаревшего чтения.

Одни доменные события Unica недостаточны: `git checkout`, IDE, платформа,
редактор и внешний скрипт изменяют файлы без вызова Unica. Один watcher тоже не
является строгим доказательством: между завершением внешней записи и доставкой
асинхронного события остаётся окно, в котором счётчик ещё выглядит прежним.

## Цель

Заменить синхронные полные обходы на запросе постоянным поколением исходников,
не ослабляя fail-closed правило RLM: результат принимается только для
доказанно доверенного поколения, которому соответствует готовый индекс, и
отбрасывается при изменении во время execute.

## Выбранный подход

### `SourceRevisionService`

Скрытый workspace-сервис для пары `workspaceRoot + sourceRoot` владеет
`SourceRevisionService`. Его публичная для инфраструктуры модель:

```rust
pub struct SourceRevision {
    pub generation: u64,
    pub digest: SourceDigest,
    pub trust: RevisionTrust,
}

pub enum RevisionTrust {
    Reconciling,
    Trusted,
    Untrusted,
}
```

`generation` монотонен внутри устойчивой идентичности и хранится рядом со
снимком workspace. `digest` — версионированный детерминированный SHA-256 по
относительным путям, типам и содержимому релевантных файлов; это дорогая
восстановительная проверка, а не операция каждого чтения. Формат записи содержит
версию алгоритма, нормализованный source root и атомарно опубликованный
generation.

Входы поколения:

- типизированные доменные события применённых операций Unica;
- события платформенного наблюдателя файловой системы;
- восстановительный полный reconcile при старте, переполнении, разрыве или
  невозможности синхронизировать наблюдатель.

Серия событий может быть объединена в одно новое поколение: свойство требует
монотонно отличить изменившийся снимок, а не посчитать каждую запись файла.

### Старт и восстановление

Сервис начинает в `Reconciling` и запускает наблюдатель до полного снимка.
Reconcile фиксирует последовательность наблюдателя, строит digest, затем
синхронизирует очередь. Если во время обхода пришли события, снимок повторяется
до тихой границы в пределах отдельного срока восстановления. После
стабильного снимка сервис сравнивает digest с сохранённым:

- совпадение сохраняет generation и разрешает повторно использовать ready
  marker;
- отличие увеличивает generation и делает индекс stale;
- отсутствие или неизвестная версия записи создаёт новое поколение и требует
  обновления индекса.

Если тихую границу доказать не удалось, состояние остаётся `Untrusted`, RLM не
получает ready и reconcile продолжается в фоне. Доступность не достигается
выдачей старого ответа.

### Freshness fence

Платформенный фасад предоставляет `SourceRevisionFence`, который завершает
только после того, как наблюдатель применил все события, предшествующие fence.
Перед допуском RLM и после execute сервис получает ревизию только через fence.
Поддерживаемая реализация может использовать журнал или синхронное дренирование
очереди ОС, но application и RLM не зависят от механизма.

После доказанного точного file-event сервис обновляет копию in-memory manifest:
`Upsert` читает только указанный contained regular file, `Remove` удаляет его
запись, затем digest складывается из entry digests без обхода файловой системы.
Событие каталога, неразрешимый путь, symlink индексируемого файла или ошибка
чтения не создают частично доверенный manifest: сервис теряет доверие и требует
полного reconcile.

Если ОС или используемый backend не способен доказать такую границу, очередь
переполнена либо наблюдатель потерял continuity, fence переводит oracle в
`Untrusted` и запускает полный reconcile. Обычный поиск не подменяет эту ошибку
последним известным generation. Так watcher используется как ускорение
доказательства, а не как вероятностная замена свежести.

### Возможности платформ

`SourceRevisionFence` является проверяемой возможностью backend, а не
безусловным свойством общей библиотеки watcher:

- на локальной файловой системе macOS FSEvents предоставляет синхронный flush,
  который доставляет уже произошедшие события до возврата;
- Linux inotify предоставляет упорядоченную очередь и явный
  `IN_Q_OVERFLOW`, но не рекурсивное наблюдение и не события удалённых изменений
  сетевой файловой системы. Реализация получает быстрый статус только после
  отдельного доказательства барьера для локального дерева; одного чтения
  очереди «до пустоты» в проектном контракте недостаточно;
- Windows `ReadDirectoryChangesW` сохраняет изменения между чтениями и явно
  сигнализирует переполнение, но обнаружение записи может зависеть от сброса
  кеша. USN-журнал даёт устойчивую последовательность только для подходящего
  локального тома и не считается безусловно доступной возможностью обычного
  процесса;
- сетевые и неизвестные файловые системы по умолчанию не объявляют быстрый
  барьер.

Backend при старте публикует внутренний признак
`fenceCapability = proven | unavailable`, подтверждённый платформенными
тестами. Только `proven` разрешает обычный путь с
O(1)-чтением поколения. `unavailable` не превращается в «почти свежо»: запрос
ждёт полного reconcile в пределах общего срока, а секция честно сообщает
неполноту, если доказательство не успело завершиться. Поэтому первая реализация
может ускорить macOS раньше других платформ, не создавая ложного
кроссплатформенного обещания.

Основания для capability-матрицы: синхронный
[flush FSEvents](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html),
[ограничения inotify](https://man7.org/linux/man-pages/man7/inotify.7.html),
[контракт ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)
и [USN-журнал](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_query_usn_journal).

### Привязка индекса

Ready marker RLM хранит одну полную ревизию: нормализованный `sourceRoot`,
`generation`, `digest` и версию алгоритма. Build/update захватывает доверенную
ревизию `R` до запуска. После успешного ответа RLM marker публикуется ready
только если post-build fence всё ещё возвращает ту же полную `Trusted(R)`.
Изменение любого компонента во время операции оставляет индекс stale и
планирует следующее update.

Поиск выполняет границу:

1. pre-execute fence возвращает полную `Trusted(R)`;
2. ready marker обязан точно совпасть с кортежем
   `(sourceRoot, R.generation, R.digest, R.algorithm)`;
3. RLM execute работает в пределах остатка общего срока;
4. post-execute fence обязан вернуть ту же полную `Trusted(R)`;
5. любое отличие, `Reconciling` или `Untrusted` отбрасывает output.

При доказанной возможности обычные пункты 1 и 4 читают ревизию после дешёвого
fence и не обходят дерево. Сессия RLM инвалидируется той же полной ревизией;
отдельного второго источника истины для тёплой сессии нет.

### Прогресс и отказ

RLM проецирует состояние в общий progress-контракт ADR-0055:

- `preparing/reconcilingSources` — строится восстановительный снимок;
- `preparing/buildingIndex` или `updatingIndex` — обслуживается индекс;
- `searching/executingQuery` — выполняется RLM-запрос;
- `failed/sourceRevisionUntrusted` — доказательство не получено до срока.

Полный reconcile сообщает обработанные файлы и известное total только когда
перечень уже замкнут; иначе сообщает число обработанных файлов и heartbeat без
процента. Частный digest, физические пути и журнал событий наружу не выходят.

## Рассмотренные альтернативы

### Только watcher и debounce

Отклонены. Они уменьшают вероятность старого чтения, но не закрывают окно до
доставки события и не восстанавливаются доказанно после overflow.

### Только доменные события и `workspace_epoch`

Отклонены. Они не видят изменения вне операций Unica и поэтому повторяют
исходный дефект после checkout или правки IDE.

### TTL полного обхода

Отклонён. Внутри TTL старый результат считается свежим по времени, а не по
снимку. Большой TTL нарушает корректность, маленький возвращает задержку.

### Хешировать дерево перед каждым чтением быстрее

Отклонено как оптимизация текущего механизма, а не устранение причины. Даже
идеальный параллельный обход остаётся линейным по корпусу и повторяется трижды.

## Проверка

Реализация начинается с падающих тестов:

1. backend с доказанным fence выполняет ноль полных обходов на неизменённом
   тёплом поиске и принимает один и тот же generation;
2. применённая операция Unica и внешняя запись увеличивают generation;
3. fence не допускает поиск, пока предшествующее внешнее событие не применено;
4. overflow и разрыв переводят сервис в `Untrusted`, запускают reconcile и не
   отдают ready path;
5. изменение во время build не публикует ready marker;
6. изменение во время execute отбрасывает output;
7. рестарт с тем же digest переиспользует marker, с другим — увеличивает
   generation и запускает update;
8. backend без доказанного fence не использует быстрый путь и не выдаёт старое
   поколение за доверенное;
9. live-измерение Sendbox отдельно записывает прямой RLM и накладные расходы
   Unica; структурный критерий для backend с доказанным fence — отсутствие full
   walk на тёплом запросе.

## Архитектурное влияние

Работа меняет владение и доказательство свежести workspace state, поэтому
требует ADR-0056. Решение уточняет ADR-0018 только для RLM: поставщик продолжает
владеть частным индексом, а оркестратор — поколением, доверием и логической
инвалидацией. Оно не определяет состояние `bsl-analyzer`, не меняет общий
прогресс и не описывает лексический поиск.
