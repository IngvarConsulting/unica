# Линейный конвейер поставки: один тег, ноль надзирателей

## Проблема

Публикация версии проходит через два репозитория, три pull request, два
подписанных тега и планировщик Release Warden с собственной state machine.
Релиз v0.12.0 прошёл по всем слабым местам этой хореографии
([#518](https://github.com/IngvarConsulting/unica/issues/518)):

1. пуш тега маркетплейса не перетриггеривает чеки промоушена — релиз
   застревал сразу после подписи человека (тактически залатано #514);
2. промоушен открывается до тега и стоит красным by design — семь упавших
   джоб на каждый релиз в истории Actions;
3. вторая подпись не добавляет информации: между двумя тегами человек не
   узнаёт ничего нового, реальный гейт — зелёные consumer-чеки;
4. заброшенный релиз держит cron-прогоны красными до пометки prerelease;
5. `codex/stage-vX.Y.Z-<run-id>` — метаданные в имени ветки, парсятся
   регекспами warden-а: строковая связность трёх компонентов;
6. `detect_promotion.py` восстанавливает намерение из сравнения git-деревьев,
   потому что пуш не несёт типизированного интента.

Корень: посреди конвейера стоит неограниченное по времени ожидание человека
(тег маркетплейса). Всё остальное — warden, PR-транспорт чеков, регекспы имён
веток — обслуживает это ожидание.

## Решение в одну строку

Убрать человеческое ожидание из середины: единственный человеческий акт —
подписанный source-тег — стоит **перед** автоматикой, дальше конвейер линеен
до going live, и надзиратель ему не нужен.

## Целевой поток

```
человек: подписанный source-тег vX.Y.Z          ← единственное действие
робот:   сборка (3 ОС) → ассеты + SHA-256 → BSP-оценка
         прямой staging-коммит в marketplace/main   (каталог не тронут)
         тег vX.Y.Z ботом на staging-коммит         (якорь резолва)
         consumer-install: fresh + upgrade, 3 ОС    (гейт)
         зелено → коммит каталога в main → live
         красно → стоп; каталог не тронут; версия сожжена; красный прогон
```

Ключевые свойства сохраняются дословно из ADR-0008:

- каталог двигается только после существующего тега и только по зелёным
  установочным проверкам (двухфазность);
- опубликованные байты никогда не двигаются; неудавшаяся версия сжигается,
  следующая — очередной patch;
- откат live-релиза — revert коммита каталога, прежний тег резолвится как
  прежде.

## Рассмотренные варианты

### A. Оставить warden, чинить точечно (#514 и далее)

Отвергнут: каждая заплатка (kick после тега, выбор прогона по head sha)
усложняет state machine, не убирая причину — ожидание в середине. Стоимость
владения растёт, латентность 20-минутных окон остаётся.

### B. Auto-merge GitHub + branch protection вместо warden

Оба PR получают auto-merge, защита ветки требует зелёные чеки. Отвергнут:
PR-транспорт, регекспы имён веток и красный by design промоушен остаются;
исчезает только merge-шаг warden-а. Половинчатое упрощение при той же
хореографии.

### C. Линейный конвейер без PR (выбран)

PR в маркетплейсе никогда не были ревью — их мёржил бот тем же токеном,
которым теперь делает прямые пуши. PR был транспортом для чеков; чеки
переезжают в сам конвейер и выполняются против тега — то есть против ровно
той ревизии, которую увидит потребитель.

### D. Один репозиторий (каталог в unica)

Отвергнут без детальной проработки: ломает потребительский контракт
(`git-subdir` по тонкому публичному репо) ради выигрыша, который вариант C
даёт без слома. Может быть отдельным решением позже.

## Судьба человеческого гейта

Сегодня формальный гейт — подписанный тег маркетплейса. Фактический гейт —
зелёные consumer-чеки: warden мёржит по ним, человек подписывает механически.
Решение переносит человеческое одобрение на source-тег: он один запускает
публикацию, и его подпись — криптографический якорь релиза. Тег маркетплейса
становится тем, чем он был по факту — якорем резолва каталога, который никто
не верифицирует (у всех тегов с v0.11 `verified: false, bad_email`).

Опциональная пауза «второго взгляда» перед коммитом каталога возможна через
GitHub Environment с required reviewer — платформенная кнопка Approve вместо
GPG-церемонии. В базовый вариант не входит: ценность паузы не показана ни
одним инцидентом, а латентность и лишний шаг — показаны.

## Что удаляется

- `.github/workflows/release-warden.yml`;
- `scripts/ci/release-warden.py` и `tests/ci/test_release_warden.py`
  (~570 строк вместе с #514);
- режим `promote` и PR-механика в `publish-unica-marketplace.yml`;
- ручные шаги 3–6 runbook (остаются: версия, source-тег, наблюдение);
- в маркетплейсе: PR-ветки promotion-логики `detect_promotion.py` после
  переноса чеков (отдельный PR в unica-marketplace).

## Отказы и их видимость

| Отказ | Поведение | Видимость |
| --- | --- | --- |
| сборка/оценка красные | конвейер не дошёл до маркетплейса | красный прогон по тегу |
| staging-пуш упал | каталог не тронут | красный прогон |
| consumer-чеки красные | тег есть, каталог не тронут, версия сожжена | красный прогон |
| каталожный пуш упал (гонка) | retry с rebase; байты каталога идемпотентны | зелёный при удавшемся retry, красный при повторном отказе |
| rerun старого релиза после новее живого | охрана монотонности версий отказывает до записи | красный прогон |

«Застрявший релиз» как класс состояний исчезает: нет ожидания между стартом
автоматики и live, кроме конечного времени самих джоб. Cron-алертинг
warden-а становится ненужным — отказ виден как красный прогон конвейера,
привязанный к тегу.

## Миграция

1. Новый конвейер добавляется рядом со старым (стадия `stage` переиспользует
   существующую джобу), прогоняется на v0.13.0.
2. Warden и PR-механика удаляются в том же PR — оставлять две дороги к
   каталогу дольше одного релиза опаснее, чем короче.
3. Marketplace-репо чистится вторым PR после зелёного v0.13.0.
