# Применённый `unica.runtime.execute` поверх долговременной записи

## Контекст

`unica.runtime.execute` с `dryRun: false` отказывает: гейт допуска возвращает
`runtime_operation_unbounded` до обнаружения рабочего пространства. Отказ ввёл
ADR-0066 из-за четырёх наблюдаемых сил — непрерываемые критические фазы раннера,
запись без ограниченного восстановления, недоказанное владение отдельно
сгруппированным процессом платформы и отсоединённый `launch`.

При этом применённая работа из поставки уже достижима: гейт смотрит только на
`ToolHandler::RuntimeAdapter`, поэтому `unica.runtime.job.start` с
`dryRun: false` порождает раннера по-настоящему. Пользователи, читая
поставляемые инструкции, заключают обратное — что применённых операций в
продукте нет (#554).

Готовых деталей больше, чем предполагал ADR-0066:

- запись задания несёт `phase`, `heartbeat_at_ms` и `unsafe_phase`, то есть
  непрерываемость наблюдаема, а не выводится из имени операции;
- работу ведёт отсоединённый рабочий процесс, поэтому она переживает обрыв
  вызова и остановку сервера;
- раннер стартует своей группой процессов, отмена убивает группу целиком, на
  Windows дерево завершается `taskkill /T /F`;
- MCP-слой уже достаёт `progressToken` из `_meta` и публикует
  `notifications/progress`, а `notifications/cancelled` доведён до доменного
  токена отмены.

## Решение в одном абзаце

Применённый вызов заводит то же долговременное задание, подписывается на его
запись, публикует прогресс по смене фазы и ждёт терминального состояния, которое
и возвращает как результат вызова. Работа принадлежит отсоединённому процессу, а
результат — записи, поэтому обрыв вызова больше не теряет ни то, ни другое.

## Устройство

**Слой application.** Ветка `ToolHandler::RuntimeAdapter` с `dryRun: false`
перестаёт звать `runtime_receipt_admission_failure` как отказ. Вместо этого она
запрашивает классификацию риска, кладёт её в предупреждение результата, заводит
задание через существующий путь `runtime.job.start` и входит в ожидание записи.

**Ожидание.** Ожидание — цикл по снимку записи с ограниченным интервалом опроса.
На каждом изменении `phase` или `heartbeat_at_ms` публикуется снимок прогресса.
Существующий seam для этого узок: `SearchProgressSink` несёт роли поиска, а
MCP-слой жёстко подписывает мету ключом `io.unica/searchProgress`. Поэтому seam
обобщается: транспортно-нейтральный синк принимает снимок с доменным ключом меты
и фазами, а поиск остаётся одним из его поставщиков. Прогресс несёт фазу и не
изображает процент: `total` — число фаз, а не доля работы.

**Терминальный результат.** По достижении терминальной фазы вызов читает из
записи код выхода, хвосты журналов и артефакты и собирает из них тот же
`OperationResult`, который раньше отдавал синхронный applied-путь. Поле `job`
результата несёт `jobId`, чтобы вызывающая сторона могла вернуться к записи.

**Отмена.** Отмена приходит доменным токеном. Вне небезопасной фазы вызов
отменяет задание существующим путём отмены, который уничтожает группу процессов,
и возвращает результат отмены. В небезопасной фазе вызов прекращает ожидание, но
задание не трогает: ответ несёт `jobId`, имя небезопасной фазы и причину, по
которой прерывание не выполнено.

**Обрыв вызова.** Если вызов умирает не по отмене, а по сроку хоста, задание
продолжает работу в отсоединённом процессе. Ничего дополнительного делать не
нужно: результат уже принадлежит записи и забирается по `jobId`.

**Классификация риска.** `runtime_admission` сохраняет карту причин, но меняет
роль: известная операция получает предупреждение с названной причиной, а не
отказ. Неизвестная операция остаётся `Unclassified` и отказывает — закрытая по
умолчанию ветвь сохраняется.

## Одно названное изъятие

Ограниченный `launch` с `waitForExit: true` остаётся синхронным: он ограничен
своим `waitTimeoutMs`, разбирает конверт ожидания и уже принадлежит одному
вызову. Заводить под него запись задания значило бы переписать зрелый разбор
конверта без выигрыша в надёжности. Все остальные применённые операции идут
через запись.

## Границы и принятые риски

1. Целостность информационной базы после принудительного завершения раннера не
   обещается. Обещается не завершать его в небезопасной фазе и называть фазу.
2. `launch` включён в применённый путь по явному решению владельца продукта.
   Отсоединённый клиент платформы подконтрольным не становится.
3. Владение процессами на Windows остаётся `taskkill /T /F` по дереву; отдельно
   сгруппированный процесс платформы им не покрыт.
4. Хост, не сбрасывающий таймаут по прогрессу, всё равно обрубит долгий вызов.
   Это наблюдаемая разница между хостами, а не потеря результата.

## Проверки

- применённый вызов заводит запись задания и возвращает её терминальный
  результат, а не отказ;
- прогресс уходит на смене фазы, и его форма не обещает процент;
- отмена вне небезопасной фазы уничтожает группу процессов;
- отмена в небезопасной фазе не убивает задание и возвращает квитанцию с
  `jobId`;
- смерть вызова оставляет результат забираемым по `jobId`;
- неклассифицированная операция по-прежнему отказывает;
- поставляемые инструкции описывают применённый вызов и не выдают предпросмотр
  за исполнение.

## Поставка

Изменение целится в ветку сопровождения `release-v0.12` и уезжает
исправительной версией 0.12.2, потому что ADR-0066 назвал закрытие применённого
runtime публичной деградацией v0.12, а не новой возможностью. Та же правка
обязана попасть в `main`, иначе 0.13 выйдет с прежним отказом; порт выполняется
отдельным изменением после слияния здесь.
