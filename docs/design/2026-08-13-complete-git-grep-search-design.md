# Полный потоковый поиск `git-grep`

## Контекст

На Sendbox с 48 159 файлами резервный `git-grep` занимал около 4–5 секунд и
возвращал шумные первые совпадения. PR #469 предложил завершать процесс после
шести результатов либо через 500 мс. Потоковое чтение и управляемое завершение
дерева процесса устраняют реальный дефект захвата всего stdout, но два условия
останова смешивают `limit` ответа с полнотой поиска.

Первые строки `git grep` следуют порядку обхода Git, а не полезности для модели.
Остановка после `limit` закрепляет этот случайный порядок и не позволяет выбрать
лучшие попадания из остального корпуса. Таймаут 500 мс на большом дереве обычно
завершается до доказанного отсутствия совпадений. После появления progress
многосекундный, но живой полный обход больше не нужно скрывать коротким
архитектурным бюджетом.

BM25F не решает этот слой без нового индекса: корректная оценка требует числа и
длины всех документов, document frequency и term frequency по полям. Вывод
`git grep` содержит только строки буквального совпадения. Построение такой
статистики на каждый запрос дороже текущего обхода, а постоянный BM25F является
другим лексическим поставщиком и требует отдельного решения.

## Цель

Сохранить `git-grep` простой буквальной реализацией роли `lexical`, пройти весь
релевантный корпус в штатном случае, вернуть ограниченный лучший результат с
честным точным или нижним счётом и сообщать живой ход без накопления всего
вывода в памяти.

## Выбранный подход

### Полный поток

Поставщик запускает буквальный case-sensitive `git grep -F` для доказанного
source root, включая отслеживаемые и допустимые неотслеживаемые файлы. Pathspec
ограничивается форматами исходного кода, которые обслуживает code search, и не
включает `.build`, кеши и игнорируемые деревья. Политика корпуса задаётся
отдельной тестируемой функцией, а не случайным текущим каталогом процесса.

Stdout читается построчно с действующим пределом строки. Каждая полная валидная
строка немедленно разбирается в кандидат, увеличивает `matchesSeen` и
участвует в bounded top-K. В памяти остаются top-K, счётчики и диагностические
пределы, а не все совпадения. `SearchRequest.limit` определяет K и никогда не
останавливает естественный обход.

### Лёгкое ранжирование

`git-grep` остаётся буквальным и не выполняет стемминг, fuzzy expansion или
межпоставщицкое сравнение score. Локальная детерминированная оценка использует
только доказанные признаки кандидата:

1. запрос совпадает с границами BSL-идентификатора;
2. строка имеет форму объявления процедуры или функции с этим именем;
3. запрос встречается в логическом `metadataPath` или относительном
   наблюдаемом `path`;
4. более узкий адрес и более ранняя строка служат стабильными tie-breakers;
5. окончательный tie-breaker — переносимый путь и номер строки.

Эвристика не штрафует мобильные, расширенные или иные предметные деревья по
непроверяемому предположению об их полезности. Score остаётся локальным для
секции, а `matchKind` сообщает `declaration`, `identifier` или `literal`.

### Логическая локализация

Кандидат физически приходит как путь относительно source root. Адаптер
преобразует BSL-модуль через существующий inverse locator в доказанный
`addressed` с `{sourceSet, metadataPath, targetKind}`. Неадресуемый, но
содержащийся в зарегистрированном наборе файл возвращает `unaddressable` с
`{sourceSet, ownerMetadataPath?, path}`. Выход за набор, symlink или
несогласованная descriptor identity не превращаются в эвристический адрес;
кандидат отклоняется с ограниченной диагностикой.

### Прогресс

Поставщик публикует общие фазы ADR-0055:

- `preparing/selectingCorpus`;
- `searching/scanningSources` с `matchesSeen` и `bytesRead`;
- `ranking/selectingTopHits`;
- терминальное состояние.

Один процесс `git grep` не сообщает число уже просмотренных файлов, поэтому
поставщик не публикует фиктивный процент. Heartbeat с elapsed, bytes и matches
доказывает активность. Дробить корпус на тысячи отдельных процессов только ради
процента не требуется: это меняет стоимость и семантику отказа без пользы для
качества результатов.

### Завершение и эпистемика

Естественное завершение с кодом 0 возвращает `ok`, точный `total` и top-K.
Код 1 без вывода возвращает `empty`, `total = 0`, `relation = exact`.
Ненулевой ошибочный exit, нечитаемая строка сверх допустимого порога и ошибка
локализации не превращаются в `empty`.

При общем или явно настроенном сроке процесс и его дерево отменяются и
дожидаются. Секция получает `timedOut`, `searchComplete: false` и
`relation: lowerBound`; уже доказанные top-K могут быть возвращены как
неполные. Отмена родительского MCP-вызова имеет приоритет и не публикует
частичный результат. Намеренного успешного завершения после K строк нет.

## Что сохраняется и снимается из PR #469

Сохраняются как самостоятельные технические заготовки:

- потоковый process runner с ограничением строки;
- отмена, завершение и reap дерева процесса;
- различение естественного exit, timeout и остановки потребителем;
- диагностика invalid UTF-8, malformed row и ненулевого exit status;
- условный запуск долгого BSP assessment по затронутому механизму.

Снимаются:

- скомпилированные 500 мс;
- остановка после шести или `limit` результатов;
- очистка всех уже найденных попаданий только из-за timeout;
- ADR-0055 из незавершённой ветки #469 в прежней формулировке.

Текущий PR #469 не вливается как архитектурное решение. Нужные технические
изменения переносятся test-first после принятия общего progress-контракта.

## Рассмотренные альтернативы

### Остановиться после top-K первых строк

Отклонено. Это ограничивает расходы, но ранжирует порядок обхода Git и не
доказывает, что возвращены лучшие K.

### BM25F поверх совпавших строк

Отклонён. IDF и нормализация длины по одному множеству совпавших документов не
являются корпусной статистикой. Постоянный BM25F может в будущем заменить
реализацию роли `lexical`, не меняя ADR-0057 задним числом: новая реализация и
её индекс получат собственное решение.

### Предварительно перечислить и обрабатывать файлы пакетами

Отклонено для первого среза. Оно даёт процент по файлам, но многократно
запускает Git, усложняет argv/pathspec на трёх ОС и может стоить дороже одного
обхода. К варианту можно вернуться только после измерения, не меняя публичный
progress-контракт.

## Проверка

Реализация начинается с падающих тестов:

1. корпус с числом совпадений больше limit полностью дочитывается, возвращает
   лучшие K и точный total;
2. позднее более сильное совпадение вытесняет раннее слабое из bounded top-K;
3. память зависит от K и диагностических пределов, а не числа строк stdout;
4. heartbeat появляется во время медленного потока без фиктивного процента;
5. timeout возвращает нижнюю границу и никогда не становится `empty`;
6. отмена и timeout завершают и reap-ят всё дерево процесса на поддерживаемых
   ОС;
7. invalid UTF-8, malformed row, код 1 без совпадений и ошибочный exit
   различаются;
8. живой Sendbox подтверждает полный обход, точный total, bounded payload и
   отсутствие 500-миллисекундного искусственного отказа.

## Архитектурное влияние

Работа меняет полноту, ранжирование и семантику timeout реализации роли
`lexical`, поэтому требует отдельного ADR-0057. Решение не нормирует RLM,
`bsl-analyzer`, общий MCP progress или межпоставщицкое ранжирование.
