# План правок конвейера под 3–7 параллельных сессий

## Задача

Разработку ведут несколько сессий ИИ одновременно, каждая своим pull
request, вливание идёт через очередь слияния. Конвейер должен давать сигнал
по PR быстро, вливать без сторожа, не пропускать ложного зелёного и не
терять результаты молча. План отвечает на три вопроса: что менять, в каком
порядке и как понять, что стало лучше.

Источник: два независимых ревью 07.09.2026 и замеры по прогонам
05–07.09.2026. Замысел площадки —
[2026-09-04-test-pipeline-platform-design.md](2026-09-04-test-pipeline-platform-design.md).

## Что есть сейчас

Организация на плане GitHub Free: 20 параллельных джоб, macOS не больше 5.
Очередь слияния: до пяти сборок сразу, вливание по одному, стратегия
`ALLGREEN`. За три дня площадки: очередь 18 из 18 зелёных, push в `main`
29 из 31, PR красные в 3 % завершённых, около 15 вливаний в день одной
сессией.

| Прогон | Стена | Минуты ubuntu | Минуты macOS | Самая долгая джоба |
| --- | --- | --- | --- | --- |
| PR, тёплый кэш | 5,5 мин | 7,3 | 4,4 | Rust на macOS, 4,4 мин |
| Очередь | 8,9 мин | 13,8 | 5,9 | Python, 8,0 мин |
| Push в `main` | 9,5 мин | 13,9 | 8,4 | Rust на macOS, 8,4 мин |

Семь сессий с push раз в полчаса и семью вливаниями в час дают около 460
минут раннеров в час: в среднем 8 параллельных джоб при лимите 20, но около
160 минут macOS в час при пяти параллельных — первый потолок. Путь от push
до вливания сегодня около 15 минут, его задают macOS в PR-гейте и
однопоточный Python в очереди.

Шаг тестов nextest лежит на пределе процессора: на macOS сумма длительностей
502 с на три ядра даёт 167 с при 143–168 с на деле, на ubuntu 396 с на
четыре ядра — 99 с при 101–128 с. Больше потоков не дадут ничего;
компиляция в той же джобе занимает больше самих тестов.

## Критерии

Считались при каждой сборке сайта скриптом `scripts/ci/pipeline_metrics.py`
из `gh run list`, вливаний и трендов Allure за скользящее окно в четырнадцать
дней и публиковались на странице «Конвейер» рядом с отчётом; таблица ниже —
снимок на день плана. Пороги остаются целями плана. *Снято 08.09.2026:*
страница и скрипт удалены, замер по требованию — см.
[2026-09-08-main-push-after-queue-design.md](2026-09-08-main-push-after-queue-design.md).

| Критерий | Сейчас | Цель | Откуда |
| --- | --- | --- | --- |
| Сигнал PR, медиана и 90-й процентиль | 5,5 мин | 4 и 6 мин | прогоны `pull_request` |

## Шаги

Правило то же, что у площадки: у каждого шага один предмет, свой способ
доказать эффект и своя цена ошибки.

| № | Шаг | Что меняется | Как проверяется | Что может сломаться | Объём |
| --- | --- | --- | --- | --- | --- |
| 1 | Починки второго ревью | Гейт закрывается на джобе вне таблицы ожиданий; подпись прогона пишется первым шагом Rust-джобы, до clippy; ночь не пересылает отменённый прогон и не пишет по нему память; ручной и ночной запуск получают свою группу `concurrency`; cron уходит с круглой минуты; страж пинов принимает любой пробел перед комментарием и падает на строке, которую не смог разобрать; стражи на строковые связи: имя джобы Rust ↔ `collect-results.py`, шаблон артефактов ↔ сайт, профили ворот ↔ профили сайта, версия nextest в `.config/nextest.toml` | Стражи и проверка мутациями; ручной ночной запуск проходит и пишет память | Ничего: поведение зелёных прогонов не меняется | малый, один PR |
| 2 | Две полосы | На `pull_request` матрица Rust — только ubuntu; метка `ci:full` возвращает полную матрицу; очередь, push и ручной запуск не меняются. Замысел площадки получает заметку: класс ошибок `#[cfg]` ловит очередь, цена — одна выкидка вместо красного `main` | Медиана сигнала PR по десяти следующим PR не выше 4 мин; нарочно сломанный `#[cfg]` в PR зеленеет на PR и краснеет в очереди | Ошибки платформы всплывают позже, в очереди; доля выкидок под наблюдением | малый |
| 3 | Python параллельно | В очереди и на `main` наборы Python идут отдельными джобами матрицы, по одной на набор; артефакт на набор; ожидания гейта и сбор результатов знают новые имена | Джоба Python в очереди не дольше 4 мин; сводка сайта показывает те же счётчики Python | Имена джоб — таблица гейта и `collect-results.py`; шаг 1 делает рассинхрон красным | малый–средний |
| 4 | План для Python | `run-unittest.py` выписывает состав до запуска, сбор дописывает недошедшие тесты Python `skipped` с причиной, как для Rust | Тест: частичные результаты Python дают `skipped` по плану; обрыв джобы на проде виден в отчёте, а не пропадает | Ничего: план без результатов только добавляет записи | средний |
| 5 | Кэш компиляции крейтов | `sccache` с хранилищем в кэше GitHub поверх кэша зависимостей; замер холодного и тёплого прогона на одном коммите; остаётся, если сборка тестов ускоряется не меньше чем на треть | Шаг сборки тестов на macOS с 137 с и на ubuntu с 99 с — до и после | Общий предел кэша 10 ГБ: вытеснение кэша зависимостей; ключи и размер под наблюдением | малый плюс замер |
| 6 | Метрики конвейера | Скрипт считает критерии из таблицы выше, ночь кладёт `data/metrics.json`, сайт рисует страницу «Конвейер» | Числа на странице совпадают с ручным запросом `gh`; страница обновляется ночью | Ничего: только чтение | средний |
| 7 | Правила сессии | В `AGENTS.md`: после открытия PR — `gh pr merge --auto`; перед постановкой в очередь при отставании от `main` по горячим файлам — подтянуть `main` и перегенерировать индекс реестра; один документ замысла на тему PR | Страж не нужен: правило процесса | Ничего | док |
| 8 | Репетиция релиза | Когда открыта релизная линия v0.13 — rc-тег на ней: `action-gh-release`, стадия маркетплейса, дым опубликованного плагина, при этом каталог не двигается | Все джобы публикации зелёные, `gate` маркетплейса отвечает «предвыпуск, не продвигать» | Всплывут дефекты релизных шагов, не проверенных после переделки — это и цель | процесс |

Зависимости: 1 → 3, потому что шаг 3 переименовывает джобы, а шаг 1 делает
незнакомую джобу красной. 3 → 4. Шаги 2, 5, 7 независимы. Шаг 6 после 2 и
3, чтобы мерить уже новую форму. Шаг 8 — когда появится линия.

## Чего в плане нет

- **Вынос релиза в отдельный workflow.** Скорости не даёт: релизные джобы на
  PR пропускаются за секунды. Это вопрос формы, его стоит поднимать, когда
  понадобится отдельная репетиция контура по кнопке или файл станет
  неудобен. Цена — два агрегатных гейта и дублирование классификации.
- **Сайт реже.** Пересборка стоит три минуты ubuntu и никого не блокирует;
  собирать реже — потерять точки истории без экономии.
- **Пересылка результатов очереди на сайт вместо прогона `main`.** Сняла бы
  22 минуты раннеров на вливание и сократила путь до отчёта, но требует
  доверия к `merge_group` как источнику и своей линии в подписи. После шага
  2 нагрузка этого не требует; возвращаться, если критерий минут на
  вливание не сойдётся.
- **Стратегия очереди `HEADGREEN`, крупные раннеры, отказ от коммита
  `arch/index.md`.** Первое не нужно при четырёхкратном запасе очереди,
  второе недоступно на плане Free, третье — отдельное решение по реестру.

## Открытые вопросы

1. **Порог выкидок из очереди после двух полос.** Если ошибки `#[cfg]`
   окажутся частыми, вернуть macOS на PR для правок под `crates/*/platform`
   по классификации, а не по метке. Решается по метрике шага 6 через две
   недели.
2. **Место метрик.** Страница сайта или файл в репозитории; сайт — единственная
   память результатов, и метрики логично держать там же.
