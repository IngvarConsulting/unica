# Логическая связка источников, события и обработчика подписки

## Задача

Действующий контракт умеет менять `EventSubscription.Source`, но рассматривает
его изолированно как описание типа XML. Это неверная граница: платформа выбирает
событие из событий источника, а обработчик — по событию и сигнатуре. Синтаксически
допустимый `v8:Type` ещё не является возможным источником подписки.

Нужно сделать редактируемой и проверяемой одну итоговую связку
`Source -> Event -> Handler`, не добавляя шестой вариант операции и не перенося
матрицу совместимости в форматный парсер.

## Установленные факты платформы 8.3.27

Исследование выполнено по точной справке и импорту платформы 8.3.27.2074, а
также по корпусу из 305 реальных `EventSubscription`.

1. Справка описывает 41 класс источника и 183 варианта сигнатур событий.
   Источниками служат классы прикладных объектов, менеджеров и наборов записей,
   а не произвольные варианты `TypeDescription`.
2. Имя `Event` в XML — точное каноническое английское имя с учётом регистра,
   например `BeforeWrite`. `beforewrite` и `ПередЗаписью` платформа отвергает.
3. Для нескольких источников допустимы только события, существующие у каждого
   источника. Одного совпадения имени недостаточно для безопасного вызова:
   сигнатуры события у всех источников также должны совпасть.
4. Обработчик находится в `CommonModule`, является экспортной процедурой,
   модуль имеет `Global=false` и `Server=true`, а число параметров процедуры
   равно числу параметров события плюс один параметр `Source`.
5. Импорт XML не является достаточным оракулом. Платформа импортирует, например,
   одну подписку на `BeforeWrite` для объекта справочника и набора записей
   регистра, хотя этим источникам требуется разное число параметров обработчика.
6. В реальном корпусе встречаются конкретные объекты, менеджеры, наборы записей,
   `SequenceRecordSet`, `RecalculationRecordSet`, общие `v8:TypeSet` классов и
   `DefinedType`. Прямых примитивов и ссылочных типов как рабочих источников в
   корпусе нет.
7. `DefinedType` не является готовым классом события: его `Properties/Type`
   нужно развернуть в составляющие порождённые типы и пересечь их события.

Отдельное уточнение после повторного чтения реализации: текущий валидатор уже
проверяет существование экспортной процедуры. Проблема уже не в одном только
поиске модуля, а в неточном текстовом поиске процедуры и отсутствии проверки её
AST-сигнатуры и флагов общего модуля.

## Выбранная граница слоёв

### Домен

Новый модуль `domain/metadata/event_subscription.rs` владеет профильным
логическим каталогом:

- классами источников событий 8.3.27;
- точными каноническими именами событий;
- сигнатурой каждого события;
- чистой проверкой совместимости множества классов, события и обработчика.

Каталог не содержит XML QName, пространств имён или путей файлов. Профиль
8.3.27 выбирается явно, поэтому последующее изменение платформы не переписывает
старую матрицу молча.

Домен принимает уже доказанные факты: классы источников, точное имя события и
описание процедуры обработчика. Он возвращает типизированные диагностики и не
читает workspace.

### Application

Существующий вызов строит весь итоговый post-image, собирает доказательства его
зависимостей и только затем проверяет связку. Валидация не зависит от порядка
операций внутри одного запроса: источник, событие и обработчик можно изменить
одним атомарным вызовом в любом порядке.

Один и тот же путь выполняется для `dryRun` и применения. Неуспешная проверка
не строит публикуемого плана и не пишет файлы.

### Infrastructure

Форматный слой `xml_model.rs` только разбирает и выпускает wire-факты
`Source`, `Event` и `Handler`. Он не решает, какое событие допустимо для типа.

Инфраструктурный адаптер:

1. разрешает логические цели в точном `sourceSet`;
2. читает зарегистрированные описатели и порождённые типы;
3. разворачивает `DefinedType` с защитой от циклов;
4. читает флаги общего модуля;
5. находит точную процедуру через существующий BSL AST parser;
6. передаёт нормализованные факты доменной проверке;
7. связывает точные байты всех использованных описателей и модулей с той же
   транзакцией, что и описатель подписки.

Регулярное выражение или `contains` не становятся вторым парсером BSL.

## Публичный JSON-контракт

Число и имена пяти вариантов `op` не меняются. `Source` остаётся отношением, а
`Event` и `Handler` становятся строковыми свойствами только для
`EventSubscription`.

Полная атомарная правка выглядит так:

```json
{
  "sourceSet": "main",
  "metadataPath": "EventSubscription.BeforeWriteProducts",
  "operations": [
    {
      "op": "editRelations",
      "relation": "source",
      "mode": "replace",
      "targets": [
        {
          "kind": "manager",
          "metadataPath": "Catalog.Products"
        }
      ]
    },
    {
      "op": "setProperties",
      "values": {
        "Event": "FormGetProcessing",
        "Handler": "CommonModule.EventHandlers.OnFormGetProcessing"
      }
    }
  ]
}
```

`Handler` принимает только каноническую трёхчастную форму
`CommonModule.<Module>.<Procedure>`. Двухчастный legacy-вариант не принимается
новой мутацией.

### Цели отношения `source`

Публичное закрытое объединение содержит только логические источники событий:

| `kind` | Поля | Смысл |
| --- | --- | --- |
| `object` | `metadataPath` | порождённый объект конкретного объекта метаданных |
| `manager` | `metadataPath`; для `Constant` также `sourceClass` | менеджер или value-manager конкретного объекта метаданных |
| `recordSet` | `metadataPath` | набор записей регистра, последовательности или перерасчёта |
| `definedType` | `metadataPath` | определяемый тип, разворачиваемый до классов источников |
| `family` | `sourceClass` | общий класс всех источников данного вида, который платформа хранит как `v8:TypeSet` |

`sourceClass` — закрытое lower-camel-case перечисление доменного каталога, а не
произвольный XML QName. Например, семейство всех объектов справочников
выражается как `{"kind":"family","sourceClass":"catalogObject"}`.

У константы один логический `metadataPath` порождает два разных платформенных
класса с разными событиями. Поэтому только для
`{"kind":"manager","metadataPath":"Constant.<Name>"}` поле `sourceClass`
обязательно и принимает `constantManager` или `constantValueManager`. Для любого
другого `manager` это поле запрещено: его класс однозначно выводится из корня
адреса.

Варианты `string`, `number`, `boolean`, `date`, `valueStorage` и `reference`
удаляются из мутационного контракта: они описывают форму `TypeDescription`, но
не доказывают класс, у которого можно выбрать событие.

Конкретный перерасчёт адресуется логически как
`CalculationRegister.<Register>.Recalculation.<Name>`. Это точечное расширение
канонического адреса метаданных, а не передача wire-имени
`RecalculationRecordSet`.

### Граница адресуемости

Каталог событий полон для установленных 41 классов платформы, но конкретная
мутация возможна только там, где Unica умеет доказать владельца по логическому
адресу. Текущий реестр не содержит корня `ExternalDataSource` и его вложенной
топологии. Поэтому:

- общие семейства из каталога могут быть представлены, если им не нужна
  конкретная зависимость;
- конкретный источник `ExternalDataSource` не принимается как `metadataPath`;
- существующая такая подписка не подменяется похожим типом: `meta.info`
  возвращает диагностику неподдержанной адресации;
- поддержка конкретных `ExternalDataSource` требует отдельного решения о
  топологии адресов и регистрации объектов.

Объявить все 41 класса редактируемыми сейчас было бы ложным контрактом. Передача
сырого QName эту логическую дыру только скрыла бы.

## Правила итоговой связки

Валидным является только полный итоговый post-image:

1. `Source` непуст и каждая цель разрешается ровно в один или несколько
   event-capable классов.
2. `Event` непуст, записан точным каноническим именем 8.3.27 и существует у
   каждого класса источника.
3. Сигнатуры события у всех классов источника совпадают. Совпадение только
   имени события недостаточно.
4. `Handler` непуст, каноничен и разрешается в том же точном владельце
   конфигурации или расширения.
5. Общий модуль имеет `Global=false`, `Server=true`.
6. Точная процедура существует, является `Procedure`, помечена `Export` и
   имеет `eventParameterCount + 1` параметров.
7. Все факты, прочитанные для этих решений, входят в optimistic-concurrency
   guard транзакции.

Пустой `Source`, ранее разрешённый как форматная операция очистки, больше не
является допустимым финальным состоянием мутации подписки. Существующий
неполный или некорректный объект можно прочитать с диагностикой, но нельзя
опубликовать заново без исправления всей связки.

## Разворачивание `DefinedType`

`DefinedType` разрешается в том же `sourceSet`, его описатель и регистрация
связываются с транзакцией. Каждый прямой член `Properties/Type` преобразуется в
доменный класс источника. Вложенный `DefinedType` разворачивается рекурсивно с
множеством посещённых адресов.

Пустой тип, цикл, отсутствующий описатель, примитив, ссылочный тип или иной член
без событий делает цель непригодной. Такие члены не отбрасываются молча, иначе
фактическое множество значений было бы шире проверенного множества источников.

## Диагностики и чтение

Диагностика указывает публичную часть запроса:

- `relations.source[i]` — неадресуемая цель или класс без событий;
- `properties.event` — неизвестное, неканоническое или несовместимое событие;
- `properties.handler` — неверная ссылка, модуль, процедура или сигнатура.

Сообщение дополнительно называет класс источника, ожидаемую сигнатуру и
наблюдаемую сигнатуру, но машинная маршрутизация не зависит от текста.

`unica.meta.info` возвращает `Event` и `Handler` в свойствах и логические цели
в `relations.source`. Синтаксически читаемый, но логически неподдержанный wire
источник не становится разрешённой целью мутации: результат содержит
диагностику и `ok: false` по действующему fail-closed контракту чтения.

## Рассмотренные альтернативы

### Матрица в `xml_model.rs`

Отклонена: XML определяет представление, но не совместимость источника, события
и процедуры. Такой выбор снова позволил бы application обойти правило другим
писателем.

### Принимать любые QName, которые импортирует платформа

Отклонена: импорт не проверяет совместимость сигнатур и уже доказанно принимает
опасную связку.

### Отдельный инструмент выбора события

Отклонена: создаёт параллельную публичную поверхность и не защищает прямой
`meta.edit`. Каталог может позднее использоваться для подсказок, но сама
мутация обязана валидировать итоговое состояние.

### Проверять только число параметров процедуры

Отклонена как недостаточная: без `Global=false`, `Server=true`, точного имени,
`Procedure` и `Export` обработчик не соответствует контракту подписки.

## Проверка реализации

1. Доменный table-test закрепляет 41 класс и 183 варианта сигнатур, точный
   регистр событий, пересечение событий и конфликт сигнатур.
2. Schema/parser tests закрепляют пять `op`, новые `Event`/`Handler`, закрытое
   объединение целей и отказ от примитивов/ссылок.
3. Integration tests проверяют единый атомарный вызов, manager-событие,
   record-set событие, `DefinedType`, семейство, перерасчёт и rollback при
   изменении любой зависимости.
4. BSL tests проверяют точное имя, `Procedure`/`Function`, `Export`, арность,
   `Global` и `Server` без текстового `contains`.
5. Корпус платформы содержит положительные случаи
   `CatalogManager + FormGetProcessing` и
   `InformationRegisterRecordSet + BeforeWrite` с трёхпараметрическим
   обработчиком, а также отрицательные случаи регистра события, несовместимого
   класса и разных сигнатур.
6. Старый fixture с двухпараметрическим обработчиком для
   `InformationRegisterRecordSet.BeforeWrite` исправляется: его успешный импорт
  доказывал только слепую зону importer, а не корректность подписки.
