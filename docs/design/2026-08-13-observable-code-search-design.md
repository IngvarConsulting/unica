# Наблюдаемый нейтральный к поставщику поиск кода

## Контекст

`unica.code.search` уже запускает `RLM`, `bsl-analyzer` и `git-grep`
параллельно, но до завершения вызова не сообщает вызывающей стороне, какой
поставщик работает, строит состояние или перестал отвечать. Для модели это
неотличимо от зависания. Короткий таймаут резервного поставщика из PR #469
уменьшает время молчания, но не решает отсутствие наблюдаемого жизненного цикла
и выбрасывает полезную работу только ради раннего ответа.

Публичный результат дополнительно закрепляет имена реализаций как смысл секций.
Это заставляет потребителя знать, чем отличаются `rlm`, `bsl-analyzer` и
`git-grep`, и делает замену движка изменением пользовательской модели. Попадание
несёт путь, хотя следующие предметные инструменты принимают `sourceSet` и
`metadataPath`; модели приходится вызывать `unica.source.locate` или угадывать
адрес по раскладке Platform XML.

Проблемы свежести RLM и полного резервного поиска связаны с общим вызовом, но не
являются одним архитектурным выбором. Первая принадлежит состоянию индексного
поставщика, вторая — реализации буквального поставщика. Они вынесены в
ADR-0056 и ADR-0057 и не нормируются этой запиской.

## Цель

Сохранить один вызов `unica.code.search`, который проверяет одну логическую
область, запускает три роли поиска параллельно, сообщает их ход через стандартные
MCP progress notifications и возвращает один окончательный типизированный ответ.
Модель должна понимать, что продолжается, что уже закончено и насколько полна
каждая секция, не опрашивая отдельный job/status API и не разбирая особенности
конкретного движка.

## Выбранный подход

### Стабильные роли вместо имён реализаций

Реестр поиска содержит ровно по одному поставщику для трёх закрытых ролей:

- `semantic` — индексный поиск по смыслу и связям кода;
- `symbol` — поиск по синтаксической и символьной модели;
- `lexical` — лексический поиск по исходному тексту.

Текущие реализации соответственно имеют идентификаторы `rlm`,
`bsl-analyzer` и `git-grep`. Роль определяет смысл секции и её порядок;
идентификатор сообщает происхождение и может измениться при замене реализации.
Модель принимает решения по роли, `matchKind`, полноте и типизированному статусу,
а не по строке поставщика.

Внутренняя граница имеет следующую форму:

```rust
pub trait SearchProvider: Send + Sync {
    fn id(&self) -> ProviderId;
    fn role(&self) -> SearchRole;
    fn search(
        &self,
        request: &SearchRequest,
        context: &CodeIntelligenceContext,
        progress: &dyn SearchProgressSink,
        deadline: ProviderDeadline,
        cancellation: &CancellationToken,
    ) -> ProviderSearchSection;
}
```

Реестр отклоняет отсутствие роли и две реализации одной роли. Оркестратор не
ветвится по `ProviderId`: специфичные фазы поставщик проецирует в общие
`preparing`, `searching` и `ranking`, сохраняя необязательный стабильный
`detailCode` для диагностики.

### Логическая область входа

Публичный запрос принимает:

```json
{
  "cwd": "/workspace",
  "sourceSet": "main",
  "metadataPath": "CommonModule.Exchange.Module",
  "query": "ОтправитьСообщение",
  "limit": 20
}
```

В каноническом входе `sourceSet` обязателен. Необязательный `metadataPath`
ограничивает поиск доказанной целью или её предметным поддеревом.
Приложение разрешает адрес один раз, до запуска работников, и передаёт всем один
`CodeIntelligenceContext`. Неизвестный набор, неверный адрес или выход за
рабочее пространство отказывают всему вызову и не запускают поставщиков.

Адаптер каждого поставщика обязан либо передать ему доказанный физический
корпус как нативное ограничение, либо отфильтровать все кандидаты по тому же
`CodeIntelligenceContext` до ранжирования и подсчёта. Поставщик, для которого
общую область нельзя доказанно соблюсти, завершает свою секцию ошибкой
`unsupportedScope`; он не расширяет поиск до всего рабочего пространства.
Поэтому три секции отвечают про одну область, даже если внутренние интерфейсы
движков различаются.

`sourceDir` сохраняется на ограниченный миграционный период как альтернативный
старый вход. Вызов обязан передать ровно один из `sourceSet` и `sourceDir`;
логический селектор никогда не откатывается к пути после ошибки. Снятие моста
выполняется отдельным изменением после обновления видимых скиллов и приёмочных
клиентов.

### Логическая область выхода

Каждое попадание использует принятую ADR-0021 закрытую алгебру местоположения.
Доказанный модуль возвращает:

```json
{
  "location": {
    "kind": "addressed",
    "sourceSet": "main",
    "metadataPath": "CommonModule.Exchange.Module",
    "targetKind": "module"
  },
  "range": {"startLine": 42, "endLine": 42},
  "symbol": {"name": "ОтправитьСообщение", "kind": "procedure"},
  "matchKind": "symbol",
  "snippet": "ОтправитьСообщение(Параметры);",
  "providerScore": 0.91
}
```

Файл зарегистрированного набора, для которого нет доказанного адреса
метаданных, возвращается как
`{kind: "unaddressable", sourceSet, ownerMetadataPath?, path}`. `path`
относителен к набору и является наблюдаемым местоположением, а не идентичностью;
абсолютные пути не сериализуются. Только `addressed`-попадание можно без
промежуточной локализации передать следующему предметному инструменту.

### Прогресс

Application layer принимает транспортно-нейтральный `SearchProgressSink`.
Поставщики публикуют в него снимки общего состояния, а MCP-адаптер переводит их
в `notifications/progress` только при наличии `progressToken` в `_meta`
запроса. Синхронная часть не вызывает `rmcp`: адаптер использует ограниченный
канал и отдельный асинхронный отправитель. Переполнение канала объединяет
промежуточные снимки и сохраняет последний; отказ отправки не меняет результат
поиска.

Используемый `rmcp 2.2.0` уже представляет `_meta` вызова,
`ProgressNotificationParam.meta` и `RequestContext.peer.notify_progress`.
Следовательно, адаптер собирается на типизированном API SDK и не возвращает в
код собственный JSON-RPC loop.

Поле MCP `progress` равно числу терминальных ролей, `total` равно трём.
Типизированное состояние помещается под ключом `_meta`
`io.unica/searchProgress`:

```json
{
  "schemaVersion": 1,
  "elapsedMs": 4200,
  "deadlineMs": 300000,
  "nextUpdateWithinMs": 2000,
  "providers": [
    {
      "role": "semantic",
      "provider": "rlm",
      "state": "running",
      "phase": "preparing",
      "detailCode": "buildingIndex",
      "resultsFound": 0
    }
  ]
}
```

Уведомление отправляется при старте, смене фазы, терминальном переходе и не
реже одного раза в две секунды, пока остаётся работа. Повторный heartbeat может
сохранять число завершённых ролей, но обновляет `elapsedMs`, состояние и
`nextUpdateWithinMs`. Процент не выдумывается. Поставщик добавляет
`completedUnits` и `totalUnits` только когда обе величины измерены одним
процессом.

### Параллельность, срок и отмена

После общей проверки три работника получают общий момент начала и запускаются до
ожидания первого результата. Вызов ждёт терминального состояния каждой роли.
Скомпилированный общий срок равен 300 секундам: измеренный холодный RLM требует
около 203 секунд, поэтому прежние 120 секунд не допускают штатный первый ответ.
По умолчанию каждый поставщик получает остаток общего срока без более короткого
скрытого бюджета; файловая политика может задать отдельный меньший срок явно.

По истечении общего срока незавершённая секция становится `timedOut`. Отмена
MCP имеет приоритет, отменяет всех работников и не возвращает частичный успех.
Неотзывчивый работник учитывается существующим ограничителем допуска и не может
создать неограниченное число фоновых потоков или процессов.

### Окончательный результат

Финальный `data` содержит `coverage` со значениями `complete`, `partial` или
`none` и три секции в порядке ролей. Секция содержит роль, происхождение,
терминальный `status`, `searchComplete`, `elapsedMs`, попадания и счёт:

```json
{
  "role": "lexical",
  "provider": "git-grep",
  "status": "ok",
  "searchComplete": true,
  "elapsedMs": 4380,
  "matches": {"returned": 20, "total": 143, "relation": "exact"},
  "hits": []
}
```

`matches.relation` равно `exact`, `lowerBound` или `unknown`; отдельный boolean
не заставляет модель угадывать смысл отсутствующего total. `empty` допустим
только при `searchComplete: true` и точном нуле. `timedOut` может нести
ограниченные уже доказанные попадания, но обязан иметь
`searchComplete: false` и `lowerBound`. Общий `ok` истинен, когда хотя бы одна
роль доказанно выполнила поиск или вернула явно неполные попадания; `coverage`
отдельно не позволяет принять частичный ответ за полный.

## Рассмотренные альтернативы

### Отдельные `search.start`, `search.status` и `search.result`

Отклонены. Они дают долговременное состояние, но требуют от модели хранить
идентификатор задания, выбирать частоту опроса и делать дополнительные вызовы.
Поиск ограничен одним MCP-соединением и общим сроком, поэтому стандартное
уведомление прогресса решает наблюдаемость без нового публичного инструмента.

### Только текстовые heartbeat-сообщения

Отклонены. Текст удобен человеку, но модель не может устойчиво различить роль,
терминальность, полноту и число найденных результатов. `message` остаётся
кратким представлением типизированной `_meta`, а не единственным контрактом.

### Публиковать попадания в progress

Отклонено. Ранние top-K могут измениться после ранжирования, повторяют большой
payload и вынуждают потребителя сливать версии. Progress сообщает состояние и
счётчики; единственный авторитетный набор попаданий приходит в финале.

## Проверка

Реализация начинается с падающих тестов, которые доказывают:

1. три fake-поставщика переходят стартовый барьер до ожидания и финал всегда
   сохраняет порядок ролей;
2. MCP-вызов с progress token получает первый снимок не позднее 250 мс и не
   остаётся без heartbeat дольше двух секунд;
3. вызов без token не отправляет уведомления и возвращает тот же результат;
4. отмена прерывает работников и не публикует частичный успех;
5. `timedOut`, `empty`, точный и нижний счёт сериализуются без двусмысленности;
6. `addressed`-местоположение каждого доказанного BSL-попадания принимается
   следующим логическим инструментом без `unica.source.locate`, а физический
   кандидат без доказанного адреса остаётся `unaddressable`;
7. поставщик с более широким внутренним корпусом не возвращает, не ранжирует и
   не считает кандидаты вне общего `metadataPath`, а неподдерживаемая область
   даёт `unsupportedScope`, а не неявный поиск всего workspace;
8. замена fake-реализации одной роли не меняет схему, порядок и оркестратор.

## Архитектурное влияние

Работа меняет публичные аргументы и результат `unica.code.search`, добавляет
прогресс открытого MCP-вызова и переносит стабильный смысл секции с реализации
на роль. Выбор принадлежит ADR-0055. При принятии он заменяет для операции
поиска пункты 2, 3, 4 и 6 ADR-0017 в части порядка секций, идентичности,
оркестрации и эпистемики; общая нейтральная граница, локальность оценок и запрет
публичного выбора поставщика сохраняются. Он также заменяет в пункте 6
ADR-0040 скомпилированные значения общего срока поиска и более коротких сроков
`RLM` и `git-grep` на один 300-секундный срок; файловая модель, приоритеты и
возможность явного уменьшения срока из ADR-0040 сохраняются. При реализации обе
исторические записи получают пометку `Обновлено`, а выведенные записи реестра
меняются тем же коммитом.
