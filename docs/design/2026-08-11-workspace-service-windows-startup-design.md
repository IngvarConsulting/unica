# Исправление запуска workspace-service на больших Windows-workspace

## Контекст

Issue #339 воспроизводится в Unica 0.11.0 на Windows для всех потребителей
workspace-service: `unica.code.diagnostics`, `unica.code.graph` и RLM-backed
поиска. После отказа остаётся `service.lock`, файлы stdout/stderr пусты, а
`service.json` отсутствует.

Сквозное воспроизведение отделило платформенную причину от симптома конкретного
инструмента. На малом source root тот же релизный `unica.exe` успешно публикует
`service.json` и отвечает на ping. На source root из 20 000 объектов вызов
завершается `workspace service did not become ready`, оставляя тот же набор
артефактов, что в пользовательских отчётах.

Причина находится в порядке инициализации. Сервис привязывает localhost и
пишет `service.json`, затем синхронно вычисляет fingerprint всего source root в
`WorkspaceServiceRuntime::new`, и только после этого входит в accept-loop.
Родитель даёт readiness handshake не более пяти секунд. На большом дереве ping
не обслуживается в этот срок, родитель завершает ещё исправный дочерний процесс
и удаляет принадлежащий ему `service.json`. В логах нет ошибки, потому что
дочерний процесс не падал.

## Требования

1. Readiness workspace-service не зависит от размера source root: после
   публикации записи сервис должен начать обслуживать ping без полного обхода
   исходников.
2. Fingerprint остаётся обязательным перед допуском первой операции анализатора
   или RLM и продолжает защищать повторно используемые сессии от устаревших
   исходников.
3. Если дочерний процесс действительно завершился до readiness, вызывающая
   сторона получает exit status и доступный хвост stderr, а не только путь к
   отсутствующему `service.json`.
4. Пятисекундный startup budget, общий 120-секундный срок запроса, публичная
   MCP-поверхность и формат `service.json` не меняются.
5. `service.lock` остаётся постоянным файлом OS advisory lock. Его наличие после
   завершения процесса не означает удерживаемую блокировку; удалять его нельзя,
   поскольку удаление создаёт риск двух независимых inode/lock-объектов.

## Рассмотренные подходы

### 1. Ленивая инициализация fingerprint — выбран

Начальные поколения анализатора и RLM хранят состояние «ещё не наблюдалось».
Конструктор runtime не обходит source root. Первый рабочий запрос вычисляет
fingerprint в пределах общего срока операции, фиксирует его как наблюдаемое
поколение и только затем запускает или переиспользует поставщика.

Подход устраняет зависимость readiness от размера дерева, сохраняет текущую
модель свежести и не вводит новый поток или протокол состояния.

### 2. Увеличить startup timeout — отклонён

Больший фиксированный срок только сдвигает границу отказа и заставляет ping
ждать работу, которая не относится к готовности транспорта. На сетевых дисках
или более крупных конфигурациях дефект вернётся.

### 3. Вычислять fingerprint фоновым заданием при старте — отклонён

Понадобились бы отдельные фазы инициализации, синхронизация рабочих запросов с
фоновым заданием и правила отмены. Для требуемого поведения это лишнее: первый
рабочий запрос уже имеет срок и токен отмены, внутри которых можно выполнить
обход.

## Проект решения

### Ленивая модель поколения

`WorkspaceServiceRuntime` хранит для анализатора и RLM `Option<u64>` вместо
обязательного начального `u64`. `None` означает, что сервис ещё не наблюдал
source root. Конструктор создаёт runtime с двумя значениями `None` и не вызывает
`source_generation`.

Перед операцией соответствующего поставщика сервис вычисляет текущее поколение
и атомарно сравнивает его с наблюдаемым:

- при `None` сохраняет первое поколение без объявления несуществующей сессии
  устаревшей;
- при совпадении сохраняет текущую сессию;
- при изменении поколения или явной инвалидации забирает и завершает старую
  сессию, затем сохраняет новое поколение.

Для RLM проверки готовности индекса до и после исполнения продолжают
использовать поколение, вычисленное на границе конкретной операции. Изменяется
только момент первого вычисления, а не критерий свежести.

### Диагностика раннего завершения

После неуспешного readiness wait менеджер до принудительной уборки проверяет
состояние дочернего процесса. Если процесс уже завершился, ошибка включает его
exit status и ограниченный хвост `service.stderr.log`. Если процесс всё ещё
жив, сообщение фиксирует, что readiness завершился неуспешно, а дочерний процесс
к этому моменту продолжал работать. Истечение startup budget упоминается только
тогда, когда исходная readiness-ошибка была таймаутом; затем существующая bounded
cleanup завершает и reap-ит дерево процесса.

Хвост лога ограничен константой, читается best effort и не заменяет исходную
причину при ошибке чтения. stdout в ошибку не включается: служебные ошибки уже
направляются в stderr, а смешивание протокольного/произвольного вывода усложнит
диагностику без пользы для этого дефекта.

### Граница блокировки

Механизм `fs2` и содержимое `service.lock` не меняются. Файл служит постоянной
точкой advisory locking, а PID внутри него описывает последнего владельца
попытки запуска и не является доказательством живого дочернего сервиса.
Уборка по-прежнему удаляет только `service.json`, если PID и token доказывают
владение породившего процесса.

## Проверки

Работа выполняется по TDD:

1. Падающий unit-тест закрепляет, что новый runtime начинает с ненаблюдаемыми
   поколениями и первый рабочий boundary инициализирует поколение без ложной
   инвалидизации; до исправления конструктор вычисляет fingerprint немедленно.
2. Падающий тест раннего завершения запускает короткоживущий дочерний fixture,
   пишет маркер в stderr и требует увидеть exit status и маркер в startup
   error; до исправления возвращается только общий readiness timeout.
3. Существующие тесты повторного использования, инвалидации, смены поколения,
   bounded cleanup и сохранения replacement record должны остаться зелёными.
4. Windows-интеграционный тест `issue_89_workspace_service` и целевые unit-тесты
   `workspace_services`/`platform::process` выполняются на текущей ветке.
5. Сквозное воспроизведение с релизным runtime повторяется на исправленном
   `unica.exe`: большой source root должен пройти readiness; дальнейший вызов
   может завершаться предметной ошибкой анализатора, но не startup timeout.

## Архитектурное влияние

Новая запись решения не нужна. Публичные инструменты, аргументы и результаты не
меняются; владение кешем, событиями, упаковкой и платформенными фасадами также
сохраняется. Исправление восстанавливает уже принятые требования ADR-0018 и
`INV-APP-LAZY-HIDDEN-SERVICES`: скрытый сервис лениво запускается для выбранного
workspace/source root и становится доступным как внутренний транспорт до
дорогой работы поставщика.

## Вне области

- файловый fallback для `unica.code.search` вне Git-репозитория (#211/#275);
- изменение жизненного цикла постоянного `service.lock` (#204);
- ускорение самого `source_generation`;
- изменение startup или request deadlines;
- публикация новых диагностических полей в публичном MCP-контракте.
