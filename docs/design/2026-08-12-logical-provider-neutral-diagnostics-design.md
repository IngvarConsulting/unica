# Логическая и нейтральная к поставщику диагностика

## Статус архитектурных решений

Основной публичный контракт принадлежит ADR-0061. С ним связаны
три атомарные записи:

- ADR-0060 сохраняет отдельно типизированную готовность RLM;
- ADR-0062 определяет композицию поставщиков диагностик;
- ADR-0063 определяет явный режим миграции читателя.

Все четыре записи приняты вместе с реализацией: ADR-0060, ADR-0061 и ADR-0062
совместно заменяют ADR-0045, а ADR-0063 заменяет ADR-0049. Номера сверены с
фактической вершиной целевой ветки перед слиянием.

## Проблема

Текущий вызов `unica.code.diagnostics` выбирает физический корень и режим
анализатора:

```json
{
  "name": "unica.code.diagnostics",
  "arguments": {
    "cwd": "<workspace>",
    "sourceDir": "src",
    "mode": "analyze"
  }
}
```

Находка возвращает путь выгрузки:

```json
{
  "kind": "diagnostic",
  "path": "src/CommonModules/Доки_Обработка/Ext/Module.bsl",
  "code": "UnusedLocalMethod",
  "severity": "warning",
  "message": "Неиспользуемый локальный метод \"Проверка\"",
  "range": {
    "startLine": 0,
    "startColumn": 10,
    "endLine": 0,
    "endColumn": 18
  }
}
```

Путь объясняет, какой файл прочёл конкретный процесс, но не является
идентичностью объекта 1С. Агенту приходится угадывать обратное соответствие с
`CommonModule.Доки_Обработка.Module`. Та же логическая цель будет иметь другую
физическую ручку в другом формате исходников.

Одновременно будущая диагностика может приходить от BSL LS, валидатора
метаданных или другого инструмента. Некоторые находки указывают не на код, а на
объект, его свойство, реквизит или реквизит табличной части. Контракт первого
анализатора не должен стать публичной моделью всех источников.

После первоначального согласования дизайна PR #478 принял общий доменный
`SourceLocation`, а зонтичная задача #481 зафиксировала две дополнительные
границы: поставщик не выбирается публичным входом, а точечный запрос якорится на
одном `sourceSet`, хотя разрешённая dependency closure результата в будущем
может содержать несколько наборов. Этот документ использует принятый
`SourceLocation` и оставляет topology, brokers и coverage отдельным срезом #481.

## Цели

1. Выбирать диагностику логическим `sourceSet + metadataPath`.
2. Возвращать самодостаточные плоские элементы, по которым агент может перейти
   к цели без знания раскладки файлов.
3. Поддержать один или несколько независимых поставщиков с видимым
   происхождением и частичным отказом.
4. Представить проблемы кода и метаданных одной моделью местоположения и
   фокуса.
5. Оставить физические URI и пути диагностируемых ресурсов внутри адаптеров,
   кроме явно маркированного безопасного наблюдения для неадресуемого ресурса.
   Общий `cwd` сохраняется как контекст выбора рабочего пространства и не
   является адресом диагностируемой цели.
6. Сделать регистрацию BSL LS, metadata-validator и последующих поставщиков
   расширением внутреннего реестра без нового входного selector-а и без нового
   типа местоположения. Роли, topology и coverage могут совместимо расширить
   общий результат отдельным решением #481.

## Неграницы первого PR

- Реальный BSL LS и поставщик проверки метаданных не подключаются.
- `MetadataAddress` не расширяется реквизитами, свойствами и табличными
  частями.
- Остальные `unica.code.*` не мигрируют.
- Межпровайдерная дедупликация и динамические сторонние плагины не вводятся.
- Низкоуровневая поверхность `unica.source.*` не меняет wire-контракт.
- `WorkspaceTopologyResolver`, provider-specific brokers, multi-source
  dependency closure и `CoverageAggregator` остаются работами #481. В первом
  PR разрешённая область диагностики содержит только якорный `sourceSet`.

## Рассмотренные варианты

### Публичный контракт одного анализатора

Сохранить upstream-действия и добавить к каждой находке вычисленный адрес.
Вариант дешевле сейчас, но `mode`, конфигурация и форма ответа первого движка
останутся публичным долгом. BSL LS снова потребует менять схему.

### Единый семантический фасад

Один `unica.code.diagnostics` публикует действия Unica, общий запрос, общий
элемент и секции поставщиков. Частные адаптеры преобразуют свои ответы во
внутренние наблюдения. Это выбранный вариант: он сохраняет одну точку входа и
делает происхождение явным без привязки к транспорту.

### Отдельный публичный инструмент на поставщика

Каждый источник получает свой `unica.code.*`. Это упрощает адаптеры, но
перекладывает объединение, таймауты и частичный успех на агента и раздувает
публичную поверхность. Вариант отклонён.

## Публичный запрос

### Общие поля

- `action` — обязательное `analyze | findings | status | catalog` без значения
  по умолчанию;
- `cwd` — необязательный абсолютный путь к корню рабочего пространства; это
  общий контекст MCP-вызова, он не заменяет `sourceSet`, не адресует цель и не
  возвращается в диагностическом результате;
- `sourceSet` — обязательное точное имя набора исходников;
- `filter` — необязательный строгий объект;
- `limit` — общий предел `1..=200`, по умолчанию `200`.

Публичного selector-а поставщика нет. План исполнения выводится внутренним
router-ом из действия, вида цели, зарегистрированных возможностей и разрешённой
области. ID `bsl-language-server` появится одновременно с реальным адаптером, а
не заранее; в первой реализации зарегистрирован только `bsl-analyzer`.

### Матрица действий

| Действие | Назначение | Допустимые поля |
| --- | --- | --- |
| `analyze` | одноразовый полный анализ `sourceSet` | `filter.minSeverity`, `filter.codes`, `limit`, `timeoutSeconds` |
| `findings` | текущие находки одной точной логической цели | `metadataPath`, `filter`, `range`, `limit` |
| `status` | готовность резидентных моделей | — |
| `catalog` | возможности и правила поставщиков | `filter.codes`, `limit` |

`metadataPath` обязателен у `findings` и запрещён у остальных действий.
`range` разрешён только для модуля. `timeoutSeconds` является общим бюджетом
`analyze`, а не параметром процесса конкретного поставщика.

`findings` выбирает ровно одну разрешённую цель. Для объекта метаданных в неё
входят свойства и неадресуемые внутренние элементы, представленные через
`focus.metadata`; самостоятельно адресуемая форма, команда, макет или модуль
является другой целью и в ответ владельца не включается.

Пример:

```json
{
  "action": "findings",
  "sourceSet": "main",
  "metadataPath": "CommonModule.Доки_Обработка.Module",
  "filter": {
    "minSeverity": "warning",
    "codes": [
      {
        "provider": "bsl-analyzer",
        "code": "UnusedLocalMethod"
      }
    ]
  },
  "range": {
    "startLine": 0,
    "startColumn": 0,
    "endLine": 100,
    "endColumn": 0
  },
  "limit": 200
}
```

### Фильтр кодов и внутренний план

Router планирует всех применимых поставщиков в каноническом порядке реестра.
`filter.codes` фильтрует нормализованные правила и наблюдения после исполнения;
он не является selector-ом поставщика и не меняет публичную семантику секций.
Безопасный pushdown в адаптер допустим только как внутренняя оптимизация, если
сохраняются те же секции, счётчики, полнота и ошибки. Неизвестный код допустим и
даёт пустую выборку, неизвестный provider namespace отклоняется схемой.
`selection.providers` сообщает фактически построенный внутренний план в порядке
реестра, но не принимается во входе.

Идентичность правила — пара `provider + code`. Строка с разделителем не
используется, потому что двоеточие может быть частью собственного кода.

Старые `mode`, `sourceDir` и `path` отсутствуют в схеме, но перехватываются до
обычной ошибки неизвестного аргумента как `legacy_target_removed`. Остальные
снятые поля не остаются скрытым контрактом.

## Каноническая выборка

Результат материализует разрешённые значения, включая умолчания:

```json
{
  "selection": {
    "sourceSet": "main",
    "metadataPath": "Catalog.Номенклатура",
    "targetKind": "metadataObject",
    "providers": ["metadata-validator"],
    "filter": {
      "minSeverity": "warning",
      "codes": []
    },
    "limit": 200
  }
}
```

`targetKind` не принимается из запроса и не доверяется поставщику. Его выводит
Unica: отсутствие `metadataPath` у полного анализа означает `sourceRoot`,
чётная арность адреса — `metadataObject`, допустимый терминал нечётной арности
— `module`.

## Местоположение и фокус

`location` отвечает на вопрос «к какой логической цели перейти», `focus` —
«что именно внутри неё подсветить».

Поле `location` имеет принятый в #478 общий тип `SourceLocation`, который уже
используют навигация и поиск. Обе его ветви совпадают по Rust-типу и wire-форме;
параллельного `DiagnosticLocation` нет. Специфичная для диагностик закрытая
причина неадресуемости публикуется соседним полем `locationReason` элемента, а
не расширяет общий location DTO. Поле обязательно при `unaddressable` и
запрещено при `addressed`.

### Адресуемая цель

Адресуемая ветвь совпадает с моделью логической цели ADR-0021 и не содержит
физического пути:

```json
{
  "kind": "addressed",
  "sourceSet": "main",
  "metadataPath": "Catalog.Номенклатура",
  "targetKind": "metadataObject"
}
```

### Неадресуемое наблюдение

Неадресуемая ветвь разрешена только для ресурса, безопасно нормализованного
внутри разрешённой области диагностики. В первом PR эта область содержит
только выбранный `sourceSet`:

```json
{
  "location": {
    "kind": "unaddressable",
    "sourceSet": "main",
    "ownerMetadataPath": "Catalog.Номенклатура",
    "path": "Catalogs/Номенклатура/Ext/Unknown.xml"
  },
  "locationReason": "resourceNotAddressable"
}
```

`path` всегда относительный и использует `/`. URI или путь за пределами
разрешённой области, другой диск и выход через `..` не становятся находкой:
адаптер получает `location_outside_scope`, вся секция поставщика получает `failed`, её
находки отбрасываются, а публичный ответ не раскрывает исходный путь.
Закрытые причины первой версии: `resourceNotAddressable`, `ownerUnproven` и
`sourceFormatUnsupported`.

### Код

```json
{
  "kind": "sourceRange",
  "range": {
    "startLine": 5,
    "startColumn": 4,
    "endLine": 5,
    "endColumn": 14
  }
}
```

### Метаданные

Свойство владельца:

```json
{
  "kind": "metadata",
  "elementPath": [],
  "property": "Synonym",
  "language": "ru"
}
```

Реквизит табличной части:

```json
{
  "kind": "metadata",
  "elementPath": [
    {
      "collection": "tabularSections",
      "name": "Товары"
    },
    {
      "collection": "attributes",
      "name": "Цена"
    }
  ],
  "property": "Type"
}
```

Коллекции и свойства являются каноническим словарём Unica. Частный XPath или
имя поля поставщика не проходит границу. Пустой `elementPath` означает свойство
самой цели. Если свойство отсутствует, путь обозначает элемент целиком. Если
даже элемент не доказан, используется `{ "kind": "target" }`.

## Применимость поставщиков

`findings` разрешает логическую цель до запуска поставщика. Внутренний план
включает только поставщиков, объявивших действие и вычисленный `targetKind`.
Публично навязать неприменимого поставщика нельзя; `unsupported` остаётся
терминальным статусом для несовпадения заявленной capability с фактическим
ответом адаптера.

В первой реализации автоматический запрос `findings` по `metadataObject` даст
`no_applicable_provider`, потому что реального метаданного поставщика ещё нет.

## Status и catalog

`status` сообщает готовность выбранного `sourceSet`, а не успешность
предыдущего вызова:

```json
{
  "action": "status",
  "selection": {
    "sourceSet": "main",
    "providers": ["bsl-analyzer"]
  },
  "state": "completed",
  "complete": true,
  "providers": [
    {
      "id": "bsl-analyzer",
      "status": "completed",
      "version": "0.2.62",
      "readiness": {
        "state": "ready",
        "retryable": false
      }
    }
  ]
}
```

Состояния готовности diagnostics: `notStarted`, `building`, `ready`, `stale`.
Успешно прочитанное `building` не является ошибкой вызова status.

`catalog` возвращает возможности и ограниченный список правил:

```json
{
  "action": "catalog",
  "selection": {
    "sourceSet": "main",
    "providers": ["bsl-analyzer"],
    "filter": {
      "codes": []
    },
    "limit": 200
  },
  "state": "completed",
  "complete": true,
  "providers": [
    {
      "id": "bsl-analyzer",
      "status": "completed",
      "version": "0.2.62",
      "capabilities": {
        "actions": ["analyze", "findings", "status", "catalog"],
        "findingsTargetKinds": ["module"],
        "emitsFocusKinds": ["sourceRange"]
      },
      "itemsTotal": 1,
      "itemsReturned": 1,
      "truncated": false
    }
  ],
  "itemsTotal": 1,
  "itemsReturned": 1,
  "truncated": false,
  "items": [
    {
      "kind": "diagnosticRule",
      "provider": "bsl-analyzer",
      "code": "UnusedLocalMethod",
      "defaultSeverity": "warning",
      "title": "Неиспользуемый локальный метод"
    }
  ]
}
```

`description` и `tags` правила необязательны. Каталог сортируется по порядку
поставщиков, затем по `code`.

## Полнота и ошибки

Статус секции описывает исполнение, `complete` — покрытие области:

- `completed` — поставщик выполнил чтение и может иметь находки;
- `empty` — поставщик доказал отсутствие находок;
- `unsupported` — действие или вид цели не поддерживается;
- `unavailable` — реализация отсутствует или модель пока не готова;
- `failed` — поставщик запускался, но не дал пригодного результата.

Матрица общего исхода:

- все выбранные поставщики успешны и полны — `completed`, `complete=true`;
- есть полезный результат, но другой источник неуспешен или неполон —
  `partial`, `complete=false`, `ok=true`;
- ни один источник не дал полезного результата — `failed`, `complete=false`,
  `ok=false`;
- отмена имеет приоритет, отменяет всех и не публикует частичные элементы.

`truncated` не меняет `complete`: анализ мог быть полным, хотя вызывающий
запросил первые 200 элементов.

Ошибка одного ресурса является отдельным элементом:

```json
{
  "kind": "resourceFailure",
  "provider": "bsl-analyzer",
  "location": {
    "kind": "addressed",
    "sourceSet": "main",
    "metadataPath": "CommonModule.Печать.Module",
    "targetKind": "module"
  },
  "error": {
    "code": "source_decode_failed",
    "message": "Source is not valid in the detected encoding",
    "retryable": false
  }
}
```

`resourceFailure` входит в `itemsTotal`, но не считается диагностикой. Его
полное число остаётся в `resourceFailures`, даже если общий `limit` скрыл сам
элемент. Обычная находка с `unaddressable` не уменьшает полноту: это полезное
наблюдение и одновременно сигнал нарушения целостности проекта.

Неготовая модель у `findings` возвращает секцию `unavailable` с
`provider_not_ready` и `retryable=true`; устаревшие находки не выдаются.

Ошибки формы или семантики запроса возникают до запуска поставщиков. Они несут
стабильный код, сообщение, `retryable=false` и, когда применимо, имя поля.
`legacy_target_removed`, `target_kind_mismatch`, неизвестный provider namespace
в `filter.codes` и `no_applicable_provider` различаются программно и не
определяются поиском текста сообщения.

## Фильтрация и порядок

- Провайдер может применить фильтр заранее, но координатор повторяет его после
  нормализации.
- Диапазон запроса обязан быть упорядоченным и непустым. Он полуоткрытый;
  `sourceRange` включается при
  пересечении; `focus.target` и `resourceFailure` выбранного модуля не
  скрываются диапазоном.
- `itemsTotal` считается после фильтров и до `limit`.
- Счётчик поставщика `itemsReturned` равен числу его элементов, попавших в
  общий усечённый массив.
- Автоматической межпровайдерной дедупликации нет.
- Сортировка учитывает логическое местоположение, фокус, реестровый порядок
  поставщика, вид элемента, код и сообщение. Для `unaddressable` ключом служит
  относительный `path`; для metadata-focus — весь `elementPath`, затем
  свойство и язык.

## Архитектура

### DiagnosticProviderRegistry

Реестр хранит поставщиков в стабильном порядке и публикуемые возможности. В
первом PR зарегистрирован только `bsl-analyzer`. Тестовые подмены BSL LS и
metadata-validator проверяют расширяемость, не попадая в live-схему.

### DiagnosticProvider

Поставщик объявляет descriptor и обслуживает поддержанные действия. Он
возвращает внутренний `DiagnosticObservation`, который может нести уже готовую
логическую цель, относительный физический ресурс или URI. Публичный JSON
поставщик не формирует.

### DiagnosticLocationMapper

Единый mapper:

1. проверяет готовые логические адреса;
2. нормализует URI или относительный путь внутри разрешённой области;
3. использует тот же доказательный механизм, что `unica.source.locate`;
4. вычисляет `targetKind`;
5. строит `addressed` или безопасный `unaddressable`;
6. нормализует диапазон либо metadata-focus.

Путь с другого диска, выход за корень и абсолютная ручка вне разрешённой
dependency closure не проходят mapper и не сериализуются. Пока topology из
#481 не подключена, closure состоит только из якорного `sourceSet`.

### DiagnosticCoordinator

Координатор выполняет:

```text
parse request
→ resolve sourceSet and optional metadataPath
→ build internal applicable-provider plan
→ execute independently
→ normalize locations and observations
→ reapply filters
→ stable sort
→ global limit
→ typed public result
```

Поставщики получают связанные дочерние токены отмены. Сбой, паника или срок
одного исполнителя превращаются в его секцию и не роняют сервер. Общая отмена
не публикует частичный набор.

### Состояние

Резидентное состояние получает закрытую provider-specific identity. Она обязана
как минимум изолировать worktree и разрешённую модель исходников, но не
фиксируется общей парой `workspaceRoot + sourceRoot`: analyzer в будущем
использует topology fingerprint, BSL LS — root leases, RLM — собственную
root/session identity. Текущий адаптер одного `sourceSet` может временно
использовать нормализованный корень как частную реализацию.

`analyze` может использовать одноразовый процесс. `findings` читает текущую
резидентную модель, `status` сообщает её готовность, `catalog` может быть
статическим или предоставленным той же сессией.

Текущий JSONL-парсер перестаёт собирать публичный JSON и возвращает
типизированный результат адаптера `bsl-analyzer`. Закрытая грамматика событий,
проверка итоговых счётчиков и ограничение строки остаются инфраструктурными
защитами.

## Тестовая стратегия

Работа выполняется по TDD: каждый новый контракт сначала закрепляется падающим
тестом на текущем коде.

### MCP-контракт

- дискриминированная схема требует `action` и `sourceSet`;
- каждая ветвь публикует только исполнимые параметры;
- вложенные объекты запрещают неизвестные поля;
- старые поля отсутствуют в schema, но три целевых поля дают
  `legacy_target_removed`;
- provider namespace внутри `filter.codes` содержит только live-регистрацию;
  отдельного входного selector-а поставщика нет.

### Домен и координатор

- внутренний план применимых поставщиков без публичного selector-а;
- все статусы, partial success и all-failed;
- фильтрация точной пары `provider + code`;
- отсутствие дедупликации;
- стабильный порядок, totals и общий `limit`;
- независимый таймаут, паника поставщика и отмена без частичной публикации.

### Логические местоположения

- корень, объект, вложенная форма и модуль;
- вычисление `targetKind` и невозможность его подмены поставщиком;
- свойство владельца, реквизит и реквизит табличной части;
- деградация недоказанного элемента до `focus.target`;
- `unaddressable` только с относительным наблюдением;
- абсолютный путь отсутствует в публичном диагностическом результате; входной
  `cwd` остаётся только контекстом выбора рабочего пространства.

### Адаптер BSL Analyzer

- JSONL преобразуется во внутренние наблюдения;
- `analyze` логически адресует каждую находку;
- `findings` получает физический ресурс только после разрешения
  `metadataPath`;
- ошибка файла становится `resourceFailure`;
- повреждённый поток и неверные итоги дают `failed`, а не чистый анализ.

### Windows

- обратные слеши, Unicode и пробелы;
- `file:///C:/...` и регистр буквы диска;
- другой диск и путь вне разрешённой области;
- `.` и `..` без выхода за корень;
- только `/` в относительном `path`.

### Расширяемость

Подменный BSL-LS-поставщик отдаёт URI и получает тот же
`addressed + sourceRange`. Подменный метаданный поставщик отдаёт логическую цель
и `metadata` focus. Их регистрация не меняет запрос, общий `SourceLocation` или
`focus`; отдельные работы #481 могут совместимо добавить роли и coverage в
общий результат, а #484 — расширить грамматику адресуемых модулей.

Сквозная Platform XML фикстура проверяет главный сценарий: запрос по
`sourceSet + metadataPath` возвращает диагностику без физического пути и с
логическим переходом. Тот же тест исполняется на Windows CI.

## Миграция

| Старый вызов | Новый вызов |
| --- | --- |
| `mode=analyze`, `sourceDir` | `action=analyze`, `sourceSet` |
| `mode=file`, `path` | `action=findings`, `sourceSet + metadataPath` |
| `mode=status` | `action=status`, `sourceSet` |
| `mode=catalog` | `action=catalog`, `sourceSet` |
| `mode=workspace` | `analyze` для полного набора либо `status` + `findings` по логическим целям |
| `codes[]` | `filter.codes[{provider, code}]` |
| `minSeverity` | `filter.minSeverity` |
| `rangeStart/rangeEnd` | строгий объект `range` |
| `config`, `format`, `detail`, `maxFiles` | сняты без публичной замены |

Миграционная таблица попадает в README пакета и заметки к релизу. Скилл
`code-diagnostics` использует только новый запрос.

## Граница первого PR

Один самостоятельно проверяемый PR меняет один публичный инструмент и включает:

- доменные DTO наблюдений, фокуса, секций и запроса;
- переиспользование общего `SourceLocation` из #478 и соседний
  `locationReason` только у диагностических элементов;
- реестр, координатор и mapper;
- адаптер `bsl-analyzer` и изменение JSONL-проекции;
- `tools()`, строгие схемы, дескрипторы операций и live-ведомость;
- скилл, README, release notes, ADR и выведенные инварианты;
- модульные, контрактные, интеграционные и Windows-тесты.

BSL LS и диагностика метаданных остаются последующими независимыми PR. Если
их регистрация соблюдает ADR-0061 и ADR-0062, она не требует нового решения;
topology, brokers, roles и coverage принадлежат отдельным решениям #481.

## Атомарность решений

Разделение специально оставляет независимые оси изменений:

- готовность RLM меняет только ADR-0060;
- логический адрес, focus или действия diagnostics — ADR-0061;
- агрегация, происхождение и partial success — ADR-0062;
- режим миграции читателей — ADR-0063.

Добавление соответствующего контракту поставщика является данными реестра, а
не причиной переписывать одно из решений.
