# `unica.check` выбирает валидаторы по виду узла

Решение: `DEC.2026-09-03.CHECK-INFERS-VALIDATORS`.

## Почему профили сняты

Профиль `filter.validation.profile` появился в катовере 31 августа как
механический перевод старых `*.validate`: `cf.validate` → `profile: cf` и
так далее. Соответствие профиля виду узла в коде было жёстким
(`accepts_kind`), а неверный выбор отвечал «pick the profile of `at`» —
Unica знала ответ и всё равно требовала его от вызывающего. Две настоящие
развилки вычислимы из данных: расширение отличается от конфигурации видом
набора в `v8project.yaml`, схема компоновки от табличного макета —
`TemplateType` дескриптора.

## Как устроено теперь

1. `execute_check` читает узел через `view` и берёт его `kind`.
2. `node_facts` добавляет вид набора (`EXTENSION`) и, для макета, вид по
   дескриптору (`Templates/<Имя>.xml`), потому что проекция называет вид
   только для схемы компоновки (ветка `DataSet`).
3. `plan_for_node` возвращает закрытый список шагов; шаги исполняются по
   порядку, вердикты складываются: `status: passed`, если прошли все.
4. Валидатор получает селектор из адреса (`validator_selector`):
   `{sourceSet, metadataPath}` плюс `ExtensionPath` для `cfe` и `CIPath`
   для `interface`. Ничего из этого не приходит с провода.
5. Диагностика несёт `validator`; ответ несёт `validators`.

## Что изменилось на проводе

- Схема `unica.check`: только `at`; `filter` отвергается как неизвестный
  аргумент канонического вызова.
- Корпус приёмки: каждый шаг `check` над узлом замораживает `status` и
  `validators`; S230 замораживает отказ на `filter`, S266 — валидатор
  `interface` на узле `Subsystem.X.Interface`.

## Ограничения

- Валидатор `cfe` исполним, но в корпусе не заморожен: фикстуры расширения,
  которую открывает строгий порт чтения, пока нет.
- `meta` не запускается для ролей и подсистем: типизированный валидатор
  читает только дескрипторы объектов.
