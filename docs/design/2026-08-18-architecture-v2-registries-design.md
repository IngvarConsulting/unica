# Архитектура v2: как описывать решения, инварианты и контракты

## Зачем

Владелец разрешил пересмотреть все принятые инварианты и ADR и спроектировать
архитектуру заново, опираясь на опыт проекта. Повод — выделенные восемь
операций публичной поверхности: они не помещаются в описание, которое росло
под семьдесят один инструмент.

Масштаб накопленного на 18.08.2026: **71 ADR**, **128 инвариантов**, 5974
строки в `spec/architecture/`, из них монолитные `invariants.md` (1851) и
порождаемая `tool-surface.md` (1750). Плюс 88 тестовых методов в
`tests/ci/test_architecture_registry.py`, которые этот формат стерегут.

Требования владельца, дословно и без смягчения:

- все реестры, инварианты и ADR — **символические**;
- имя файла ADR **начинается с даты**;
- ADR **атомарны и очень просто написаны**, чтобы легко менять один на другой;
- накопленное **сохранить в историческом контексте**, но архитектуру
  переписать проще для поиска решений;
- **superpowers не мешает** архитектурным описаниям;
- **markdown с пропсами** для адресации и быстрого чтения.

## Что именно признаётся устаревшим — и что нет

Сброс объявляется для **слоя описания**, а не для добытого знания.

| Слой | Судьба | Почему |
| --- | --- | --- |
| `spec/decisions/` (71 ADR) | заморожен как история | решения принимались под другую поверхность |
| `spec/architecture/invariants.md` (128) | заморожен как история | монолит, выросший под 71 инструмент |
| `spec/architecture/*` — концепции, блоки, runtime | заморожено | описывают устройство v1 |
| Стражи архитектурного слоя (`test_architecture_registry`, `test_architecture_sync_guard`, `test_design_documents`) | недействительны вместе с реестрами | проверяют формат, которого больше нет |
| **Тесты поведения и формата** (большинство из 3226) | **остаются в силе** | проверяют правду о платформе 1С — порядок узлов, BOM, стиль перевода строки, вывод 8.3.27 — а не наши решения |

Разграничение существенное. Форматные тесты — это то самое накопленное знание,
которое #283 называет обязательством: полная пересборка артефакта теряет байты,
которые контракт обязан сохранить. Архитектура v2 нуждается в них сильнее, чем
v1: они становятся свидетельством новых контрактов, а не удаляются. Работа —
переатрибуция (какой контракт стережёт этот тест), не переписывание.

## Устройство: четыре дерева вместо одного

```
arch/                                  ← v2, единственный нормативный слой
  README.md                            ← как читать; двадцать строк, не больше
  index.md                             ← ПОРОЖДАЕТСЯ; одна строка на символ
  decisions/2026-08-18-<symbol>.md     ← один ADR = один файл
  invariants/<SYMBOL>.md               ← один инвариант = один файл
  contracts/<SYMBOL>.md                ← один контракт = один файл

spec/                                  ← v1, заморожен, читается как история
  STATUS.md                            ← дата заморозки и правило чтения

docs/design/, docs/plans/              ← планирование и разбор пути (superpowers)
```

**Почему новый корень, а не правка `spec/`.** Заморозка на месте оставляет v1
байт-в-байт как историю, не воюет с его же правилом «запись становится историей,
когда доходит до main», и даёт v2 собственного стража с первого дня — без 88
унаследованных утверждений под ногами. Перенос `spec/` в `history/` не делаем:
на его пути ссылаются `AGENTS.md`, тесты и скрипты, и переезд ломает их без
пользы.

**Одна оговорка к заморозке.** `spec/architecture/tool-surface.md` порождается
из бинаря и обслуживает действующий код. Заморозка не запрещает его
перегенерацию — она запрещает **ручные** правки `spec/`. Как только у ведомости
появляется замена в `arch/contracts/`, генератор переключается на неё.

## Символы

Одна схема на все три реестра: `<ВИД>.<ОБЛАСТЬ>.<ИМЯ>`, точки как разделитель —
тот же разделитель, что в именах инструментов, поэтому глазу не нужно
переключаться.

| Вид | Форма | Пример |
| --- | --- | --- |
| Решение | `DEC.<ГГГГ-ММ-ДД>.<ИМЯ>` | `DEC.2026-08-18.ADDRESS-GRAMMAR` |
| Инвариант | `INV.<ОБЛАСТЬ>.<ИМЯ>` | `INV.SURFACE.ONE-ADDRESS` |
| Контракт | `CTR.<ОБЛАСТЬ>.<ИМЯ>` | `CTR.WIRE.VIEW-RESULT` |

Дата в символе решения делает требование «имя файла начинается с даты»
истинным и для символа: `DEC.2026-08-18.ADDRESS-GRAMMAR` лежит в
`arch/decisions/2026-08-18-address-grammar.md`. Символ и путь выводятся друг из
друга, поэтому индекс не нужен для навигации — только для чтения.

Номера (`ADR-0070`) не переносятся: номер сообщает лишь очерёдность, а его
дефицит — единственная причина, по которой в v1 однажды появились два ADR с
одним номером.

## Пропсы: адресация в начале файла

Каждый файл всех трёх реестров открывается блоком props. Он машинно читается,
человеком просматривается, и в нём нет ничего, что можно вывести из текста.

**Решение** — `arch/decisions/2026-08-18-address-grammar.md`:

```markdown
---
id: DEC.2026-08-18.ADDRESS-GRAMMAR
status: active
supersedes: []
superseded-by: null
establishes: [INV.SURFACE.ONE-ADDRESS, CTR.ADDRESS.GRAMMAR]
issue: 548
---

# Адрес — чередование `Вид.Имя`

**Решение.** Адрес узла — полное имя 1С, где нечётный сегмент называет вид, а
чётный — имя; правило действует на любой глубине и на ветке тоже.

**Почему.** Платформа уже пишет так в RLS, правах и составе планов обмена —
модель знает синтаксис и новой грамматики не учит. Ветка как узел закрывает
перечисление одним правилом вместо частных случаев.

**Цена.** Вид узла перестаёт выводиться из одной чётности: нужен словарь
видовых токенов, иначе `Catalog.Валюты.Attribute` неотличим от модуля.
```

**Инвариант** — `arch/invariants/INV.SURFACE.ONE-ADDRESS.md`:

```markdown
---
id: INV.SURFACE.ONE-ADDRESS
status: active
decision: DEC.2026-08-18.ADDRESS-GRAMMAR
check: tests/arch/test_address_grammar.py::test_every_branch_is_addressable
scope: [wire, source]
---

Любой именуемый узел дерева метаданных достижим одним адресом, и никакая
операция не требует второго способа адресации.
```

**Контракт** — `arch/contracts/CTR.WIRE.VIEW-RESULT.md`:

```markdown
---
id: CTR.WIRE.VIEW-RESULT
status: active
version: 1
producer: unica.view
consumers: [host, unica.apply]
decision: DEC.2026-08-18.VIEW-SLOTS
check: tests/arch/test_view_contract.py
---

Ответ `view` несёт слоты `at`, `kind`, `title`, `props`, `branches`, `can`,
`limits`, `set`. Пустые слоты не сериализуются. `branches[].at` — адрес,
готовый к подстановке в следующий вызов.
```

**Инвариант против контракта** — граница, которой в v1 не было и из-за которой
ведомость поверхности лежала среди архитектуры:

- **инвариант** — правило, которое не должно молча сломаться; у него есть
  проверка и нет версии;
- **контракт** — форма наблюдаемого (провод, формат файла, конверт ответа); у
  него есть производитель, потребители и версия.

## Атомарность и заменяемость ADR

Три правила, и они же — то, что стражу легко проверить:

1. **Одно решение на файл.** Если в тексте два «решение», это два файла.
2. **Жёсткий потолок — 40 строк тела.** Всё, что длиннее, — это разбор пути, и
   его место в `docs/design/`, куда ADR ссылается ссылкой, а не пересказом.
3. **Никакого пересказа соседей.** Чужое решение упоминается символом. Тогда
   замена одного ADR другим не требует правки соседних файлов — ровно то
   свойство, ради которого атомарность и вводится.

Замена оформляется двумя строками props и ничем больше: у нового
`supersedes: [DEC.…]`, у старого `status: superseded` и
`superseded-by: DEC.…`. Текст старого не редактируется никогда — он остаётся
тем, что было решено на свою дату.

## Индекс: одна строка на символ

`arch/index.md` **порождается** скриптом из props и руками не правится:

```markdown
| Символ | Вид | Статус | Суть | Файл |
| --- | --- | --- | --- | --- |
| DEC.2026-08-18.ADDRESS-GRAMMAR | решение | active | адрес — чередование Вид.Имя | decisions/2026-08-18-address-grammar.md |
| INV.SURFACE.ONE-ADDRESS | инвариант | active | один адрес до любого узла | invariants/INV.SURFACE.ONE-ADDRESS.md |
| CTR.WIRE.VIEW-RESULT | контракт | active | слоты ответа view | contracts/CTR.WIRE.VIEW-RESULT.md |
```

Это и есть ответ на «быстрое чтение»: один файл, который целиком помещается в
контекст и по которому `rg` находит символ за один проход. Полный текст
читается только тогда, когда символ уже выбран.

## Граница superpowers

Правило одной строкой: **скиллы superpowers пишут в `docs/plans/` и
`docs/design/` и никогда в `arch/`.**

Формы документов, которые навязывают скиллы — заголовки `Goal` / `Architecture`
/ `Tech Stack`, чек-листы шагов, блоки «For agentic workers», — в `arch/` не
появляются: там свой формат, заданный выше. Обратная связь допустима и полезна:
план ссылается на символ решения, решение ссылается на разбор пути в
`docs/design/`.

Проверяется стражем `tests/arch/test_layer_boundary.py`: ни один файл `arch/`
не содержит маркеров superpowers, и ни один документ `docs/` не объявляет
символов реестра.

## Новые стражи вместо старых

`tests/arch/` — маленький набор, растущий вместе с реестром:

| Страж | Что проверяет |
| --- | --- |
| `test_registry_props.py` | props разбираются, обязательные поля на месте, символ совпадает с именем файла |
| `test_registry_links.py` | каждая ссылка на символ разрешается; `superseded-by` взаимен `supersedes` |
| `test_registry_checks.py` | путь в `check:` существует и содержит названный тест |
| `test_registry_index.py` | `index.md` совпадает с тем, что порождает скрипт |
| `test_registry_atomicity.py` | тело ADR ≤ 40 строк, ровно один блок «Решение» |
| `test_layer_boundary.py` | граница superpowers, и `spec/` не меняется руками после заморозки |

Восемьдесят восемь методов старого стража не переносятся: они стерегли форму,
которой больше нет.

## Порядок перехода

1. `spec/STATUS.md` объявляет v1 замороженным с датой; в `AGENTS.md` порядок
   источников истины переписывается на `arch/`.
2. `arch/` заводится с `README.md`, пустыми каталогами и первым стражем.
3. Восемь операций поверхности дают первые записи: решение о грамматике
   адреса, решение о слотах `view`, контракт ответа, контракт квитанции.
4. Старые стражи архитектурного слоя удаляются вместе с переключением
   `AGENTS.md`; поведенческие тесты не трогаются.
5. Дальше реестр наполняется **по мере принятия решений**, а не переводом 71
   старого ADR. Старая запись не портируется; когда её предмет всплывает в
   работе v2, пишется новое атомарное решение, которое может сослаться на
   архивную как на историю.

Пункт 5 — главный: перевод семидесяти одного ADR был бы проектом на недели и
воспроизвёл бы в v2 ту же плотность, от которой уходим. Пустой реестр,
наполняемый по потребности, — единственный способ получить «проще для поиска».

## Открытые вопросы

1. **Разделитель символа** — точка (`INV.SURFACE.ONE-ADDRESS`) против дефиса
   (`INV-SURFACE-ONE-ADDRESS`, как в v1). Точка предложена ради совпадения с
   именами инструментов; дефис дешевле для миграции упоминаний в коде.
2. **Область (`<ОБЛАСТЬ>`) — закрытый перечень или свободная?** Закрытый держит
   реестр от расползания, свободный не требует решения заранее.
3. **Судьба `spec/acceptance/` и `spec/provenance/`** — они не про архитектуру
   v1, а про свидетельства формата и происхождение заимствований. Возможно,
   они переезжают в `arch/contracts/` как свидетельства, а не замораживаются.
4. **Потолок в 40 строк** — назначен по опыту чтения v1, не измерен.
