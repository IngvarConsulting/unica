# Предметная поверхность `unica.meta.*`

## Результат проектирования

Публичная группа метаданных сокращается до четырёх предметных операций:

- `unica.meta.info` — один просмотр существующего объекта;
- `unica.meta.add` — создание одного объекта по внутреннему минимальному
  шаблону с необязательным атомарным массивом тех же операций, которые
  принимает `meta.edit`;
- `unica.meta.edit` — атомарное применение массива типизированных операций к
  одному объекту;
- `unica.meta.remove` — удаление одного объекта после анализа ссылок.

`unica.meta.compile`, `unica.meta.profile` и `unica.meta.validate` удаляются без
псевдонимов времени выполнения. Файловый Meta JSON DSL и строковая грамматика
`Operation + Value` также перестают быть публичными контрактами. Генерация XML,
индексное обогащение и валидация не исчезают: они становятся внутренними
частями четырёх оставшихся операций.

Проект меняет публичную MCP-поверхность, логические селекторы, контракт
мутаций и границы внутренних компонентов. Архитектурным выбором владеет
принятая запись ADR-0025; эта записка фиксирует путь к нему и нормативной
не является.

## Исходное состояние и противоречия

На baseline `35311f52` опубликованы шесть инструментов `unica.meta.*`.
Поверхность смешивает три разных модели:

- `unica.meta.info` уже выбирает существующий объект логически через
  `sourceSet + metadataPath`;
- `unica.meta.profile` отдельно читает индекс RLM через `sourceDir + name`;
- `unica.meta.compile`, `unica.meta.edit`, `unica.meta.remove` и
  `unica.meta.validate` принимают физические пути и общий словарь аргументов
  нативных XML/DSL-операций.

`unica.meta.compile` создаёт объект из внешнего JSON-файла, а
`unica.meta.edit` принимает либо второй JSON-файл, либо один из сорока глаголов
со строкой `Value`. Поэтому удаление одного `compile` не устранило бы внешний
DSL: тот же контракт остался бы внутри `edit`. Строки вида
`Сумма: Число(15,2) | req, index` сами являются языком, который MCP-схема не
может проверить до вызова.

`unica.meta.profile` не дублирует `unica.meta.info`: он добавляет модули, роли,
подписки, функциональные опции и предопределённые элементы. Простое удаление
инструмента потеряло бы эти сценарии. `unica.meta.validate` также выполняет не
только XML parse, но и проверяет UUID, обязательную структуру, свойства,
дочерние элементы, уникальность, ссылки и типоспецифичные ограничения.

Наконец, файл
`crates/unica-coder/src/infrastructure/native_operations/meta.rs` превышает
22 тысячи строк и одновременно содержит чтение, валидацию, компиляцию,
редактирование и удаление. Смена публичного контракта без выделения доменной
модели закрепила бы новый API поверх старых строковых ветвей.

## Цели

1. Дать модели четыре легко различимых действия: понять, создать, изменить и
   удалить объект метаданных.
2. Сделать точные операции независимыми от файловой раскладки поставщика.
3. Оставить один типизированный контракт редактирования вместо внешнего DSL и
   сорока строковых глаголов.
4. Не потерять индексное обогащение и диагностику при сокращении числа
   инструментов.
5. Сохранить preview, support guard, анализ ссылок, точные преобразы, атомарную
   публикацию, rollback и событие `MetadataChanged`.
6. Отделить доменную модель метаданных от Platform XML writer-а и RLM.
7. Сделать опубликованную MCP-схему достаточной для построения корректного
   вызова без знания проверок Rust runtime и вернуть результат как настоящий
   структурированный MCP-ответ.
8. Обеспечить симметрию чтения и записи: каждое успешно изменяемое свойство,
   поле коллекции и отношение наблюдается последующим `meta.info`.

## Неграницы

- Проект не меняет судьбу `*.compile`, `*.validate` и `*.decompile` в других
  группах инструментов.
- Проект не вводит универсальный JSON Patch, desired-state документ или
  низкоуровневую запись произвольного ресурса.
- Один вызов не создаёт и не изменяет несколько объектов метаданных.
- Читаемость нового формата источника не даёт ему capability записи
  автоматически.
- Проект не обещает совместимость со старыми именами инструментов, аргументов,
  операциями или файлами Meta JSON DSL.

## Рассмотренные варианты

### Переименовать `compile` и сохранить старый DSL

`meta.add` мог бы принять прежний `JsonPath`, а `meta.edit` — сохранить
`DefinitionFile` и сорок `Operation`. Это самый короткий переход, но он меняет
словарь, не меняя модель: ИИ по-прежнему конструирует внешний язык, который не
выражен схемой MCP. Вариант отклонён.

### Универсальные `add/update/remove` по строковому пути

Три операции в стиле JSON Patch дают маленькую схему, но строковый путь снова
скрывает тип цели, допустимые коллекции и предметные предусловия. Ошибка в пути
обнаруживается только внутри writer-а, а XML-структура становится частью
публичного знания модели. Вариант отклонён.

### Много узких MCP-инструментов

Отдельные инструменты для реквизитов, табличных частей, свойств и связей дали бы
самые простые локальные схемы. Цена — рост `tools/list`, больше ошибок выбора
инструмента и повторение общих гарантий мутации. Вариант отклонён.

### Четыре инструмента и компактная алгебра операций

Выбран один предметный контракт пяти типизированных видов операций. Его
используют `meta.edit` и необязательное поле `meta.add.operations`, поэтому
сложное создание остаётся одной транзакцией и не вводит второй язык описания.
Схема остаётся ограниченной, а доменные типы переиспользуются между
коллекциями, чтением и Platform XML writer-ом.

## Публичная поверхность

### `unica.meta.info`

Вход существующей точной цели:

```json
{
  "sourceSet": "main",
  "metadataPath": "Catalog.Номенклатура"
}
```

Локальная часть `data` сохраняет разрешённую цель, вид, имя, синоним,
поддержку, свойства, отношения (`owners`, `registerRecords`, `basedOn`,
`inputByString`), реквизиты, измерения, ресурсы, табличные части, значения
перечисления, формы, макеты и команды. Элементы коллекций наблюдаемо возвращают
изменяемые поля `type`, `required`, `fillValue`, а реквизиты табличных частей —
те же типизированные поля рекурсивно. Порядок массивов совпадает с порядком в
исходном дескрипторе.

Данные бывшего `meta.profile` входят в поле `related` с именованными секциями:

- `modules`;
- `roles`;
- `subscriptions`;
- `functionalOptions`;
- `predefinedItems`.

Каждая секция возвращает `status`, `freshness`, `total`, `returned`,
`truncated`, `items` и `diagnostics`. Ошибка или недоступность RLM не уничтожает
локальный ответ: секция получает `unavailable`. После мутации индексная секция
либо дожидается ограниченного обновления, либо явно отвечает
`freshness: "stale"`; устаревшие данные не выдаются за текущие.

Без `sections` вызов остаётся локальным и не запускает RLM. `modules`, `roles`,
`subscriptions`, `functionalOptions` и `predefinedItems` запрашиваются только
явно. `limit` ограничивает число элементов каждой индексной секции, по
умолчанию двадцать и не более пятидесяти; `total` и `truncated` сохраняют
наблюдаемую полноту. Локальная XML-структура не режется этим лимитом.

`meta.info` также запускает внутренний validator. Разбираемый, но семантически
некорректный объект возвращается вместе с `validation.status: "failed"` и
типизированными диагностиками. Полностью неразбираемый XML завершает вызов
ошибкой, потому что объектную структуру из него вывести нельзя.
Отсутствующий `FillValue` и `<FillValue xsi:nil="true"/>` означают отсутствие
значения. Пустой нетипизированный `<FillValue/>` значением не является: элемент
получает `incomplete: true`, а validation — диагностику вместо молчаливой
нормализации к `null`.

### `unica.meta.add`

Вход создания одного объекта верхнего уровня:

```json
{
  "sourceSet": "main",
  "kind": "Catalog",
  "name": "Номенклатура"
}
```

`kind` является enum доказанных внутренних шаблонов. Первый состав сохраняет
23 типа, которые поддерживает текущий Meta compiler. Шаблон выбирается по
формату и capability набора исходников; публичных `template`,
`templateVersion`, `JsonPath`, объекта определения и batch-режима нет.

Шаблон создаёт минимальный валидный объект: UUID, обязательные свойства,
`InternalInfo`, стандартные реквизиты, регистрацию у владельца и обязательные
вспомогательные ресурсы. Синоним выводится из имени единым внутренним правилом.
Необязательный непустой `operations` применяет к приватному образу шаблона ту
же закрытую алгебру, что `meta.edit`, до validation и публикации. Минимальное
создание по-прежнему не требует `operations`; сложное создание не оставляет в
источнике минимальный объект, если одна из операций неуспешна.

Существующий или частично зарегистрированный объект приводит к
`already_exists`; операция не является repair или upsert. Preview сообщает
канонический будущий `metadataPath`, ресурсы, регистрации и проверки. Apply
публикует весь доказанный post-image одной транзакцией.

### `unica.meta.edit`

Вход содержит существующую точную цель и непустой упорядоченный массив
`operations`:

```json
{
  "sourceSet": "main",
  "metadataPath": "Document.Заказ",
  "operations": [
    {
      "op": "setProperties",
      "values": {
        "NumberLength": 12,
        "CheckUnique": true
      }
    },
    {
      "op": "add",
      "collection": "tabularSections",
      "elements": [{"name": "Товары"}]
    },
    {
      "op": "add",
      "scope": {"tabularSection": "Товары"},
      "collection": "attributes",
      "elements": [
        {
          "name": "Количество",
          "type": {
            "variants": [
              {
                "kind": "number",
                "digits": 15,
                "fraction": 3,
                "sign": "nonNegative"
              }
            ]
          },
          "required": true
        }
      ]
    }
  ]
}
```

Пять видов операций:

| `op` | Назначение |
| --- | --- |
| `setProperties` | изменить свойства самого объекта |
| `add` | добавить элементы в коллекцию |
| `update` | изменить или переименовать существующие элементы |
| `remove` | удалить элементы |
| `editRelations` | добавить, удалить или заменить связи |

Коллекции первого контракта: `attributes`, `tabularSections`, `dimensions`,
`resources`, `enumValues`, `columns`, `forms`, `templates` и `commands`.
`scope.tabularSection` выбирает реквизиты внутри существующей табличной части.
Связи первого контракта: `owners`, `registerRecords`, `basedOn` и
`inputByString`; `editRelations.mode` принимает `add`, `remove` или `replace`.

Типы, позиции и ссылки структурны. Число задаётся полями `digits`, `fraction` и
`sign`; ссылочный тип — логическим `metadataPath`; составной тип — массивом
`variants`; позиция — объектом с одним из `before` или `after`. Публичный
контракт не принимает тип через строку, флаги через `|`, batch через `;;` или
XML-путь.

Операции применяются последовательно, и следующая видит результат предыдущей.
Весь массив образует одну транзакцию. `add` отказывает при совпадении имени,
`update` и `remove` — при отсутствии цели; неявного upsert нет. Ошибка одной
операции отменяет весь вызов и называет её `operationIndex`.

Публикуемая MCP-схема является закрытым discriminated union из пяти вариантов
через `oneOf`. Каждый вариант фиксирует своё значение `op`, обязательные поля и
`additionalProperties: false`; вложенные типы фиксируют условные варианты
позиции, типа, значения заполнения и ссылки. Application layer независимо
преобразует вход в закрытый enum `MetaEditOperation` и повторно проверяет
допустимую форму каждого варианта. Совместимость схемы доказывается реальными
`tools/list` в поддерживаемых клиентах, а не служит причиной публиковать форму,
принимающую заведомо неполные операции.

### `unica.meta.remove`

Операция принимает `sourceSet + metadataPath`, разрешает объект через того же
поставщика, проверяет поддержку и ссылки, удаляет payload и регистрацию и
очищает зависимые дескрипторы подсистем.

Обычный вызов отказывает при найденных ссылках. Принудительный apply требует
одновременно `force: true`, `confirm: true` и `dryRun: false`. Режима
«разрегистрировать, но оставить файлы» нет.

## Общий контур мутации

Для `add`, `edit` и `remove` действует один порядок:

1. MCP-аргументы преобразуются в доменные типы.
2. Разрешается `sourceSet`, формат и capability поставщика.
3. Открывается сессия источника и читаются точные снимки всех зависимостей.
4. В памяти строится полный post-image или план удаления.
5. Внутренний `MetadataValidator` проверяет post-image и зависимых владельцев.
6. Support/reference guards повторяются по фактическим зависимостям.
7. Preview возвращает план и не пишет источник или состояние workspace.
8. Apply повторно сверяет преобразы, публикует изменение, а затем сообщает
   `MetadataChanged` и его влияние на кеш.

Для `remove` validator проверяет оставшиеся регистрации, подсистемы и ссылки,
а не уже удалённый дескриптор. Ошибка восстановления опубликованных ресурсов
остаётся жёсткой ошибкой целостности.

## Ошибки и результаты

Четыре инструмента отвечают типизированным `OperationResult.data` без второго
представления в `stdout`. MCP `tools/list` публикует `outputSchema`, а
`tools/call` помещает тот же `OperationResult` в `structuredContent`; текстовый
content остаётся кратким сериализованным представлением для клиентов MCP,
которые его требуют. `OperationResult.ok: false` сопровождается
`isError: true`, но сохраняет структурированные диагностики и доступный
частичный `data`. Общий конверт сохраняется. Поле `diagnostics`
содержит записи со следующей формой:

```json
{
  "code": "validation_failed",
  "severity": "error",
  "message": "Attribute name is duplicated",
  "metadataPath": "Document.Заказ",
  "operationIndex": 2,
  "field": "elements[1].name"
}
```

Первый стабильный словарь кодов:

- `invalid_arguments`;
- `unsupported_kind`;
- `capability_unavailable`;
- `target_not_found`;
- `already_exists`;
- `support_locked`;
- `reference_conflict`;
- `validation_failed`;
- `concurrent_modification`;
- `provider_unavailable`;
- `rollback_failed`.

Диагностика не выдаёт физический путь за идентичность и не раскрывает
внутреннее имя поставщика. `rollback_failed` всегда означает, что целостность
дерева не доказана, и не понижается до предупреждения.

Preview мутации возвращает `effects` с видом действия, логической целью и
нормализованными `before`/`after`. Для `meta.edit` это ровно один эффект на
каждую входную операцию с `operationIndex` в исходном порядке. `meta.add`
всегда начинает массив эффектом `createTemplate` без `operationIndex`, с
`before: null` и `after: {kind, name}`, а затем добавляет эффекты переданных
операций с индексами `0..N`. `meta.remove` возвращает один эффект
`removeObject` без `operationIndex`: его `target` равен каноническому
`metadataPath`, `before` содержит доказанную разрешением идентичность
`{metadataPath, kind, name}`, `after` равен `null`. Полный XML в ответ не
включается.

## Внутренние границы

Изменение выделяет только те компоненты, которые нужны новой поверхности:

- `domain/metadata/` владеет `MetadataKind`, `MetadataType`,
  `ElementDefinition`, `MetaEditOperation`, ссылками, диагностикой и
  типизированными результатами;
- application service владеет выбором источника, capabilities, preview/apply,
  кеш-событием и общей последовательностью мутации;
- Platform XML provider владеет чтением XML, каталогом шаблонов и построением
  post-image;
- `MetadataValidator` остаётся внутренней переиспользуемой службой;
- RLM provider поставляет только секции `related`;
- publisher владеет точными преобразами, блокировками, атомарной заменой и
  rollback.

Исходный JSON MCP не передаётся writer-у. Infrastructure получает доменную
команду и закрытую физическую ручку. Разделение `meta.rs` выполняется по этим
границам и не становится общей переписью остальных native operations.

## Ломающая миграция

Переход выполняется одним переключением публичной поверхности:

| Старый контракт | Новый контракт |
| --- | --- |
| `meta.compile` | `meta.add` с необязательным `operations`; отдельный `meta.edit` для последующих изменений |
| `meta.profile` | `meta.info` с секциями `related` |
| `meta.validate` | `meta.info.validation` и внутренняя проверка мутаций |
| `ObjectPath` | `sourceSet + metadataPath` |
| `ConfigDir + Object` | `sourceSet + metadataPath` |
| `Operation + Value` | `operations[]` |
| `DefinitionFile` | удаляется |

Старые имена отсутствуют в `tools/list`; runtime не принимает их как скрытые
псевдонимы. Удаляются скиллы `meta-compile` и `meta-validate`, добавляется
`meta-add`, а `meta-info`, `meta-edit`, `meta-remove` и все вызывающие их скиллы
переписываются.

`plugins/unica/references/specs/meta-dsl-spec.md` и
`plugins/unica/skills/meta-edit/json-dsl.md` удаляются после переноса уникальных
фактов о Platform XML в действующие форматные спецификации и фикстуры.
Генератор и validator сохраняются как внутренний код; удаляются парсер и
публичное описание Meta JSON DSL.

## Форма реализации

Работа образует один связный PR и меняет публичный контракт один раз. Для
ревью она делится на проверяемые коммиты:

1. доменные типы, диагностика и внутренний validator;
2. разделение `meta.rs` без изменения поведения;
3. `meta.add` и внутренние шаблоны;
4. новый `meta.edit`;
5. объединённый `meta.info`;
6. логический `meta.remove`;
7. переключение поверхности и удаление DSL;
8. синхронизация документации, пакета и release migration note.

Параллельные дочерние PR не используются. Если работа потребует нескольких
последовательных PR, каждый следующий начинается только после слияния
предыдущего в `main`, а публичное переключение остаётся одним изменением.

## Приёмка

### Публичный контракт

- `tools/list` содержит ровно `unica.meta.info`, `unica.meta.add`,
  `unica.meta.edit` и `unica.meta.remove`;
- старые имена, пути и DSL-аргументы отсутствуют в схемах и runtime;
- схема `operations[]` реально преобразуется поддерживаемыми Codex и Claude
  Code, а не только проходит локальный JSON Schema validator;
- каждый вариант `operations[]` отклоняет неполную или чужую форму уже по
  опубликованной JSON Schema;
- `tools/list` публикует `outputSchema`, а `tools/call` — совпадающий с ней
  `structuredContent` и корректный `isError`;
- исходная и упакованная поставки публикуют одинаковый контракт.

### Создание

- preview/apply проверяются для всех 23 начальных видов;
- сложный объект создаётся `meta.add.operations` одной транзакцией, а ошибка
  любой операции не оставляет минимальный объект;
- duplicate и partial registration отказывают без записи;
- capability matrix различает чтение и создание;
- каждый созданный объект проходит корпус Platform XML 8.3.27/2.20 и
  платформенный round-trip.

### Редактирование

- пять видов операций покрыты на всех допустимых коллекциях;
- структурные простые, ссылочные и составные типы не используют строковый
  parser;
- следующая операция видит предыдущую;
- отказ на каждом `operationIndex` оставляет все преобразы неизменными;
- повторная семантически идентичная правка ничего не публикует;
- сохранённые возможности снятого DSL либо имеют типизированное представление,
  либо перечислены в migration note как намеренно удалённые; отсутствие
  представления не маскируется общей строкой `compile -> add + edit`;
- preview называет нормализованные семантические эффекты по `operationIndex`.

### Чтение и удаление

- `meta.info` различает локальную ошибку, `ready`, `stale`, `partial` и
  `unavailable` состояния индексных секций;
- вызов без `sections` не обращается к RLM, а `limit > 50` отклоняется;
- результат чтения наблюдаемо покрывает свойства, поля коллекций и отношения,
  которые изменяет публичная алгебра операций;
- лимит секции всегда сопровождается `total` и `truncated`;
- внутренний validator одинаково классифицирует post-image мутации и объект,
  прочитанный через `meta.info`;
- `meta.remove` доказывает логический выбор, анализ ссылок и тройной gate
  принудительного удаления.

### Надёжность и поставка

- проверяются support guard, конкурентное изменение, точные преобразы,
  блокировки, отмена и rollback failure;
- форматные фикстуры, MCP smoke, tool-surface ledger, skills parity и package
  parity проходят вместе;
- поиск по tracked-файлам не находит старых инструментов, Meta
  `DefinitionFile`, строковых примеров `Operation + Value` и ссылок на
  удалённые документы;
- оба манифеста плагина получают одну версию, а release notes содержат таблицу
  ломающей миграции.
