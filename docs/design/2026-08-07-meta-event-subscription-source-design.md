# Типизированные источники подписки на событие

## Задача

Подписка на событие должна принимать набор записей регистра сведений как
источник через действующую поверхность `unica.meta.*`. Предыдущая реализация из
ветки `aef3de1c` доказала важные сценарии безопасности, но была построена до
редизайна ADR-0025 и использовала снятый строковый/файловый DSL с физическими
селекторами. На свежей основной ветке эти формы не могут быть восстановлены
даже как псевдонимы.

Проект должен сохранить четыре публичных инструмента метаданных, пять значений
`op`, общий контракт операций для создания и редактирования и локальный
readback через `meta.info`. Форматный результат ограничен платформой 8.3.27 и
форматом выгрузки 2.20 по ADR-0016.

## Наблюдаемая форма данных

`EventSubscription.Source` — набор описаний типов без значимого порядка. JSON
и XML представляют этот набор повторяющимися элементами; один элемент может
быть примитивом с квалификаторами, `ValueStorage`, обычным
`cfg:GeneratedType` в `v8:Type` или `DefinedType` в `v8:TypeSet`. Поэтому
скалярный реестр `setProperties`, который хранит только строки, логические
значения и целые числа, эту структуру не представляет.

ADR-0025 уже оставляет предметную точку расширения: `editRelations` описывает
замену связей и используется одинаково в `meta.add.operations` и `meta.edit`.
Добавление `relation: "source"` сохраняет существующие пять тегов. В отличие от
других отношений, цель здесь является не только адресом объекта метаданных, но
закрытым вариантом описания типа.

## Выбранная модель

Один элемент операции имеет форму:

```json
{
  "op": "editRelations",
  "relation": "source",
  "mode": "replace",
  "targets": [
    {
      "kind": "recordSet",
      "metadataPath": "InformationRegister.Изменения"
    }
  ]
}
```

`add` и `remove` для этого отношения не нужны: полная замена делает состав и
итоговый post-image явными. Пустой `targets` очищает `Source` и разрешён только
для сочетания `source + replace`; общие отношения сохраняют прежнее требование
непустого массива.

Закрытое объединение целей содержит:

| `kind` | Поля | Назначение |
| --- | --- | --- |
| `string` | `length: 0`, `allowedLength: "variable"` | канонический строковый источник подписки |
| `number` | `digits`, `fraction`, `sign` | число с проверенными квалификаторами |
| `boolean` | — | логический тип |
| `date` | `fractions` | дата или дата-время |
| `valueStorage` | — | хранилище значения, только как единственная цель |
| `object` | `metadataPath` | порождаемый объектный тип существующего объекта |
| `reference` | `metadataPath` | порождаемый ссылочный тип существующего объекта |
| `recordSet` | `metadataPath` | набор записей одного из четырёх регистров |
| `definedType` | `metadataPath` | существующий определяемый тип |

Число принимает `digits` от 0 до 38, `fraction` не больше `digits` и знак
`any` или `nonNegative`. Дата принимает `date` или `dateTime`. Матрица
конфигурационных целей ограничена типами, для которых профиль 8.3.27 доказывает
соответствующий `GeneratedType`: десять объектных, девять ссылочных, четыре
регистровых вида и сам `DefinedType`.

Такая форма различает семантику цели до сериализации и не заставляет вызывающую
модель собирать строку платформенного типа. `metadataPath` остаётся логическим
адресом существующего объекта, а `kind` выбирает порождаемую роль этого объекта.

## Проверка зависимостей

Для примитивов нет отдельного файла-зависимости. Для конфигурационной цели
планировщик находит объект под тем же точным `Configuration.xml`, что и
подписка, и проверяет его прямую регистрацию, канонический путь, точные корень,
вид и имя описателя. `InternalInfo` подтверждает один полный ожидаемый
`GeneratedType` с корректными `TypeId` и `ValueId`.

Предпросмотр выполняет те же чтения, что применение. Точные байты владельца,
описателей зависимостей и целевой подписки, а также состав её прямого каталога
входят в один план публикации. Изменение любого преображения или подмена пути
после планирования срывают применение вместо записи результата из устаревших
данных.

## Создание, изменение и чтение

Для существующей подписки операция передаётся в `unica.meta.edit`. При создании
она передаётся в `unica.meta.add.operations`; все конфигурационные цели уже
существуют, а минимальный шаблон, новый `Source` и регистрация подписки
публикуются вместе.

`unica.meta.info` раскладывает XML обратно в тот же wire-массив типизированных
целей. Это удерживает заявленный ADR-0025 паритет writer, validator и readback
и позволяет проверить результат без чтения сырого XML. Позиция цели в массиве
не входит в её семантическую идентичность: запрос с теми же членами в другом
порядке даёт exact-byte no-op. При действительном изменении писатель выпускает
члены в детерминированном порядке по группе платформенного типа и
семантическому ключу; вход с `cfg:` никогда не нужен.

## Рассмотренные варианты

### Отдельный тег `setEventSources`

Он был бы простым для диспетчеризации, но расширил бы закреплённое множество
пяти операций и заставил бы `meta.add`, `meta.edit`, schema и скиллы согласовать
шестую ветвь. Существующее отношение уже выражает полную замену.

### `setProperties.Source`

Скалярное значение не представляет повторяющиеся `v8:Type`, `v8:TypeSet` и
квалификаторы. Строка вернула бы снятую грамматику и сделала бы schema слабее
writer-а.

### Строка из платформенных типов

Строковое представление платформенных типов компактно, но не проверяется
MCP-схемой, смешивает идентичность и сериализацию и повторяет снятый контракт.

### Проверка только написания адреса

Синтаксически правильный адрес отсутствующего регистра создал бы висячую
ссылку. Проверка описателя и `GeneratedType` дороже, зато позволяет связать
решение с точным снимком исходников.

## Доказательная граница

Локальные тесты могут доказать закрытую JSON-схему, матрицу видов, точное XML,
readback, отказы зависимостей, no-op, preview и транзакционную гонку. Корпус
может быть порождён дважды локально, а его нормализованный контракт, хеши и
топология — проверены без 1С.

Это не доказывает приёмку платформой. Последний завершённый exact-platform
инвентарь уже включает `xdto-add-nested-property`; новый контрольный пункт
`meta-edit-event-source` остаётся единственным ожидающим дополнением. До двух
независимых порождений с одинаковым нормализованным дайджестом и полного
точного прогона платформой 8.3.27.2074 результат `PASS` относится только к
предыдущему инвентарю.
