# Типизированные находки правил представления метаданных

## Контекст

Pull request [#316](https://github.com/IngvarConsulting/unica/pull/316)
добавляет предупреждение, когда `ListPresentation` повторяет `Synonym`, а pull
request [#317](https://github.com/IngvarConsulting/unica/pull/317) разделяет два
порога длины текста командного интерфейса: рекомендуемые 30 символов и верхний
порог 38 символов. Оба изменения выполняются внутри `MetadataValidator`, который
по ADR-0025 обслуживает `unica.meta.info` и все три мутации `unica.meta.*`.

В обеих ветках новое правило сейчас попадает в `MetaValidationReporter` как
строка. При построении публичного результата `validation_warning` превращает
любую такую строку в один и тот же код `validation_failed`, ставит общее поле
`properties` и сохраняет язык только внутри английского `message`. Клиент не
может устойчиво отличить правило, свойство и язык без разбора текста. Это
противоречит направлению issue
[#283](https://github.com/IngvarConsulting/unica/issues/283) на стабильные
машинные коды и типизированные местоположения и не реализует точность
диагностик, требуемую ADR-0025.

`ListPresentation` отсутствует в `METADATA_PROPERTY_SPECS`, однако этот разрыв
существовал до обоих pull request: текущая проверка длины уже выбирает непустой
`ListPresentation` раньше `Synonym`. По правилу происхождения дефекта он не
расширяет эти pull request до нового публичного свойства. Ветка правила
проверяется на реальном Platform XML, а отдельное расширение алгебры
`setProperties` должно иметь собственную задачу и самостоятельно проверяемый
pull request.

## Решение

### Публичная модель находки

`MetaDiagnostic` сохраняет существующие поля и получает необязательное поле
`language: string`. Поле присутствует только у находки, относящейся к одному
языковому варианту платформенного `MLText`. Отсутствие поля означает, что
находка не зависит от языка; пустая строка наружу не публикуется.

Новые правила используют следующие стабильные коды:

| Правило | `code` | `field` | `severity` |
| --- | --- | --- | --- |
| `ListPresentation` повторяет `Synonym` | `redundant_list_presentation` | `properties.ListPresentation` | `warning` |
| текст длиннее 30, но не длиннее 38 символов | `command_text_recommended_limit` | `properties.Synonym` или `properties.ListPresentation` | `warning` |
| текст длиннее 38 символов | `command_text_upper_limit` | `properties.Synonym` или `properties.ListPresentation` | `warning` |

`metadataPath` продолжает называть проверяемый объект. `message` остаётся
понятным человеку пояснением, но не является машинным контрактом и не
используется тестами для распознавания правила. Язык записывается в `language`,
а не кодируется в `field` или `message`.

### Семантика порогов

Длина считается в Unicode scalar values тем же `chars().count()`, что и сейчас.

- до 30 символов включительно предупреждения о длине нет;
- от 31 до 38 символов включительно возвращается только
  `command_text_recommended_limit`;
- от 39 символов возвращается только `command_text_upper_limit`.

Оба результата остаются предупреждениями: `validation.status` равен `passed`,
`OperationResult.ok` остаётся истинным, а применение с `dryRun: false` не
блокируется только из-за длины. Термин «жёсткий предел» удаляется из справки и
сообщений, потому что он обещает блокировку, которой контракт не предусматривает.

Для каждого зарегистрированного языка непустой `ListPresentation` остаётся
источником текста с приоритетом перед `Synonym`. Если `ListPresentation` пуст,
проверяется `Synonym`. Одно значение не порождает сразу оба предупреждения о
длине.

### Внутреннее представление

`MetaValidationReporter` получает структурный путь добавления предупреждения:
код, точное поле, необязательный язык и сообщение передаются отдельными
значениями. Существующие строковые предупреждения продолжают преобразовываться
в `validation_failed`, поэтому текущая миграция не требует одномоментно
типизировать весь старый валидатор.

Преобразование структурной находки в `MetaDiagnostic` выполняется один раз на
границе `MetadataValidator`, где уже известен `metadataPath`. Код новых правил
не извлекается из строки и не определяется поиском подстроки. Такой переходный
контур позволяет последующим срезам issue #283 переносить правила по одному,
не создавая второй валидатор.

### Границы pull request

Оба pull request остаются независимыми и имеют базу `main`; дочерний pull
request не создаётся.

- #316 несёт общий минимальный контракт структурной находки и правило
  `redundant_list_presentation`.
- #317 несёт тот же общий контракт до слияния #316 и два кода длины.
- После слияния #316 ветка #317 обновляется от `main`; совпадающая общая часть
  перестаёт быть изменением #317, а его предметный diff сохраняет только два
  правила длины и их проверки.

Параллельное использование следующего номера ADR допустимо правилами
`spec/decisions/README.md`: номер, существующий только в открытом pull request,
не занят окончательно. Перед каждым слиянием номер сверяется с актуальным
`main`.

## Неграницы

- Работа не добавляет `ListPresentation` в публичный `setProperties` и не меняет
  строковое представление `Synonym`.
- Работа не типизирует все существующие сообщения `MetadataValidator`.
- Работа не закрывает открытые поддеревья `data`, `diagnostics` и `job` общей
  `outputSchema`. Этот существовавший до pull request разрыв между схемой и
  типизированным результатом ADR-0025 требует отдельного изменения поверхности.
- Работа не меняет формат Platform XML, порядок его узлов или профиль
  `8.3.27`/`2.20`.
- Работа не выводит остальные `unica.*.validate`, не добавляет tombstone-ответы
  и не реализует `mxl.edit` или `role.edit`.
- Issue #283 не закрывается этими двумя pull request.
- Предупреждение о значении длиннее 38 символов не становится ошибкой.

## Проверка через тесты

Каждый дефект сначала воспроизводится падающим тестом на соответствующей head-
ветке. До правки реализации тест обязан падать из-за отсутствующего кода,
точного поля, языка или покрытия ветки, а не из-за фикстуры.

Общий контракт проверяется следующими утверждениями:

- новый код входит в закрытый сериализуемый словарь `MetaDiagnosticCode` и
  появляется в `structuredContent`;
- `language` отсутствует у неязыковой диагностики и содержит код языка у новых
  правил;
- `message` можно изменить без поломки машинных утверждений теста;
- предупреждение сохраняет `validation.status = passed` и успешность операции.

Проверки #316 покрывают одинаковое значение, отличающееся значение и fallback
на `Synonym`. Проверки #317 покрывают длины 30, 31, 38 и 39, оба источника текста
и исключительность двух кодов. Ветка `ListPresentation` строится через
отслеживаемую XML-фикстуру или локальный fixture helper, а не через несуществующее
публичное свойство.

После локальных целевых тестов на каждой ветке выполняются форматирование,
Clippy с `-D warnings`, полный набор `unica-coder`, релевантные Python-стражи
публичной поверхности и `git diff --check`. После push проверяются GitHub CI и
состояние review threads. После первого слияния тот же контур повторяется на
перебазированной второй ветке.

## Архитектурная синхронизация

Поскольку добавляются значения публичного `code` и поле результата `language`,
изменение затрагивает контракт полезной нагрузки. Тот же набор правок включает:

- новую запись решения `ADR-0035` о структурных кодах и языковом местоположении
  находок `MetadataValidator`;
- выведенное проверяемое правило `INV-MCP-META-FINDINGS`, нормативная
  формулировка которого остаётся в `spec/architecture/invariants.md`;
- синхронизацию тестов `structuredContent` и справки соглашений.

ADR-0025 и его инвариант не переписываются: они уже находятся в `main` и
остаются историческими владельцами поверхности `unica.meta.*`. Новая запись
уточняет публичную форму находок, не меняя набор инструментов или владение
валидацией.
