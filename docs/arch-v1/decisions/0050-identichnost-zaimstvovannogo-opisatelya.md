# ADR-0050: Идентичность заимствованного описателя выдаётся один раз

- Статус: `accepted`
- Дата: `2026-08-11`
- Задача: [#435](https://github.com/IngvarConsulting/unica/issues/435)

## Контекст

`unica.cfe.borrow` переписывает описатель расширения целиком на каждом вызове.
Идентичность в этот описатель до сих пор подставлялась безусловно: `fresh_uuid`
у обёртки объекта, у `xr:ThisNode` плана обмена и у пары `xr:TypeId` /
`xr:ValueId` каждого `xr:GeneratedType`.

Поэтому повторное заимствование того же объекта выдавало ему новую
идентичность. Наблюдение на минимальной фикстуре, два одинаковых вызова подряд:

```
BEFORE: <Catalog uuid="53e038c0-95c5-41e9-83a8-f2ae3e82f636">
AFTER:  <Catalog uuid="15e2aba6-3379-42f7-aefb-3c541533bfb9">
```

Вместе с обёрткой менялись `TypeId` и `ValueId` всех пяти категорий.

Ветка формы вела себя иначе: она читала существующий uuid обёртки и сохраняла
его. Две ветки одного инструмента расходились в политике идентичности, и вывести
общее правило из кода было нельзя — только из того, какая ветка исполнилась.

Цена расхождения не в шуме diff-а. Идентичность объекта расширения — это ссылка:
на неё указывают зарегистрированные типы и потребители, уже получившие описатель.
Молчаливая её замена делает операцию неидемпотентной там, где вызывающий имеет
все основания считать повтор безопасным.

## Решение

1. Заимствованный описатель получает идентичность один раз — при первом
   заимствовании. Идентичность — это `uuid` обёртки объекта, `xr:ThisNode`
   плана обмена и пара `xr:TypeId` / `xr:ValueId` каждого `xr:GeneratedType`.
2. Повторное заимствование уже заимствованного объекта — идемпотентная запись,
   а не отказ. Инструмент перечитывает существующий описатель, переиспользует
   найденную идентичность и заново выводит остальное содержимое из источника.
3. Элемент идентичности, которого в существующем описателе нет, выпускается
   свежим. Это делает правило одинаковым для первого заимствования, для
   восстановления повреждённого описателя и для профиля, у которого появилась
   новая категория `GeneratedType`.
4. Политику несёт один тип — `CfeBorrowIdentity`, — и обе ветки инструмента,
   объектная и формы, читают идентичность через него. Ветка, которая выпускает
   идентичность мимо этого типа, — дефект.
5. Идемпотентность наблюдаема в отчёте: повтор оставляет байты описателя
   неизменными, поэтому план записи не публикует по нему ни `created`, ни
   `updated`. Отдельного признака «повтор» в отчёте не заводится — его роль
   играет отсутствие изменения.

## Неграницы

1. Решение не касается содержимого описателя помимо идентичности. Если источник
   изменился, повтор переносит новое содержимое и честно сообщает `updated`.
2. Решение не вводит проверку, что заимствованный объект всё ещё соответствует
   источнику, и не отменяет существующие отказы по версии формата.
3. Решение не распространяется на идентичность реквизитов и табличных частей,
   которые дописывает обогащение: они добавляются только при отсутствии и в
   повторную запись уже готового описателя не попадают.
4. Решение не обещает побайтовую идемпотентность прочих файлов пакета
   заимствования — регистрация владельца остаётся отдельным изменением со своей
   классификацией.

## Последствия

1. Повторный `unica.cfe.borrow` перестаёт давать diff во всём описателе. Вызов
   становится безопасным для повторения, в том числе внутри пакета из нескольких
   заимствований.
2. Отчёт мутации на повторе становится пустым по описателю. Потребитель, который
   считал непустой `updated` признаком выполненной работы, увидит изменение
   поведения; это намеренно и вытекает из пункта 5 решения.
3. Инструмент теперь читает целевой описатель до записи. Это одно дополнительное
   чтение на заимствуемый объект и оно идёт через план записи, поэтому файл,
   запланированный ранее в том же пакете, виден.
4. Проект отказывается от варианта «повтор — явный отказ». Отказ потребовал бы
   от вызывающего различать первое и повторное заимствование до вызова, тогда как
   идемпотентная запись снимает этот вопрос и совпадает с уже сложившимся
   поведением ветки формы.

## Верификация

- `cargo test --package unica-coder --lib
  borrow_cfe_preserves_object_identity_on_repeated_borrow` — два одинаковых
  вызова оставляют байты описателя неизменными, и повтор не публикует по нему ни
  `created`, ни `updated`.
- `cargo test --package unica-coder --lib
  borrow_cfe_preserves_existing_form_module_on_repeated_form_borrow` — ветка
  формы сохраняет прежнюю идентичность через тот же тип.
- `cargo test --package unica-coder --lib
  borrow_cfe_reports_a_first_borrow_as_created_and_its_owner_as_updated` —
  первое заимствование по-прежнему выпускает свежую идентичность и сообщает
  `created`.
- `cargo test --package unica-coder --lib
  cfe_write_plan_identical_bytes_publish_no_created_or_updated_entry` —
  свойство плана записи, на котором держится пункт 5.
