# ADR-0068: Публикация идёт линейным конвейером от единственного человеческого тега

- Статус: `accepted`
- Дата: `2026-08-16`
- Задача: [#518](https://github.com/IngvarConsulting/unica/issues/518)

## Контекст

ADR-0008 разделила публикацию на две фазы: staging кладёт байты плагина на
ветку маркетплейса, promotion переводит каталог на неизменяемый тег. Механика
вокруг этого инварианта выросла в хореографию: три pull request, два
подписанных человеком тега и работающий по расписанию Release Warden,
продвигающий релиз через границы, потому что посреди конвейера стояло
неограниченное по времени ожидание второго тега.

Релиз v0.12.0 показал цену ([#518](https://github.com/IngvarConsulting/unica/issues/518)):
пуш тега не перетриггеривает чеки и релиз застревает сразу после подписи
(заплатка #514); промоушен стоит красным by design; вторая подпись не несёт
информации — фактический гейт это зелёные потребительские проверки, а подписи
тегов маркетплейса никем не верифицируются; метаданные едут в именах веток и
парсятся регекспами.

Выбор вариантов и целевой поток описаны в
[проектной записке](../../../docs/design/2026-08-16-linear-release-pipeline-design.md).

## Решение

1. Единственное человеческое действие релиза — подписанный source-тег
   `vX.Y.Z` в `unica`. Он фиксирует версию артефактов, запускает сборку и
   является человеческим одобрением публикации.
2. После успешной сборки, публикации ассетов и BSP-оценки публикация идёт
   одним линейным конвейером без pull request и без планировщика:
   staging-коммит пушится в ветку маркетплейса напрямую (каталог не тронут),
   тег `vX.Y.Z` создаётся автоматикой на staging-коммит, потребительские
   проверки выполняются против этого тега, и только по их зелёному исходу
   каталог переводится отдельным коммитом.
3. Двухфазный инвариант ADR-0008 сохраняется дословно: каталог никогда не
   называет байты, не прошедшие потребительскую установку, и никогда не
   называет несуществующий тег. Порядок «тег раньше проверок, проверки раньше
   каталога» закреплён в конвейере, а не в дисциплине человека.
4. Потребительские проверки остаются проверками установки глазами
   потребителя: свежая установка и обновление с предыдущей стабильной версии
   на трёх целевых платформах, против материализованного кандидатного
   состояния — staging-коммит плюс кандидатный каталог плюс реальный тег.
5. Тег маркетплейса создаёт автоматика без GPG-подписи. Криптографический
   якорь релиза — подписанный source-тег; тег маркетплейса — якорь резолва
   каталога. Неиспользуемый тег проваленной публикации безвреден, версия
   сжигается по правилам ADR-0008.
6. Отказ любой ступени останавливает конвейер до перевода каталога и виден
   как красный прогон, привязанный к source-тегу. Класс состояний
   «застрявший релиз» исчезает вместе с ожиданием в середине конвейера;
   отдельный сторож по расписанию не нужен и удаляется.
7. `REQ-REL-NO-SILENT-STALL` переопределяется этим решением: тишина
   исключается не докладом сторожа, а отсутствием точки, где конвейер может
   молча остановиться.

## Неграницы

1. Решение не меняет состав проверок: BSP-оценка, smoke, потребительские
   установки сохраняются как есть; ими владеют ADR-0008 и ADR-0055.
2. Решение не вводит паузу ручного одобрения перед переводом каталога.
   Если она понадобится, это отдельное решение поверх той же линейной формы
   (GitHub Environment с required reviewer), а не возврат второго тега.
3. Решение не переносит каталог в репозиторий исходников и не меняет
   потребительский контракт `git-subdir` по тонкому публичному репозиторию.
4. Решение не отменяет ручной аварийный путь: оператор перезапускает весь
   конвейер через `workflow_dispatch` от записанного `source_run_id`, и
   идемпотентные ступени сами проходят уже сделанное; отдельного запуска
   ступеней нет.

## Последствия

1. Релиз требует одного человеческого действия вместо трёх и не содержит
   окон ожидания по расписанию; латентность равна сумме длительностей джоб.
2. Удаляются Release Warden (workflow, скрипт, тесты), PR-механика staging и
   promotion и регекспы имён веток; runbook сокращается до версии, тега и
   наблюдения.
3. Бот получает право прямого пуша в ветку маркетплейса. Это фиксация
   фактического положения: PR-ы и сегодня мёржит бот тем же токеном без
   человеческого ревью.
4. Проваленные потребительские проверки оставляют опубликованный тег без
   каталога — как и прежний abort после шага 4 runbook; версия сжигается.
5. `detect_promotion.py` в маркетплейсе теряет ветку promotion-PR и подлежит
   упрощению отдельным изменением в том репозитории.
6. Подпись source-тега — конвенция владельца ключа, а не проверяемое
   конвейером свойство: конвейер доказывает существование тега и
   происхождение payload из его успешной push-сборки, но криптографию подписи
   не верифицирует — GitHub сегодня не подтверждает эти подписи
   (`bad_email`). Гарантию «тег создаёт только уполномоченный» дают права
   записи и правила защиты тегов репозитория; включить защиту тегов
   рекомендуется, проверка build-аттестаций — возможное отдельное усиление.

## Верификация

- `python3.12 -m unittest tests.ci.test_unica_workflow` — форма линейного
  конвейера: порядок stage → tag → verify → promote, отсутствие warden.
- `python3.12 -m unittest tests.ci.test_product_contracts` — публикация
  недостижима без source-тега и зелёных потребительских проверок.
- Первый живой прогон — релиз v0.13.0 с наблюдением всех ступеней.
