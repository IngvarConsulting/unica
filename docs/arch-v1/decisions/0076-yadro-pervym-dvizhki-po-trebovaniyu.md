# ADR-0076: Ядро запускается первым, движки доставляются неизменяемыми артефактами

- Статус: `accepted`
- Дата: `2026-08-20`

## Контекст

Полный runtime дублировал в каждом выпуске Unica уже опубликованные байты
`unica-toolchain` и достигал 439 МБ. Bootstrap обязан был получить весь этот
набор до запуска MCP, хотя отдельному вызову нужен только один движок. На
медленном канале старт упирался в срок хоста, а изменение сборки движка без
смены его upstream-версии могло совпасть с прежним адресом кеша.

Одновременно нельзя ослабить тонкий пакет ADR-0008, замкнутость многофайлового
RLM из ADR-0061 и доказательство исполняемых байтов ADR-0055. Разделение
поставки обязано сохранить один публичный сервер `unica`, проверку SHA-256,
атомарную публикацию, полную файловую полезную нагрузку и двухфазное продвижение
маркетплейса.

Происхождение выбора и рассмотренные альтернативы записаны в
[проектной записке](../../docs/design/2026-08-20-core-first-engine-delivery-design.md).

## Решение

1. Публичный пакет маркетплейса остаётся тонким и несёт файлы плагина и три
   bootstrap-бинарника. Исходный выпуск Unica публикует по одной паре
   «архив + метаданные» ядра `unica` для каждой поддерживаемой цели. Движки не
   перепубликуются: манифест пакета адресует закреплённые артефакты
   `unica-toolchain` по адресу, SHA-256, форме доставки и полной файловой
   полезной нагрузке.
2. Bootstrap получает и проверяет только ядро до запуска MCP. Оркестратор
   разрешает нужный инструмент из общего артефактного кеша и доставляет
   отсутствующий движок перед вызовом его обработчика. `prefetch` заранее
   доставляет ядро и все движки цели для образа, который будет работать без
   сети.
3. Неизменяемая идентичность поставки равна паре «семантическая версия и
   SHA-256 доставляемого ассета». Проверенный корень публикуется под
   `<cacheRoot>/<artifact>/<version>--<assetSha256>/<target>`; версия плагина не
   является идентичностью байтов движка. Другая сборка той же апстрим-версии
   получает другой корень и не перезаписывает прежнюю.
4. Блокировка, недокачка, журнал попытки, транзакция и маркер готовности используют
   ту же идентичность артефакта. Владелец точной блокировки докачивает,
   проверяет внешний SHA-256, безопасно материализует полный объявленный набор
   обычных файлов, сверяет их суммы, размеры и режимы и публикует каталог
   атомарным переименованием. Перед новой попыткой он удаляет только устаревшие
   транзакции той же поставки и цели; пригодная недокачка сохраняется для
   продолжения.
5. Внутри процесса `unica` одна идентичность артефакта имеет не более одной
   серверной доставки. Вызов-владелец ждёт не более 30 секунд и оставляет не
   менее двух секунд до известного срока хоста; присоединившийся вызов не ждёт
   это окно и сразу получает состояние. Отмена отдельного вызова не отменяет
   общую доставку.
6. Если движок не прибыл внутри окна, обработчик не запускается, а обычный
   конверт результата получает необязательное `work` с `status`,
   `statusMessage` и, когда он известен, `pollIntervalMs`. `working` является
   успешным промежуточным состоянием, отказ доставки — неуспешным результатом с
   причиной. Следующий предметный вызов служит повторной проверкой; отдельный
   публичный инструмент доставки и возможность `MCP Tasks` не вводятся.
7. Каждый платформенный раннер по-прежнему одной обязательной командой собирает
   `unica` и `unica-bootstrap`, упаковывает детерминированное ядро и до передачи
   проверяет архив, метаданные, состав, суммы, режимы и времена. Дымовая
   проверка MCP
   исполняет ядро из этого проверенного архива, а нужные утверждениям движки
   получает как явно подготовленный и проверенный вход, не подменяющий байты
   ядра. Оценка `BSP` аналогично записывает слой движка в отчёт.
8. Между заданиями не передаются каталоги Cargo или полный набор инструментов. Кроме
   метаданных, bootstrap и архива ядра допускается только узкий однодневный
   вход движка, нужный конкретной оценке. На теге опубликованные байты ядра
   скачиваются и проверяются повторно, все адреса движков проверяются на
   достижимость, а `prefetch` доказывает доставку целиком до продвижения
   каталога.
9. Публикация маркетплейса сохраняет две фазы ADR-0008: полезная нагрузка
   сначала попадает в промежуточную ветку, а стабильный каталог переводится на неизменяемый тег
   только после потребительских проверок. Переход старых установок через
   неизменяемый выпуск `v0.7.8` также сохраняется.

Эта запись заменяет ADR-0008, ADR-0055 и ADR-0061, объединяя сохранённые ими
гарантии с разделённой поставкой ядра и движков.

## Неграницы

1. Решение не меняет набор или имена инструментов `unica.*`, идентичность
   сервера и внутреннюю маршрутизацию анализа кода.
2. Решение не вводит MCP Tasks, отдельный сервер доставки, UI или новый
   публичный инструмент установки.
3. Решение не обещает начальную установку без сети: для закрытого контура сеть
   нужна на стадии явного `prefetch` при сборке образа.
4. Решение не меняет происхождение или версии движков и не ослабляет
   `tools.lock.json` как источник их закрепления.
5. Решение не заменяет нормативный слой `spec/`, не вводит architecture v2 и не
   пересматривает публичную поверхность ради стоимости контекста.

## Последствия

1. Холодный старт оплачивает только ядро; первый вызов конкретного движка может
   вернуть `work=working`, после чего повторный предметный вызов продолжит уже
   с готовым кешем.
2. Кеш хранит артефакты независимо и может временно содержать несколько сборок
   одной версии; сборщик мусора удерживает ограниченное число свежих поставок
   каждого артефакта.
3. Выпуск Unica больше не дублирует engine-байты, но его пригодность зависит от
   неизменяемых ассетов `unica-toolchain`; release gate поэтому проверяет и
   адреса, и полный `prefetch`.
4. CI получает узкий engine overlay для сценариев, которым недостаточно ядра.
   Отчёт обязан различать проверяемый core candidate и дополнительный input.
5. Общая серверная доставка переживает отмену одного вызова; это осознанное
   владение процессом, предотвращающее повторные загрузки и исчерпание 32
   admission slots одинаковыми ожидателями.

## Верификация

- `crates/unica-bootstrap/tests/runtime_install.rs` проверяет неизменяемый ключ
  поставки, возобновление, точную блокировку, stale transactions, атомарную
  публикацию, file-set closure и `prefetch`.
- `cargo test -p unica-coder engine_delivery` проверяет single-flight,
  ограниченное окно владельца, немедленный ответ followers, прогресс, отмену и
  повтор после отказа.
- `cargo test -p unica-coder bundled_tools` проверяет разрешение движка по
  версии и SHA-256 и типизированный отказ отсутствующего движка.
- `tests/ci/test_package_unica_runtime.py` и
  `tests/ci/test_package_unica_plugin.py` проверяют разделение core/engine,
  разрешённые origin и полный манифест поставки.
- `tests/ci/test_unica_workflow.py` и
  `tests/ci/test_release_assessment.py` проверяют core smoke, узкий engine
  overlay, повторную проверку опубликованных байтов, достижимость и prefetch.
- `scripts/ci/verify-delivery-reachable.py` проверяет все адреса артефактов для
  трёх поддерживаемых целей.
