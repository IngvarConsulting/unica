# ADR-0035: Находки проверки метаданных несут код правила и языковое местоположение

- Статус: `accepted`
- Дата: `2026-08-10`
- Обновлено: `2026-08-10`

## Контекст

ADR-0025 оставляет единый внутренний `MetadataValidator` для чтения и мутаций
`unica.meta.*` и требует от публичного результата стабильных предметных
диагностик с точным полем. Часть проверок всё ещё передаёт предупреждения как
строки. Публичная граница присваивает всем таким строкам общий код
`validation_failed`, общее поле `properties` и сохраняет язык только внутри
`message`.

Правила представления метаданных применяются к отдельному свойству и языковому
варианту `MLText`. Разбор текста сообщения для определения правила, свойства
или языка делает машинный контракт зависимым от формулировки и не позволяет
менять понятное человеку пояснение независимо от вызывающего кода.

Проектные основания и границы первых правил записаны в
[проектной записке](../../../docs/design/2026-08-10-meta-validation-findings-design.md).

## Решение

1. Публичная находка `MetadataValidator` называет правило стабильным значением
   `MetaDiagnosticCode`; код не извлекается из `message` и не определяется
   поиском подстроки.
2. Находка называет точное свойство в `field`. Когда правило относится к одному
   языковому варианту платформенного `MLText`, она дополнительно возвращает
   непустой код языка в необязательном поле `language`.
3. `message` остаётся понятным человеку пояснением и не является машинным
   идентификатором правила или местоположения.
4. Перенос строкового предупреждения в структурную находку не меняет его
   `severity` и сам по себе не меняет успешность проверки или мутации.
5. Переход выполняется по одному правилу. Ещё не перенесённое строковое
   предупреждение сохраняет общий код `validation_failed`; отдельный публичный
   валидатор или второй проверяющий компонент для миграции не создаётся.

## Неграницы

1. Решение не добавляет `ListPresentation` в алгебру `setProperties` и не меняет
   публичное представление `Synonym`.
2. Решение не требует типизировать все существующие находки одним изменением.
3. Решение не меняет формат Platform XML и не определяет судьбу инструментов
   `unica.*.validate` вне уже принятой поверхности `unica.meta.*`.
4. Решение не превращает превышение 38 символов в ошибку и не запрещает
   применение мутации.
5. Решение не закрывает поддеревья `data`, `diagnostics` и `job` общей
   `outputSchema`; оно типизирует фактический `structuredContent`.

## Последствия

- Клиент распознаёт правило, свойство и язык без разбора английской строки.
- Формулировка `message` может меняться без нарушения машинного контракта.
- Закрытый словарь `MetaDiagnosticCode` растёт при переносе каждого нового
  правила, но открытая `outputSchema` не сообщает вызывающему этот словарь.
- До завершения миграции типизированные и общие `validation_failed`-находки
  сосуществуют в одном результате.

- `cargo test -p unica-coder diagnostic_codes_serialize_to_the_stable_exhaustive_vocabulary`
  проверяет закрытый словарь кодов и их сериализацию.
- `cargo test -p unica-coder meta_info_surface_tests -- --test-threads=1`
  проверяет код, поле, язык и предупреждающую семантику
  `redundant_list_presentation`.
- `cargo test -p unica-coder meta_add_surface_tests -- --test-threads=1`
  проверяет оба кода длины, границы 30, 31, 38 и 39 и успешность применения.
- `python3.12 tests/ci/test_architecture_registry.py` проверяет связь записи с
  выведенным правилом реестра после принятия решения.
