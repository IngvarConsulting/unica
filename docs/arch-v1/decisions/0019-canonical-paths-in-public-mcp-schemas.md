# ADR-0019: Публичные MCP-схемы используют канонические имена путей

- Статус: `accepted`
- Дата: `2026-07-29`
- Задача: #261

## Контекст

Нативные операции принимают несколько написаний одного пути. Например,
`unica.role.validate` нормализует `RightsPath`, `rightsPath`, `Path` и `path` в
один аргумент `RightsPath` до проверки контракта. Эта совместимость нужна для
старых прямых клиентов.

Публикуемая схема версии `0.11.0` пыталась выразить ту же совместимость через
`allOf`, внутри которого находился `anyOf` из четырёх вариантов `required`.
Верхний массив `required` из-за этого оставался пустым. Сервер MCP возвращал
валидную JSON Schema, но хосты преобразуют её в собственные сигнатуры
инструментов и поддерживают композицию неодинаково. В Codex схема
`unica.role.validate` могла превратиться в функцию без аргументов, после чего
клиент не мог передать путь, который runtime справедливо требовал.

Совместимость принимаемого запроса и форма публикуемого контракта решают разные
задачи. Первая обязана сохранить старые прямые вызовы, а вторая обязана
однозначно назвать аргумент, который должен сформировать хост.

## Решение

1. Публичная входная схема каждого нативного инструмента показывает из группы
   алиасов пути только каноническое имя, заданное
   `PathAliasGroup.canonical`.
2. Обязательный канонический путь находится непосредственно в верхнем массиве
   `required`; композиция `allOf` и `anyOf` для алиасов пути не публикуется.
3. Алиасы остаются допустимыми во входе runtime и нормализуются в каноническое
   имя до проверки аргументов. Конфликтующие непустые значения по-прежнему
   отклоняются.
4. `application/operation_descriptors.rs` остаётся единственным владельцем
   групп алиасов и канонического имени. `application/tool_contracts.rs`
   использует эти данные и для публикации схемы, и для нормализации входа.

## Неграницы

Решение не удаляет алиасы из runtime и не меняет полезную нагрузку результата
ни одного инструмента. Прямой MCP-клиент может продолжать отправлять старое
написание, даже если оно больше не объявлено в `tools/list`.

Решение не нормирует выбор между разными видами полезной нагрузки, который не
является алиасом пути. Например, `unica.form.edit` продолжает публиковать
`anyOf` для `JsonPath` и `definition`.

Решение не разделяет общий словарь аргументов нативных XML-операций на точные
словари каждого обработчика. Это отдельное сужение контракта; текущая правка
выбирает для каждой группы пути один канонический аргумент, убирает из
публичной схемы все остальные принимаемые runtime имена и возвращает
обязательность пути на верхний уровень.

## Последствия

- Хост получает обычный обязательный аргумент без необходимости понимать
  композицию JSON Schema для алиасов.
- Публичная схема становится уже, чем множество запросов, принимаемых runtime:
  это осознанная совместимость на чтение, а не два равноправных публичных
  написания.
- В частности, `unica.cfe.init` больше не публикует `ExtensionPath` вместо
  канонического `OutputDir`, а `unica.support.edit` — `TargetPath` и
  `targetPath` вместо канонического `Path`; runtime продолжает принимать эти
  прежние имена.
- Ошибка в каноническом имени затронет все хосты, поэтому соответствие
  дескриптору проверяется для каждого нативного инструмента, а не только для
  `unica.role.validate`.

## Верификация

- `cargo test -p unica-coder native_operation_descriptors_drive_canonical_required_schema_paths`
  — проверяет верхний `required`, его выполнимость через опубликованные
  `properties`, отсутствие `allOf` и публикацию только канонического пути для
  каждого нативного инструмента.
- `cargo test -p unica-coder every_native_path_alias_group_normalizes_to_one_canonical_argument`
  — проверяет сохранение входной совместимости и отказ при конфликтующих
  значениях алиасов.
- `cargo test -p unica-coder role_validate_schema_publishes_canonical_required_path_without_composition`
  — проверяет наблюдаемый контракт задачи #261 на транспортной границе.
- `.venv/bin/python -m unittest tests.ci.test_unica_mcp_script_parity.UnicaMcpScriptParityTests.test_every_documented_tools_call_uses_published_argument_names`
  — проверяет аргументы примеров `tools/call` во всех документах скиллов против
  реально опубликованного `tools/list`.
