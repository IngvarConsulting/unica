# ADR-0017: Нейтральная к поставщику модель анализа кода

- Статус: `accepted`
- Дата: `2026-07-29`

## Контекст

Поиск и навигация по коду объединяют три движка с разными возможностями,
транспортами и сроками исполнения: `RLM`, `bsl-analyzer` и буквальный
`git grep`. До этого оркестрация публичных инструментов знала команды
конкретных процессов, форму их ответов и детали индекса `RLM`. Из-за этого замена
движка меняла слой `application`, а частичный отказ разных источников получал
разную семантику.

Обоснование границы, рассмотренные варианты и отказ от общего межветочного
индекса записаны в
[проектной записке](../../docs/design/2026-07-27-provider-neutral-code-intelligence-design.md).

## Решение

1. Слой application работает через типизированный
   `CodeIntelligenceProvider`, нейтральный к конкретному движку. Поставщик
   объявляет устойчивый идентификатор и исполнимые возможности, возвращает
   собственную секцию поиска и обслуживает только заявленные операции чтения.
2. Реестр встроенных поставщиков собирается в корне композиции и допускает
   внедрение подмен для тестов. Порядок реестра задаёт порядок секций публичного
   результата.
3. `unica.code.search` запускает поставщиков `rlm`, `bsl-analyzer` и
   `git-grep`. Ранги и оценки остаются локальными для секции; Unica не
   объединяет, не пересортировывает и не удаляет совпадения между секциями.
4. Слой application один раз проверяет запрос и разрешает корень рабочего
   пространства и исходников, затем передаёт всем поставщикам один
   `CodeIntelligenceContext`. Он запускает поставщиков параллельно, ограничивает
   допуск и сроки исполнения и связывает отмену каждого исполнителя с отменой
   MCP-вызова.
5. Инфраструктурная реализация поставщика владеет вызовом движка, разбором
   ответа и переходами его состояния. Слой application не читает частное
   хранилище поставщика и не зависит от его схемы.
6. Отказ поставщика остаётся в его секции. Публичный поиск успешен, если хотя бы
   один поставщик вернул `ok` или `empty`; отмена имеет приоритет и никогда не
   выдаёт частичный результат за успешный.
7. Публичная граница остаётся одним MCP-сервером `unica`. Выбор поставщика не
   становится аргументом инструмента, а `git-grep` остаётся внутренней секцией,
   а не отдельным публичным инструментом.

## Неграницы

1. Решение не вводит динамическую загрузку и пользовательскую настройку
   сторонних поставщиков.
2. Решение не меняет API RLM и не создаёт публичный сервер поставщика.
3. Решение не сравнивает оценки релевантности разных поставщиков.
4. Владение процессами, индексами и сессиями поставщиков определяет ADR-0018.

## Последствия

1. Новый движок анализа кода проверяется подменным поставщиком без запуска
   процесса и построения индекса.
2. Замена транспорта или места исполнения поставщика не меняет контракт слоя
   `application`.
3. Публичный результат сохраняет эпистемику каждого источника: недоступная или
   отказавшая секция не маскируется успешной секцией другого поставщика.
4. Пакетные и приёмочные проверки обязаны удерживать один публичный MCP-сервер и
   три секции поиска в фиксированном порядке.

## Верификация

- `cargo test -p unica-coder code_intelligence` проверяет реестр возможностей,
  внедрение подмен, параллельный запуск, сроки, отмену и политику частичного
  успеха.
- `cargo test -p unica-coder --test platform_code_intelligence` проверяет
  инфраструктурных поставщиков, разбор ответов и порядок секций.
- `python3.12 -m unittest tests.ci.test_product_contracts` проверяет отсутствие
  зависимости от частной схемы `SQLite` поставщика `RLM`.
- `python3.12 -m unittest tests.ci.test_release_assessment` проверяет форму и
  порядок трёх секций в блокирующей оценке пакета.
