# ADR-0018: Состояние поставщиков изолировано рабочим деревом

- Статус: `accepted`
- Дата: `2026-07-29`

## Контекст

ADR-0006 закрепил скрытый сервис рабочего пространства в момент, когда
`bsl-analyzer` держал тёплую модель, а `RLM` был только файловым индексом с
короткими заданиями построения и обновления. Текущая интеграция `RLM` использует
долгоживущий MCP-транспорт и логическую сессию чтения, поэтому запрет
долгоживущего процесса `RLM` из ADR-0006 больше не описывает работающую
архитектуру.

Для связанных рабочих деревьев общий индекс основной ветки почти всегда требует
учёта изменившихся файлов. Поддерживаемого API для композиции базового индекса и
дельты рабочего дерева у встроенных поставщиков нет. Копирование или слияние их
частных хранилищ сделало бы Unica владельцем чужой схемы и не доказало бы
свежесть результата.

Варианты и условия возврата к двухуровневому индексу записаны в
[проектной записке](../../../docs/design/2026-07-27-worktree-scoped-provider-state-design.md).

Это решение заменяет ADR-0006. Граница поставщика определяется ADR-0017.

## Решение

1. Состояние индекса, процесса и логической сессии поставщика изолируется
   нормализованной парой `workspaceRoot + sourceRoot`. Связанное рабочее дерево
   получает отдельное состояние и не разделяет индекс с основной рабочей
   копией.
2. Поставщик владеет внутренним форматом своего индекса и жизненным циклом
   процесса или сессии. Оркестратор владеет логической инвалидацией по доменным
   событиям, но не читает, не копирует и не объединяет частное хранилище
   поставщика.
3. Поставщик может применять поддерживаемое им обновление внутри одной
   идентичности. Общий индекс основной ветки с дельтой рабочего дерева,
   содержательно адресуемые фрагменты и перенос индекса между рабочими деревьями
   требуют отдельного измеренного решения и поддерживаемого API поставщика.
4. Место исполнения поставщика остаётся инфраструктурным выбором. Текущие
   `bsl-analyzer` и `RLM` работают за скрытым сервисом рабочего пространства,
   тогда как `git-grep` выполняется в основном процессе.
5. Скрытый сервис держит независимые тёплые MCP-транспорты
   `bsl-analyzer` и `RLM`. Одна логическая сессия `RLM` переиспользуется до
   инвалидации индекса или домена, истечения сессии, остановки сервиса либо
   смены корня исходников и затем закрывается вызовом `rlm_end`.
6. Повторное использование внутри одной идентичности является внутренней
   оптимизацией, а не публичной гарантией межчатового повторного использования.
   Разные рабочие пространства, связанные рабочие деревья и корни исходников
   всегда получают разные ключи сервиса, сессии и индекса.
7. `initialize`, `tools/list`, `unica.project.status` и `unica.project.map` не
   запускают скрытый сервис. Предпросмотр не запускает процессы поставщиков;
   настоящий `unica.code.search` может запустить сервис для `RLM` и
   `bsl-analyzer`.
8. Сервис остаётся внутренним, ограниченным по допуску и времени и управляет
   дочерними процессами как деревьями. Его отмена, управляющая полоса,
   протокол `JSONL`, сроки простоя и максимального возраста сохраняются как
   проверяемые runtime-контракты, а не становятся API поставщика.
9. Публичная поверхность остаётся одним MCP-сервером `unica`; ни сервис, ни
   движок поставщика не регистрируется публично.

## Неграницы

1. Решение не вводит наблюдатель файловой системы и пользовательский демон для
   всех рабочих пространств.
2. Решение не обещает, что холодное построение индекса будет дешёвым.
3. Решение не запрещает будущий двухуровневый индекс, если измерения покажут
   пользу, а поставщик даст явный контракт композиции и инвалидирования.
4. Решение не определяет публичный выбор поставщика.

## Последствия

1. Новое рабочее дерево может потребовать собственного ленивого построения
   индекса; последующие изменения внутри него используют поддерживаемое
   обновление поставщика.
2. Unica не получает хрупкую зависимость от `SQLite`-схемы `RLM` ради экономии,
   польза которой для короткоживущих рабочих деревьев не измерена.
3. Долгоживущий процесс `RLM` допустим внутри скрытого сервиса и разделяет его
   ограниченное управление жизненным циклом с анализатором.
4. Будущее предложение общего индекса обязано измерить время построения и
   обновления, срок жизни рабочих деревьев, частоту повторного использования и
   стоимость корректного инвалидирования.

## Верификация

- `cargo test -p unica-coder --test issue_89_workspace_service` проверяет
  раздельные тёплые транспорты, повторное использование сессии `RLM`,
  инвалидацию, отмену и ограниченное завершение сервиса.
- `cargo test -p unica-coder --test platform_code_intelligence`
  проверяет единую каноническую идентичность символической ссылки и отказ при
  выходе корня исходников из рабочего пространства.
- `cargo test -p unica-coder git_worktree_boundary` проверяет изоляцию
  связанного рабочего дерева и разрешение `.git` как файла-указателя.
- `python3.12 -m unittest tests.ci.test_product_contracts` проверяет отсутствие
  чтения частной схемы `SQLite` и согласованность runtime-бюджетов.
