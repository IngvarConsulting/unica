# 0.12.0: типизированная поверхность `unica.meta.*`

Версия `0.12.0` делает clean break: публичная группа метаданных теперь состоит
ровно из `unica.meta.info`, `unica.meta.add`, `unica.meta.edit` и
`unica.meta.remove`. Старые инструменты и их аргументы удалены без псевдонимов
совместимости.

## Таблица перехода

```text
meta.compile         -> meta.add.operations[] only for ledger-supported capabilities
meta.profile         -> meta.info.related
meta.validate        -> meta.info.validation / automatic mutation validation
ObjectPath           -> sourceSet + metadataPath
ConfigDir + Object   -> sourceSet + metadataPath
Operation + Value    -> operations[]
DefinitionFile       -> removed
```

`meta.add` создаёт один минимальный валидный объект из обязательных
`sourceSet`, `kind`, `name` и необязательного `dryRun`. `meta.add` не принимает
прежнюю нагрузку определения из `meta.compile`. Структура сверх минимального
шаблона задаётся следующим вызовом через типизированный массив
`meta.edit.operations[]` либо атомарно при создании через такой же массив
`meta.add.operations[]`.

Это не безусловный паритет прежнего `compile`. Машиночитаемая
[ведомость возможностей](../../spec/architecture/meta-capability-parity.json)
учитывает все 97 ключей таблиц снятого DSL: 56 имеют доказанный типизированный
маршрут, 41 снят с конкретным последствием миграции. `supported` означает, что
совпадают схема, матрица видов, область значений, writer, validator, readback
`meta.info` и литеральный round-trip. Наличие похожего XML-тега само по себе
поддержкой не считается.

Скалярные свойства передаются в `setProperties` под платформенными именами в
PascalCase; точный список и enum-значения публикует схема инструмента. Владельцы
справочника и движения документа переходят в `editRelations` (`owners`,
`registerRecords`), значения перечисления — в `add` с коллекцией `enumValues`.

## Что нельзя перенести механически

- Массив объектов из одного `JsonPath` не заменяется одним вызовом. Разбейте
  его на отдельные `meta.add`; атомарность действует только внутри одного
  объекта и его `operations`, но не между объектами.
- Вложенные `HTTPService.urlTemplates/methods` и
  `WebService.operations/parameters` не имеют типизированного child writer.
  Создайте оболочку сервиса, а вложенную структуру настройте в Designer.
- Ссылки и определения расписания, включая `CalculationRegister.schedule` и
  переназначение `ScheduledJob.methodName`, не кодируются строкой в
  `setProperties`. После создания настройте зависимость и расписание в
  Designer.
- Флаги дочерних полей `index`, `indexAdditional`, `nonneg`, `master`,
  `mainFilter`, `denyIncomplete` и `useInTotals` представлены не полностью.
  Простые элементы можно добавить структурно, но недостающие флаги нужно
  выставить в Designer; shorthand через `|` не поддерживается.
- Составные корневые типы, учётные признаки, реквизиты адресации, графы журнала
  с ссылками и прочие строки ведомости со статусом `removed` требуют указанного
  там внешнего шага. Не передавайте их как произвольные строки и не
  восстанавливайте `DefinitionFile` или JSON DSL.

`meta.info` включает локальную структуру и `validation`, а данные прежнего
профиля находятся в `related`. Внутренняя проверка также автоматически
выполняется после каждой из трёх мутаций.

`meta.info`, `meta.edit` и `meta.remove` адресуют существующий объект только
через `sourceSet + metadataPath`. Физические селекторы `ObjectPath`,
`ConfigDir + Object` и файловый `DefinitionFile` больше не входят в публичный
контракт.
