# Unica v0.12.3 → v0.13 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Выпустить один ломающий v0.13, который заменяет опубликованную поверхность v0.12.3 на восемь предметных входов, обслуживает долгую работу через SEP-2663 либо три compatibility-инструмента и выполняет её в одном версионированном пользовательском демоне без потери изоляции worktree.

**Architecture:** Тонкий stdio-фронтенд остаётся единственным публичным MCP-сервером `unica`; все `tools/call` превращаются во внутренние Invocation и исполняются демоном. Демон держит WorkspaceActor на канонический worktree, устойчивые Invocation/Task, точный SharedWork и одну предметную сериализацию результата. Новая поверхность строится рядом со старой как непубличный профиль и включается только одним финальным переключением версии.

**Tech Stack:** Rust 2021, `rmcp 3.1.2`, Tokio, Serde/JSON, UUID v4, `fs2`, существующие platform-facade и atomic publication primitives, Python 3 CI probes, GitHub Actions, пакет Unica для Codex и Claude Code.

**Spec:** `docs/design/2026-08-23-v0-13-execution-surface-design.md`; `docs/design/2026-08-23-v0-13-module-contract-design.md`; `DEC.2026-08-23.V0-13-EXECUTION-SURFACE`; `DEC.2026-08-23.MODULE-CONTRACT`; baseline release `v0.12.3`; release umbrella issue `#581`.

## Global Constraints

- Источник сравнения — опубликованный `v0.12.3`, а не только `main`: baseline содержит 74 уникальных `unica.*`, включая шесть `unica.runtime.job.*`.
- До Task 22 текущий профиль v0.12 остаётся единственным профилем production-сборки. Внутренние тесты получают v0.13 через явный `SurfaceRelease::V13`; переменная окружения не может случайно опубликовать его.
- Публичный cutover атомарен: никакой сборки с 71 старыми и 8 новыми именами, никаких алиасов и никакого частичного снятия доменов.
- Один packaged binary `unica` сохраняется. Демон — скрытый режим того же бинаря, а не второй поставляемый executable и не второй MCP-сервер.
- SDK-типы `rmcp` живут только в `interfaces/mcp.rs`. Application, daemon protocol и durable store используют собственные типы.
- Окно handoff равно 7 000 мс от приёма `tools/call`, включая admission. Известная долгая граница материализует Task сразу. Тесты управляют временем через fake clock и не спят семь секунд.
- Клиент с `io.modelcontextprotocol/tasks` видит 8 инструментов. Клиент без capability видит те же 8 плюс `unica.task.get`, `unica.task.result`, `unica.task.cancel`.
- `tasks/get`, `tasks/update`, `tasks/cancel` реализуются до объявления server Tasks capability. В v0.13 после материализации нет `input_required`; `tasks/update` возвращает стабильную ошибку `task_input_not_supported` для всех живых Task.
- Compatibility `task.result` — ограниченный wait, а не копия отсутствующего wire-метода `tasks/result`; один вызов удерживается не более остатка общего семисекундного окна.
- `OperationResult.job` и `OperationResult.work` не переносятся в v0.13 предметный результат. Task/compatibility receipt — transport projection поверх результата.
- Durable store не записывает raw arguments, токены, команды, URL с credentials или пути из пользовательского текста. Для восстановления допустимы только типизированные безопасные `ResumeDescriptor`.
- `apply` принимает непустой упорядоченный `ops[]`; `dryRun` и apply проходят одну валидацию, а весь пакет публикуется либо целиком, либо никак.
- Доставка остаётся core-first. `tools-download` не становится операцией `run`: engine delivery — SharedWork демона.
- `tests`, `features`, `log` и gRPC-профиль 8.5 не входят в v0.13. Они принадлежат v0.14/#563 или будущему platform profile.
- Публикация релиза не авторизуется этим планом. Task 23 подготавливает и доказывает release candidate; тег и marketplace publication выполняются отдельно по `docs/release-runbook.md`.

## TOGAF Gates and Dependency Order

Это Architecture Roadmap и Implementation/Migration Plan фаз E–F. Фаза G начинается только после принятия Gate F0.

```text
F0 contract closure
 └─ F1 reproducible v0.12.3 baseline
     └─ F2 Invocation + durable TaskStore
         └─ F3 daemon + WorkspaceActor + SharedWork
             └─ F4 Tasks/compatibility wire
                 └─ F5 eight domain contracts + parity
                     └─ F6 one public cutover + packaged migration matrix
```

Каждый gate заканчивается отдельным зелёным коммитом. Коммиты одного gate можно ревьюить независимо, но выпускать наружу разрешено только F6.

## Stop Conditions

Stop implementation and return to architecture review if any of these occurs:

- an old scenario cannot be assigned to exactly one of the eight entries;
- a host requires a different public schema rather than a capability-dependent profile;
- durable recovery would require storing raw secrets or blindly replaying a mutation;
- a platform writer cannot stage the whole `apply` batch before publication;
- a provider can only be shared by merging WorkspaceActor state;
- a release artifact needs a second public MCP server or second independently versioned executable;
- the packaged matrix cannot distinguish v0.12.3 full-runtime cache from v0.13 core/engine cache.

Such a stop is an architecture finding. It requires a successor `DEC.*` and derived `INV.*`/`CTR.*`, not a local exception in code.
