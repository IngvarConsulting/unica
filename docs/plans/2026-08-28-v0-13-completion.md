# Unica v0.13 Completion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Завершить миграцию Unica с опубликованной поверхности v0.12.3 на один локальный MCP `unica` с private daemon, восемью предметными входами, native/compatibility Tasks profiles и атомарным RC cutover без сохранения legacy aliases.

**Architecture:** До cutover production остаётся на V12. PR #631 сначала закрывает подтверждённый W0 blocker: отдельный private durable `ReceiptLedger` резервирует exact Invocation/Task/request identity до предметной работы, связывает promised Task и TaskStore recoverable write-ahead protocol с атомарным переключением projection, хранит terminal Direct до private ACK и не допускает replay после `Reserved::Begun`. После S1 три workers собирают schema-derived/behavior evidence v0.12.3 и классифицируют upstream-влияние на skills, пока integrator закрывает W2a-core. Затем integrator последовательно собирает content-addressed capability baseline и immutable provenance scope review и получает два независимых review; только этот join освобождает три непересекающиеся worker-линии W1. Параллельно integrator завершает W2a-seams до первого перехода любой линии в W3 и непрерывно выполняет W2b wiring. W4 превращает review в content-addressed cutover patch lock. Отдельный RC PR атомарно переключает package-selected surface, skill routing, bootstrap verification и архитектурные evidence records.

**Tech Stack:** Rust 2021, `rmcp 3.1.2`, Tokio, Serde/JSON, UUID v4, `fs2`, существующие platform facade и atomic publication primitives, Python 3.12 CI probes, GitHub Actions, пакеты Unica для Codex и Claude Code.

**Spec:** `docs/design/2026-08-28-v0-13-completion-wavefront-design.md`

## Global Constraints

- Источник baseline — опубликованный `v0.12.3`: 74 уникальных публичных имени, включая шесть `unica.runtime.job.*`. G6 атомарно снимает 71 текущую V12-регистрацию, а RC acceptance доказывает отсутствие всех 74 имён release fixture. Три baseline-имени уже отсутствуюют в текущей ведомости `main`: `unica.help.add`, `unica.template.add`, `unica.template.remove`; ведомость из 71 имени не заменяет immutable release fixture.
- До Gate G6 package-selected production surface остаётся V12. Hidden V13 доступен только через уже существующие injected constructors и тестовые harnesses; новый CLI flag, environment switch или secret package mode запрещён.
- Единственный публичный MCP-сервер сохраняет identity `unica` и local stdio transport. Daemon остаётся private per-user mode того же versioned core.
- Целевой native Tasks profile содержит ровно восемь entry points: `unica.view`, `unica.apply`, `unica.find`, `unica.search`, `unica.check`, `unica.diff`, `unica.run`, `unica.docs`. Compatibility profile добавляет только `unica.task.get`, `unica.task.result`, `unica.task.cancel`.
- В пределах bounded ReceiptLedger retention/deduplication horizon один exact `ReceiptKey` создаёт одну Invocation и допускает не более одной попытки `prepare`/`execute`; после `Reserved::Begun` replay запрещён. Frontend не делает fallback или replay; exact duplicate до expiry только reconciles уже существующий receipt/outcome. После physical expiry вечная idempotency, exactly-once outcome и exactly-once delivery не обещаются.
- Потеря submit session сама по себе не отменяет вызов, не меняет receipt и не форсирует Task: daemon продолжает original lifecycle/cutoff и ещё может durable завершить Direct. Только исходный cutoff либо current post-prepare `KnownLong` выбирают соответствующий Task handoff; reconnect/recovery не создаёт новый budget.
- Strict valid-submit boundary наступает после authenticated strict outer-envelope parse с каноническими `InvocationId`, `reservedTaskId`, tool/arguments/workspaceHint и daemon-side recomputation request identity, но до validation tool arguments/workspace, actor admission, `prepare` и `execute`. Неразбираемая strict envelope не valid submit, поэтому не создаёт ledger row и не запускает предметную работу; caller-provided digest никогда не принимается на доверии.
- `ReceiptLedger` атомарно резервирует exact пару IDs и secret-free digest immutable request scope, исключающий response budget. Same pair + same identity reconciles existing state; same InvocationId с другим TaskId, same TaskId с другим InvocationId или same pair с другим request identity закрыто отклоняются, не меняя original. Workspace-selector digest не является actor-derived workspace identity.
- Перед первым `service.prepare` ledger durable-фиксирует `Reserved::Begun`. Crash до terminal commit завершает receipt как `outcome_uncertain`, проецируемый как closed `interrupted`, без replay; известный outcome после такого crash разрешён только операции с доказанной atomic coupling/idempotent recovery.
- Cutoff внутри `Reserved::Unbound` validation/admission durable-создаёт receipt-backed `TaskPromisedUnbound` с exact TaskId. Если pipeline ещё блокируется, projections уже возвращают эту durable queued Task, но TaskStore record не создаётся до actor bind. В `TaskPromisedUnbound` cancel/restart именно до actor bind terminalizes receipt-backed Task без callback и TaskStore. После actor bind `TaskPromisedActorBound` несёт actor-derived identity, exact promotion intent и durable cancel flag; до commit `TaskBound` этот flag остаётся под ReceiptLedger authority, а `BoundStartCancelGate` + exact TaskStore create/identity/flag readback + `TaskBound` переносят authority в TaskStore. Current `ExecutionClass::KnownLong`, cutoff во время `prepare`/`execute` и любой cutoff после `Reserved::ActorBound/Begun` вместо этого создают `TaskHandoffActorBound { begun, exact intent }` и пытаются exact TaskStore create/readback; proven Capacity до `Begun` закрывает receipt-backed `task_capacity`, а после `Begun` оставляет поток в `TaskReceiptOwnedActorBound` без TaskStore record. Общей физической транзакции между stores нет; атомарно меняется источник projection после exact reconciliation. Граница остаётся 7 000 мс от приёма `tools/call`; тесты используют fake clock и barrier.
- Для `TaskBound { begun:false }` start и cancel линеаризует один live per-invocation `BoundStartCancelGate`, который также охватывает transfer cancel-authority в `bind_task`. Под held guard start reauthorize-ит actor/lease proof, затем TaskStore sole-writer одной atomic `start_working_if_not_cancel_requested` без separate false-read либо возвращает durable cancel/terminal winner, либо commits exact versioned Queued→Working/readback. `mark_bound_task_begun(guard, authorization, readback)` повторно проверяет proof, пишет receipt begun, после чего gate освобождается и вызывается `service.prepare`. Cancel берёт тот же gate, заново определяет текущий durable authority, commits flag/terminal и только затем сигналит token. Missing/foreign/stale proof до authorization ничего не меняет; stale после Working запрещает begun/prepare и ведёт к fail-stop/recovery interrupted-before-execution. Executor удерживает proof/actor/resource lease до terminal cleanup или смерти PID. До receipt begun commit `resolve_task` маскирует underlying Working как queued. Crash с Queued/Working и `begun:false` terminalizes cancelled только при durable TaskStore flag, иначе interrupted-before-execution; crash после receipt `begun:true` terminalizes `outcome_uncertain` без replay; `begun:true` + Queued является fail-stop mismatch.
- Direct terminal result/rejection сначала durable-фиксируется в ReceiptLedger, затем пишется в private submit session. Потеря transport при живом daemon или restart после durable terminal commit возвращают тот же result до часовой terminal expiry. Private exact ACK той же identity компактирует его в bounded dedupe tombstone; без ACK physical expiry/delete освобождает quota без tombstone. Это не public API.
- `TaskReceiptOwnedActorBound` остаётся в том же 64-record/541 065 216-byte live payload pool до receipt-backed terminal; proven TaskStore `Capacity` не вытесняет чужой Task, не занимает link slot и не повторяет create после `Begun`.
- ReceiptLedger и TaskStore имеют независимые count/byte caps и retention. Один общий live count cap 64 охватывает `CancelReserved`, `Reserved`, promised/handoff, `DirectTerminalUnacked` и `TaskTerminalReceiptBacked`; actual-plus-reserved byte cap равен 541 065 216 (`64 × 8 454 144`). `CancelReserved` занимает один count slot и ≤1 024 bytes metadata без result reservation; exact submit атомарно получает полный result reserve в том же byte cap. `DirectTerminalUnacked` хранится час либо до ACK; по истечении часа physical deletion освобождает exact live count/result quota без tombstone. `TaskTerminalReceiptBacked` хранится час от terminal epoch без Direct ACK. Submit reserve освобождается только одним из четырёх durable events: exact TaskStore bind/readback, Direct ACK, physical expiry/delete Direct terminal или expiry receipt-backed Task terminal. Отдельные 4 096 bound Task links, 4 194 304 bytes и максимум 1 024 bytes/link живут не короче соответствующей Task. `28 864` post-ACK Direct tombstones (= `32 acknowledged calls/s × 900 s + 64`) хранятся 15 минут, ≤512 bytes каждый и ≤14 778 368 bytes суммарно. W0 проводит 28 800 ACKed lifecycle за fake-clock 900 секунд одновременно с boundary 64 live records и 4 096 Task links; отдельный case удерживает 32 receipt-backed terminals, сохраняет 32 immediate-ACK Direct calls/s и закрыто отклоняет 65-й live receipt. На каждой OS за 60 секунд проходят не менее 1 920 полных lifecycle с p99 ≤250 мс и drain writer queue ≤2 с; неистёкший payload/link не вытесняется.
- После receipt прогресс v0.13 наблюдается polling-ом status и `updatedAt`. Новый public progress/log API и generic resume protocol не создаются. После restart продолжение допустимо только для зарегистрированного typed owner; иначе Task получает terminal outcome без повторного исполнения mutation.
- Engines доставляются лениво из `unica-toolchain` по immutable identity; `prefetch` наполняет offline closure. `tools-download` и raw CLI passthrough не входят в `run`.
- `apply` сначала строит полный staged postimage и validation result, затем публикует Source и WorkspaceCache как закрытый transaction set. Ambient filesystem reads после actor admission запрещены.
- Domain layer не импортирует infrastructure. Типы validation target/finding/failure принадлежат domain; read port принадлежит application; persisted и staged adapters принадлежат infrastructure.
- Любой дефект сначала воспроизводится падающим тестом. Увеличение test/CI timeout не считается исправлением daemon hang или неверной ownership boundary.
- Любой новый Rust test filter сначала выполняется с `-- --list`; ноль найденных тестов является RED infrastructure failure, а не зелёным результатом slice.
- Planned `DEC.2026-08-28.DAEMON-RECEIPT-LEDGER` владеет W0 receipt/dedupe/recovery direction, но его пустой `establishes` не может быть дописан после merge. W0 implementation создаёт newly dated active successor `DEC.*` с realized evidence и полным `establishes`, создаёт derived active `INV.*`/`CTR.*`, а у planned predecessor меняет только `status`/`superseded-by`.
- Planned `DEC.2026-08-28.V0-13-MIGRATION-EVIDENCE-GATE` владеет общей semantic/provenance release policy. До реализации обоих validators он не является действующим правилом; W4 создаёт active successor и derived checkable records в том же PR.
- Изменение публичной поверхности, wire identity, task observation, packaging или границы слоёв вносит successor `DEC.*` и derived `INV.*`/`CTR.*` в том же PR. Body уже merged product record не меняется; у superseded predecessor обновляются только lifecycle-поля `status` и `superseded-by`.
- `tests`, `features`, `log`, gRPC и platform 8.5 profile остаются вне v0.13.
- Публикация tag, prerelease, stable assets и marketplace promotion требует отдельного owner approval по `docs/release-runbook.md`; этот план не даёт такого разрешения.

## Completion Definition

Migration is complete only at S4, when the stable published package—not only source tests—proves the target architecture on all supported hosts. S1 and S2 are internal readiness states; S3 is an RC state. “Daemon exists”, “hidden tests pass” and “CI is green” are necessary evidence but are not synonyms for completed v0.13 migration.
