## Результат и граница работы

Существующий `arch/` становится историей в `docs/arch-v2/`. `docs/arch-v1/`
сохраняется. Новый `arch/` начинается с десяти правил продукта и связанных
с ними содержательных тестов. Владелец оценивает эти десять записей до
расширения набора и переписывания процесса разработки.

После вычитки пилота сокращаем AGENTS.md и создаём локальные скиллы разработки.
`unica-development` — основной вход; общие MCP-скиллы подключаются по
необходимости. `unica-testing` описывает выбор, написание, разметку и запуск
тестов. Количество остальных скиллов определяем по рабочим сценариям.
Существующий release-скилл переносим в общий каталог как `unica-release`;
после переноса удаляем репозиторную папку `.claude/`.

Этот план не требует новых DEC, инвариантов об оформлении или тестов на слова
в Markdown. Изменение организационной модели уже предложено владельцем.
Обязательный слой ADR, сгенерированный индекс и проверки их неизменности
в новый `arch/` не переходят.

Схему из AI_DEV реализуем через существующие входы и скиллы. Сам AI_DEV
остаётся обзором для настройки процесса: не включать его целиком в стартовый
контекст и не копировать каталоги descriptions в AGENTS или этот план.

## 1. Подготовить технически целостный переход

Выполнено в `a9131074`; результаты проверок приведены в конце плана.

Работать в отдельной ветке от актуальной `main`. До изменений проверить статус
дерева, потребителей `arch/` и действующий состав проверок. Список затронутых
путей хранить в рабочем diff или описании PR; новый постоянный реестр миграции
не нужен.

Перенести текущий `arch/` в `docs/arch-v2/` целиком. Сохранить содержание
исторических записей. В начале архивного README добавить краткую отметку
об архивном статусе и исходном коммите. Однократно сравнить перенесённые файлы
с исходным Git-деревом; единственное ожидаемое изменение снимка — эта отметка.
Не создавать checksum-манифест и постоянные тесты заморозки нового архива.

Отделить живые данные от исторического снимка. Планируемые рабочие пути:

| Текущий вход | Новый рабочий путь | Потребители |
| --- | --- | --- |
| `arch/tool-surface.md` | `docs/tool-surface.md` | Генератор поверхности, проверка пакета и release proof |
| `arch/tool-surface-review.json` | `tests/fixtures/v013/tool-surface-review.json` | Контрактные тесты, MCP smoke, генератор поверхности |

| `arch/meta-capability-parity.json` | `tests/fixtures/migration/meta-capability-parity.json` | Проверки снятого DSL и миграционной совместимости |

Исторические копии остаются в `docs/arch-v2/`. Исполняемые проверки и генераторы
читают рабочие файлы. Перенос путей не меняет содержимое машинных контрактов.
Сводка поверхности пока сохраняется как вход существующих инструментов;
она не становится сводным реестром архитектурных обязательств.

Проверить весь путь данных: `scripts/ci/generate-tool-surface.py` (включая
порождаемые ссылки), `scripts/ci/smoke-unica-mcp.py`, Rust `include_str!` в

- убрать из `.github/PULL_REQUEST_TEMPLATE.md` требования DEC, индекса и стражей

- минимально поправить AGENTS.md: обозначить архив, новый пилот и прекращение

- одновременно снять в AGENTS и CONTRIBUTING безусловную обязательность

- исправить ссылку из `docs/release-runbook.md` на
  `arch/decisions/2026-08-20-engines-come-from-the-toolchain.md`: архивная запись
  остаётся историческим основанием в `docs/arch-v2/`, действующий порядок
  выпуска задаёт runbook.

До создания скиллов сохранить классификацию задач и независимые проверки
в AGENTS. Их удаление из старого места и подключение нового выполнить одним
изменением на этапе 4. Переходные входы не должны требовать отсутствующих
скиллов или чтения прежнего индекса.
Разово проверить такой вход в новой сессии: нет поручений создавать DEC,
запускать удалённый `tests/arch` или читать отсутствующий файл; существующий
релизный маршрут по-прежнему доступен.

Не переносить в архив единственный рабочий экземпляр фикстуры. Если живая
проверка использует содержательные данные из старого документа, выделить их
в рабочую фикстуру. Упоминание источника в комментарии не равно зависимости
исполнения от архива.

**Граница безопасности перехода:** поведение продукта и его действующие
содержательные тесты сохраняются. Отсутствие обязательства в первой десятке
не разрешает менять существующую гарантию или удалять её проверки.
Архив читается для конкретного исторического вопроса, а не как второй
обязательный набор инструкций. Пилот не объявляется полным описанием продукта.

## 2. Написать первые десять правил

Выполнено в `a9131074`. В `1ccb5c47` все десять правил переписаны понятным
языком по замечаниям владельца; гарантии, `id` и `check` сохранены.

Владелец выбрал разнообразную десятку для проверки подхода. В неё должны войти
изоляция данных, владение, отсутствие побочных эффектов, граница компонентов
и публичный контракт. Предложения формулировок проверяем по коду и телам тестов.

Начальная форма: `arch/rules/<понятное-имя>.md`, одна гарантия на файл.
В `arch/README.md` — назначение каталога и граница пилота. Сводную таблицу всех
записей и отдельный генератор индекса не создаём.

Формат — Markdown с коротким YAML-блоком. Два свойства:

- `id` — постоянное имя обязательства для ссылок и обсуждения;
- `check` — список точных адресов тестов `путь::имя_теста`, даже если тест один.

Ниже — заголовок и короткий текст обязательства с границей действия.
Краткую причину добавляем, когда без неё легко принять неверное решение.
Поля `status`, `decision`, `governs`, `supersedes`, `establishes` и повтор
текста правила в свойствах не нужны. Существующий ID сохраняем, если смысл
обязательства сохраняется; выделенная из составного правила гарантия получает
собственное имя. Поля уже существующей исполняемой схемы не пересказываем.
Согласование самих обязательств фиксируется в задаче или PR. Согласие с планом
пилота не подменяет вычитку десяти конкретных формулировок.

Пример формы:

```markdown
---
id: INV.CACHE.INDEX-PREVIEW-WRITE-FREE
check:
  - crates/unica-coder/src/infrastructure/workspace_index.rs::dry_run_does_not_start_indexing_or_write_state
---

# Preview индексирования

Preview индексирования не запускает сборку индекса и не записывает
его состояние.
```

В реальной записи ссылка ведёт к точному файлу, а команда запуска учитывает
крейт, test target и профиль. Несколько сценариев допустимы для одного
обязательства; тест-обёртка ради единственной ссылки не нужен.
YAML служит удобству чтения и поиска. Новый валидатор формы записей
или тест на наличие этих свойств в Markdown в пилоте не создаём.

### Проверка связи правила с тестом

Для каждого кандидата:

1. Найти тест в исполняемом наборе. Отсутствующий, игнорируемый или не попадающий
   в заявленный профиль тест не считается действующей защитой.
2. Прочитать тело теста и ограничить обещание тем, что проверяется.
3. Запустить выбранную проверку на исходной реализации.
4. Назвать нарушение и показать, где тест его обнаруживает: существующим
   негативным сценарием, отрицательной фикстурой или инъекцией отказа.
   Временная мутация нужна, если по телу и сценариям теста это остаётся неясным.
5. Если выполнялась мутация, восстановить реализацию и повторить проверку.
   Мутация не входит в PR.

Если проверка не обнаруживает нарушение, зафиксировать пробел и исправить
саму проверку с воспроизведением. Если это требует отдельного изменения продукта,
вынести его из пилота и согласовать замену кандидата. Нельзя получить десять
«закрытых» записей за счёт проверки названий, skip или ослабления утверждения
без обсуждения с владельцем.

Для семи Rust-проверок используется обычная библиотечная цель `unica-coder`.
Сначала подтвердить отбор ровно одного неигнорируемого теста, затем запустить:

```sh
cargo nextest list -p unica-coder --lib --profile default -E 'test(=infrastructure::workspace::tests::git_worktree_boundary_prevents_parent_workspace_discovery)'
cargo nextest run -p unica-coder --lib --profile default -E 'test(=infrastructure::workspace::tests::git_worktree_boundary_prevents_parent_workspace_discovery)'
```

Повторить с именами из таблицы. `--profile pr` для доказательства всей десятки
не подходит: он исключает medium-тесты workspace и MCP. Для Python использовать
`python3.12 -m unittest <модуль>.<класс>.<метод>` из таблицы. Результат `skip`
не засчитывать как проверку; POSIX-обязательство проверять на POSIX.

## 3. Остановиться и вычитать пилот

Проверка трёх сценариев и редактура по замечаниям выполнены. Окончательное
принятие структуры и формулировок владельцем остаётся открытым шагом.

На этом этапе предъявить владельцу десять записей и результаты их проверок.
До принятия структуры не переносить остальные правила и не закреплять
окончательное разбиение скиллов.

Проверить удобство на трёх реальных сценариях в свежем контексте агента:

- локальная правка с сохранением обязательств: найти применимое правило,
  выбрать проверку, обойтись без архитектурной записки;
- предложение разделить ранее изолированное состояние: найти конфликт,
  объяснить цену сохранения и изменения правила, передать выбор человеку;
- предложение ввести организационный порядок: оставить его вне `arch/`.

Смотрим, какие файлы агент открыл, какое действие выбрал и какие проверки
потребовались. Ответ агента о том, что он «понял правила», не является проверкой.
Скептик ищет лишние обязательства и более простой способ решить задачу.
Замечания владельца исправляются на этой десятке.

## 4. Подключить скиллы и загрузку контекста

Согласованный состав и кандидаты для проверки после пилота:

| Скилл | Когда нужен | Результат |
| --- | --- | --- |
| `unica-development` | Исследование и изменение самого продукта Unica | Граница задачи, нужные правила и проверки, реализация и подготовка PR |
| `unica-testing` | Написание, изменение или ревью тестов; выбор проверок для задачи | Проверяемое поведение, место теста, размер, разметка и достаточный запуск |
| `unica-writing` | Создание, редактура или ревью текстов Unica | Понятные правила, комментарии, документация, сайт и тексты GitHub без обязательного `/post` |

### Основной скилл и чтение правил

В `unica-development` перенести классификацию задач, организацию независимых
проходов скептика и reviewer, разбор замечаний, границы PR и работу с очередью.
Сохранить различие независимого ревью и самопроверки. Если появится
`unica-review`, основной скилл выбирает момент проверки, а её процедуру
хранит review-скилл. Перенос не отменяет независимость проверяющего.

Дать агенту маршрут до выбора решения: область изменения → ближайшие исходники
и тесты → поиск в действующем `arch/` по путям и предметным понятиям → чтение
применимых правил. При расширении задачи повторять поиск только для новой
области. Спецификацию XML/DSL, MCP-схему и предметную справку дочитывать там,
где они нужны для решения. Не ждать первого падения теста, чтобы узнать правило.

При конфликте с обязательством показать цену соблюдения и изменения;
дождаться только ещё не принятого решения. Явное решение пользователя в этой
задаче повторно не согласовывать. Перед передачей работы или сжатием контекста
по возможности сохранить пути/ID правил, существенные ограничения, решения
и следующий шаг в сводке задачи. При продолжении проверить её полноту;
потерянные ссылки восстановить поиском и перечитать нужное. Нового постоянного
документа памяти не создавать и сохранность всей истории не обещать.

### Контекст инструментов

Для обычной Rust/Python-правки не вводить обязательный набор внешних MCP.
Различать CLI сборки/тестирования, LSP rust-analyzer и MCP-клиент Inspector.
Для GitHub использовать доступный connector либо `gh`; конкретный сервер
не закреплять как предпосылку любой работы.

При изменении MCP проверять бинарь текущего checkout с нужным cwd и отдельным
состоянием демона. Агент читает схему затронутого tool и ответ сценария;
полный `tools/list` нужен для проверки состава поверхности. Успех установленного
плагина не является проверкой изменяемой сборки. В текущем коде восемь основных
tools и три дополнительных в профиле совместимости Tasks: не требовать
одиннадцать во всех профилях. Каталог и описания брать из проверяемой сборки,
не из снимка AI_DEV. Внутренние движки Unica не подключать как дополнительные
публичные серверы агента.

### Скилл тестирования

Создать `.agents/skills/unica-testing/SKILL.md`. Его порядок действий:
определить проверяемое поведение → выбрать границу и место теста → назначить
размер → воспроизвести нарушение → проверить исправление и затронутый набор.
Для новой возможности сначала сформулировать ожидаемый результат; для дефекта
получить падение по его причине до исправления. Если автоматическое
воспроизведение недоступно, назвать ограничение и способ проверки.

**На что писать.** На новое или изменённое поведение продукта, воспроизводимый
дефект, публичный контракт, инвариант, границу данных или компонентов.
Выбирать нужные случаи отказа, отмены, восстановления и конкуренции по риску
изменения. Сначала искать существующий тест: расширение его сценариев может
быть достаточным. Архитектурное правило связывать с тестом конкретного нарушения;
отдельная копия теста ради ссылки из `arch/` не нужна.

**На что не писать.** На наличие фраз, заголовков и объём прозы в AGENTS,
скиллах и архитектурных записях; на факт прошлой ручной проверки; на детали
реализации, изменение которых сохраняет контракт. Не создавать тест,
который повторяет вычисление проверяемого кода или дублирует готовое доказательство.
Исследование платформы отделять от регулярных проверок регрессии. Эталонный
XML, ответ MCP, схема или конфигурация, читаемая программой, могут быть
полноценными тестовыми входами: запрет касается проверки прозы вместо поведения.

**Где и как писать.** Выбирать ближайшую границу, на которой нарушение видно:
чистую логику проверять рядом с модулем, взаимодействие компонентов — через
их реальные интерфейсы, протокол и запуск продукта — интеграционным тестом.
Python-проверки CI и инструментов разработки оставлять в соответствующих
наборах `tests/ci/` и `tests/dev/`. Архитектурное назначение не требует
отдельного каталога или размера. Ожидаемый результат выводить из контракта;
проверять наблюдаемый результат и необходимые побочные эффекты. Внешние
зависимости можно подменять, проверяемую гарантию — нельзя. Изолировать файлы,
процессы и состояние; управлять временем и случайностью, освобождать ресурсы
при падении. Для проверок границ кода использовать структуру зависимостей
и положительные/отрицательные примеры, а не поиск имени служебной функции.
Повторы, произвольные задержки и `ignore` не устраняют причину нестабильности.

**Размер и разметка.** Сохранить имена `small`, `medium`, `large`.
Объяснить их через стоимость запуска и зависимости. Вид теста
(модульный, интеграционный, контрактный) выбирать отдельно от размера.

| Размер | Как выбирать | Как задан в текущем конвейере |
| --- | --- | --- |
| `small` | Локальная проверка с малыми затратами, без запуска продукта и сетевого взаимодействия | Остаток после отбора старших размеров; отдельной аннотации в тесте нет |
| `medium` | Процесс продукта, сокет или взаимодействие, требующее интеграционного окружения | Rust: все Cargo integration targets и тесты файлов с признаками процесса/сокета; Python: записи `[medium].entries` в `.config/python-sizes.toml` |
| `large` | Нагрузка, ёмкость, длительный сценарий или существенное потребление ресурсов, необходимое для доказательства | Rust: явные фильтры в `.config/nextest.toml`; Python-переопределение в `large` пока не реализовано |

Текущая классификация приблизительна: Rust анализирует весь файл, поэтому
чистый тест в нём тоже может стать `medium`. Не объявлять его `small`
по одному названию и не обходить классификатор ради быстрого PR.
Генерируемые Rust-блоки обновлять `python3.12 scripts/ci/size-filters.py --write`;
команда вызывает Cargo и может собирать тесты. Фильтры `large` она не меняет.
Python размечать по имени модуля, класса или метода в манифесте. При появлении
Python-теста `large` потребуется поддержка в runner; одной записи в TOML
недостаточно. Подробности брать из действующего кода, не заводить второй реестр.

**Что запускать.** Сначала точный тест до и после исправления, затем достаточные
проверки затронутого поведения и обязательные проверки перед push/слиянием.
Расширять или повторять локальный прогон при сбое, новой неопределённости
или требовании CI. Профили `scripts/ci/run-tests.py`:
`pr` — small, `queue`/`main` — small и medium,
`release`/`all` — все размеры. Профиль `large` выбирает тяжёлые Rust-тесты;
на Windows у него отдельный отбор. По листингу и отчёту убедиться, что нужный
тест действительно исполнился с нужными features. Пустой отбор, пропуск
и `--dry-run` не считать проверкой поведения. Объяснить отдельный запуск
`daemon_receipt_ledger` с `receipt-ledger-test-support` через штатный runner;
не включать эту feature всему workspace. `all` не включает автоматически
все features и ignored-тесты. После правки разметки проверять её стражи
(`test_size_guard`, `test_gate_profiles`, `test_python_sizes`) по затронутой
экосистеме. Состав запусков сверять по runner, обоим конфигам и workflow;
устаревшие комментарии не переносить в скилл.

**Что дочитать после падения.** Научить скилл различать ошибку утверждения,
сбой окружения/сборки и отсутствие исполнения. Из свежего вывода или отчёта
получить `fullName`, target, профиль и features; затем установить исходный
файл, модуль/класс и тело теста. `fullName` не равен адресу `check`.
Искать точный `путь::имя_теста` в действующем `arch/`, открыть совпадения
в `check` и прочитать связанные обязательства. Ноль или несколько записей —
допустимый результат; правило ради заполнения связи не создавать.
Это действие агента, а не существующая функция runner. Новый автозагрузчик,
обратный индекс и ссылки на архитектуру в каждом тесте для пилота не нужны.

### Перенос release-скилла

При подготовке плана в `.claude/` найден один файл:
`.claude/skills/release/SKILL.md`. Перед исполнением повторить проверку,
включая скрытые и игнорируемые файлы; не удалить появившиеся локальные настройки
вместе с перенесённым скиллом.

Перенести его в `.agents/skills/unica-release/SKILL.md` и установить
`name: unica-release`. Описание должно обозначать выпуск самого Unica и
продолжение незавершённого выпуска. Убрать `argument-hint` и другие расширения
конкретного хоста; версию принимать из запроса пользователя. Инструкции писать
по-русски, команды и технические имена сохранять.

Сверить действия с `docs/release-runbook.md` и текущими workflow. Убрать
устаревшие ссылки на ADR и повторное изложение процедуры; оставить маршрут
в runbook и необходимые условия выбора шага. Сохранить границы согласования
публикации, обращения с подписью и неизменности уже выпущенных артефактов.
Перенос скилла не разрешает публикацию релиза.

После переноса проверить ссылки и удалить оставшиеся пустые каталоги `.claude/`.
Менять только обращения к локальному release-скиллу. Пути `.claude/skills/...`
в сведениях о внешних донорах и их проверках описывают чужие репозитории;
их не заменять массовым поиском.

Различать фактическое и требуемое поведение: код показывает, что работает,
согласованное обязательство — что должно сохраняться. Расхождение разбирается
как дефект либо предложение изменить правило. Агент не переписывает правило
под текущую реализацию без согласования.

## 5. Проверить скиллы на работе и завершить пилот

Для `unica-writing` проверены инструкция и обнаружение в текущей сессии Codex.
Полная проверка разработки в свежих сессиях обоих хостов остаётся впереди.

Три сценария этапа 3 использовать как исходный замер. После создания минимальных
скиллов повторить их в свежих сессиях Codex и Claude. Сравнивать фактические
чтения и действия, не самоотчёт агента. В Codex проверить обнаружение
`.agents/skills`; в Claude — загрузку AGENTS через импорт и выбор скилла
по шапке после удаления `.claude/`. Наличие файлов на диске этого не доказывает.

Дополнить эти проходы следующими проверками; совмещать их в одном сценарии,
когда это проверяет тот же маршрут:

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Локальная правка и независимое ревью | Нужное правило прочитано до решения; reviewer получил задачу, diff и основания. Полные CONTRIBUTING, CODE_OF_CONDUCT, AI_DEV, весь `arch/` и тела неприменимых скиллов не дочитываются |
| Дефект с известным `check` | Падение воспроизведено по его причине; агент по полному имени нашёл исходник и правило, сохранил гарантию при исправлении. Отдельно разобрать отсутствие связи и несколько совпадений |
| Выбор проверки процесса MCP или тяжёлого сценария | Выбраны место, размер и действующая разметка; нужный тест действительно исполнился. Агент распознаёт профиль, который его пропускает, и не считает сбой запуска нарушением архитектуры |
| Изменение MCP-поверхности | Проверена нужная сборка и профиль; схема tool загружена по задаче. Старый установленный плагин не выдан за проверку checkout |
| Правка прозы или организационной инструкции | Нет нового продуктового обязательства и теста на слова; нужный процесс остаётся в скилле |
| Продолжение после передачи или сокращения контекста | Агент восстанавливает применимые правила по ссылкам или поиском, учитывает уже принятое решение и не требует согласовать его снова |
| Запрос о состоянии выпуска | В обоих хостах прочитаны общий `unica-release` и runbook, предложен следующий шаг без публикации |

Если хост недоступен для прогона, назвать конкретный непроверенный маршрут;
не подменять его проверкой текста. Короткий результат вычитки и ссылки
на свидетельства оставить в задаче или PR. Новый постоянный реестр сценариев,
файлы отчётов о чтении и тесты на текст скиллов не нужны.

Формат frontmatter проверить штатным валидатором скиллов: эти поля читает хост.
Полезность инструкции проверять действиями агента. Тесты на слова, заголовки
и длину текста в AGENTS.md или SKILL.md не писать.

Редактуру выполнять через `unica-writing`: нужные приёмы уже включены
в проектный навык, внешний `$post` не требуется. Проверять его на реальных
задачах разных жанров, сохраняя факты и границы обещаний; отдельная редполитика
и тесты на формулировки для этого не нужны.

Результат пилота: архив v2 сохранён, десять правил приняты человеком,
проверки обнаруживают названные нарушения, AGENTS и скиллы направляют к нужной
части продукта до изменения и после ошибки, оба хоста проходят проверку
маршрута, CI не зависит от архивной прозы. Массовый перенос оставшихся
обязательств — следующая работа после оценки результата.

## Границы коммитов и PR

Первый связный набор изменений — архив v2, рабочие пути контрактных данных,
снятие старых стражей, десять правил и переходные правки AGENTS, CONTRIBUTING,
PR-шаблона и живых ссылок runbook.
До вычитки владельцем он остаётся в рабочей ветке. Публикуемый к слиянию PR
должен быть целостным и иметь зелёные применимые проверки.

Второй набор — `unica-development`, `unica-testing`, принятые дополнительные
скиллы, перенос `unica-release`, удаление `.claude/`, подключение обоих хостов
и согласованная редактура AGENTS/CLAUDE/CONTRIBUTING. Перенос процесса
из AGENTS и подключение его нового владельца неделимы. AI_DEV уточняется
по результатам фактической проверки маршрутов.
Если это отдельный PR, его база — актуальная `main`
после слияния первого. Не создавать стек PR с базой в открытой head-ветке.

Во время пилота не менять гарантии продукта, не публиковать релиз и не
переносить сотни оставшихся правил. Найденные ранее существовавшие дефекты
учитывать отдельно; ошибки, внесённые самим переходом, исправлять в нём же.

## Проверки целостности переноса

Кроме десяти проверок правил выполнить затронутые проверки инфраструктуры:

- `tests.ci.test_run_tests`, `test_python_sizes`, `test_unica_workflow`,
  `test_release_proof` — состав и запуск CI;
- `tests.ci.test_v013_implementation_coverage`, `test_v013_surface_first_matrix`,
  `test_meta_surface_contract`, `test_subsystem_surface_contract`,
  `test_unica_skills`, `test_unica_mcp_script_parity` — новые пути данных;
- оставшиеся содержательные проверки `test_format_profile_contract` и
  `test_product_contracts`; проверки прежнего оформления документов снять
  одновременно с архивированием, не откладывая до создания скиллов;
- `tests.ci.test_smoke_unica_mcp` — разрешение ledger в checkout и отказ читать
  файл за его пределами;
- `cargo test -p unica-coder --lib tool_specs_match_reviewed_result_contracts`
  и `python3.12 -m unittest tests.ci.test_tool_surface_ledger` — Rust include,
  генератор и живой MCP; после правок Rust также `cargo fmt --all -- --check`
  и `cargo clippy --workspace --all-targets --all-features -- -D warnings`.

Python-наборы запускать с зависимостями `tests/ci/requirements.txt`; не удалять
`tree-sitter`, он нужен оставшимся проверкам границ продукта. Проверить новую
матрицу через `python3.12 scripts/ci/run-tests.py --profile pr --python-matrix`.
Перед слиянием — штатные проверки PR и очереди. Это план запуска, а не отчёт
об уже пройденных тестах.

Перед первым PR сравнить собранные наборы тестов до и после перехода.
Каждое исчезновение должно объясняться удалением проверки прежнего
документооборота; содержательные тесты остаются исполняемыми. Результат
показать в PR. Постоянный список тестов или новый страж для этой сверки не нужен.

Разово проверить живые зависимости поиском по `crates/`, `scripts/`, `tests/`,
`.github/`: старые пути данных и удалённые команды не должны исполняться,
`docs/arch-v2/` не должен стать новым входом CI. Поиск служит проверкой переезда;
постоянный тест на отсутствие слов в файлах из него не делать.

## На какие рекомендации опираемся

- [OpenAI: AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md):
  учитывать порядок загрузки инструкций и проверять получившуюся конфигурацию
  в новой сессии. В корневом файле оставляем только постоянные ориентиры.
- [OpenAI: skills](https://learn.chatgpt.com/docs/build-skills): один навык
  решает определённую задачу; описание задаёт границы выбора, подробности
  загружаются по необходимости. Репозиторные навыки доступны из `.agents/skills`.
- [Anthropic: Claude Code best practices](https://code.claude.com/docs/en/best-practices):
  сокращать постоянные инструкции, загружать условные процедуры через навыки
  и проверять результат работы агента.
- [Anthropic: skill authoring](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices):
  начать с реальных сценариев и исходного поведения, затем добавить минимальную
  инструкцию и проверить изменение результата.
- [Anthropic: размещение skills](https://code.claude.com/docs/en/skills):
  штатное обнаружение использует `.claude/skills`. По выбору владельца этот
  каталог удаляем; в Claude используем явное чтение общего файла через
  корневые инструкции и проверяем этот маршрут в новой сессии.

Это основание для предложенной организации. Точный состав навыков и размер
инструкций определит пилот, а не числовой лимит из документации.
