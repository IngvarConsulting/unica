# Code Search

## MCP routing

- Preferred path: use MCP `unica` tools `unica.search`, `unica.view`, and and.
  `unica.check`.
- Не зови индекс кода, анализатор или пакетные адаптеры напрямую: они спрятаны
  за MCP `unica`.
- Имя набора исходников — не константа. Его называет `unica.view {}`;
  `"main"` в примерах ниже иллюстрация, а не умолчание. В адресе имя стоит до
  двоеточия: `main:Document.Заказ`.

## Tool choice

- MCP-first discipline: держись публичных `unica.*` до того, как спускаться к
  оболочке. К поиску по файлам переходи, только когда вызовы выше не закрыли
  пробел, и сообщай what was tried, если это важно для ответа.
- **Что искать** выбирает свод. `unica.search` с `corpus: "text"` (умолчание)
  ищет по тексту BSL. Локальное совпадение сохраняет `scope`, `line`, `column`
  и `snippet`; его `at` открывай напрямую в `unica.view`: это
  `…Method.<Имя>.Body#L<n>` внутри установленного метода либо
  `…Body#L<n>` вне метода. Номер строки абсолютный, от начала файла.
  Провайдерный результат тоже получает такой `at`, когда текущий исходник
  подтверждает его строки и фрагмент. Символьное имя от поставщика само
  по себе не доказывает границы метода. Если их установить нельзя,
  `limits` называет предел; адрес строки Body модуля не доказывает,
  что строка находится вне метода. Если текущий текст не подтверждает
  фрагмент поставщика, сохраняется исходное свидетельство с `limits`,
  без выдуманного адреса чтения.
  Совпадение без доказанного модуля (файл вне раскладки,
  незарегистрированный владелец) приходит без `at`, с причиной
  `unaddressed` и `fileId`. С `corpus: "names"` поиск по именам и синонимам
  отвечает `at`, `kind`, `title` объекта. Физического пути нет ни у одного свода.
- **Чем искать** выбирает `role` в текстовом своде: `symbol` идёт по индексу
  символов, `semantic` — по смыслу. Без `role` поиск буквальный: строка
  целиком, `regex: true` — регулярное выражение, `ignoreCase: true` — без
  учёта регистра. Он принимает корень конфигурации, поддерево объекта
  метаданных или один модуль, например `main:Catalog.Items.Module.Object`:
  поиск не расширится до соседних модулей. Роли `lexical` нет.
- Первая страница буквального поиска несёт `data.totals` — точный объём всей
  области: `matches` и `files`, раскладку `kinds` по видам объектов,
  `unaddressed` без адреса, модули-лидеры `modules` с адресом и счётом и
  остаток `rest`. Сначала прочитай её и реши, нужен ли весь поток: если
  совпадений много, а нужное — в нескольких лидерах, сузь `scope` до модуля
  или объекта лидера; иди по курсору, только когда нужны все места.
  Продолжения сводку не повторяют. Долгий подсчёт, особенно без Git, может
  прийти заданием: дождись его результата.
- Если `symbol` завершён со `status: "empty"` и `searchComplete: true`,
  поставщик не нашёл символ. Это успешный пустой результат. Ожидание индекса
  с `dependencyPending` требует повторить тот же запрос; оно не доказывает
  отсутствия символа. `indexFreshness: "unknown"` сохраняет предел актуальности.
- `scope` сужает поиск до одного логического поддерева. У локального поиска
  по тексту и именам `limit` задаёт размер страницы (по умолчанию 20,
  максимум 50). Пока есть `cursor`, продолжай с теми же аргументами поиска.
  `page.stoppedBy: "complete"` означает конец полученного потока. Буквальный
  поиск идёт страницами до последнего совпадения; `stoppedBy: "deadline"` с
  курсором значит, что страница кончилась по времени, а обход продолжается:
  иди по курсору, даже если совпадений на странице нет. Если прочитанная часть
  изменилась, курсор отвечает `stale_cursor`; начни поиск заново. Роли
  провайдеров дают страницы только внутри полученного окна: если секция
  сообщает `limitReached`, последняя страница не доказывает полноту поиска.
  При 200 полученных совпадениях попроси пользователя уточнить искомое, прежде
  чем искать снова; `scope` предлагай только для поиска без роли, поскольку
  `symbol` и `semantic` пока не поддерживают ограничение логическим поддеревом.
  Меньшие пределы `bsl-analyzer` и RLM сохраняй как неполный результат, не
  называя запрос слишком широким только по этому признаку.
- Признак `approximate` у попадания по имени означает совпадение по близости,
  а не точное. Проверяй `sourceCoverage`: при `complete: false` часть
  дескрипторов не прочитана, `omitted` и `details` называют число и причину
  пропусков. Даже пустая выдача тогда не доказывает отсутствия объекта.
- **Читать узел** — `unica.view {at}`. У владельца есть ветвь `Module`, у
  модуля — `Method`, у метода — подпись, контекст компиляции, собственные
  строки и ветвь `Body` с исходным текстом метода. Это дешевле, чем читать модуль
  целиком, и точнее, чем догадываться по совпадению.
- **Граф вызовов** — ветви `Caller` и `Callee`, которые узел метода называет
  в `branches` без счёта. Читай их адресом ветви:
  `unica.view {at: "<метод>.Caller"}`. Секции `callGraph` у `view` нет.
  Ответ ветви называет состояние графа в `props.callGraph`: страница соседей
  приходит только при `ready`, а `indexing` просит повторить позже. Если
  анализатора нет, а установка может заказать его поставку, ветвь заказывает
  её этим же вызовом; при `delivery_in_progress` повтори тот же вызов.
  Иначе ответ — отказ `provider_absent` с полями движка в `data`: `tool`,
  `stage` и следующий шаг в сообщении. Передай пользователю этот шаг, не
  повторяя вызов.
- Профиль объекта метаданных — тот же `unica.view {at}`: состав, модули, права,
  подписки и функциональные опции лежат в его `props` и ветвях.
- Путь к файлу нужен только когда он пришёл снаружи — из диффа, лога сборки,
  трассы или поиска средствами хоста. Тогда его переводит в адрес
  `unica.resolve`. Совпадения `rg -n` передавай одним вызовом в `paths`
  элементами `путь:строка` без колонки и текста совпадения
  (`rg -n --no-heading … | sed -E 's/^((.:)?[^:]+:[0-9]+):.*/\1/'`; путь с буквой диска сохраняет строку): строка внутри метода даёт адрес метода
  (`line: "inMethod"`), строка вне методов — адрес модуля
  (`line: "outsideMethod"`). Ответ `data.items` идёт в порядке входа;
  несуществующий путь или строка отказывают только своему элементу.
  В обычном ходе работы путь не нужен.

## Workflow

1. Разметь пространство: `unica.view {}` называет наборы исходников и их
   формат, когда набор или формат неясен.
2. Найди предмет по имени: `unica.search {corpus: "names"}` с необязательным
   `kind`. Точное имя объекта закрывает вопрос быстрее любого текстового
   поиска.
3. Прочти узел: `unica.view {at}`. Ветвь `Module` ведёт к модулям владельца,
   ветвь `Method` — к его методам; узел метода даёт подпись и строки.
4. Ищи по тексту то, что именем не находится: фрагменты запросов, строковые
   литералы, заголовки, нестандартные токены. `role` нужна, только когда
   вопрос о символе или смысле.
5. Расширяй только после неудачи точного поиска: синонимы, деловые термины,
   префиксы общих модулей, заголовки команд форм.
6. К локальному `rg` спускайся только за файлами вне индекса Unica или когда
   попытки выше не закрыли пробел — и скажи, что было испробовано. Его
   совпадения переводи в адреса одним `unica.resolve {paths}`, а не вызовом
   на каждое.
7. Разделяй объявление, вызов, обработчик и мёртвое совпадение. Поток по
   одному попаданию не выводится.
8. Отчитывайся логическими адресами и строками внутри узла, а не путями к
   файлам; приводи запрос, которым получено важное попадание.

## Common searches

- Object lifecycle: `ОбработкаПроведения`, `ПередЗаписью`, `ПриЗаписи`, `ПриСозданииНаСервере`.
- Managed form flow: command handler, server procedure, client wrapper, form attribute name.
- Integrations: HTTP service root URL, method name, header name, endpoint path, exchange plan node.
- BSP entry points: exported common-module procedure plus surrounding callers.

## MCP examples

```jsonc
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "unica.view",
    "arguments": {}
  }
}
```

Совпадения `rg -n` в логические адреса одним вызовом:

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "unica.resolve",
    "arguments": {
      "paths": [
        "src/Documents/Invoice/Ext/ObjectModule.bsl:4",
        "src/Documents/Invoice/Ext/ObjectModule.bsl:70",
        "src/Documents/Invoice/Ext/ManagerModule.bsl"
      ]
    }
  }
}
```

Объект по имени:

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "unica.search",
    "arguments": {
      "query": "Заказ",
      "corpus": "names",
      "kind": "Document",
      "limit": 20
    }
  }
}
```

Текст внутри поддерева:

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "unica.search",
    "arguments": {
      "query": "ОбработкаПроведения",
      "scope": "main:Configuration",
      "limit": 20
    }
  }
}
```

Символ по индексу — определения и ссылки по имени:

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "unica.search",
    "arguments": {
      "query": "ОбработкаПроведения",
      "role": "symbol",
      "limit": 25
    }
  }
}
```

Кто вызывает метод — ветвь графа:

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "unica.view",
    "arguments": { "at": "main:CommonModule.ПроведениеСервер.Method.ОбработкаПроведения.Caller" }
  }
}
```

Профиль объекта метаданных:

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "unica.view",
    "arguments": { "at": "main:Document.Заказ" }
  }
}
```

Метод целиком: подпись в узле, текст в ветви `Body`:

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "unica.view",
    "arguments": { "at": "main:CommonModule.Продажи.Method.ОбработкаПроведения" }
  }
}
```
