# Metadata Modeling

Use this reference when deciding which class of object holds a piece of business
data, and how its attributes are typed.

Adjacent subjects have their own references: register internals in
`register-design.md`, what a document records and when in `document-posting.md`,
event handlers in `object-events.md`, where code is hosted in
`module-placement.md`.

The normative rules here are development standards, not platform evidence:
`#std432` string attributes, `#std468` custom object presentations, `#std474`
name, synonym and comment, `#std531` and `#std587` the comment and responsible
fields, `#std603` document posting requirements, `#std649` attributes, `#std677`
common attributes, `#std697` predefined items, `#std704` defined types, `#std728`
composite type attributes, and diagnostics `АПК:93`, `АПК:192`–`АПК:195`,
`АПК:304`, `АПК:305`, `АПК:1205`, `АПК:1207`, `АПК:1210`–`АПК:1217`, `АПК:1329`,
`АПК:1330`, `v8cs:db-object-anyref-type`, `v8cs:db-object-ref-non-ref-type`.
Confirm the current wording with `unica.standards.explain` before citing one.

## Which Class Holds The Data

Ask what changes and who changes it:

- **A fact that happened at a point in time** is a document. Registration in
  accounting goes through posting, so most documents post (`#std603`), and an
  unposted document is a draft. What the document then records lives in registers.
- **A relatively stable list of entities the user maintains** is a catalog.
- **A fixed set known when the configuration is written** is an enumeration.
  Enumeration values are metadata child objects, not data rows, so adding a value
  is a configuration change and a deployment — never a user action.
- **A set of kinds the user must be able to extend at run time** is a chart of
  characteristic types. This is the answer whenever "the customer will add their
  own types later" appears in the requirements and an enumeration was the first
  instinct.
- **One value for the whole infobase** is a constant.
- **A resource accumulated or a state keyed by dimensions** is a register; the
  class choice among registers is in `register-design.md`.

A value that several objects carry identically across the configuration may be a
common attribute (`#std677`) rather than a repeated attribute.

## Typing Attributes

### Strings

- Use variable allowed length and always set a maximum (`#std432`). Fixed length
  is only for a genuine guarantee of equal length through right-padding; it is
  otherwise `АПК:1205`.
- Where the maximum is externally regulated, use that number. Where a string is
  built by concatenation, size it as the sum of its parts. Where nothing
  regulates it, pick a limit that covers the normal case.
- Unlimited length is for two cases: large user text in a multiline field — the
  comment field of `#std531` is the canonical one — and technical strings
  generated by programs and not meant to be read.

### Composite Types

`#std728` is the standard most often violated by convenience:

- A composite attribute used in joins, filters, or sorting must contain only
  reference types. Do not mix in `Строка`, `Число`, `Дата`,
  `УникальныйИдентификатор`, `Булево`, or `ХранилищеЗначения`: the physical
  storage of composite types makes such queries markedly slower (`АПК:1329`,
  `v8cs:db-object-ref-non-ref-type`).
- To combine a reference with free text, add a separate catalog for the free
  values instead of a primitive type — an `Адрес` attribute takes `Контакты` plus
  a `ПроизвольныеАдреса` catalog, not `Строка`. Fill that catalog automatically
  on write and clean unused items with a scheduled job.
- Tables known to stay small, up to about a thousand records, can be excepted.
- Do not use `ЛюбаяСсылка`, `СправочникСсылка`, `ДокументСсылка` and similar
  universal composites on stored objects; list the types explicitly
  (`АПК:1330`, `v8cs:db-object-anyref-type`). Universal mechanisms genuinely
  written for arbitrary references are the exception.
- The cost of an over-wide composite is concrete: dotted access without
  `ВЫРАЗИТЬ` joins every table in the type; deleting a referenced metadata object
  forces restructuring; algorithms grow to support types the task never needed;
  the user picks from a type list far longer than the three to five that matter;
  and marked-object deletion pays more for reference search and table locks.

### Defined Types

`#std704`: when a type is used widely and may change on implementation, declare
it once as a defined type and reference it everywhere — object attributes,
resources, form attributes, template parameters. It keeps length and precision
identical across every use, and for a composite type used across a subsystem it
fixes one type set instead of a dozen hand-maintained copies.

## Predefined Items

`#std697` (platform 8.3.3 and above, outside 8.2 compatibility mode):

- Prefer creating predefined items automatically: keep
  `ОбновлениеПредопределенныхДанных = Авто`, and do not flip the mode from code
  with `УстановитьОбновлениеПредопределенныхДанных` (`АПК:304`, `АПК:305`).
- Deny interactive deletion of predefined data. The four rights —
  `ИнтерактивноеУдалениеПредопределенныхДанных`,
  `ИнтерактивнаяПометкаУдаленияПредопределенныхДанных`,
  `ИнтерактивноеСнятиеПометкиУдаленияПредопределенныхДанных`,
  `ИнтерактивноеУдалениеПомеченныхПредопределенныхДанных` — are off by default
  and stay off (`АПК:192`–`АПК:195`).
- Subordinate nodes of a distributed infobase are the exception: predefined items
  are neither created nor updated automatically there and must arrive from the
  main node with the configuration change. So load the exchange message before
  running code that touches them, avoid touching them in main-node load logic and
  registration rules, and run the update handlers that fill them only in the main
  node. With the БСП exchange subsystem from 2.1.4 the first two requirements
  drop.
- For tables whose predefined items are outside any distributed-infobase exchange
  plan and unrelated to tables inside one, set
  `ОбновлениеПредопределенныхДанных = ОбновлятьАвтоматически`. `Авто` is wrong
  there: in a subordinate node `Авто` means do-not-update, and the items are never
  created.

## Names And Presentations

- Names, synonyms and comments follow `#std474`. An object and its own child must
  not share a name (`АПК:1207`, `BSLLS:SameMetadataObjectAndChildNames`).
- Fill object presentation or list presentation; leaving both empty is `АПК:93`.
  A presentation equal to the synonym is not stored, so setting it to the same
  text achieves nothing (`АПК:1210`–`АПК:1217`). Custom presentations are
  `#std468`.
- Overriding a presentation from the manager module is `#std746`; its constraints
  live in `module-placement.md`.
- Documents carry a comment field (`#std531`), and the responsible and comment
  pair follows `#std587`.
- When an object is created on the basis of another, fill every inherited
  attribute (`#std649`).

## Stop Rules

- Do not model an extensible set of kinds as an enumeration.
- Do not mix reference and non-reference types in a composite attribute used in
  joins, filters, or sorting.
- Do not reach for `ЛюбаяСсылка` because the type list is long; list the types.
- Do not add a string attribute without a maximum length.
- Do not switch predefined-data update mode from code.
- Do not change an attribute's type, length, or composite type set without a
  stated migration for the data already stored.
- If public MCP `unica` lacks the operation needed to inspect the object, its
  attribute types, or its predefined items, report a Unica MCP contract gap.
