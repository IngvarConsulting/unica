# Точки входа для агента

## Состояние: архитектура переписывается

Слой архитектурного описания v1 — `spec/decisions/` (71 ADR),
`spec/architecture/` (128 инвариантов, концепции, блоки, runtime) — **заморожен
18.08.2026 и нормативным больше не является**. Он читается как история и не
правится руками.

Нормативный слой v2 (`arch/`) ещё не заведён. Пока его нет, действующими
источниками истины остаются только:

1. **код и тесты** — поведение системы;
2. **`plugins/unica/.mcp.json`**, `plugins/unica/.codex-plugin/plugin.json`,
   `plugins/unica/.claude-plugin/plugin.json`,
   `plugins/unica/third-party/tools.lock.json` — контракт пакета;
3. **`plugins/unica/references/specs/`** — контракт форматов XML 1С; старше
   прозы, но не старше поведения эмиттера, доказанного фикстурой или дампом
   платформы.

Схема v2 предложена в
[`docs/design/2026-08-18-architecture-v2-registries-design.md`](docs/design/2026-08-18-architecture-v2-registries-design.md)
и ждёт принятия. **Не выводите архитектурных правил из замороженного `spec/`**:
запись там говорит, что было решено на свою дату, а не как система устроена
сейчас.

Тесты поведения и формата заморозкой не затронуты и остаются в силе: они
проверяют правду о платформе 1С, а не наши решения.

## Гигиена поиска

Не сканируйте локальные игнорируемые корпуса при обычном изучении репозитория:

- `target`, `.build`, `dist`;
- `docs-local` — локальный исследовательский материал; в поставку не входит и
  источником справки платформы не является, её отдаёт
  `unica.documentation.search`.

Датированные деревья планов и проектных записок отслеживаются гитом, но
описывают, как было сделано прошлое изменение, а не как система ведёт себя
сейчас:

- `docs/design/**`, `docs/plans/**`, `docs/provenance/reviews/**`.

Открывайте их только чтобы восстановить историю конкретного изменения. CI-тест
может закрепить архивный файл по пути как живой тестовый вход — перед удалением
проверяйте `rg <path> tests/ scripts/`.

Начинайте с `rg` и `git ls-files`.

## Проектные документы

Проектные записки — `docs/design/YYYY-MM-DD-<topic>-design.md`, планы
реализации — `docs/plans/YYYY-MM-DD-<feature-name>.md`. Это переопределяет
каталоги по умолчанию в скиллах `brainstorming` и `writing-plans`. Черновики
сессии остаются в игнорируемом `.superpowers/`; никогда не делайте `git add -f`
для игнорируемого пути.

Скиллы superpowers пишут в `docs/`, и когда появится `arch/` — никогда в него.

## Релизы

Публикация версии в публичный маркетплейс выполняется по
[`docs/release-runbook.md`](docs/release-runbook.md). Прочитайте его прежде, чем
действовать по любой просьбе выпустить, отгрузить, продвинуть или доделать
релиз: порядок шагов несёт гарантию о том, что каталог никогда не указывает на
неокончательные байты.

## Правила разработки

- Устраняйте причины, а не симптомы.
- Сначала падающий тест, потом исправление. На любой найденный дефект — кем бы
  он ни был найден — сначала воспроизведение тестом.
- Выносите наружу противоречия между допущениями, документацией, тестами и
  кодом, а не сглаживайте их.
- Публичная граница MCP — один сервер с именем `unica` и инструментами в
  пространстве `unica.*`.
- Видимые модели скиллы остаются MCP-first.
- Один каталог плагина обслуживает Codex и Claude Code; оба манифеста держатся
  на одной версии.
- Изменение публичной поверхности `unica.*` требует перегенерации
  `spec/architecture/tool-surface.md`
  (`python3 scripts/ci/generate-tool-surface.py --binary target/release/unica`).
  Ведомость порождается из бинаря и остаётся живой до появления замены в
  `arch/contracts/`.

## Топология pull request

- По умолчанию — один самостоятельно проверяемый PR на одно связное изменение.
- Не открывайте PR, базой которого является head-ветка другого открытого PR.
- Перед открытием PR посмотрите предполагаемую базу на GitHub; если она не
  `main`, перебазируйтесь.
- Стек из PR допустим, только если пользователь явно об этом попросил.
- Дефект, найденный во время ревью, разбирается по его происхождению: не
  внесённый текущим PR уходит отдельным PR от `main`.

## Обязательные навыки разработки MCP

- `build-mcp-server` — вход для разработки MCP-сервера;
- `build-mcp-app` — для MCP Apps, UI-ресурсов и интерактивных виджетов;
- `build-mcpb` — для MCPB, локальной упаковки и поставки MCP-сервера.
