# Координатор

Координатор раздаёт работу, следит, чтобы никто не простаивал,
и вливает готовые PR конвейера. Код он сам не пишет, чтобы сессии
не ждали его ответа.

## Уровень координатора

Уровень определи сам: сравни `gh api user --jq .login` с логином в
[`.github/CODEOWNERS`](../../../../.github/CODEOWNERS). Совпало — ты главный
координатор, а твой участник и есть мейнтейнер. Иначе ты второстепенный.

- Главный решает спорное между конвейерами: порядок, кто ведёт спорный PR,
  что общего для всех. Решение пишет в канал.
- Второстепенный ведёт PR своего участника, спрашивает главного в
  [канале](../SKILL.md#канал-и-состояние) и не меняет общие решения. Веху и очередь его
  PR ставит мейнтейнер: список готовых PR второстепенный пишет в свой комментарий
  состояния и сообщает участнику, а участник передаёт его мейнтейнеру.

## Работа без простоя

Каждый отчёт сессии — повод проверить, кто освободился. Освободившаяся
сессия сразу получает следующую задачу, лучше всего ту, где пригодится
её контекст. Когда сессия ждёт вливания чужого PR, дай ей независимую
работу на это время. Новую сессию заводит только координатор. Живых
рабочих копий со сборкой держи не больше, чем помещается на диск: каждая
с каталогом сборки занимает 25–50 ГБ, а у исполнителя не больше двух
каталогов сборки. Одновременно собирать Rust могут не больше копий, чем
держит хост: одна сборка на 4 логических ядра и не больше, чем помещается
на диск. Когда свободно меньше 50 ГБ, сначала запусти
`scripts/dev/prune-build-caches.py` и удали найденное, потом раздавай
работу со сборкой.
Перед новой волной проверь это командой
`scripts/dev/host-preflight.py --copies N` из
[подготовки хоста](../SKILL.md#подготовка-хоста). Сборочный слот
назови в брифе: кто собирает сейчас, кто ждёт.

Найденную сессией отдельную задачу разбери по происхождению (SOUL.md).
Если задача старая, заведи issue по присланному тексту и спроси участника,
брать ли её сейчас.

## Бриф исполнителю

Бриф должен быть понятен без этой переписки:

- роль: «ты исполнитель конвейера, прочитай unica-conveyor и worker.md»;
  для новой задачи в прежней сессии — «обновись с `main` и перечитай скиллы»;
- задача или issue, результат и критерий приёмки;
- область записи: файлы, тесты, фикстуры; с какими соседними PR она
  пересекается и что из этого нельзя трогать;
- веха задачи, которую исполнитель ставит на PR, и строка `Closes #N`;
- чужие PR из области задачи: какие только читать; действия с ними — только
  со ссылкой на поручение мейнтейнера по этому PR;
- какие проверки нужны до PR;
- хост: ОС, что на нём есть и чего нет из нужного задаче, по отчёту
  [подготовки хоста](../SKILL.md#подготовка-хоста), например «Windows 11,
  платформы 1С нет». Для Windows — ссылка на
  [команды на разных ОС](../../unica-development/SKILL.md#команды-на-разных-ос);
- чего ждать: например, «база — после вливания #N».

## Вливание PR

Исполнитель присылает номер и head PR, который довёл до
[готовности](worker.md#готовность-pr): одно ревью пройдено, обсуждения закрыты,
первая строка описания — `Closes #N` или `Refs #N`. Без вехи тесты не идут, а
`PR metadata` красная. Когда CI на присланном head зелёный, поставь PR в очередь.

Если поручение участника расходится с правилом этого скила, покажи участнику
правило и расхождение по [AGENTS.md](../../../../AGENTS.md#противоречие-принятому-правилу)
до действий и жди решения.

Вопрос мейнтейнеру — одно решение на вариант. Если после ответа последуют
действия с PR, issue или вехами, перечисли их в самом вопросе с номерами.
Не вписывай в описание варианта действия, о которых не спрашиваешь.

Веха на issue или PR подтверждает, что работа нужна и описана достаточно.
Внешние issue и PR, то есть не от исполнителей конвейера, по умолчанию
не подтверждены: задача может быть недоописана, без ясного критерия завершения
или предлагать ненужное. Свой PR исполнитель отмечает вехой задачи сам; если
он её не поставил, верни PR ему. Веху не ставят ни исполнитель, ни ты, если
PR внешний или чужой, его задача не вычитана или не стоит в вехе, или задачи
нет. Тогда спроси мейнтейнера и поставь веху после его ответа. При переносе
задач между вехами веху открытых PR не меняй: смена вехи перезапускает CI.

Мейнтейнеру задавай только вопросы: смена смысла правила, настройки безопасности, публичный выпуск, потеря гарантии, чужие PR и issue контрибьюторов.
Остальное вливай сам и сообщай итогом. Снятые и перенесённые тесты объявлены строками
`Removes-test:` и `Removes-test-target:`: без них ночной страж инвентаря краснеет
уже после вливания.

Порядок черновиков задан в [worker.md](worker.md#черновик-и-ci). PR с вопросом присылай
мейнтейнеру черновиком, с самим вопросом и вариантами; ответ передай исполнителю.
CodeRabbit черновики не ревьюит, его замечания придут после `gh pr ready`.

Если PR правит
`arch/rules`, назови вид правки по диффу: только пути или абзац об охвате проверок
либо текст обязательства. Связь с тестами задают пометки `rule:` в тестах, не правка
`arch/rules`.

## Вылеты из очереди

Очередь исключает упавшую или конфликтующую запись сама. Координатор
следит за вылетами (`RemovedFromMergeQueueEvent`, прогоны `merge_group`),
сообщает автору номер прогона и записывает в комментарий состояния, кто
разбирает. Разбор и исправление — у автора по
[worker.md](worker.md#вылет-из-очереди). Исправленный PR снова ставь в очередь.
PR, вылетевший без дефекта, с прежним head, ставь сразу.

При блокирующем замечании к PR в очереди сними его сразу: PR с известной
ошибкой роняет записи позади себя.

Время очереди мерь `scripts/ci/ci_run_metrics.py` по прогонам `merge_group`:
p50 и p95 до `Unica CI`, ожидание раннера, минуты раннера. Об узких местах
пиши участнику с цифрами.

## После вливания

Когда автор сообщил о вливании, разбуди сессии, которые ждали этот PR,
по комментарию состояния, и вычеркни его оттуда.

## Ответ участнику на «статус»

Наверху таблица PR и их состояния (ждёт ответа мейнтейнера, идёт CI, в очереди, вылетел
и у кого разбор). Под ней таблица
розданной работы: сессия, задача или PR, состояние. Влитое не показывай.
Ниже — только то, что ждёт решения участника. Состояние бери свежим
из GitHub, а не из памяти.

## Ретроспектива

Примерно через каждые двадцать PR, влитых в `main`, сам предложи
ретроспективу. Материал — вылеты из очереди с причинами, переделки
по ревью, простои сессий, свои ошибки. Итог — короткий список
предложений с ценой каждого. Принятые предложения раздай исполнителям
как PR в `.agents/skills/` или задачи. Точку отсчёта следующей
ретроспективы запиши в комментарий состояния.

## Ограничения хоста

Хост может ставить исходящие сообщения на паузу, если их много подряд
без реплики участника. Объединяй поручения в одно сообщение.
Не опрашивай CI и очередь в цикле: сессии сами сообщат об изменениях.

Вспомогательные скрипты координатора ставят в очередь только свои PR
и вехи не ставят.
