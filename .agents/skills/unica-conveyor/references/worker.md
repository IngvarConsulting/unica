# Исполнитель

Исполнитель доводит одну задачу до PR, готового к вливанию, и сопровождает
его до `main`. Работает по
[unica-development](../../unica-development/SKILL.md) и его правилам PR.
Ниже — то, что в конвейере работает иначе.

## Новая задача

Каждую новую задачу, в том числе следующую в той же сессии, начинай так:

1. Обнови рабочую копию после `git fetch`. Если бриф называет
   существующую ветку PR, работай в ней; `main` вливай только при конфликте.
   Иначе создай новую ветку от `origin/main`: прошлая база могла устареть
   на десятки PR.
2. Перечитай SOUL.md, SKILL.md конвейера, этот файл и unica-development,
   а затем скиллы, на которые он направит для этой задачи. Скиллы
   меняются вместе с `main`: версия, прочитанная для прошлой задачи,
   не в счёт.
3. Прочитай [канал](../SKILL.md#канал-и-состояние): там могут быть договорённости
   по твоей области.

## Рабочее место

- Своя ветка и своя рабочая копия.
- Свой каталог сборки. Cargo решает, что пересобрать, по времени изменения
  файлов, а не по их пути: у копии другой ревизии с общим `CARGO_TARGET_DIR`
  остаются устаревший список модулей из `build.rs` и ложные ошибки или
  ложный зелёный. Как задать каталог на своей ОС — в
  [командах на разных ОС](../../unica-development/SKILL.md#команды-на-разных-ос).
- Каталоги сборки лежат в общем корне хоста: `C:\cargo-target\<имя>-*`
  на Windows, `$HOME/cargo-target/<имя>-*` на macOS и Linux. Каждый
  занимает 25–50 ГБ. У исполнителя их не больше двух; новый PR
  переиспользует свободный каталог, а не заводит третий. Переиспользуемый
  каталог называй без номера PR (`worker-2`, `worker-2b`): каталог с номером
  влитого PR очистка считает свободным. `target/` внутри рабочей копии
  не держи: preflight его не считает, а очистка удаляет.
- Каталог сборки и рабочая копия PR удаляются сразу, как только PR влит
  или закрыт. Рабочую копию удаляй
  `git worktree remove`, каталог сборки — целиком. Что ещё можно удалить
  на хосте, покажет `scripts/dev/prune-build-caches.py`: без `--apply`
  он только печатает.
- Если на хосте нет того, что нужно проверке задачи (например, платформы 1С),
  сообщи координатору, чего и для какого шага не хватает.
- Пиши только в области записи из брифа. Если нужно выйти за неё, спроси
  координатора: соседний PR мог занять эти файлы.

## До PR

1. Реализация и проверки по классу задачи из unica-development. Гоняй
   проверки изменённого поведения и стражи, которые называет unica-testing;
   полный набор, уже пройденный на этом дереве, после правки не повторяй,
   а повтори затронутые проверки. Полные наборы исполнят CI и очередь,
   ожидание веди в фоне, отчёты пиши коротко.
2. Одно независимое ревью субагентом на итоговый diff. Исправь замечания
   до публикации; новый круг ревью нужен, только если правка сменила замысел.
3. Сверь удалённые и перенесённые `#[test]` по `git diff origin/main...HEAD`
   со строками `Removes-test:` и `Removes-test-target:` в описании PR.
   Тест, который уходит из профиля `queue` (например в nightly), для ночного
   стража инвентаря тоже пропажа и объявляется так же. Каждая строка — отдельный шаблон,
   без фигурных скобок.
4. Открой PR черновиком (`--draft`). Первая строка описания — `Closes #N`,
   если PR выполняет приёмку задачи, иначе `Refs #N`. Assignee — аккаунт
   твоего участника: `--assignee @me`.
5. Веха на issue или PR подтверждает, что работа нужна и описана достаточно.
   Внешние issue и PR, не от исполнителей конвейера, по умолчанию не подтверждены.
   Веху ставь только на свой PR и только ту, что следует из задачи: задача уже
   в вехе, PR её реализует (`gh pr create --milestone`). На внешний или чужой PR,
   на PR с невычитанной или не стоящей в вехе задачей и на PR без задачи веху
   не ставь: об этом координатор спрашивает
   мейнтейнера. Веху issue ставит мейнтейнер. Веху открытого PR не меняй: это
   перезапускает CI. Под токеном мейнтейнера GitHub видит агента как мейнтейнера,
   поэтому это правило, а не замок. Подробности допуска — в
   [разделе о нём](../../../../CONTRIBUTING.md#вливание).

## Черновик и CI

У черновика CI не идёт. Готовый PR пушится один раз: сначала проверено локально,
потом push. Следующий push — только по замечанию или красному CI. `main` вливается в ветку PR только при конфликте, итоговое дерево
проверит очередь.

- Обычный PR: локальные целевые проверки и одно ревью, затем `gh pr ready` и номер с head
  координатору. Идёт CI, затем координатор ставит PR в очередь.
- PR с вопросом мейнтейнеру (смена смысла правила, настройки безопасности, публичный
  выпуск, потеря гарантии) остаётся черновиком до ответа: вопрос задаёт координатор.
- Остальные PR переводи из черновика сам, когда они готовы.

CodeRabbit черновики не ревьюит: его замечания приходят после `gh pr ready`.

## Готовность PR

PR готов к вливанию, когда выполнено всё:

- одно независимое ревью пройдено, обсуждения в PR закрыты;
- первая строка описания — `Closes #N` или `Refs #N`;
- снятые и перенесённые тесты объявлены (`scripts/ci/removed_tests.py
  --base <merge-base> --description-file <описание>` без нарушений).

Тогда пришли координатору номер PR, head и что PR снимает. В очередь PR
сам не ставь и автовливание не включай: это делает координатор. Красный CI
разбираешь ты. Когда PR влит, сообщи координатору одной строкой и удали каталог сборки и рабочую копию.

## После PR

- Если к PR, который уже в очереди, пришло блокирующее замечание, сразу
  сообщи координатору, чтобы он снял PR. Сам из очереди не снимай.
- Сопровождай CI и ревью. Собственный дефект исправляй коммитом
  в head своего PR и сообщи координатору новый head.

## Вылет из очереди

Вылет своего PR разбираешь ты. Причину бери из события
`RemovedFromMergeQueueEvent` и упавших джоб прогона `merge_group`.

- Конфликт с записью впереди: влей свежий `main`, повтори затронутые
  проверки и пришли координатору новый head.
- Вылет без дефекта в PR (снят при пересборке очереди, джоба отменена
  и `runner_name` пуст — «not acquired by Runner») исправлять не нужно:
  сообщи координатору одной строкой, чтобы PR поставили снова.
- Остальное — собственный дефект: исправь коммитом в head и пришли
  координатору новый head вместе с номером прогона и причиной.

## Находки и новые задачи

Дефект, найденный за границей задачи, разбери по происхождению (SOUL.md).
В чужую ветку не правь. Новых сессий не заводи. Отдельную задачу пришли
координатору текстом issue: воспроизведение, происхождение, критерий
приёмки. Субагенты внутри своей задачи разрешены.

## Конец работы

После вливания последнего PR удали его каталог сборки и рабочую копию
и сообщи координатору, что свободен. Сессию архивирует участник.
