# Подготовка и сопровождение PR

Читайте с начала порученной реализации и при сопровождении существующего PR.
Границу работы задаёт
[поручение человека](../SKILL.md#граница-поручения); само чтение инструкции
не даёт разрешения публиковать изменения.

- Связанные issues сопровождайте по
  [правилу исходного текста](../SKILL.md#исходный-текст-пользовательского-issue).
  В PR отдельно называйте пользовательский запрос и расширенную задачу
  владельца. Закрывающая ссылка относится к задаче, чья собственная приёмка
  выполнена; создание связанного issue не закрывает внешний репорт.
- По умолчанию — один самостоятельно проверяемый PR на одно связное изменение, с
  базой `main` или явно названной релизной веткой.
- Не открывайте PR, базой которого является head-ветка другого открытого PR. Не
  используйте дочерние PR как очередь правок по ревью: коммитьте и пушьте такие
  правки в head-ветку существующего PR.
- Перед открытием PR посмотрите предполагаемую базу на GitHub. Если она
  принадлежит открытому PR, остановитесь и либо возьмите его head-ветку, либо
  спросите пользователя, как поступить; имя ветки само по себе не доказывает
  независимость базы.
- Стек из PR допустим, только если пользователь явно попросил именованный стек и
  задал порядок слияния и перебазирования. Каждый участник стека объясняет в
  описании своего PR, кто его родитель, где проходит граница самостоятельного
  ревью и как он будет закрыт.
- Если агент не может пушить в head существующего PR, он обязан предоставить
  патч или попросить доступ; создавать дочерний PR в обход нельзя.
- Дефект, найденный во время ревью, разбирается по его происхождению.
  - **Привнесённый этим же PR** — правится в нём же, коммитом в его head-ветку.
    Отдельный PR на собственную регрессию оставляет в истории заведомо сломанный
    коммит и делит ревью одного изменения на два.
  - **Существовавший до него** — идёт независимым PR с базой `main` или
    заводится задачей. В текущий PR он не втягивается: это расширяет его границу,
    смешивает несвязанные изменения в одном ревью и задерживает то, что уже
    готово.
  - Когда происхождение неочевидно, решает `git log -S` или `git blame` по
    строке дефекта, а не ощущение. Если и после этого неясно — дефект считается
    существовавшим ранее и выносится наружу.
  - Ни в одном из двух случаев дефект не превращается в неявный стек PR.

## Вливание через очередь

Очередь слияния стоит на `main` и проверяет ровно то дерево, которое ляжет в
ветку, профилем `queue` из
[unica-testing](../../unica-testing/SKILL.md#что-запускать).
Автовливание выполняет слияние; агент сопровождает свой PR до проверки
результата в целевой ветке. Несколько сессий работают параллельно, каждая
своим PR.

- Перед ревью и публикацией, если ветка отстала от целевой по горячим файлам —
  `arch/`, `.github/workflows/`, реестры плагина, — подтяните целевую ветку слиянием,
  никогда перебазированием, и прогоните затронутые проверки локально.
- Перед push правок Rust: `cargo fmt --all -- --check` и
  `cargo clippy --workspace --all-targets --all-features -- -D warnings`.
  Остальные проверки до push выбирайте по
  [unica-testing](../../unica-testing/SKILL.md#что-запускать).
- Подготовленный коммит проходит проверки и ревью по
  [классу задачи](../SKILL.md#класс-задачи-и-независимая-проверка).
  Зафиксируйте SHA проверенной версии и результат проверки по классу задачи
  в описании PR.
  Вердикт относится к этой версии изменений, а не к номеру PR.
- После проверки и ревью опубликуйте подготовленный коммит, создайте PR
  или обновите head существующего. Если PR нужен раньше, оставляйте его
  draft без автовливания до готовности.
- Сверьте проверенный SHA с head на GitHub; если PR ещё draft, переведите
  его в готовый. Включите автовливание:
  `gh pr merge --auto --match-head-commit <проверенный-SHA> <номер>`.
  При сменившемся head сначала разберите новую версию. Не обходите очередь
  или защиту ветки через `--admin`.
- Проверьте состояние PR и очереди после команды: при зелёных проверках
  команда сразу ставит PR в очередь, иначе включает автовливание.
  Само отсутствие `autoMergeRequest` не доказывает, что PR не поставлен.
- Наблюдайте CI, замечания ревью и очередь до слияния. Для ожидания используйте
  штатные команды наблюдения `gh`; при изменении состояния разбирайте новый
  результат, вместо повторного чтения одних и тех же полных логов.

## Замечания и сбои до слияния

Блокирующее замечание к уже опубликованной версии сначала требует остановить
её слияние: отключите автовливание, уберите PR из очереди, если он уже там,
и проверьте результат. Исправление и повторное ревью выполняйте в том же PR
по правилам происхождения дефекта выше.

После изменения head повторите затронутые проверки и ревью изменившейся
семантики, включая разрешение конфликтов с новой базой, до публикации
исправленного коммита. Обновите привязку результатов к текущему SHA до
следующего разрешения на слияние. Механическая
правка без изменения проверенного дерева не требует нового полного ревью.

При красном CI, исключении из очереди или конфликте установите причину по
актуальному head и прогону. Собственный дефект и интеграцию с новой базой
устраняйте в пределах поручения; после проверки и ревью снова разрешите
слияние. Повторяйте прогон после исправления или подтверждённого сбоя
окружения; не ослабляйте тест ради зелёного результата. Ошибка API или таймаут
ожидания не подтверждают ни отказ, ни слияние — перечитайте состояние.

Если продолжение требует недоступных прав, внешней предпосылки или решения
человека вне согласованных границ, назовите конкретный блокер, состояние PR
и необходимое действие. Не объявляйте доставку завершённой. Пока обычный
прогон идёт и зависимого решения не требуется, продолжайте сопровождение.

## Подтверждение доставки

Завершайте поручение после проверки всех условий:

1. GitHub показывает `MERGED`; `CLOSED` без слияния не подходит.
2. Обязательные ворота, включая очередь для `main`, прошли для слитой версии
   изменения; существенные замечания получили проверяемый исход.
3. После свежего `git fetch` коммит из `mergeCommit` PR входит в историю
   `origin/main` или явно выбранной целевой ветки. При squash исходный head
   PR может не быть её предком; целевая ветка может уже уйти вперёд.
4. Согласованные постусловия выполняются в целевой ветке. Если другие PR уже
   изменили те же файлы, проверьте смысл результата, сохраняя чужие изменения.

В итоговом ответе дайте ссылку на PR, коммит слияния, результаты проверок
и существенные ограничения. Успешный выход команды ожидания сам по себе
не заменяет перечисленные свидетельства.

- Ветку PR удаляйте только после того, как `gh pr view <номер> --json state`
  показал `MERGED`: закрытый по ошибке PR с удалённой веткой восстанавливать
  дольше, чем дождаться.
- Красный тест на Windows в ночном ярусе гейт не красит и виден только в
  отчёте на сайте; у каждого такого теста должна быть задача с владельцем.
