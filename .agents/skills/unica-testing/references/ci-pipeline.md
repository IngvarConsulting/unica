# Конвейер и отчёты

Читай при изменении `.github/workflows/`, отбора, итогового шлюза, отчётов,
сайта и ночного яруса в `scripts/ci/`, а также сборки, передачи и публикации
артефактов.

Маршрут задаёт `classify-workflow-changes.py` по неизменяемым SHA из payload
события. В PR сохраняется отбор по контурам изменённых файлов. Дополнительно PR
и очередь получают явный пропуск Rust-тестов и Clippy при доказанном изменении
разрешённой прозы: список `PROSE_PATHS` и Markdown в `arch/`, только
добавления и правки обычных файлов без смены режима. Инструкции плагина,
спецификации, генерируемые реестры и сайт не входят в этот список. Смешанная
группа очереди, пустой или неизвестный diff, удаление, переименование и смена
типа файла сохраняют полный контур очереди. Метка `ci:full` отменяет отбор PR.
Guards и Python `small` обоих наборов (`tests/ci`, `tests/dev`) остаются.
Средние Python-тесты исключаются и внутри `dev`: они тоже могут собирать продукт.
Документационный маршрут не компилирует Rust; `cargo fmt` в guards и чтение
манифестов через `cargo metadata --no-deps` в малых проверках сохраняются.
Матрица и допущенные размеры вычисляются общей политикой; итоговый gate
сверяет весь ожидаемый состав, поэтому неполная кодовая очередь не проходит.

Guards, Clippy и тесты работают на отдельных раннерах. Rust lint использует
ту же матрицу ОС, что Rust tests; Windows остаётся advisory только ночью.
Ошибка линта или загрузки SARIF не должна лишать отчёт тестовых результатов.
Итоговый `Unica CI` проверяет обязательные результаты, включая lint; сборка
поставки также ждёт успешные guards, lint и тесты. Линтеры публикуют SARIF
в Code Scanning, тесты — планы и результаты Allure.

`build-rust-ordinary`, `build-rust-receipt` и `build-rust-vendor` независимо
создают nextest archive, полный план и разбиение на shards для каждой ОС.
`run-rust-*` зависят только от своего producer и теневого selector, получают
архив и выполняют его через `run-tests.py --phase run`. Cargo cache им
не передаётся. Ordinary в очереди имеет две части; остальные конфигурации —
по одной. `test-rust-platforms` сверяет точное непустое объединение планов,
результаты каждой части, SHA, archive hash, ОС/features/profile и попытку
workflow. Повторы nextest остаются в Allure, а не считаются новыми случаями.
Неожиданно пустой план, потерянная часть и обязательный skip блокируют gate.

Архивы сохраняют встроенные абсолютные пути `CARGO_MANIFEST_DIR` и
`CARGO_BIN_EXE_*`: producer и executor должны иметь одинаковый путь workspace,
ОС, target, toolchain и cfg. Произвольная релокация этим механизмом не обещана.
Фактическую работу process/FS-тестов из архива проверяй отдельно от полноты
разбиения. `ci_rust_lanes.py` сохраняет build/list/execution durations,
размер архива и identity; download/runner wait доступны в jobs того же run.

`build-python-product` создаёт ordinary binary до завершения Rust suites.
Python получает его архив с manifest и проверяет его через `prepared_binary.py`:
исходное дерево/SHA, host target/toolchain/cfg, ordinary features, hash, размер,
режим и состав архива. Только после проверки извлечённые bytes становятся
доступны по `UNICA_PREPARED_BINARY_MANIFEST`, вне изменяемого Cargo target.
Test-support и stale binary отвергаются; при заданном manifest возврата
к локальной сборке нет. Без него локальные consumers сохраняют Cargo fallback.

`ci_shadow_selector.py` строит кандидата по union base/head Cargo graphs и
обратным consumers. Общие/неизвестные входы, locks/features, fixtures/specs
и изменения composition оставляют full. Для известного кандидата executor
сравнивает inventory с полным планом и дополнительно исполняет выбранную часть
тех же архивных bytes. Обязательный набор всегда полный; shadow failure
не разрешает affected admission. Отчёт полного fallback не выдавай за
доказательство полезного сокращения или репрезентативный benchmark.

Push в `main` не повторяет Python-тесты, Rust-тесты и Clippy. При изменении
CI/toolchain или неизвестном диапазоне push `warm-rust-cache` прогревает
зависимости на Ubuntu и macOS. На промахе кеша она компилирует обычный workspace
и отдельный вариант ReceiptLedger с `cargo test --no-run`, затем выполняет
`cargo check --workspace --all-targets --all-features`. Точный cache hit
пропускает компиляцию. Прогрев не запускает тесты и не публикует их результаты.
Lint и warm используют прежний `shared-key`; producers ordinary/Receipt/vendor
имеют отдельные ключи и то же значение `CARGO_PROFILE_DEV_DEBUG`.
Artifact producers используют `lookup-only: true`: проверяют ключ, но не
восстанавливают изменяемый Cargo cache в собираемые binary/test archives.
Готовые проверенные архивы по-прежнему передаются и используются executor-ами.
Lint только читает кеш. Кеш зависимостей не передаёт
готовые бинарные файлы workspace другой job. Релизная ветка, тег и ручной запуск,
включая ночной `large`,
сохраняют свои полные контуры без исключения для прозы.

Ночной gate profile `large` теперь допускает все размеры, оба Python suites
и ordinary/Receipt/vendor. Он выбирает nextest `nightly-full`, сохраняя
существующие сроки и повторы. Nextest `large` остаётся точным каталогом
нагрузочных тестов для size guards. `run.json` архивных конфигураций помечает
новый объём как `full-nightly-v1`; старые large-only прогоны этим объёмом
не становятся. Итоговый `verification.json` различает `mandatoryComplete`
и `fullMatrixPassed`: Windows advisory сохраняет видимую причину и не даёт
утверждать прохождение полной матрицы или готовность affected admission.

При правках CI сверяй отбор с событием и профилем запуска. Результат должен
сохранять коммит, линию, профиль, раннер и попытку прогона. Разные раннеры —
разные случаи теста; повторы одного случая остаются видимыми. Отключённый тест
показывается как `skipped` с причиной автора. Если раннер не дошёл до теста,
сохрани `skipped` с причиной и ссылкой на прогон; состав из прошлого прогона
явно обозначь как восстановленный, а не как точный план новой сборки.
Для пропуска разрешённой прозы сохраняй подпись и причину отдельно для каждого
Rust-раннера в `results-ci-routing`. Это сведения об отборе, а не новый план
состава тестов или доказательство их прохождения.
Python обнаруживает состав текущей ревизии без исполнения `setUpClass` и тестов.
В очереди исключённые `medium` остаются в плане и отчёте со статусом `skipped`
и причиной `docs_only`; профиль остаётся `queue`. В PR средние тесты и раньше
не допускались, поэтому дополнительных пропусков этого размера нет.
Ошибка обнаружения состава документационной очереди останавливает проверку.

При объединении профилей сохраняй поздний результат случая вместе со всеми
его попытками. Пересборка прежних результатов не добавляет новый прогон в
историю. Только 404 при чтении сохранённых данных означает их отсутствие;
сбой загрузки не должен стирать историю или результаты другого профиля.
Память проверенной ночной вершины обновляет только состоявшийся `large`:
тег или отменённый прогон его не заменяет. Для публикации проверяй источник
и репозиторий прогона, а не только имя ветки. Красный прогон тоже результат.

Проверки преобразования и сохранения результатов находятся в
`tests/ci/test_allure_results.py`, `test_collect_results.py`,
`test_build_site.py`, `test_site_fetch.py` и `test_nightly_lines.py`;
связь событий с джобами — в `test_unica_workflow.py` и `test_gate_profiles.py`.
Это проверки данных и исполняемой конфигурации. Не заменяй их проверкой
наличия прежнего плана или этих инструкций.

При изменении сборки сохраняй сборку ядра и загрузчика одним обязательным
`cargo build --release --locked` в отдельный каталог целевой платформы на каждом раннере. Кеш ускоряет сборку, но не заменяет её;
его ключ учитывает ОС, цель, тулчейн и Cargo.lock без префиксного восстановления.
Сохраняй в отчёте цель, попадание в кеш и длительность сборки.

Между джобами передавай нужные архивы и метаданные, а не каталог Cargo или
полный набор инструментов. Промежуточные поставочные артефакты хранятся сутки;
данные тестовых отчётов и тонкий пакет для продвижения имеют собственные сроки.
Раннер проверяет состав, хеши, режимы и нулевые отметки времени
своего архива, затем запускает MCP из извлечённых байтов с проверенными движками.
При выпуске повторяй проверку на скачанных опубликованных байтах.

Публикация релизных артефактов относится к push тега. PR и ручная проверка
не публикуют их; размещение и продвижение каталога остаются отдельными
действиями. Итог PR принимает стабильный агрегирующий CI gate по результатам
всех обязательных джоб, включая условно исполняемые. Проверки отбора и шлюза —
`tests/ci/test_unica_workflow.py` и `tests/ci/test_evaluate_ci_gate.py`.
