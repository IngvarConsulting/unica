# Конвейер и отчёты

Читай при изменении `.github/workflows/`, отбора, итогового шлюза, отчётов,
сайта и ночного яруса в `scripts/ci/`, а также сборки, передачи и публикации
артефактов.

Workflow три, и ни один не запускает другой через завершение прогона.

- `ci.yml` — ворота pull request и очереди: одна Linux-джоба `Unica CI`, в очереди
  ещё `Clippy (windows-latest)`. На pull request она исполняет `cargo fmt`, контракт
  версий, Clippy и `run-static-tests.py`: модули Python без `medium` и без объявления
  `PR_SKIP` в самом модуле (`scripts/ci/python_sizes.py`), параллельно, и `removed_tests.py`:
  снятый тест Rust или Python объявлен `Removes-test`, перенос узнаётся сам (у Python — та же пара
  `Класс.тест` в другом модуле). Цель до трёх минут. Тесты идут в очереди.
- `release.yml` — сборка, проверка и публикация. Запуски: тег `v*` (профиль
  `release`), кнопка на ветке (`main` или `large`) и вызов ночи.
- `nightly.yml` — расписание и кнопка на `main`. Если вершина сдвинулась, вызывает
  `release.yml` через `workflow_call` с профилем `large`. Итог ночи — итог этого
  прогона: красная джоба красит её. Релизные линии ночь не проверяет.

Linux-джоба очереди при каждой попытке использует пул
`[self-hosted, Linux, X64, unica-pve]`, если переменная репозитория
`UNICA_SELF_HOSTED` равна `true`. Общая метка есть и у GPU-раннера: он берёт
обычные задания вместе с остальными. PR, Windows, ночь и выпуск остаются
на GitHub-hosted.

На PVE каталог `target` перед очисткой checkout временно перемещается
в `.unica-ci-target` рядом с рабочей копией, а после очистки возвращается обратно.
Во время исполнения это обычный каталог внутри checkout: тесты могут искать
плагин относительно пути бинаря. При прерывании между этими шагами следующий
прогон восстанавливает сохранённый каталог. Cargo проверяет актуальность сборки
для нового дерева; продукт для Python
снова подготавливается и проверяется в каждом задании. Каталог не разделяется
между ВМ или одновременно работающими копиями. Общий rust-cache на этом пути
не восстанавливается: его версия зависит от абсолютных путей GitHub-hosted.
На GitHub сохраняется чтение кэша main и сборка при его отсутствии; локальный
каталог PVE для повторного запуска не требуется. При нехватке диска локальный
кэш можно удалить только когда раннер не выполняет задание — следующий прогон
его пересоздаст.

При недоступности PVE установите `UNICA_SELF_HOSTED=false` в Actions variables
репозитория. Отсутствие переменной тоже выбирает GitHub. Переключатель действует
на новые назначения и не переносит уже ожидающее или выполняющееся задание.
При повторе также действует переключатель. Если
неуспешная проверка уже исключила PR из очереди, выключите PVE перед повторным
добавлением PR: новая группа создаёт новый прогон с первой попыткой.
После восстановления PVE верните `true`.

Очередь всегда исполняет Clippy всего workspace на Linux и Windows, весь Rust `small`,
Python small, смоук продукта и снимки контрактов (`QUEUE_KEEPS_MEDIUM` в модулях). К ним `queue-tests.py`
добавляет `medium` изменённых крейтов, включая `unica-coder` и `unica-daemon`. Изменённым считается и крейт,
в исходниках которого упомянут правленый путь из `tests/fixtures` или `scripts`, кроме
`scripts/ci` и `scripts/research`. Запись только из `docs/pages`, `docs/visual-kit`,
`arch/rules`, `.agents`, `scripts/research` и `.md` корня Rust не запускает. Прямые зависимые изменённого кода исполняют интеграционные цели
(`kind(test)`), кроме `daemon_receipt_ledger`. Полный набор идёт при смене внешних
зависимостей в `Cargo.lock`, правке корневого `Cargo.toml`, тулчейна и при сбое чтения diff.
Правка `Cargo.lock` только в записях крейтов рабочей области полного набора не требует. `medium` остальных крейтов,
транзитивные зависимые, Python medium и large идут ночью.

Тесты Rust очереди на Linux держат временные каталоги в памяти: `queue-tests.py` ставит
`TMPDIR` в `/dev/shm`, если там свободно не меньше 1 ГиБ и оттуда можно исполнять файлы.
Публикации состояния и журнала квитанций там не ждут `fsync`. Ночь и выпуск идут на диске:
поведение настоящей файловой системы проверяется там. Тест, которому нужен настоящий
диск, берёт каталог на диске явно, а не из `TMPDIR`.

**Красная ночь.** Виновный PR откатывается, очередь стоит до зелёного `main`.

**Откат выбора.** Переменная репозитория `QUEUE_FULL_TESTS=true` включает полный набор без
правки кода. Её ставят, когда ночь за 30 дней дважды находит поломку в тесте, который
очередь пропустила на этом PR, или когда такая поломка дошла до выпуска.

Задания `release.yml` идут подряд одним прогоном. `Unica CI` и `Rust (<runner>)` —
проверка; при `alpha` зелёная проверка даёт `alpha-tag`, и сборка идёт на его
служебном коммите; `build-tools` и дальше до `Delivery CI` — сборка и ассеты;
`gate`, `stage`, `anchor`, `verify-*`, `promote` — маркетплейс, только после зелёного
`Delivery CI` на push тега; `pages-build` и `pages-deploy` — сайт, после всего, в том
числе после красного прогона. Отменённый прогон сайт не обновляет. В вызванном
workflow API отдаёт имя джобы как `Вызов / Джоба`; `await_os_jobs.py`
и `collect-results.py` снимают этот префикс.

Токен маркетплейса лежит в окружении `marketplace` (только `main` и теги `v*`, без
ревьюера и без ключа тегов: публикация с тега идёт до конца без одобрения). Ключ тегов
лежит только в окружении `alpha` (только `main`). Задания маркетплейса берут из `main` один файл
`scripts/ci/release-channel.py` и не берут код тега.

Внутри `release.yml` маршрут считает `classify-workflow-changes.py`: у тега, кнопки
и ночи диапазона нет, поэтому маршрут всегда полный. Ветви оценщика для событий
pull request и очереди остаются в `evaluate-ci-gate.py`, а их шагов в `release.yml`
нет (`ABSENT_STEPS`).

Прогон занимает по одной джобе на ОС. `Unica CI` подряд, в одном каталоге `target`,
исполняет маршрут, guards, продукт для Python, архивы и прогоны полос Linux, Clippy,
Python, сверку инвентаря, снятые тесты и итог. Clippy исполняется в фоне
(`background_step.py`), пока идут тесты Rust; Python ждёт его конца и идёт после:
MCP-тесты под нагрузкой сборки и nextest падают по таймауту. Наборы Python идут
параллельно друг другу. `large` добавляет `Rust (windows-latest)`; его красная джоба
красит прогон, как любая другая ОС. Кнопка `main` исполняет Clippy Windows отдельной
лёгкой джобой `Clippy (windows-latest)`, запись `lint-rust-windows`. Красный шаг не
отменяет следующие (`!cancelled()`), поэтому ошибка линта или загрузки SARIF не лишает
отчёт тестовых результатов.

`needs` на другую ОС сделал бы прогон последовательным. Поэтому `Unica CI` в конце
ждёт джобы других ОС по jobs API (`await_os_jobs.py`, не дольше часа, в `large` три)
и забирает их артефакты `plan-<runner>` и `results-<runner>`. Джоба ОС считает маршрут
тем же классификатором. Расхождение маршрутов видно как пропавшая конфигурация при
сверке. Итог `Unica CI` — последний шаг `evaluate-ci-gate.py` над `toJSON(steps)`.
Каждая запись таблицы — группа шагов (`STEP_GROUPS`). Группа зелёная, только если
зелёный каждый её шаг, и пропущена, только если пропущен каждый: частичный пропуск —
дефект wiring. Исход джоб ОС — отдельная запись `os-jobs`. Хвост поставки оценивает
`Delivery CI` тем же оценщиком по результатам `Unica CI` и джобам поставки.

Состав полос задаёт профиль и ОС (`ci_rust_lanes.lanes`). Vendor идёт только в `large`
и на теге. На macOS тесты и Clippy идут своим профилем: `large` и тег (`release`) — все
размеры, кнопка `main` — `small` и `medium`. В джобе ОС Clippy идёт до сборки тестов,
а сборка и прогон идут и после его отказа: оба сигнала приходят в одном прогоне. Цена:
ветки `cfg` и `medium` под macOS и Windows впервые проверяет ночь, когда изменение уже
в `main`. Изменение такого поведения автор гоняет кнопкой `release.yml` на своей ветке.
SARIF Clippy и zizmor идут в Code Scanning с Linux; сбой их загрузки гейт не красит.

Каждая джоба собирает nextest archive своих полос, полный план и одну часть
(`--phase build`), выгружает планы до тестов и исполняет архивы
(`--phase run`) в той же джобе. Архив не передаётся между джобами: он пинует
байты, которые перечислил план, к байтам, которые исполняет прогон. Сборка
Receipt пересобирает `unica` со своим признаком, а прогон каждой полосы
извлекает свой архив. Упавшая полоса оставляет подписанную конфигурацию
и не останавливает следующие. Сверка (`--phase verify`) проверяет точное
непустое объединение планов, результат каждой полосы, SHA, archive hash,
ОС/features/profile и попытку workflow, а также исход джоб ОС
(`CI_JOB_RESULTS`). Повторы nextest остаются в Allure, а не считаются
новыми случаями. Неожиданно пустой план, потерянная полоса и обязательный
skip блокируют gate. При «Re-run failed jobs» перезапускай весь прогон:
артефакт джобы прошлой попытки отвергается.

Сверка сравнивает план с прежним инвентарём.
`rust_inventory_baseline.py` берёт артефакт `ci-rust-inventory-<profile>`
у ближайшего first-parent предка; при его отсутствии — артефакт очереди.
Артефакт публикуют успешные прогоны `release.yml`: ночь, кнопка и тег, причём ночь
от имени `nightly.yml`. Gate краснеет,
если в той же ОС и lane исчез test binary архива или, при том же составе
раннеров, джоба ОС.
При профиле с тем же допуском размеров и разбиением красными становятся
пропавшая конфигурация с её результатами, опустевший выбор по бинарю
и каждый пропавший результат теста.

Намеренную пропажу объясняет описание pull request: его видит ревьюер.
Учитываются PR, влитые после базы, а в прогоне pull request — ещё и сам
проверяемый PR. Строка `Removes-test-target: <binary-id>` снимает
действительно исчезнувший бинарь вместе с его кейсами. Строка
`Removes-test: <binary-id>::<имя>` снимает один кейс этого бинаря, а с `*`
в конце — его кейсы с этим префиксом. Объявление без известного
`<binary-id>::` ничего не снимает. Тест, который после базы переехал в другой
крейт или модуль и затем снят, PR объявляет по ID после переезда: такое точное
объявление объясняет пропавший кейс с тем же именем функции, если имя пропало
один раз, объявлено одним ID и этого ID нет ни в базе, ни в текущем прогоне.
Один исходник может компилироваться в несколько целей (крейт включает модули
другого): точное объявление объясняет и тот же кейс — тот же путь модулей и имя
функции — в другой цели базы. На pull request `removed_tests.py --nightly-profile large`
сверяет снятые тесты ещё и от коммита инвентаря ночи, с объявлениями влитых
после него PR и самого PR: ID, который знает только ночь, называется на PR.
Номера влитых PR gate берёт из `(#N)`
в темах first-parent коммитов диапазона, номер проверяемого PR — из события
`pull_request`. Принятые объяснения, их PR и объявленный сброс видны в summary
джобы и в `verification.json`. Сообщения коммитов ничего не объясняют.

Без найденной базы gate красный в любом профиле, пока описание PR
не объявит `Rust-inventory-baseline: reset`. В pr и queue сброс действует
только из описания самого проверяемого PR. Сброс соседней записи очереди
не действует: запись за PR со сбросом выпадет из пачки, поэтому такой PR
вливают отдельно. Остальные профили пачек не имеют и принимают сброс
из любого PR, влитого после их базы. Без базы диапазон — один HEAD.
Тогда в pr сброс объявляет описание проверяемого PR из события, а в queue
и остальных профилях — PR, названный в теме HEAD.

Снятый из исходников тест `Unica CI` проверяет отдельно: `removed_tests.py
--baseline` сравнивает дерево с коммитом базы и требует объявления из описаний PR,
влитых после неё. Это видит и тест, не попавший ни в один план.

### Возможности хоста

Тест, которому не хватает возможности хоста, не проходит молча (#1893).
В `tests/platform/` и фасадах `src/platform/` возможность, которую задаёт
сама ОС, тест объявляет через
`#[cfg_attr(not(<ОС>), ignore = "host capability ...")]`. На остальных ОС
он виден в отчёте как `skipped` с причиной. Инвентарь считает его
ignored-кейсом, а не потерей. Вне этих путей OS-cfg запрещён
(INV.PLATFORM.OS-BEHIND-FACADE). Там тест спрашивает пробу фасада
и пропускается через helper с именем возможности ОС.

Возможность, зависящую от тома или прав, тест проверяет при исполнении.
Если её нет, он вызывает `skip_without_host_capability` и выходит. Helper
пишет запись в каталог `UNICA_HOST_CAPABILITY_SKIPS`, который задаёт
`ci_rust_lanes.py`. Раннер превращает такой PASS в `skipped` с причиной
`host capability <имя>: ...`. На раннере, где возможность обязательна
(`REQUIRED_HOST_CAPABILITIES`), такой пропуск роняет gate.
`tests/ci/test_host_capability_skips.py` не даёт выйти рядом с пробой
возможности в обход helper-а. Места, найденные до механизма, перечислены
в allowlist стража, и переводы снимают их пакетами.

| Возможность | Обязательна на | Где исполняется |
| --- | --- | --- |
| `symlink` | ubuntu, macOS | очередь Linux; macOS — nightly и `ci:full`; Windows без привилегии — `skipped` |
| `case-sensitive-filesystem` | ubuntu | очередь Linux |
| `case-insensitive-filesystem` | macOS | macOS: nightly и `ci:full` |
| `normalization-insensitive-filesystem` | macOS | как предыдущая |
| `enforced-permission-bits` | ubuntu, macOS | очередь Linux |
| `directory-mtime` | ubuntu, macOS | очередь Linux |
| `non-utf8-file-names` | ubuntu | очередь Linux |
| `rename-under-open-handle`, `unix-process-groups`, `unix-permission-bits` | ubuntu, macOS | очередь Linux |
| `windows-job-object`, `windows-path-syntax` | — | nightly Windows |
| `archive-fixture-binary` | ubuntu, macOS, Windows | очередь Linux; PR — medium-фаза на Linux; macOS и Windows — nightly; вне раннера архива — `skipped` |

Для `windows-latest` из возможностей хоста не обязательна ни одна. Это решение,
а не свойство раннера: пропуск там виден, но не отвергается, хотя красная
Windows-джоба красит ночной прогон. `archive-fixture-binary` — свойство самого
раннера архива, а не хоста, поэтому она обязательна везде. Причины
пропусков собраны в отчёте в категорию «Нет возможности хоста».

Сценарий доставки сервисных движков получает путь и SHA256 уже включённого
в ordinary archive non-test binary `unica`. Producer выбирает его по metadata
nextest; parent и дочерний тест сверяют hash перед запуском. Вложенной сборки
Cargo нет. Этот executable — фикстура архива; проверенный production artifact
для Python готовится и проверяется отдельно.

Архивы сохраняют встроенные абсолютные пути `CARGO_MANIFEST_DIR` и
`CARGO_BIN_EXE_*`: producer и executor должны иметь одинаковый путь workspace,
ОС, target, toolchain и cfg. Произвольная релокация этим механизмом не обещана.
Фактическую работу process/FS-тестов из архива проверяй отдельно от полноты
разбиения. `ci_rust_lanes.py` сохраняет build/list/execution durations,
размер архива и identity; download/runner wait доступны в jobs того же run.
Сводку серии прогонов собирает `ci_run_metrics.py` из jobs, логов и этих
артефактов. Время до `Unica CI` сравнимо между событиями: хвост поставки
ждёт `Delivery CI`. У прогонов до двухджобовой раскладки прежний гейт
только собирал исходы, поэтому их сравнивай по времени до последней
непоставочной джобы.

Шаг `product` собирает ordinary binary (`prepared_binary.py build
--target-dir target`) в тот же `target`, что и архивы, и сразу копирует его
с manifest вне него. Python проверяет копию через `prepared_binary.py`:
исходное дерево/SHA, host target/toolchain/cfg, ordinary features, hash,
размер и режим. Отчёты джобы (SARIF, маршрут) лежат в игнорируемом
`.build/`: неотслеживаемый файл в дереве сменил бы отпечаток исходников.
Test-support и stale binary отвергаются; при заданном manifest возврата
к локальной сборке нет. Без него в CI (`GITHUB_ACTIONS=true`) `ensure_binary`
отказывает; локально собирает одной командой и сообщает об этом в stderr.
Модуль-потребитель `ensure_binary` объявляется `medium`; это держит
`tests/ci/test_python_sizes.py`.

Обе джобы используют один ключ зависимостей на ОС (`ci-rust-ordinary`) и то же
значение `CARGO_PROFILE_DEV_DEBUG`. В ключе только зависимости: крейты workspace
rust-cache перед записью вычищает. Пишут ключи ночь и кнопка; `ci.yml` и тег читают
область main и берут ближайший ключ по префиксу. Кеш зависимостей не передаёт готовые
бинарные файлы workspace другой job.

Ночной gate profile `large` теперь допускает все размеры, оба Python suites
и ordinary/Receipt/vendor. Он выбирает nextest `nightly-full`, сохраняя
существующие сроки и повторы. Nextest `large` остаётся точным каталогом
нагрузочных тестов для size guards. `run.json` архивных конфигураций помечает
новый объём как `full-nightly-v1`; старые large-only прогоны этим объёмом
не становятся. Итоговый `verification.json` даёт один вердикт `mandatoryComplete`
по всем ОС прогона, Windows ночи тоже: рекомендательных отказов нет.

При правках CI сверяй отбор с событием и профилем запуска. Результат должен
сохранять коммит, линию, профиль, раннер и попытку прогона. Разные раннеры —
разные случаи теста; повторы одного случая остаются видимыми. Отключённый тест
показывается как `skipped` с причиной автора. Если раннер не дошёл до теста,
сохрани `skipped` с причиной и ссылкой на прогон; состав из прошлого прогона
явно обозначь как восстановленный, а не как точный план новой сборки.
Python обнаруживает состав текущей ревизии без исполнения `setUpClass` и тестов.

При объединении профилей сохраняй поздний результат случая вместе со всеми
его попытками. Пересборка прежних результатов не добавляет новый прогон в
историю. Только 404 при чтении сохранённых данных означает их отсутствие;
сбой загрузки не должен стирать историю или результаты другого профиля.
Память проверенной ночной вершины обновляет только состоявшийся `large`:
тег или отменённый прогон его не заменяет. Для публикации проверяй источник
и репозиторий прогона, а не только имя ветки. Красный прогон тоже результат.

Проверки преобразования и сохранения результатов находятся в
`tests/ci/test_allure_results.py`, `test_collect_results.py`,
`test_build_site.py`, `test_site_fetch.py` и `test_nightly_lines.py`;
связь событий с джобами — в `test_unica_workflow.py` и `test_gate_profiles.py`.
Это проверки данных и исполняемой конфигурации. Не заменяй их проверкой
наличия прежнего плана или этих инструкций.

При изменении сборки сохраняй сборку ядра и загрузчика одним обязательным
`cargo build --release --locked` в отдельный каталог целевой платформы на каждом раннере. Кеш ускоряет сборку, но не заменяет её;
его ключ учитывает ОС, цель, тулчейн и Cargo.lock без префиксного восстановления.
Сохраняй в отчёте цель, попадание в кеш и длительность сборки.

Между джобами передавай нужные архивы и метаданные, а не каталог Cargo или
полный набор инструментов. Промежуточные поставочные артефакты хранятся сутки;
данные тестовых отчётов и тонкий пакет для продвижения имеют собственные сроки.
Раннер проверяет состав, хеши, режимы и нулевые отметки времени
своего архива, затем запускает MCP из извлечённых байтов с проверенными движками.
При выпуске повторяй проверку на скачанных опубликованных байтах.

Публикация релизных артефактов относится к push тега. PR и ручная проверка
не публикуют их; размещение и продвижение каталога остаются отдельными
действиями. Итог PR принимает стабильный агрегирующий CI gate по результатам
всех обязательных джоб, включая условно исполняемые. Проверки отбора и шлюза —
`tests/ci/test_unica_workflow.py` и `tests/ci/test_evaluate_ci_gate.py`.
